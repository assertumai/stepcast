Реши, что этот заход узнал такого, чего в репозитории ещё не записано, — и
только это.

В контексте — оглавление памяти заголовками и правила письма единицы знания.
Изменение — `${params.change}`; смотри `git diff` и артефакты изменения.

**Файлы памяти не правь.** Твоя работа — описание, а записывает движок:
ревизию якоря он подставляет сам, и якорь, записанный тобой напрямую, не
проверялся бы на устаревание вовсе. Правка любого файла рабочего дерева
провалит шаг.

## Что сделать

Положи описание в файл `${run.scratch}/knowledge.json` — JSON, объект либо
список объектов:

```json
{
  "id": "judge-verdict-owns-failure",
  "title": "Провал шага объявляет только вердикт судьи",
  "scope": ["src/judge/**"],
  "anchors": ["src/judge/verdict.ts"],
  "body": "Текст утверждения и его причина.",
  "status": "active"
}
```

`anchors` — только пути, без ревизий: ревизию подставит движок. Путь якоря
обязан существовать, иначе запись будет отклонена.

## Когда чего не делать

1. Прочитай оглавление. Если существующая единица уже утверждает то же —
   опиши **её же** идентификатором с исправленным телом: это обновление, а не
   вторая запись.
2. Если узнанное отменяет существующую единицу — положи список из двух
   объектов: старая целиком со `status: "superseded"` (тело возьми
   `stepcast knowledge select --id <id>` через Read по её файлу) и новая со
   ссылкой на неё в теле. Не удаляй: отменённое остаётся человеку.
3. Не больше одной новой единицы за заход. Оглавление ограничено, и место в
   нём — единственное, что удерживает память от разрастания.
4. **Заходу нечего добавить — не создавай файл вовсе.** Это законный и самый
   частый исход: большинство изменений не открывают ничего, что не читалось
   бы из кода. Выдумывать единицу, чтобы показать работу, не нужно.
