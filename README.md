# Stepcast

Движок пайплайнов для разработки с ИИ-агентами.

Агент — это тип шага, а не оркестратор. Топология работ, условия перехода,
бюджеты, повторы и проверка результата описаны декларативно и исполняются
движком. Модель не решает, что делать дальше — она делает то, что поручил
текущий шаг, и отдаёт результат, который проверяется контрактом.

## Статус

Ранний. Пайплайн из нескольких работ с агентскими шагами исполняется целиком,
но часть формата пока отклоняется с ошибкой — см. [состояние
реализации](docs/status.md).

Движок применён к собственной разработке: петля саморазвития
[`.stepcast/pipelines/self-improve.yml`](.stepcast/pipelines/self-improve.yml)
берёт очередное улучшение из [очереди](backlog.md), заводит под него
OpenSpec-изменение, реализует до зелёной сборки, ревьюит отдельной сессией и
коммитит — по коммиту на улучшение. Первые пункты очереди нужны в первую
очередь ей самой.

- [Состояние реализации](docs/status.md) — что работает, а что ещё нет
- [Формат пайплайна](docs/pipeline-format.md) — работы, шаги, сессии, контекст
- [Прогон](docs/run-layout.md) — рабочее дерево, состояние, resume, дифф, расход
- [Конфигурация](docs/config.md) — глобальная и проектная, политика
- [Запускаемый пример](examples/minimal/stepcast.yml)

## Как это выглядит

```yaml
version: 1
kind: pipeline
name: fix-tests

jobs:
  fix:
    until: { max_iterations: 3, check: [{ cmd: npm test }] }
    steps:
      - id: repair
        agent: claude
        prompt: file:./prompts/fix-tests.md
        expect: [{ changed_only: ["src/**", "test/**"] }]

  verify:
    needs: [fix]
    steps:
      - id: lint
        run: [npm, run, lint]
        expect: [{ exit_code: 0 }]
```

```bash
npm install && npm run build
node dist/src/bin.js run examples/minimal/stepcast.yml --input topic=сессии
```

## Установка

Пакет объявляет бинарник `stepcast`, но сборка сама по себе не выкладывает его
на `PATH` — до установки команду зовут полным путём (`node dist/src/bin.js`), а
`stepcast up` отвечает `command not found`.

Разработка ведётся по симлинку: он указывает прямо в рабочее дерево, поэтому
правки видны сразу после пересборки, без переустановки.

```bash
npm install && npm run build && npm link
```

`npm link` создаёт симлинк в глобальном каталоге npm (`$(npm prefix -g)/bin/stepcast`),
ведущий на `dist/src/bin.js` этого репозитория. Следствия, о которых стоит
знать заранее:

- **После правки исходников нужен `npm run build`.** Симлинк ведёт на
  собранный файл, а не на исходник, и без пересборки команда продолжит
  работать по прошлой сборке.
- **Каталог репозитория нельзя переносить или удалять** — симлинк повиснет, и
  `stepcast` перестанет запускаться.
- **Если `$(npm prefix -g)/bin` не в `PATH`,** линковка ничего не изменит:
  проверьте `npm prefix -g` и добавьте его `bin` в `PATH`.

Откат:

```bash
npm unlink -g stepcast
```

Демон витрины в автозапуск не прописывается: после перезагрузки машины
`stepcast up` нужно вызвать заново.

Витрина, которую отдаёт `stepcast up`, сама по себе исходники на React и
TypeScript в `ui/`; `npm run build` уже собирает её (`vite build` в
`dist/ui-web/index.html`) вместе с кодом на Node — отдельного шага не нужно.
При правке самой витрины удобнее `npm run dev:ui`: он поднимает dev-сервер
Vite с горячей перезагрузкой и проксирует `/api` на уже запущенный демон
(`stepcast up` в другом терминале), не заставляя пересобирать `dist/ui-web`
на каждое изменение.

## Принципы

**Управление потоком детерминировано.** Порядок работ, ветвления и реакция на
отказ вычисляются движком из объявленного графа, а не выводятся моделью по ходу
дела.

**Результат шага проверяется контрактом.** У каждого шага объявлен `expect`.
Жёстким гейтом становятся только проверки, которые дешевле и надёжнее самой
работы: код возврата, схема, зелёные тесты. Оценка агентом-судьёй доступна, но
по умолчанию совещательная.

**Работы обмениваются файлами, шаги внутри работы — диалогом.** Каждая работа
производит один структурированный JSON, и он автоматически попадает в контекст
последующих агентских работ. Внутри работы агентские шаги по умолчанию идут в
общей сессии: перекладывать через диск то, что обсуждалось шаг назад, незачем.

**Повторы ограничены бюджетом и числом попыток.** Проверок того, что попытка
чем-то отличается от предыдущей, нет. Каждая попытка записывается отдельно,
поэтому шаг, стабильно проходящий не с первого раза, виден как диагноз промпта
или спеки.

**Работа не знает о пайплайне.** Она описывает только то, что делает, свой
бюджет и условие сходимости, и выносится в отдельный файл. Зависимости, условия
и окружение живут на месте подключения — поэтому одна работа переиспользуется в
разных пайплайнах без изменений.

**Ошибки ловятся до запуска.** `stepcast lint` проверяет структуру статически:
циклы, недостижимые работы, неразрешимые ссылки, цикл без предела, подстановку
данных модели в командную строку. Отрабатывает до того, как потрачен первый
токен.

**Непонятного поведения не бывает.** `stepcast config` показывает происхождение
каждой настройки, `stepcast context` — что именно увидит шаг, `stepcast status` —
почему шаг признан невалидным. Кеш и политика, про которые непонятно, откуда
они взялись, обходятся дороже, чем их отсутствие.

**Происходящее видно целиком.** `stepcast up` поднимает локальную витрину:
один демон наблюдает за прогонами всех проектов сразу, подхватывает новые по
мере появления и показывает их живьём — вход и выход каждой работы, файлы
журнала, разрез контекста агентских шагов. Останавливается `stepcast down`.

## Раскладка

| | |
|---|---|
| Бинарник | `stepcast` (на `PATH` после `npm link`, см. [Установку](#установка)) |
| Пайплайн | `stepcast.yml` или `.stepcast/pipelines/*.yml` |
| Работы | `.stepcast/jobs/*.yml` |
| Конфиг | `~/.stepcast/config.yml` и `.stepcast/config.yml` |
| Прогоны | `~/.stepcast/runs/<project>/<run>/` |
| Переменные | `STEPCAST_*` |
