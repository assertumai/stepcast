# Очередь улучшений

Очередь для пайплайна саморазвития (`.stepcast/pipelines/self-improve.yml`).
Один заход петли берёт первый свободный пункт сверху, доводит до зелёной сборки
и коммитит.

Порядок задаёт человек и он же единственный приоритет: петля берёт первый
свободный сверху, других критериев выбора нет. Пополняется вручную —
`docs/status.md` служит источником кандидатов, но очередью не является.

Формат пункта: заголовок второго уровня — слаг в kebab-case, он же имя
OpenSpec-изменения. Под ним плоские поля `ключ: значение`.

| Поле | |
|---|---|
| `status` | `pending`, `in_progress`, `done` или `failed` |
| `title` | одна строка о том, что делается |
| `why` | зачем это нужно |
| `done_when` | по чему признаётся выполненным |
| `group` | слаг смежности; по умолчанию — слаг самого пункта |
| `started_at` | ISO 8601, проставляется петлёй при взятии в работу |
| `reason` | причина отказа, проставляется петлёй при `failed` |

Группа объявляет, что пункты правят одно и то же. `pick --slots N` выдаёт до
`N` пунктов сверху, все из разных групп: занятая группа не выдаётся, пока её
пункт не завершён, даже если ниже есть свободные пункты той же группы. Пункт
без `group` образует группу из себя одного.

Пункт со статусом `in_progress`, взятый более 6 часов назад, считается зависшим
и берётся заново: прогон, оборванный по `Ctrl-C`, крашу или бюджету, иначе
заблокировал бы его навсегда.

## portable-backlog-format

status: done
title: Универсальный формат очереди и команда stepcast backlog
group: portable-loop
why: Очередь — соглашение одного репозитория, а не движка. Формат описан только преамбулой самого backlog.md, разбирает его scripts/backlog.mjs, и работа slots зовёт его как `node scripts/backlog.mjs pick`, то есть путём внутри проекта. В package.json объявлено files: ["dist", "schema"] — при установке stepcast пакетом ни один из трёх скриптов петли не поедет вовсе. ## openspec-follows-repo

status: done

## nested-repo-isolation

status: done
title: Дорожка получает вложенные репозитории в своём рабочем дереве
group: nested-repos
why: git worktree корня даёт пустые каталоги вложенных — агенту нечего править, и заход по межрепозиторному пункту умирает на первом же шаге. Клонировать их заново каждый заход дорого по диску и времени старта; дешевле git worktree каждого объявленного внутрь дерева дорожки: общая база объектов, мгновенный старт, и каждый остаётся настоящим git-деревом, а значит составной якорь и покоммитное сведение работают без оговорок. Цена — учёт и радиус разрушения. Записи в .git/worktrees вложенных живут вне каталога прогона, в чужом репозитории проекта, и неубранные копятся от захода к заходу. А разрушительные операции петли — reset --hard и clean -fd отката, worktree remove --force уборки — до сих пор писались в расчёте на одно дерево: применённые в составном, они обязаны остаться внутри того репозитория, в котором сработали, и никогда не доставать до основных деревьев проекта. Незакоммиченная правка соседнего вложенного или корня, стёртая откатом чужого репозитория, невосстановима — тот же несимметричный риск, ради которого заведён guard-clean-nested.
done_when: рабочее дерево дорожки содержит объявленные вложенные репозитории в состоянии их HEAD, каждое — отделённым worktree своего собственного репозитория; заведение и уборка не трогают ни рабочее дерево вложенного в проекте, ни корневой репозиторий; уборка прогона снимает только заведённые этим прогоном записи worktree, в том числе после отказа, отмены и остановки по бюджету, и риск снести чужую запись вслепую (prune в чужом репозитории убирает всякую осиротевшую, не только свою) либо исключён, либо назван документацией; откат внутри дорожки действует на дерево того репозитория, где сработал, и не выходит за его границы — правки в соседних объявленных вложенных и в корне дорожки переживают его; ни одна разрушительная операция дорожки не выполняется в деревьях проекта; наследование дерева зависимой работой переносит вложенные наравне с корнем; режим cwd поведения не меняет; сценарий покрыт проверкой: правки в двух вложенных и в корне, откат одного вложенного — остальные целы
started_at: 2026-08-29T22:24:17.259Z

## merge-lanes-per-repo

status: done
title: Сведение накладывает и коммитит по каждому затронутому репозиторию
group: nested-repos
why: merge-lanes накладывает один дифф, зовёт одну проверку и делает один коммит в одном дереве — межрепозиторный пункт так не сводится вовсе, и вся работа над ним выбрасывается на последнем шаге захода. Порядок обязан стать иным: наложить во все затронутые, проверить все, и только потом коммитить, иначе красная проверка второго репозитория застаёт первый уже закоммиченным.
