# Очередь улучшений

Очередь для пайплайна саморазвития (`.stepcast/pipelines/self-improve.yml`).
Один заход петли берёт первый свободный пункт сверху, доводит до зелёной сборки
и коммитит.

Порядок задаёт человек и он же единственный приоритет: петля берёт первый
свободный сверху, других критериев выбора нет. Пополняется вручную —
`docs/status.md` служит источником кандидатов, но очередью не является.

Формат пункта: заголовок второго уровня — слаг в kebab-case, он же имя
OpenSpec-изменения. Под ним плоские поля `ключ: значение`.

| Поле | |
|---|---|
| `status` | `pending`, `in_progress`, `done` или `failed` |
| `title` | одна строка о том, что делается |
| `why` | зачем это нужно |
| `done_when` | по чему признаётся выполненным |
| `started_at` | ISO 8601, проставляется петлёй при взятии в работу |
| `reason` | причина отказа, проставляется петлёй при `failed` |

Пункт со статусом `in_progress`, взятый более 6 часов назад, считается зависшим
и берётся заново: прогон, оборванный по `Ctrl-C`, крашу или бюджету, иначе
заблокировал бы его навсегда.

## usage-visibility

status: done
title: Показ расхода — команда stepcast usage и расход в витрине
why: Расход считается и пишется полностью — на каждую попытку в step.json, агрегатом по работам и шагам в usage.json, — но увидеть его нечем. Команда stepcast usage описана в run-layout.md и pipeline-format.md, но в CLI не зарегистрирована; витрина расход не показывает вообще; stepcast status печатает только сумму по прогону. done_when: stepcast usage <run-id> печатает разбивку по работам, шагам и номерам попыток; витрина показывает расход прогона и каждой работы; измерения, не сообщённые бэкендом, помечены как несообщённые, а не как ноль; docs/status.md, docs/run-layout.md и спека ui-dashboard согласованы с реализацией

## iteration-note-budget

status: done
title: Выдержка о прошлой итерации обязана укладываться в предел контекста
why: withIterationNote вшивает в контекст следующей итерации весь detail упавшего предиката — для check вида npm run check это вывод сборки, линта и тестов целиком. Запись идёт как kind: text, такие помечаются pinned, а applyBudget понижает только записи с kind: path. Уложиться нельзя, понизить нечего, остаётся исключение: в прогоне aa2090 работа implement умерла на второй итерации с «Контекст шага превышает предел: 17.5k против 8k», хотя сама итерация 1 занимала 3.9k. Отказ устроен наихудшим образом — выдержка тем больше, чем сильнее сломана сборка, поэтому цикл рвётся ровно тогда, когда следующая итерация нужнее всего.
done_when: выдержка о прошлой итерации имеет предел и при его превышении усекается по границам строк с явной пометкой об усечении, сохраняя конец вывода, где стоит причина; предел объявляется и имеет разумное умолчание; шаг с узким context_max_tokens проходит вторую итерацию после падения многословной проверки; исключение остаётся только для случая, когда предел не выдерживает и сам объявленный контекст; docs/status.md обновлён

## dependent-job-workspace

status: pending
title: Наследование рабочего дерева зависимой работой
why: В режимах worktree и copy каждая работа получает снимок от исходного HEAD, а не от результата предшественника, поэтому многоработный пайплайн, передающий изменения файлами, возможен только в cwd — без изоляции. Петля саморазвития из-за этого правит движок прямо в рабочем дереве разработчика, и сломанная сборка приземляется туда же.

## run-progress-output

status: pending
title: Прогресс прогона в терминале
why: Команда run печатает диагностику линта, уходит в await runPipeline и молчит до самого конца — сорок минут захваченного терминала без единой строки. Понять, идёт ли работа, какая именно и не завис ли шаг, нечем: события пишутся в журнал, но никто их не выводит.
