# Очередь улучшений

Очередь для пайплайна саморазвития (`.stepcast/pipelines/self-improve.yml`).
Один заход петли берёт первый свободный пункт сверху, доводит до зелёной сборки
и коммитит.

Пункты со статусом `done` переносятся в `resolved.md` — тот же формат, тот же
порядок; там история решённого, здесь только то, что ждёт работы.

Порядок задаёт человек и он же единственный приоритет: петля берёт первый
свободный сверху, других критериев выбора нет. Пополняется вручную: кандидаты
берутся из оговорок документации `docs/` и из разбора отказов, а сводного
учёта, который сам называл бы кандидатов, у репозитория нет.

Формат пункта: заголовок второго уровня — слаг в kebab-case, он же имя
OpenSpec-изменения. Под ним плоские поля `ключ: значение`.

| Поле | |
|---|---|
| `status` | `pending`, `in_progress`, `done` или `failed` |
| `title` | одна строка о том, что делается |
| `why` | зачем это нужно |
| `done_when` | по чему признаётся выполненным |
| `group` | слаг смежности; по умолчанию — слаг самого пункта |
| `track` | метка веса; этот пайплайн знает `express` — облегчённая цепочка |
| `started_at` | ISO 8601, проставляется петлёй при взятии в работу |
| `reason` | причина отказа, проставляется петлёй при `failed` |

`track: express` ставится пункту, чей `done_when` проверяется механически и не
требует проектного решения: облегчённая цепочка снимает планирование и ревью,
оставляя описание изменения, реализацию и объявленную проверку. Пункт без поля
идёт полной цепочкой. Слово знает пайплайн, а не движок: очередь несёт метку,
проверяя только её форму. Разметка — весь критерий: неверно размеченный пункт
доедет до коммита без второго мнения. Подробнее — `docs/backlog.md`.

Группа объявляет, что пункты правят одно и то же. `pick --slots N` выдаёт до
`N` пунктов сверху, все из разных групп: занятая группа не выдаётся, пока её
пункт не завершён, даже если ниже есть свободные пункты той же группы. Пункт
без `group` образует группу из себя одного.

Пункт со статусом `in_progress`, взятый более 6 часов назад, считается зависшим
и берётся заново: прогон, оборванный по `Ctrl-C`, крашу или бюджету, иначе
заблокировал бы его навсегда.

## script-step-runners

status: done
title: Шаг script — файл на любом языке, исполняемый раннером из расширяемой таблицы
group: script-steps
why: Единственный способ выполнить свой код в пайплайне — шаг `run` (`src/core/pipeline/model.ts`, `RunStep`): список argv либо строка через `sh -c`. done_when: шаг `script: <путь>` с необязательными `args` и `runner` описан в схеме пайплайна и исполняется подпроцессом с теми же `STEPCAST_*`, таймаутами, `expect`, `on_fail` и `attempts`, что и `run`; раннер выбирается по явному `runner`, иначе по расширению, иначе по shebang; таблица раннеров содержит встроенные `node`, `python3`, `sh` и пополняется в конфигурации проекта и домашней записью «имя — шаблон argv»; путь скрипта разрешается слоями проект, домашний каталог, встроенные, и линтер отказывает на несуществующий файл и неизвестный раннер до захода; отсутствующий на машине раннер — отказ шага с именем раннера и подсказкой; выбор раннера, слои и отказы покрыты тестами; `docs/pipeline-format.md` описывает шаг и таблицу

## script-step-contract

status: done
title: Вход и выход скрипта — файлы по контракту, а не argv и stdout
group: script-steps
why: Скрипт получает данные только подстановками в argv, а структурированный выход отдаёт единственным способом — печатая JSON в stdout при объявленном `output_schema` (`docs/pipeline-format.md`, «run»). Для скрипта на Python или Go это значит собирать аргументы вручную и держать stdout чистым от логов. Нужен контракт, одинаковый для любого языка: вход — `input.json` в каталоге шага с путём в `STEPCAST_INPUT`, выход — `output.json` с путём в `STEPCAST_OUTPUT`, публикация — прежний `stepcast data set`; stdout остаётся логом. Поверх контракта — тонкий SDK для TS/JS `stepcast/step` с `input()`, `output()`, `publish()`, `log()`, `exec()`, читающий `STEPCAST_*` из окружения и потому пригодный в любом дочернем процессе; раннер `node` подключает обёртку, которая вызывает default export модуля, пишет возвращённое значение в `output.json` и проверяет схемой. Библиотека для Python — отдельным пунктом, когда понадобится.
done_when: шаг `script` принимает поле `input` с подстановками и записывает его в `input.json` каталога шага, путь передаётся в `STEPCAST_INPUT`; выход читается из файла по `STEPCAST_OUTPUT`, проверяется `output_schema` и доступен `expect`, `output.from` и `${jobs.*.output.*}` так же, как выход агентского шага; `run` с `output_schema` продолжает разбирать stdout как раньше; пакет экспортирует `stepcast/step` с `input`, `output`, `publish`, `log`, `exec`, работающий по одним лишь `STEPCAST_*`; раннер `node` для модуля с default export вызывает его и пишет результат в `output.json`, а модуль без default export исполняется как обычный скрипт; контракт, SDK и обёртка покрыты тестами, включая скрипт на Python, работающий по контракту без SDK; `docs/pipeline-format.md` и `docs/plugins.md` описывают контракт и SDK
started_at: 2026-09-10T23:27:57.991Z

## builtin-pages-as-plugins

status: pending
title: Встроенные экраны — плагины того же формата, что и пользовательские
group: ui-runtime
why: Стабильность интерфейса для пользователя должна держаться не на замороженном API виджета, а на том, что встроенное и пользовательское пишется одним способом: тогда любой встроенный экран можно взять за образец, скопировать и заменить.
