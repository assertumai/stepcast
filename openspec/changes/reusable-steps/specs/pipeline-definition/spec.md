## ADDED Requirements

### Requirement: Шаг uses зовёт переиспользуемый шаг по имени

Документ пайплайна и файл работы SHALL признавать шаг с ключом `uses`, называющим переиспользуемый шаг по имени, и с необязательным отображением `with` — параметрами вызова.

Ключ `uses` внутри `steps` MUST различать вид шага при разборе так же, как его
различают ключи `run`, `script` и `prompt`: документ, объявивший `uses` вместе
с любым из них, MUST отклоняться разбором.

Ключи `script`, `args`, `runner`, `input` и `output_schema` рядом с `uses`
MUST отклоняться: файл, раннер, вход и схему выхода объявляет манифест шага, и
место вызова их не переопределяет. Шаг `uses` MUST принимать те же общие ключи,
что и остальные шаги: `id`, `env`, `context`, `timeout`, `budget`, `expect`,
`attempts`, `on_fail`.

Значение `with` MUST быть отображением; значения его полей MAY быть любыми
представимыми в JSON — теми же, что допускает `input` шага `script`. Это
отличает `with` шага от `with` работы, где значением остаётся строка, число
либо логическое.

Опубликованная JSON Schema документов (`schema/pipeline.schema.json`,
`schema/job.schema.json` и вывод `stepcast schema`) MUST содержать ветвь шага
`uses`, чтобы редактор подсказывал её наравне с `run`, `script` и `agent`.

#### Scenario: Шаг объявлен именем

- **WHEN** работа объявляет `uses: changed-files` с `with: { ref: HEAD }`
- **THEN** раскрытый шаг несёт имя шага, разрешённый манифест и параметры вызова

#### Scenario: Два вида шага сразу

- **WHEN** шаг объявляет одновременно `uses` и `script`
- **THEN** разбор документа отклоняет шаг, называя файл и место объявления

#### Scenario: Переопределение объявленного манифестом

- **WHEN** шаг объявляет `uses` вместе с `runner`, `args`, `input` либо `output_schema`
- **THEN** разбор документа отклоняет ключ, называя его объявляемым манифестом шага

#### Scenario: Общие ключи принимаются

- **WHEN** шаг объявляет `uses` вместе с `timeout`, `expect`, `attempts` и `env`
- **THEN** разбор принимает их, и шаг подчиняется им как любой другой

#### Scenario: Параметры не отображением

- **WHEN** шаг объявляет `with: [a, b]`
- **THEN** разбор документа отклоняет значение, называя место объявления

#### Scenario: Ветвь есть в опубликованной схеме

- **WHEN** пакет напечатал JSON Schema документов
- **THEN** описание шага допускает ключи `uses` и `with`

### Requirement: Параметры вызова раскрываются как JSON, а не как строка

Значения внутри `with` шага `uses` SHALL раскрываться подстановками тем же типизированным проходом, что и `input` шага `script`: строка ровно из одной подстановки даёт значение исходного типа.

Правило MUST действовать на обоих этапах раскрытия: `${inputs.*}` и
`${params.*}` — при разборе документа, `${jobs.*}`, `${run.*}` и `${env.*}` —
перед исполнением работы. Строка, где подстановка соседствует с другим текстом,
MUST раскрываться в строку.

#### Scenario: Объект из выхода работы выше по графу

- **WHEN** шаг объявляет `with: { item: "${jobs.plan.output.item}" }`, а выход работы `plan` содержит объект в поле `item`
- **THEN** параметр несёт этот объект целиком

#### Scenario: Число остаётся числом

- **WHEN** шаг объявляет `with: { retries: "${params.retries}" }` при `params.retries: 3`
- **THEN** параметр несёт число `3`

#### Scenario: Подстановка внутри текста даёт строку

- **WHEN** шаг объявляет `with: { title: "чинить ${jobs.plan.output.slug}" }`
- **THEN** параметр несёт строку с подставленным значением

### Requirement: Статическая валидация шага uses

`stepcast lint` SHALL называть промахи вызова переиспользуемого шага до захода: неизвестное имя, нечитаемый манифест, несовпадение имени, отсутствующий файл шага, неизвестный и непереданный обязательный параметр, значение параметра не по схеме.

Каждое сообщение MUST называть работу, шаг и — кроме ненайденного имени —
файл манифеста. Ненайденное имя MUST перечислять просмотренные каталоги слоёв.

Значение параметра, в котором осталась отложенная подстановка (`${jobs.*}`,
`${run.*}`, `${env.*}`), MUST пропускаться проверкой схемы — тем же правилом,
каким линт уже пропускает пути с подстановками. Пропускаться MUST именно это
значение, а не весь набор: соседний параметр, известный статически, MUST
проверяться схемой как обычно. Состав параметров MUST проверяться всегда:
неизвестное имя и непереданный обязательный от значений не зависят.

Ни один из этих промахов MUST NOT быть исключением раскрытия: разбор
документа продолжается, и `stepcast lint` называет все промахи за один проход.

#### Scenario: Неизвестное имя шага

- **WHEN** работа объявляет `uses: no-such-step`
- **THEN** линт завершается ошибкой с именем шага и перечнем просмотренных каталогов

#### Scenario: Несколько промахов за один проход

- **WHEN** пайплайн объявляет два шага `uses`: один с неизвестным именем, другой с неизвестным параметром
- **THEN** линт называет оба промаха

#### Scenario: Значение с отложенной подстановкой не проверяется схемой

- **WHEN** параметр объявлен `{ type: object }`, а передан как `"${jobs.plan.output.item}"`
- **THEN** линт проверяет наличие параметра, но не его значение

#### Scenario: Отложенное значение не прячет промаха соседнего

- **WHEN** шаг передаёт `with: { a: "${jobs.plan.output.x}", b: 42 }` при объявленном `b: { type: string }`
- **THEN** линт называет промах параметра `b`, не дожидаясь прогона

#### Scenario: Прогон отказывает неразрешённому шагу

- **WHEN** прогон дошёл до шага `uses` с неизвестным именем
- **THEN** шаг отказывает одной терминальной попыткой с тем же текстом, что дал линт

## MODIFIED Requirements

### Requirement: Правила разрешения путей

Пути в `uses` работы, `prompt: file:` и `schema` SHALL разрешаться относительно файла, в котором объявлены. Правило для `schema` MUST применяться одинаково к
`output_schema` шага, к `output.schema` работы и к предикату `schema` в
`expect` и в `until.check`.

Пути в `context`, `output` и аргументах `run` SHALL разрешаться относительно
корня рабочей директории работы. По этому же правилу разрешаются пути
предиката `file_exists`.

Значение `script` SHALL разрешаться третьим правилом: голое имя — слоями
(проект, домашний каталог, встроенный каталог пакета), значение с явным
префиксом `./` или `../` — относительно файла, в котором объявлено. Разрешение
относится к определению шага, а не к его работе: файл читается на раскрытии, а
рабочей директорией процесса остаётся рабочая директория работы. Этим же
третьим правилом SHALL разрешаться путь предиката `script` — и в `expect`
шага, и в `until.check` работы: слоёв и явного префикса предикат не отличает
от шага `script`.

Значение `uses` **шага** SHALL разрешаться четвёртым правилом, и путём оно не
бывает вовсе: это имя, которое ищут слоями каталогов шагов — `<корень
проекта>/.stepcast/steps/`, `~/.stepcast/steps/`, встроенный каталог пакета.
Пути внутри найденного манифеста (`file`, `output_schema`) MUST разрешаться
относительно каталога шага и MUST NOT выходить за его пределы; слои внутри
манифеста не применяются.

#### Scenario: Промпт рядом с файлом работы

- **WHEN** файл `.stepcast/jobs/implement.yml` объявляет `prompt: file:../prompts/implement.md`
- **THEN** читается `.stepcast/prompts/implement.md`

#### Scenario: Контекст от корня рабочей директории

- **WHEN** тот же файл работы объявляет `context: [AGENTS.md]`
- **THEN** читается `AGENTS.md` из корня рабочей директории, а не из `.stepcast/jobs/`

#### Scenario: Схема предиката рядом с файлом работы

- **WHEN** файл `.stepcast/jobs/implement.yml` объявляет предикат
  `expect: [{ schema: ../schemas/implement.json }]`
- **THEN** читается `.stepcast/schemas/implement.json`

#### Scenario: Схема предиката в условии сходимости

- **WHEN** тот же файл работы объявляет `until.check` с предикатом
  `schema: ../schemas/implement.json`
- **THEN** путь разрешается по тому же правилу, что и в `expect`

#### Scenario: Файл, созданный шагом, от корня рабочей директории

- **WHEN** файл работы вне корня объявляет `expect: [{ file_exists: report.json }]`
- **THEN** проверяется `report.json` в корне рабочей директории

#### Scenario: Предикат script голым именем

- **WHEN** предикат объявлен как `expect: [{ script: checks/no-todo.py }]`, и файл есть в `.stepcast/scripts/` проекта
- **THEN** исполняется файл проекта, тем же слоем, что выбрал бы шаг `script` с тем же именем

#### Scenario: Предикат script явным путём

- **WHEN** файл `.stepcast/jobs/nightly.yml` объявляет `until.check: [{ script: ../checks/converged.sh }]`
- **THEN** путь разрешается от каталога файла работы, а слои не просматриваются

#### Scenario: Имя шага uses ищется слоями каталогов шагов

- **WHEN** файл `.stepcast/jobs/review.yml` объявляет шаг `uses: changed-files`
- **THEN** ищется `changed-files/step.yml` в каталогах шагов проекта, домашнего каталога и пакета — независимо от того, где лежит файл работы

#### Scenario: Файл шага ищется от каталога манифеста

- **WHEN** манифест `~/.stepcast/steps/changed-files/step.yml` объявляет `file: ./main.mjs`
- **THEN** исполняется `~/.stepcast/steps/changed-files/main.mjs`, а слои не просматриваются
