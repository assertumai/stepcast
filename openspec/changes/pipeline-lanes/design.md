## Context

Петля саморазвития — семь работ строго последовательно, `workspace.mode: cwd`,
`concurrency: 1`. Режим `cwd` был выбран вынужденно: до наследования рабочего
дерева изолирующие режимы давали каждой работе снимок от `HEAD`, и `review` не
увидел бы правок `implement`. Это ограничение снято пунктом
`dependent-job-workspace`: линейная цепочка работ в `worktree` продолжается в
каталоге предшественника, а развилка получает собственный каталог, приведённый
к якорю предшественника. Значит, цепочка `propose → … → verify` может целиком
жить в своём дереве, а несколько таких цепочек — не видеть друг друга.

Планировщик ведёт независимые работы параллельно в пределах
`min(pipeline.concurrency, limits.concurrency)`, а `backends.<имя>.concurrency`
отдельно ограничивает одновременные обращения к бэкенду (умолчание для
`claude` — 2). Очередь умеет выдавать несколько несмежных пунктов одним
проходом: `backlog.mjs pick --slots N` берёт по одному пункту на действующую
группу и помечает всех выбранных одной записью в файл.

Чего нет: способа передать дорожке её слот. Выдачу делает командный шаг, а
командный шаг структурированного вывода не имеет — `output.from`, названный на
шаге `run`, тихо не даёт ничего. Без выхода работы у `if` дорожки нет данных, и
пустая дорожка не может себя пропустить.

Чего ещё нет: способа свести одну дорожку. `stepcast apply` накладывает либо
все изолированные работы прогона подряд, либо одну работу по `--job`; на работе
из цепочки `--job` даёт дифф, предполагающий уже применённые вклады
предшественников, и в одиночку обычно конфликтует — это записано в
`docs/status.md` как известное ограничение.

## Goals / Non-Goals

**Goals:**

- Заход петли обрабатывает несколько несмежных пунктов очереди одновременно.
- Дорожка изолирована по рабочему дереву и не видит правок соседней до сведения.
- Дорожка без пункта пропускает себя, не роняя ни прогон, ни соседей.
- Сведение — по одной дорожке, с проверкой после каждой, с коммитом на
  улучшение и с внятным отказом, не теряющим работу дорожек.
- Расход и цена читаются по дорожкам, а не только по работам.
- Всё это работает на встроенных умолчаниях конфигурации, без обязательного
  глобального конфига.

**Non-Goals:**

- Динамическое размножение работ (`matrix`, `for_each`). Граф статичен;
  дорожки выписываются в пайплайне.
- Дорожка как область бюджета, отмены или `fail_fast`. `lane` — метка
  группировки, а не единица исполнения.
- Автоматическое разрешение конфликта между дорожками — ни трёхсторонним
  слиянием сверх того, что делает `git apply --3way`, ни агентом.
- Блокировка файла очереди: выдача по-прежнему происходит один раз, до
  расхождения дорожек, и состязания не возникает.
- Показ дорожек в витрине и в `stepcast status`. Признак выполненности
  называет `stepcast usage`, и этим изменение ограничивается.

## Decisions

### Дорожка — метка обвязки, а не сущность исполнения

Альтернатива — сделать дорожку узлом формата (`lanes: { a: { jobs: [...] } }`)
— вводит второй способ описывать граф и требует правил для зависимостей между
дорожками, отмены дорожки, бюджета дорожки. Дорожка при этом ничего не решает:
порядок задают `needs`, изоляцию — `workspace`, пропуск — `if`. Всё это уже
работает.

Поэтому `lane` — необязательный ключ обвязки со значением-слагом, как `needs`,
`on`, `if` и `with`. Он не влияет ни на порядок, ни на изоляцию, ни на статусы.
Он отвечает на один вопрос: какие работы считать одним делом при подведении
итогов и при наложении результата. Место ему — рядом с прочей обвязкой, на
месте подключения: файл работы у дорожек общий, и объявить дорожку внутри него
нельзя по построению. Запрет обвязки внутри файла работы в формате уже есть, и
`lane` просто попадает в тот же список.

Значение проверяется тем же правилом kebab-case, что и слаг пункта очереди и
идентификатор работы. Работы одной дорожки не обязаны быть связаны
зависимостями — валидатор этого не требует: связность обеспечивают `needs`, а
дорожка, собранная из несвязанных работ, осмысленна для учёта расхода. Для
наложения она осмысленна не всегда, и `apply --lane` говорит об этом сам (см.
ниже).

### Командный шаг публикует выход только по явному объявлению

Разбирать `stdout` каждого командного шага как JSON нельзя: шаг, случайно
напечатавший объект, стал бы выходом работы. Признаком служит объявленный на
шаге `output_schema` — тот же ключ, которым агентский шаг просит у бэкенда
структурированный вывод. Смысл ключа один и тот же — «этот шаг отдаёт структуру
такой формы», — меняется только способ её получить: у агента через штатный
механизм бэкенда, у команды через `stdout`.

Разбор строгий: пробелы по краям снимаются, всё остальное обязано быть одним
JSON-документом. Ни поиска первой `{`, ни склейки последней строки: шаг,
печатающий лог вперемешку с результатом, должен получить отказ с причиной, а не
угаданный выход. Отказ — обычный отказ шага, то есть повторяется по
`attempts.max` и виден в журнале как причина, а не как отсутствие выхода на три
шага дальше.

Следствием предикат `schema` начинает работать и на командных шагах: он
проверяет структурированный вывод, которого у них раньше просто не было.

### Слот дорожки передаётся выходом работы выдачи и файлом в каталоге прогона

Выдача — одна работа `slots` в режиме `cwd`: она обязана видеть настоящее
дерево (проверка чистоты) и править настоящий `backlog.md`. Её командный шаг
зовёт `backlog.mjs pick --lanes a,b`, и его `stdout` становится выходом работы.

Выход устроен так, чтобы `if` дорожки всегда вычислялся:

```json
{ "lanes": {
    "a": { "filled": true,  "slug": "…", "title": "…", "group": "…", "item": "…/item-a.json" },
    "b": { "filled": false, "slug": "",  "title": "",  "group": "",  "item": "…/item-b.json" } } }
```

Условие дорожки — `if: "jobs.slots.output.lanes.b.filled == true"`. Направление
сравнения выбрано осознанно: неопределённое значение делает условие ложным, то
есть неизвестность приводит к пропуску дорожки, а не к её запуску вслепую.
Поля пустой дорожки присутствуют и пусты по той же причине: подстановка
`${jobs.slots.output.lanes.b.slug}` не должна ронять прогон, даже если
когда-нибудь окажется раскрытой у пропущенной работы.

Сам пункт кладётся файлом `item-<дорожка>.json` в каталог прогона — туда же,
куда его клал одиночный заход. Каталог прогона лежит вне проекта, поэтому файл
не попадает ни в `changed_only`, ни в коммит, а `finalize` находит его и тогда,
когда `slots` до публикации выхода не дошла.

Обращение к идентификаторам работ вида `verify-a` допустимо в подстановках
`${jobs.verify-a.status}`, но не в выражениях `if`: грамматика выражений не
знает дефиса в имени. Дорожки этим не задеты — их условия смотрят только на
`jobs.slots.output.*`, — но правило стоит помнить, объявляя новые условия.

### Пропуск пустой дорожки распространяется по цепочке сам

`if` объявляется только на головной работе дорожки. Дальше действует уже
описанное правило: работа, у которой все зависимости пропущены, пропускается
сама. Пропускать нужно поэтому только `propose-<дорожка>`, а `plan`,
`implement`, `review`, `fix-review` и `verify` этой дорожки уходят следом без
единого условия. Дублировать `if` на каждой работе значило бы шесть мест, где
можно ошибиться, вместо одного.

### Дорожка — линейная цепочка в своём рабочем дереве

Пайплайн переходит на `workspace.mode: worktree`. Головная работа дорожки
зависит только от `slots` и объявляет `workspace.inherit: none`: наследовать
там нечего — `slots` исполняется в `cwd`, — а явное объявление избавляет от
зависимости от того, как наследование трактует источник без изолированного
дерева. Дальше дорожка линейна: у каждой работы ровно один предшественник и она
у него единственный потомок, поэтому цепочка продолжается в одном каталоге,
и `review` видит правки `implement`, а `verify` собирает изменённый код — ровно
то, ради чего когда-то был выбран `cwd`.

Работы `slots`, `merge` и `finalize` переопределяют режим на `cwd`: они правят
настоящее дерево проекта и очередь в нём. Смешение режимов в одном пайплайне
формат допускает, а предупреждение линта о `cwd` при `concurrency > 1`
смотрит на режим пайплайна и на переопределения работ не распространяется —
расширять его в этом изменении не будем: три работы в `cwd` разнесены графом и
одновременно не идут.

### Сведение накладывает дорожку одним диффом и коммитит по одной

`stepcast apply --lane <имя>` отбирает изолированные работы дорожки в порядке
графа и накладывает **один** дифф: от `tree_before` первой работы дорожки до
последнего известного `tree_id` последней. Это принципиально не то же самое,
что наложить работы дорожки по очереди: цепочка делит один каталог, вклады в
ней накапливаются, и промежуточные состояния незачем воспроизводить на чужом
дереве. Заодно это снимает для дорожки известное ограничение `--job` на работе
из цепочки — оно возникало именно из-за наложения части накопленного изменения.

Если у дорожки нет ни одной изолированной работы с якорями (вся пропущена,
отказала до первого якоря), команда сообщает, что накладывать нечего, и
завершается успехом: пустая дорожка — обычный исход, а не ошибка.

Скрипт сведения `scripts/merge-lanes.mjs` идёт по дорожкам в объявленном
порядке и для каждой:

1. пропускает дорожку, чья `verify` не завершилась успехом, записав причину;
2. зовёт `$STEPCAST_BIN apply --lane <имя> <run-id>` в дереве проекта;
3. гоняет `npm run check` на объединённом дереве;
4. помечает пункт очереди выполненным и коммитит `<слаг>: <заголовок>`.

Инвариант, на котором всё держится: перед наложением очередной дорожки дерево
чисто, потому что предыдущая уже закоммичена. Поэтому откат неудачного
наложения — возврат дерева к `HEAD`, без снимков и стеша, а конфликт наложения
`stepcast apply` откатывает и сам. Красная проверка после успешного наложения
останавливает сведение: оставшиеся дорожки не накладываются, причина называет
дорожку и то, чем она не сошлась, и работа всех дорожек остаётся в их рабочих
деревьях — прогон их не удаляет, а причина называет путь.

Отметка исхода идёт до коммита и попадает в него же — то же правило, что и в
одиночном заходе: улучшение и его бухгалтерия суть одно событие.

### Завершение проставляет исход каждому взятому пункту

`finalize` остаётся с `needs: all` и `on: always` — единственной конструкцией,
отрабатывающей и при отмене, и при остановке по бюджету. Меняется её
внутренность: она обходит все файлы `item-*.json` каталога прогона и каждому
пункту, не помеченному сведением как выполненный, проставляет `failed` с
причиной, различающей случаи — дорожка не получила пункта (такому пункту
проставлять нечего), `verify` дорожки отказала, наложение не сошлось, проверка
после сведения покраснела, сведение до дорожки не дошло. Коммитов `finalize`
больше не делает: коммит каждой сошедшейся дорожки создаёт сведение.

### Дорожек две, и предел задают встроенные умолчания

Число дорожек упирается не в планировщик, а в два потолка. `limits.tokens` со
встроенным умолчанием `20M` ужесточается снизу, но не поднимается, а проектный
конфиг лежит в репозитории и потолок поднять не может — значит, объявить
`budget.tokens` на весь трёхдорожечный заход нечем. `backends.claude.concurrency`
с умолчанием `2` ограничивает одновременные обращения к бэкенду: третья дорожка
молча ждала бы места.

Отсюда две дорожки и такой бюджет захода: `wallclock: 4h`, `rate_limit_pct: 80`
и денежный потолок вместо токенного. Токенный потолок — величина, которая не
масштабируется дорожками и вдобавок слепа к модели (это и было причиной пункта
`budget-cost-ceiling`); деньги масштабируются и сравнимы между дорожками. Заход
одной дорожки стоил около шестнадцати долларов, две укладываются под встроенный
`limits.cost: $50` с запасом.

Третья дорожка — правка одной строки в пайплайне плюс поднятые в
`~/.stepcast/config.yml` `limits.cost` и `backends.claude.concurrency`. Это
описывается в документации, но в репозиторий не кладётся: глобальный конфиг —
машина пользователя, а не проект.

### `STEPCAST_BIN` вместо угадывания движка

Скрипту сведения нужен тот же движок, который его запустил. `PATH` может вести
к другой установке, а `dist/` в дереве проекта — вообще чужой артефакт: этот
проект и есть stepcast, и его `dist/` пересобирается работами захода.
Переменная `STEPCAST_BIN` указывает на точку входа исполняющего процесса и
попадает к шагу вместе с остальными `STEPCAST_*`, то есть не переопределяется
и не отсеивается `env_deny`.

### Расход по дорожкам считается из тех же данных

Дорожка работы попадает в её запись в `status.json` — новое необязательное
поле. `stepcast usage` строит по нему группировку: строка итога дорожки над
строками её работ, суммы по тем же измерениям, что и у работы, с той же
пометкой несообщённого вместо нуля. Прогоны без дорожек печатаются как сегодня:
группировки нет, потому что группировать не по чему.

## Risks / Trade-offs

- **Дорожки правят один файл, хотя очередь считала их несмежными.** →
  Смежность объявляет человек полем `group`, и ошибка в объявлении даёт
  конфликт при наложении второй дорожки. Ущерб ограничен: конфликт
  откатывается, первая дорожка уже закоммичена, вторая цела в своём дереве и
  доводится вручную `stepcast apply --lane`.
- **Красная проверка после сведения обесценивает дорожку, зелёную у себя.** →
  Это честный исход: улучшения совместимы по отдельности и несовместимы
  вместе. Пункт получает `failed` с причиной, называющей именно это, а не
  «тесты упали».
- **Денежный потолок работает, только пока бэкенд сообщает цену.** Токенного
  потолка на заход больше нет, и полностью несообщённая цена оставила бы заход
  без потолка вовсе. → `wallclock: 4h` остаётся жёстким пределом при любом
  учёте, а неучтённые в деньгах попытки уже помечаются в отчёте.
- **Две параллельные агентские сессии выбирают окно лимита подписки вдвое
  быстрее.** → `rate_limit_pct: 80` и `on_exceed: stop` не меняются: заход
  останавливается осознанно, а не спит до утра.
- **Журнал с полем `lane` не читается прежней версией движка.** Запись работы
  разбирается строгой схемой, и незнакомое поле для неё — ошибка. → Та же
  асимметрия отката, что уже описана в `docs/status.md`; изменение дополняет
  тот раздел, а не заводит новое правило.
- **`apply --lane` на дорожке из несвязанных работ даёт дифф между чужими
  якорями.** → Команда отбирает работы дорожки в порядке графа и берёт края
  этого порядка; для дорожки, не являющейся цепочкой, результат может не
  сойтись — и тогда это обычный конфликт с откатом и перечислением путей.
- **Сведение зовёт движок из шага прогона этого же движка.** → Читается только
  журнал прогона, уже записанный к этому моменту; пишет команда исключительно в
  дерево проекта. Прогон о наложении не знает и знать не должен.

## Migration Plan

Изменение обратно совместимо для всего, кроме пайплайна самой петли:
`lane`, `output_schema` на командном шаге, `STEPCAST_BIN` и `--lane`
необязательны, а прогоны без дорожек печатаются как прежде. Записи `status.json`
прежней формы читаются: поле `lane` необязательное.

Порядок выкладки: сперва движок (`lane`, выход командного шага, `STEPCAST_BIN`,
`apply --lane`, расход по дорожкам) со своими тестами, затем очередь
(`pick --lanes`), затем пайплайн петли и скрипты. До последнего шага петля
работает по-старому: ни один из добавленных ключей не обязателен.

Откат — возврат пайплайна к одной дорожке; движковые добавления при этом просто
перестают использоваться. Откат самого движка под уже записанным журналом с
полем `lane` невозможен — как и любой откат под журналом новой формы.

## Open Questions

- Стоит ли расширять предупреждение линта о `cwd` при `concurrency > 1` на
  переопределения режима у работ. Сейчас оно смотрит только на пайплайн, и
  собственный пайплайн петли под расширенное правило попал бы ложно.
- Нужна ли дорожка в `stepcast status` и в витрине. Признак выполненности
  требует только `stepcast usage`; остальное — отдельный пункт, если окажется
  нужно.
