## ADDED Requirements

### Requirement: Пространство project публикует команду проверки документов изменения

Система SHALL публиковать действующее значение `project.spec.check` подстановкой `${project.spec.check}` в документе пайплайна, файлах работ и файлах промптов — тем же правилом, каким публикуются `${project.check}` и остальные имена группы `spec`.

Состав пространства `project` MUST называть новое имя в диагностике:
обращение к имени вне состава (`${project.spec.command}`) MUST отказывать
разбором и перечислять доступные имена, включая `spec.check`. Обращение к
имени из состава, не объявленному ни пайплайном, ни `.stepcast/config.yml`,
MUST отказывать разбором с указанием обоих мест объявления, а не раскрываться
в пустую строку.

Документ пайплайна MUST принимать ключ `check` в секции `project.spec` верхним
ключом `project` и перекрывать им конфигурацию — тем же полистовым порядком
слоёв, каким он перекрывает `dir`, `rules` и `tool`.

Значение MUST оставаться скаляром: списком оно не раскрывается, и правило
раскрытия списочного значения в элемент списка его не касается.

#### Scenario: Подстановка раскрывается значением конфигурации

- **WHEN** `.stepcast/config.yml` объявляет `project.spec.check`, а файл работы содержит шаг `run: ${project.spec.check}`
- **THEN** раскрытый пайплайн несёт объявленную команду целиком и ни одной подстановки

#### Scenario: Пайплайн перекрывает конфигурацию

- **WHEN** конфигурация объявляет одну команду, а документ пайплайна — в секции `project.spec` другую
- **THEN** подстановка раскрывается командой из пайплайна

#### Scenario: Ссылка на необъявленный ключ

- **WHEN** файл работы ссылается на `${project.spec.check}`, а ключ не объявлен ни одним слоем
- **THEN** разбор завершается ошибкой, называющей оба места, где ключ можно объявить

#### Scenario: Имя вне состава пространства

- **WHEN** файл работы ссылается на `${project.spec.validate}`
- **THEN** разбор завершается ошибкой, перечисляющей доступные имена пространства, среди которых назван `spec.check`
