## Why

Требование «прогон останавливается только по объявленным причинам» на практике
нарушается: ошибка, возникшая внутри работы, не превращается в её отказ, а
проходит насквозь до CLI и убивает процесс прогона.

В `executeJob` цикл итераций обёрнут в `try { … } finally`, где `finally`
освобождает якорь, но `catch` нет. Любое исключение из машинерии шага —
нечитаемый файл контекста, нечитаемая схема предиката — уходит выше.

Последствия наблюдались дважды на живом прогоне:

```
step.started propose create-change     ← и тишина
```

Ни `step.finished`, ни `job.finished`, ни `run.finished`. `status.json`
навсегда остаётся в `running`, все работы — в `pending`, хотя часть из них уже
отработала. Работы с `needs: all` и `on: always` не выполняются, а именно на
них держится завершающая бухгалтерия: пункт очереди улучшений остаётся
помеченным в работе и освобождается только протуханием через шесть часов.

Спека уже требует, чтобы неисполнимость выявлялась до запуска первой работы,
но у этого правила есть законное исключение, записанное там же: пути с
подстановками статически не проверяются. Значит нечитаемый файл посреди
прогона — не гипотетический случай, а штатный, и вести себя он обязан как
отказ работы.

## What Changes

- **Ошибка, возникшая при исполнении работы, становится отказом этой работы.**
  Прогон продолжается по объявленным правилам: `fail_fast` решает, запускать ли
  оставшиеся, а работы с `needs: all` и `on: failure` выполняются и разбирают
  случившееся.
- **Состояние прогона дописывается при любом исходе.** `status.json` получает
  конечный статус, а не остаётся в `running`; работы, успевшие отработать,
  сохраняют свои статусы.
- **Причина записывается в журнал** событием и в причину отказа работы, с
  указанием работы и шага, на которых она наступила.
- Причиной остановки объявляется `spawn_failed` — из закрытого перечня, как это
  уже сделано для неудачи подготовки рабочей директории и раскрытия
  подстановок. Новой причины не заводится: перечень закрыт сознательно.

Сознательно вне объёма: превращение таких ошибок в повторяемые попытки —
нечитаемый файл не станет читаемым от повтора; отказ от статической проверки
там, где она возможна.

**BREAKING**: нет. Меняется поведение в случае, который сегодня оканчивается
крушением процесса.

(нет)

### Modified Capabilities

- `pipeline-execution`: ошибка внутри работы ограничивается её отказом, а не
  прекращает прогон в обход объявленных причин.

## Impact

- Изменяется: `src/core/run/runner.ts` — у цикла итераций работы появляется
  `catch`, приводящий исключение к отказу работы.
- Тесты: работа с нечитаемым файлом контекста и с нечитаемой схемой предиката
  отказывает, прогон получает конечный статус, работа с `needs: all`
  выполняется.
