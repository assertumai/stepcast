## ADDED Requirements

### Requirement: Работа публикует данные командой stepcast data

Движок SHALL предоставлять команду `stepcast data`, которой шаг публикует произвольные значения своей работы по ходу её исполнения.

Признаются три действия: `set <ключ> <значение>`, `merge --json <объект>` и
`get [<ключ>]`.

`set` MUST принимать ключ и значение **двумя позиционными аргументами**, а не
одной парой `ключ:значение`: значения содержат двоеточия штатно, и разбор пары
либо терял бы хвост значения, либо требовал экранирования на каждом вызове.

Целевая работа MUST выводиться из переменной окружения `STEPCAST_JOB_DIR`,
которую движок инжектирует в каждый шаг. Команда MUST NOT принимать ни
идентификатора работы, ни каких-либо путей. Это даёт разом три свойства
устройства: единственного писателя на файл, невозможность записать в чужую
работу и невозможность записать в рабочее дерево — файл внутри рабочего дерева
попал бы в `git add -A` при снятии якоря и вышел бы за границы `changed_only`.

Вызов вне шага прогона MUST отказывать с объяснением, что команда работает
только внутри шага, а не заводить каталог данных по умолчанию.

#### Scenario: Значение с двоеточием

- **WHEN** шаг выполняет `stepcast data set title "Витрина: расход деньгами и токенами"`
- **THEN** по ключу `title` публикуется вся строка целиком, включая часть после двоеточия

#### Scenario: Дописывание объектом

- **WHEN** шаг выполняет `stepcast data merge --json '{"repo":"backend","slug":"nested-repo-anchor"}'`
- **THEN** оба ключа публикуются поверх уже опубликованных, не затирая соседних

#### Scenario: Чтение опубликованного

- **WHEN** шаг выполняет `stepcast data get title` после публикации этого ключа
- **THEN** команда печатает значение ключа

#### Scenario: Вызов вне шага прогона

- **WHEN** команда вызвана в окружении без `STEPCAST_JOB_DIR`
- **THEN** она отказывает, называя причину: работа определяется этой переменной, и вне шага писать некуда

#### Scenario: Путь аргументом не принимается

- **WHEN** команда вызвана с флагом, называющим каталог или файл
- **THEN** разбор аргументов отклоняет неизвестный флаг

### Requirement: Данные работы хранятся плоской картой строк в каталоге прогона

Движок SHALL хранить опубликованные работой данные в файле `<каталог прогона>/jobs/<работа>/data.json` — плоской картой строка-в-строку.

Вложенных значений MUST NOT быть: в `${jobs.x.data.a.b}` не различить вложенный
объект и ключ с точкой, а пространство подстановки обязано быть
одноуровневым. По той же причине точка MUST отклоняться и в имени ключа.

Запись MUST быть атомарной — временный файл и переименование: параллельные
подпроцессы одного шага иначе прочитали бы половину документа.

Последняя запись по ключу MUST побеждать. Файл MUST жить на всю работу —
все её шаги и все итерации цикла `until` пишут в один и тот же.

Отсутствующий или повреждённый файл MUST читаться пустотой, а не отказом:
данные — необязательная публикация, и ронять из-за них прогон или витрину не
за что.

#### Scenario: Ключ с точкой

- **WHEN** шаг выполняет `stepcast data set a.b значение`
- **THEN** команда отказывает, называя недопустимый ключ, и файл данных не меняется

#### Scenario: Повторная запись по тому же ключу

- **WHEN** работа дважды публикует ключ `title` разными значениями
- **THEN** в файле остаётся последнее значение, а соседние ключи сохраняются

#### Scenario: Повреждённый файл

- **WHEN** `data.json` содержит не разбираемый JSON
- **THEN** чтение данных даёт пустую карту, а не ошибку

### Requirement: Движок складывает данные работы в состояние прогона после каждого шага

Движок SHALL перечитывать `jobs/<работа>/data.json` после каждого шага работы и класть содержимое в поле `data` записи работы в `status.json`.

Подпроцесс `stepcast data` MUST NOT писать `status.json` сам: файлом владеет
движок и переписывает его на каждом событии журнала, а конкурентная запись
двух процессов в один файл была бы гонкой.

Складывание MUST происходить и после переиспользованного шага, а не только
после исполненного.

Поле `data` MUST быть необязательным: журналы прежней формы и работы, ничего
не публиковавшие, его не несут.

#### Scenario: Данные видны до конца работы

- **WHEN** первый шаг работы опубликовал `title`, а второй ещё идёт
- **THEN** запись работы в `status.json` уже содержит `data.title`

#### Scenario: Работа ничего не публиковала

- **WHEN** ни один шаг работы данных не публиковал
- **THEN** запись работы поля `data` не несёт

### Requirement: Возобновление переносит данные переиспользуемой работы

Движок SHALL переносить `data.json` работы из исходного прогона в новый, когда хотя бы один шаг этой работы переиспользуется.

Без переноса потребитель `${jobs.<работа>.data.<ключ>}` ломался бы на пустоте
именно при возобновлении: новый прогон заводит свой каталог, а
переиспользованный шаг не исполняется и ничего не пишет. Это то же правило,
которое уже действует для выхода работы.

Работа, переисполняемая с начала, переноса MUST NOT получать: она обязана
начать с чистого листа. Уже записанное в новом прогоне MUST NOT затираться.

Неудача переноса MUST оставаться записью внутреннего учёта и MUST NOT менять
статус работы.

#### Scenario: Работа переиспользована целиком

- **WHEN** прогон возобновлён с работы ниже по графу, и все шаги работы выше переиспользованы
- **THEN** её данные присутствуют в новом прогоне и доступны подстановкой

#### Scenario: Работа переисполняется с начала

- **WHEN** возобновление названо `--from` этой самой работой
- **THEN** данные исходного прогона не переносятся
