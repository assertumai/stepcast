## ADDED Requirements

### Requirement: Вход и выход шага script — файлы контракта

Шаг `script` SHALL получать вход файлом `input.json` в своём каталоге шага и отдавать выход файлом `output.json` там же; пути обоих файлов SHALL передаваться процессу переменными `STEPCAST_INPUT` и `STEPCAST_OUTPUT`.

Файл входа MUST записывать движок до первой попытки шага: объявленный `input`
— его раскрытым значением, необъявленный — пустым отображением. Файл входа
MUST существовать у всякого шага `script`, чтобы читателю не требовалась
проверка его наличия.

Оба файла MUST лежать в каталоге шага директории прогона, а не в рабочей
директории работы: попав в рабочее дерево, они вышли бы за границы
`changed_only` и изменили бы `diff.patch` шага. Работа с циклом `until` MUST
получать свою пару файлов на каждой итерации — по каталогу шага итерации.

Файл выхода MUST сниматься движком перед каждой попыткой: выход, записанный
прошлой попыткой, MUST NOT доживать до следующей и выдаваться за её результат.
Снятого файла для этого мало — значение, прочитанное на прошлой попытке, MUST
сниматься вместе с ним: попытка, файла не записавшая, MUST оставлять шаг без
структурированного выхода, чем бы ни кончились прошлые. Прочитанный файл MUST
оставаться на диске ровно таким, каким его записал скрипт: движок его не
переписывает.

`stdout` шага `script` MUST оставаться логом и MUST NOT разбираться как
структурированный выход ни при каких объявлениях шага. Публикация данных
работы MUST оставаться прежней — командой `stepcast data` из каталога,
названного `STEPCAST_JOB_DIR`.

#### Scenario: Вход доезжает файлом

- **WHEN** шаг объявляет `input: { slug: bug-42 }`
- **THEN** файл по пути из `STEPCAST_INPUT` содержит `{"slug": "bug-42"}`, и скрипту достаточно прочитать его

#### Scenario: Вход не объявлен

- **WHEN** шаг `script` не объявляет `input`
- **THEN** файл по пути из `STEPCAST_INPUT` существует и содержит пустое отображение

#### Scenario: Выход доезжает файлом

- **WHEN** скрипт записал JSON-документ по пути из `STEPCAST_OUTPUT` и завершился успехом
- **THEN** этот документ становится структурированным выходом шага, а файл `output.json` в каталоге шага содержит записанные скриптом байты

#### Scenario: Лог не мешает результату

- **WHEN** скрипт печатает в `stdout` ход своей работы и отдельно записывает файл выхода
- **THEN** шаг проходит, а напечатанное попадает только в `stdout.log`

#### Scenario: Выход прошлой попытки не выдаётся за нынешний

- **WHEN** первая попытка записала файл выхода и провалила `expect`, а вторая упала до записи
- **THEN** структурированного выхода у шага нет, и выход первой попытки в него не попадает

#### Scenario: Успешная попытка без выхода

- **WHEN** первая попытка записала файл выхода и провалила `expect`, а вторая прошла, ничего не записав
- **THEN** шаг успешен и структурированного выхода не даёт: работа не публикует значение первой попытки

#### Scenario: Файлы контракта не меняют рабочее дерево

- **WHEN** шаг `script` объявляет `expect: [{ changed_only: ['src/**'] }]` и ничего не правит в дереве
- **THEN** предикат проходит, а файлы входа и выхода на него не влияют

### Requirement: Объявленный выход шага script проверяется движком

Движок SHALL читать файл выхода шага `script` после завершения процесса попытки, разбирать его как один JSON-документ и, когда шаг объявил `output_schema`, проверять разобранное значение этой схемой.

Проверка MUST выполняться движком, а не раннером и не обёрткой: она одинакова
для скрипта на любом языке. Каждый из трёх промахов MUST давать отказ попытки
с причиной, называющей шаг и существо промаха, и MUST подчиняться обычным
правилам повторных попыток:

- файл записан, но не разбирается как JSON;
- объявлен `output_schema`, а файла нет;
- разобранное значение не соответствует объявленной схеме.

Файл, записанный шагом без объявленного `output_schema`, MUST становиться
структурированным выходом шага без проверки — но неразбираемым он MUST NOT
оставаться незамеченным.

Промах контракта MUST NOT отменять объявленных шагом предикатов: причиной
попытки MUST становиться первый из них, не прошедший, а промах контракта —
дописываться последним. Иначе у скрипта, упавшего ненулевым кодом и потому не
записавшего файл, журнал называл бы следствие вместо причины.

#### Scenario: Схема соблюдена

- **WHEN** шаг объявляет `output_schema`, а записанный файл ей соответствует
- **THEN** шаг проходит, а разобранное значение становится его структурированным выходом

#### Scenario: Файл не разбирается

- **WHEN** скрипт записал в файл выхода не JSON
- **THEN** попытка отказывает с причиной, называющей шаг и неразбираемый файл

#### Scenario: Обещанного выхода нет

- **WHEN** шаг объявляет `output_schema`, но скрипт файла не записал
- **THEN** попытка отказывает с причиной, называющей шаг и отсутствующий файл

#### Scenario: Значение не по схеме

- **WHEN** записанный файл разбирается, но не соответствует объявленной схеме
- **THEN** попытка отказывает с причиной, несущей замечания валидатора

#### Scenario: Упавший скрипт назван упавшим

- **WHEN** шаг объявляет `output_schema` и `expect: [{ exit_code: 0 }]`, а скрипт упал кодом 3, не записав файла
- **THEN** причиной попытки становится непройденный `exit_code`, а не отсутствие файла выхода

#### Scenario: Выход без объявленной схемы

- **WHEN** шаг без `output_schema` записал разбираемый JSON-документ
- **THEN** документ становится структурированным выходом шага

### Requirement: Обёртка раннера зовёт точку входа модуля

Раннер SHALL исполнять скрипт через объявленную у него обёртку, когда запись таблицы раннеров её называет: обёртка вставляется в argv между командой раннера и путём скрипта.

Обёртка, поставляемая пакетом для раннеров `node` и `node-ts`, MUST:

- подставлять на место собственного пути путь скрипта в `process.argv`, чтобы
  скрипт видел свои аргументы там же, где увидел бы их без обёртки;
- импортировать модуль — чем исполнять его тело; модуль без default export
  MUST исполняться как обычный скрипт, и большего с ним происходить MUST NOT;
- найдя default export-функцию, вызывать её входом шага, дожидаться результата
  и записывать возвращённое значение, отличное от `undefined`, в файл выхода;
- завершаться ненулевым кодом с сообщением в `stderr`, когда модуль или
  вызванная функция бросили ошибку.

Что считается объявленной точкой входа, MUST решаться по формату модуля — тем
же правилом, каким формат выбирает сам Node: расширение, а для `.js` и `.ts` —
поле `type` ближайшего `package.json`.

- в модуле ESM точка входа — объявленный default export; не являющийся
  функцией, он MUST давать отказ с названной причиной: модуль объявил точку
  входа, которую невозможно позвать;
- в модуле CommonJS точкой входа MUST считаться только `module.exports`,
  оказавшийся функцией. Всё прочее содержимое `module.exports` — пустой объект
  скрипта, ничего не экспортировавшего, в том числе — MUST исполняться как
  обычный скрипт и отказа давать MUST NOT: в этом формате «ничего не
  экспортировал» и «объявил точку входа объектом» неразличимы, а обычных
  скриптов на `.js` и `.cjs` несравнимо больше.

Модуль, одновременно записавший файл выхода сам и вернувший значение, MUST
оставлять в файле возвращённое значение — запись обёртки последняя.

#### Scenario: Модуль с точкой входа

- **WHEN** файл `.stepcast/scripts/pick.mjs` экспортирует default-функцию, возвращающую объект
- **THEN** функция вызывается входом шага, а возвращённый объект оказывается в файле выхода

#### Scenario: Модуль без точки входа

- **WHEN** у файла нет default export, а его тело печатает лог и записывает файл выхода само
- **THEN** тело исполняется, а файл выхода остаётся таким, каким его записал модуль

#### Scenario: Обычный скрипт CommonJS

- **WHEN** файл `.cjs` — или `.js` там, где нет `"type": "module"`, — ничего не экспортирует, а его тело печатает лог и записывает файл выхода само
- **THEN** тело исполняется, шаг проходит, и пустой `module.exports` за объявленную точку входа принят не будет

#### Scenario: Точка входа в CommonJS

- **WHEN** файл `.cjs` присваивает `module.exports` функцию
- **THEN** она вызывается входом шага наравне с default export модуля ESM, а возвращённое значение оказывается в файле выхода

#### Scenario: Точка входа объявлена не функцией

- **WHEN** модуль ESM экспортирует по умолчанию объект
- **THEN** процесс завершается ненулевым кодом, а `stderr` называет причиной default export, который невозможно позвать

#### Scenario: Свои аргументы на месте

- **WHEN** шаг объявляет `args: ['--dry-run']`, а модуль читает `process.argv.slice(2)`
- **THEN** модуль видит `['--dry-run']`, а не путь обёртки

#### Scenario: Асинхронная точка входа

- **WHEN** default-функция возвращает промис
- **THEN** обёртка дожидается его и пишет разрешённое значение

#### Scenario: Ошибка внутри модуля

- **WHEN** default-функция бросает исключение
- **THEN** процесс завершается ненулевым кодом, а сообщение об ошибке попадает в `stderr.log`

#### Scenario: Обёртка снята у переопределённого раннера

- **WHEN** конфигурация объявляет у раннера `wrapper: none`
- **THEN** argv шага не содержит обёртки, а файл исполняется раннером напрямую

## MODIFIED Requirements

### Requirement: Сборка окружения шага

Система SHALL формировать окружение шага, наследуя окружение своего процесса
целиком и накладывая поверх, в порядке возрастания приоритета: `env_files`,
`env` пайплайна, `env` на месте подключения работы, `env` в файле работы, `env`
шага. Затем MUST добавляться переменные `STEPCAST_*`, не подлежащие
переопределению, и последним MUST применяться фильтр `env_deny`.

Шаг `script` MUST дополнительно получать `STEPCAST_INPUT` и `STEPCAST_OUTPUT` —
пути файлов входа и выхода в своём каталоге шага. Остальным видам шага эти две
переменные MUST NOT инжектироваться: у шага `run` вход — argv и выход —
`stdout`, у агентского шага оба канала свои.

#### Scenario: Перекрытие по уровням

- **WHEN** пайплайн задаёт `NODE_ENV: test`, а шаг `NODE_ENV: development`
- **THEN** процесс шага получает `NODE_ENV=development`

#### Scenario: Запрет применяется последним

- **WHEN** переменная присутствует в окружении процесса и попадает под действующий шаблон `env_deny`
- **THEN** она отсутствует в окружении шага
- **AND** в журнал событий пишется запись с именем переменной и сработавшим шаблоном

#### Scenario: Инжектируемые переменные

- **WHEN** шаг исполняется
- **THEN** его окружение содержит `STEPCAST_RUN_ID`, `STEPCAST_RUN_DIR`, `STEPCAST_JOB`, `STEPCAST_JOB_DIR`, `STEPCAST_STEP`, `STEPCAST_STEP_DIR`, `STEPCAST_ATTEMPT`, `STEPCAST_WORKSPACE`, `STEPCAST_ARTIFACTS`

#### Scenario: Инжектируемые переменные не переопределяются

- **WHEN** шаг объявляет `env` с ключом `STEPCAST_JOB`
- **THEN** действующим остаётся значение, подставленное системой

#### Scenario: Переменные контракта у шага script

- **WHEN** исполняется шаг `script`
- **THEN** его окружение дополнительно содержит `STEPCAST_INPUT` и `STEPCAST_OUTPUT`, указывающие в каталог этого шага

#### Scenario: Переменные контракта у прочих шагов

- **WHEN** исполняется шаг `run` либо агентский шаг
- **THEN** `STEPCAST_INPUT` и `STEPCAST_OUTPUT` в его окружении отсутствуют

#### Scenario: Контракт виден дочернему процессу

- **WHEN** скрипт запускает свой дочерний процесс, не меняя окружения
- **THEN** тот видит те же `STEPCAST_INPUT`, `STEPCAST_OUTPUT` и `STEPCAST_JOB_DIR`
