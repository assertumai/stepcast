## ADDED Requirements

### Requirement: Перенос накопленного в хранилище годен к вызову перед отбором

Перенос прогонов, лежащих на диске корня, в хранилище расхода SHALL быть доступен в виде, не ограниченном одним вызовом за время жизни процесса, и MUST допускать сужение обхода до одного проекта либо до явного списка прогонов. Защита от повторного переноса MUST оставаться у того входа, который зовут при открытии хранилища, и MUST NOT распространяться на догон, который зовут перед отбором. Догон MUST дописывать записи только тех прогонов, каталоги которых лежат на диске и чья сводка расхода уже подведена, MUST NOT переписывать и MUST NOT удалять ни одной уже существующей строки хранилища и MUST NOT изменять ни одного каталога прогона. Повторный догон при неизменном диске MUST не дописывать ничего. Отказ дозаписи — корень только для чтения, кончилось место, чужой файл хранилища — MUST вырождать догон в отсутствие свежих записей и MUST NOT доходить до вызывающего исключением: догон пополняет производное, а зовут его пути, которые сами по себе только читают.

#### Scenario: Прогон появился после первого переноса

- **WHEN** перенос уже выполнялся в этом процессе, а затем на диске появился прогон со сводкой расхода и без записи в хранилище
- **THEN** догон дописывает его запись, и отбор по хранилищу его называет

#### Scenario: Догон сужен проектом

- **WHEN** догон запрошен с указанием проекта, а прогоны без записи есть в двух проектах корня
- **THEN** дописаны записи прогонов названного проекта, и ни одной записи прогона чужого проекта не появилось

#### Scenario: Догон ничего не портит

- **WHEN** догон выполняется на хранилище, где уже есть записи
- **THEN** прежние строки остались как были, ни одна не удалена и не переписана, а каталоги прогонов не изменились

#### Scenario: Повторный догон впустую

- **WHEN** догон выполнен дважды подряд, а диск между вызовами не менялся
- **THEN** второй вызов не дописал ни одной строки

#### Scenario: Догон сужен списком прогонов

- **WHEN** догон запрошен с явным списком прогонов, а в корне есть и другие прогоны без записи
- **THEN** дописаны записи названных прогонов, и ни одного из остальных догон не обходил

#### Scenario: Дозапись отказала

- **WHEN** догон выполняется на корне, в который писать нельзя, а прогон без записи на диске есть
- **THEN** догон завершается без исключения, отбор идёт дальше и отвечает по тому, что в хранилище уже было

### Requirement: Отбор по признаку называет прогоны, которых не смог проверить

Отбор кандидатов на уборку по признакам SHALL сообщать вместе с отобранными число прогонов области отбора, статус которых не удалось прочитать ни из состояния, ни из манифеста и которые в отбор поэтому не попали. Такой прогон MUST NOT считаться ни оборванным, ни отказавшим: признак «оборванные» утверждает, что состояние осталось `running`, а процесс мёртв, и прогон, о котором ничего не известно, ему не отвечает. Такой прогон MUST по-прежнему попадать в отбор по сроку, возраст которого считается по времени его каталога, и, попав в него, MUST NOT входить в число непроверенных: он уже назван списком, и счёт его вторым разом прибавлял бы к итогу отбора то, что в итоге уже посчитано. Число непроверенных MUST считаться по той же области, что и отбор: по одному проекту, если проект назван, и по всем проектам корня, если не назван.

#### Scenario: Прогон с испорченным состоянием при отборе по признаку

- **WHEN** запрошен отбор по признакам «оборванные» и «отказавшие», а в корне лежит прогон, чьи `status.json` и `run.json` не проходят разбор
- **THEN** он не назван отобранным, и отбор сообщает, что один прогон проверить не удалось

#### Scenario: Тот же прогон при отборе по сроку

- **WHEN** запрошен отбор прогонов старше срока, которому отвечает время каталога этого прогона
- **THEN** он назван отобранным, и число непроверенных прогонов при этом нулевое

#### Scenario: Читаемые прогоны непроверенными не считаются

- **WHEN** запрошен отбор по признаку в корне, где все журналы читаются
- **THEN** число непроверенных прогонов нулевое
