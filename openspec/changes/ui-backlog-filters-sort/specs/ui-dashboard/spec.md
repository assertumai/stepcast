## ADDED Requirements

### Requirement: Пункт очереди назван своим плановым номером

Экран очереди SHALL показывать по каждому пункту его плановый номер — место пункта в файле очереди своего проекта, считая с единицы и по всем пунктам файла, включая завершённые и отказавшие. Номер MUST присваиваться до применения фильтров и выбора направления порядка и MUST NOT зависеть ни от того, что показано рядом, ни от места строки на экране. Пропуски в номерах при суженном списке MUST сохраняться, а не сжиматься в непрерывный счёт строк: между показанными пунктами в плане стоят другие, и экран MUST NOT это скрывать. Номер MUST относиться к очереди своего проекта: нумерация каждого проекта начинается заново.

#### Scenario: Номер совпадает с местом в файле

- **WHEN** у проекта в файле очереди семьдесят три пункта
- **THEN** экран показывает у первого пункта номер 1, а у последнего — 73

#### Scenario: Отбор не перенумеровывает пункты

- **WHEN** список сужен так, что показаны только пункты, стоящие в файле 58-м, 61-м и 73-м
- **THEN** экран показывает у них номера 58, 61 и 73, а не 1, 2 и 3

#### Scenario: Обратный порядок не перенумеровывает пункты

- **WHEN** выбран обратный плановый порядок
- **THEN** каждый пункт сохраняет свой номер, а меняется только порядок строк

#### Scenario: Нумерация не сквозная между проектами

- **WHEN** на экране показаны очереди двух проектов
- **THEN** нумерация второго проекта начинается с единицы, а не продолжает нумерацию первого

### Requirement: Список пунктов очереди сужается фильтрами по статусу и по проекту

Экран очереди SHALL фильтроваться по статусу пункта и по проекту, и фильтры MUST объединяться по «и»: пункт показан, только если отвечает каждому заполненному фильтру. Незаполненный фильтр MUST означать «все». Значениями фильтра статуса MUST быть все статусы формата очереди — `pending`, `in_progress`, `done`, `failed`, — независимо от того, есть ли пункты в каждом из них, и рядом с каждым значением MUST быть названо число отвечающих ему пунктов. Это число MUST считаться по пунктам, прошедшим остальные действующие фильтры, чтобы оно совпадало с числом строк, которые даст выбор. Значения фильтра проектов SHALL собираться из полученных очередей, а значение, выбранное пользователем, MUST оставаться выбранным, даже если ни одна очередь ему больше не отвечает, — список в этом случае MUST быть пуст, а не переключён на другое значение молча. Фильтрация MUST выполняться над уже полученной очередью и MUST NOT изменять её состав, приходящий живым потоком. Пока показанных пунктов меньше, чем пришло очередями, экран SHALL называть число показанных и общее их число; общее число MUST считаться по всем пришедшим очередям, включая отсечённые фильтром по проекту, потому что эта пара отвечает на вопрос «сколько очереди сейчас не видно», а фильтр по проекту прячет пункты наравне с фильтром по статусу. Пока вид отличается от умолчания хоть чем-нибудь — фильтром или одним лишь направлением порядка, — экран SHALL давать вернуться к умолчанию одним действием.

#### Scenario: Фильтры объединяются по «и»

- **WHEN** выбраны проект и статус `pending`
- **THEN** показаны только непройденные пункты этого проекта, а непройденные пункты других проектов не показаны

#### Scenario: Статус без единого пункта назван числом ноль

- **WHEN** ни один пункт очереди не отказал
- **THEN** значение `failed` присутствует в фильтре и названо числом ноль, а не отсутствует в перечне значений

#### Scenario: Число у статуса считается по выбранному проекту

- **WHEN** выбран проект, у которого два непройденных пункта, а у соседнего проекта их пять
- **THEN** рядом со значением `pending` названо два, то есть ровно столько строк, сколько даст его выбор

#### Scenario: Под фильтры не подошёл ни один пункт

- **WHEN** сочетание фильтров не отвечает ни одному пункту ни одной очереди
- **THEN** экран говорит, что под фильтры не подошёл ни один пункт, и предлагает вернуться к умолчанию

#### Scenario: Выбранный проект ушёл из очереди

- **WHEN** выбран проект, чей файл очереди перестал приходить
- **THEN** фильтр остаётся на выбранном значении, а список честно пуст

#### Scenario: Новый пункт под действующим фильтром

- **WHEN** при включённом фильтре живым потоком приходит очередь с дописанным пунктом
- **THEN** пункт показан, если отвечает фильтрам, и не показан, если не отвечает, — без перезагрузки страницы

#### Scenario: Сужение названо числом

- **WHEN** список сужен фильтром
- **THEN** экран называет, сколько пунктов показано из скольких

#### Scenario: Общее число считается по всем пришедшим очередям

- **WHEN** выбран проект, у которого два пункта, а всего в пришедших очередях их четыре
- **THEN** экран называет «показано 2 из 4», то есть считает и пункты очереди, отсечённой выбором проекта

#### Scenario: Один лишь обратный порядок не сужает список

- **WHEN** фильтры не выбраны, а выбрано только обратное направление порядка
- **THEN** числа «показано N из M» нет — показаны все пришедшие пункты, — а возврат к умолчанию есть

### Requirement: Направление планового порядка выбирается пользователем

Экран очереди SHALL упорядочивать пункты по плановому порядку в обоих направлениях по выбору пользователя, и умолчанием MUST быть порядок файла — тот, в котором петля берёт первый свободный пункт сверху. Плановый порядок MUST быть единственной величиной, по которой список упорядочивается: ни статус, ни заголовок, ни группа, ни момент взятия MUST NOT становиться порядком списка, потому что приоритет у очереди один и второго порядка над ним не существует. Порядок MUST применяться внутри очереди каждого проекта, а не поперёк проектов: плановый номер определён только внутри своего файла. Возврат к умолчанию MUST снимать выбранное направление вместе с фильтрами одним действием.

#### Scenario: Умолчание — порядок файла

- **WHEN** экран открыт и порядок не выбирался
- **THEN** пункты каждого проекта идут в том же порядке, в каком стоят в его файле очереди

#### Scenario: Обратный порядок

- **WHEN** выбрано обратное направление планового порядка
- **THEN** последний пункт файла показан первым, а состав списка остаётся прежним

#### Scenario: Порядок не смешивает проекты

- **WHEN** выбрано обратное направление, и на экране показаны очереди двух проектов
- **THEN** каждый проект остаётся отдельным разделом со своим перевёрнутым порядком, а пункты двух проектов не перемешиваются между собой

#### Scenario: Возврат к умолчанию

- **WHEN** выбраны фильтр и обратное направление, и нажат возврат к умолчанию
- **THEN** сняты и фильтры, и направление: список снова показывает все пункты в порядке файла

### Requirement: Выбранный фильтр и порядок переживают смену проекта и обновление очереди

Выбранные фильтр по статусу и направление порядка SHALL сохраняться при смене выбранного проекта и при каждом обновлении очереди живым потоком, потому что это линза экрана, а не свойство показанных данных. Смена одного фильтра MUST NOT сбрасывать другой. Выбор MUST жить состоянием открытого экрана и MUST NOT записываться в адрес страницы: адреса витрины разбираются по пути, без строки запроса. Следствие MUST быть названо экраном честно — перезагрузка возвращает вид к умолчанию, и потому, пока вид сужен или порядок обратен, экран обязан это показывать.

#### Scenario: Смена проекта сохраняет выбранный статус

- **WHEN** выбран статус `pending` и затем выбран другой проект
- **THEN** статус остаётся выбранным, и показаны непройденные пункты нового проекта

#### Scenario: Смена проекта сохраняет направление порядка

- **WHEN** выбрано обратное направление и затем выбран другой проект
- **THEN** очередь нового проекта показана в обратном порядке

#### Scenario: Обновление живым потоком не сбрасывает выбранного

- **WHEN** при выбранных фильтре и обратном порядке файл очереди правится, и живой поток присылает новую очередь
- **THEN** экран показывает обновлённую очередь под теми же фильтром и порядком, не возвращаясь к умолчанию

### Requirement: Сломанная очередь не скрывается фильтром по статусу

Раздел проекта, чья очередь не разобралась, SHALL показываться при любом выбранном статусе, потому что пунктов у такого проекта нет вовсе, и скрытие выдало бы сломанную очередь за очередь без пунктов этого статуса. Фильтр по проекту MUST скрывать такой раздел наравне с прочими чужими разделами: там скрытие отвечает прямому выбору пользователя. Раздел проекта, чей файл очереди есть, но пуст, MUST оставаться видимым в умолчании статуса и MUST скрываться при суженном статусе, потому что сообщение о пустой очереди верно про файл, а не про отбор. Тем же правилом MUST скрываться раздел, ни один пункт которого не прошёл суженный фильтр: раздел из одного заголовка проекта не сообщает ничего, кроме того, что отбор состоялся, а повторённый в каждом непопавшем разделе — превращает суженный экран в шум; отличие такого раздела от сломанного в том, что про него отбор знает ответ, а про сломанный — нет.

#### Scenario: Сломанная очередь видна при выбранном статусе

- **WHEN** очередь одного проекта не разбирается, и выбран статус `pending`
- **THEN** раздел этого проекта по-прежнему показывает объяснение отказа, а не исчезает с экрана

#### Scenario: Отбор по проекту скрывает чужой сломанный раздел

- **WHEN** очередь одного проекта не разбирается, и выбран другой проект
- **THEN** раздел со сломанной очередью не показан

#### Scenario: Пустая очередь под суженным статусом

- **WHEN** у проекта есть файл очереди без единого пункта, и выбран статус `pending`
- **THEN** раздел этого проекта не показан, а в умолчании статуса он по-прежнему говорит, что очередь пуста

#### Scenario: Раздел, где под фильтр не подошёл ни один пункт

- **WHEN** показаны очереди двух проектов, и выбран статус, которому отвечают пункты только одного из них
- **THEN** показан раздел этого проекта, а раздел второго не показан вовсе — не заголовком с пустой таблицей
