## ADDED Requirements

### Requirement: Очередь предложенных правок — каталог проекта с записью-файлом

Очередь SHALL храниться в каталоге `<проект>/.stepcast/proposals/` по файлу `<id>.json` на предложение, где `<id>` собирается из момента постановки и цели, свёрнутой в безопасный сегмент, так что сортировка имён и есть порядок очереди. Запись MUST нести цель, действие (`create` либо `update`), содержимое файла целиком, причину, происхождение (прогон, работа, шаг — когда предложение сделано внутри прогона), отпечаток цели на момент постановки и состояние (`pending`, `accepted`, `rejected`) с моментом решения. Запись MUST создаваться атомарной заменой и MUST не переписывать уже существующую запись очереди: два предложения одной цели, поставленные в пределах точности штампа момента, MUST остаться двумя записями. Содержимое длиннее 256 КиБ MUST быть отказом постановки с названным пределом, а не записью в очередь. Отсутствие каталога очереди MUST быть обычным состоянием проекта, а не отказом.

#### Scenario: Предложение появляется файлом очереди

- **WHEN** пайплайн предложил правку виджета `clock`
- **THEN** в `<проект>/.stepcast/proposals/` появляется одна запись с состоянием `pending`, целью `.stepcast/widgets/clock.tsx`, предложенным содержимым, причиной и названным прогоном-источником

#### Scenario: Слишком большое содержимое не встаёт в очередь

- **WHEN** предлагается содержимое больше предела записи
- **THEN** постановка отказывает, называя предел, и ни одного файла в каталоге очереди не появляется

#### Scenario: Очереди ещё нет

- **WHEN** проект не получал ни одного предложения
- **THEN** каталога очереди нет, и чтение очереди даёт пустой перечень, а не отказ

#### Scenario: Два предложения одной цели подряд

- **WHEN** одна цель получила два предложения в пределах одной секунды
- **THEN** в очереди две открытые записи, и ни одна не переписана другой

### Requirement: Единственный писатель очереди — команда `stepcast propose`

Постановка предложения SHALL быть возможна только командой `stepcast propose <цель>`, которая берёт содержимое из файла, названного `--from`, либо со стандартного ввода, принимает необязательную причину (`--reason`) и записывает происхождение из окружения шага. Команда MUST быть вызываема из командного шага пайплайна через `$STEPCAST_BIN` и из агентского шага, которому это право дано объявленными правами шага. Команда MUST отказывать с внятной причиной, когда содержимое не дано ни файлом, ни вводом, и когда названный файл не читается. Движок MUST не принимать в очередь записи, созданные мимо команды: файл записи неизвестной формы MUST быть показан как негодная запись с именем файла, а не молча истолкован.

#### Scenario: Постановка из шага пайплайна

- **WHEN** командный шаг зовёт `"$STEPCAST_BIN" propose .stepcast/widgets/clock.tsx --from "$STEPCAST_SCRATCH/clock.tsx" --reason "имя ушло из таблицы"`
- **THEN** в очередь встаёт запись с этой целью, содержимым черновика, причиной и происхождением — прогоном, работой и шагом

#### Scenario: Содержимое со стандартного ввода

- **WHEN** команда вызвана без `--from`, а содержимое подано на стандартный ввод
- **THEN** в очередь встаёт запись с этим содержимым

#### Scenario: Содержимого нет вовсе

- **WHEN** команда вызвана без `--from` и без ввода
- **THEN** она отказывает с названной причиной, и очередь не меняется

#### Scenario: Негодный файл в каталоге очереди

- **WHEN** в каталоге очереди лежит файл, не разбираемый как запись
- **THEN** он показан негодной записью с именем файла, а остальные записи очереди читаются как обычно

### Requirement: Целью предложения вправе быть только файл кабинета проекта

Целью предложения SHALL быть ровно один из трёх видов файла проекта: `.stepcast/widgets/<id>.tsx` непосредственно в каталоге виджетов, `.stepcast/dashboards/<id>.yml` непосредственно в каталоге дашбордов и любой файл внутри каталога плагина `.stepcast/plugins/<id>/` на любой глубине. Каждый сегмент цели MUST проверяться тем же предикатом безопасного сегмента, каким проверяются сегменты адресов витрины, а итоговый путь MUST приводиться к реальному и оставаться внутри каталога кабинета: шаг вверх по дереву и выход по символической ссылке MUST быть отказом. Любая иная цель — файл конфигурации, файл вне `.stepcast`, вложенный каталог виджетов, чужое расширение — MUST быть отказом постановки с названной причиной.

#### Scenario: Три законные цели

- **WHEN** предлагаются `.stepcast/widgets/clock.tsx`, `.stepcast/dashboards/release.yml` и `.stepcast/plugins/board/plugin.json`
- **THEN** все три встают в очередь

#### Scenario: Цель за пределами кабинета

- **WHEN** целью названы `.stepcast/config.yml`, `src/index.ts` или `.stepcast/widgets/../../secret`
- **THEN** постановка отказывает, называя причину, и очередь не меняется

#### Scenario: Выход по символической ссылке

- **WHEN** каталог виджетов содержит символическую ссылку наружу, и цель ведёт через неё
- **THEN** постановка отказывает, а файл за пределами кабинета не затрагивается

#### Scenario: Чужое расширение и вложенный каталог

- **WHEN** целью названы `.stepcast/widgets/clock.js` или `.stepcast/widgets/sub/clock.tsx`
- **THEN** постановка отказывает: читателем кабинета такой файл виджетом не считается

### Requirement: Очередь принадлежит проекту прогона, а не рабочей директории шага

Проект, в чью очередь встаёт предложение, SHALL определяться по прогону, внутри которого команда вызвана, а не по рабочей директории шага. Команда, вызванная внутри шага, MUST брать проект из каталога прогона и его указателя проектов; вне прогона MUST браться проект каталога запуска. Предложение из шага, работающего в изолированном дереве (`worktree`, `copy`), MUST оказаться в очереди самого проекта, а не временного дерева, которое снимет уборка прогона.

#### Scenario: Шаг в изолированном дереве

- **WHEN** шаг работы с `workspace: worktree` ставит предложение
- **THEN** запись появляется в `<проект>/.stepcast/proposals/`, а во временном дереве работы каталога очереди не появляется вовсе

#### Scenario: Вызов вне прогона

- **WHEN** человек зовёт команду из корня проекта руками
- **THEN** запись встаёт в очередь этого проекта, а поля происхождения остаются пустыми

### Requirement: Режим доставки правки решает, встаёт ли она в очередь

Команда постановки SHALL действовать по режиму, объявленному проектом: при `queue` она MUST записать предложение и не тронуть цель, при `direct` — записать цель немедленно, теми же проверками пути и той же атомарной заменой, не создавая записи очереди. Режим `direct` MUST печатать, какой файл записан. Умолчанием MUST быть `queue`.

#### Scenario: Очередь по умолчанию

- **WHEN** проект режима не объявлял и пайплайн предложил правку виджета
- **THEN** файл виджета на диске не меняется, а в очереди появляется открытая запись

#### Scenario: Прямая запись

- **WHEN** проект объявил `project.proposals: direct` и пайплайн предложил ту же правку
- **THEN** файл виджета записан сразу, команда называет записанный файл, и очередь остаётся пустой

### Requirement: Витрина показывает очередь дифом и решает запись двумя кнопками

Витрина SHALL показывать очередь предложений всех проектов экраном `screen-proposals` по адресу `/proposals`: цель, причина, прогон-источник, момент и диф между содержимым цели на диске и предложенным содержимым. Маршрут чтения `GET /api/proposals` MUST отдавать записи вместе с текущим содержимым цели, чтобы диф строился страницей. Маршрут `POST /api/proposals` MUST принимать решение по одной названной записи — принять либо отклонить. Открытые записи MUST показываться развёрнуто, решённые — свёрнуто; записи одного прогона MUST быть сгруппированы, но решаться по одной. Действующий режим доставки MUST быть виден на экране: прямая запись не вправе быть тихим состоянием. Отказ решения MUST показываться на месте своей записи, не гася остальные. Неразбираемая конфигурация одного проекта MUST не гасить очереди остальных: причина MUST показываться названной, а режим такого проекта MUST считаться умолчанием.

#### Scenario: Открытая запись показана дифом

- **WHEN** в очереди есть предложение правки существующего виджета
- **THEN** экран показывает построчный диф файла на диске и предложенного содержимого, причину, прогон-источник и кнопки принять и отклонить

#### Scenario: Предложение нового файла

- **WHEN** предложен файл, которого в кабинете ещё нет
- **THEN** диф показывает создание файла целиком, а не отказ чтения отсутствующей цели

#### Scenario: Отказ решения локален

- **WHEN** принятие одной записи отказало
- **THEN** причина показана на месте этой записи, а остальные записи очереди остаются доступными для решения

#### Scenario: Сломанная конфигурация проекта

- **WHEN** конфигурация одного проекта не разбирается, а в его очереди есть записи
- **THEN** маршрут чтения отдаёт записи этого и остальных проектов, называет причину отказа конфигурации и считает режим доставки умолчанием

### Requirement: Принятие записывает файл кабинета и вызывает обычную перезагрузку

Принятие записи SHALL записывать цель атомарной заменой, создавая недостающие каталоги внутри кабинета, переводить запись в состояние `accepted` с моментом решения и будить наблюдателя демона. Дальнейшее применение MUST идти обычным путём живой правки: часть отпечатка наблюдателя сдвигается, поток событий несёт новый состав и версию, и страница переимпортирует сдвинувшийся модуль без перезапуска демона. Отклонение записи MUST переводить её в `rejected` с моментом решения и MUST не трогать ни цели, ни иных файлов проекта.

#### Scenario: Принятая правка виджета видна в открытой витрине

- **WHEN** человек принял предложение правки виджета
- **THEN** файл виджета записан, версия виджета в потоке событий изменилась, и открытая страница показывает новый виджет без перезагрузки

#### Scenario: Принятие создаёт недостающий каталог

- **WHEN** принято предложение дашборда, а каталога дашбордов в проекте ещё нет
- **THEN** каталог создаётся, файл записан, и дашборд становится действующим

#### Scenario: Отклонение ничего не пишет

- **WHEN** человек отклонил предложение
- **THEN** цель на диске не изменилась, а запись помечена отклонённой с моментом решения

### Requirement: Расхождение отпечатка цели отменяет принятие

Принятие SHALL сверять отпечаток цели с отпечатком, записанным при постановке, и при расхождении MUST отказывать с названной причиной, оставляя запись открытой и не трогая файл. Предложение создания файла, который к моменту решения уже появился, MUST отказывать тем же правилом. Слияния предложенного содержимого с изменившимся файлом MUST не происходить ни при каких условиях.

#### Scenario: Цель правили руками

- **WHEN** файл виджета изменён после постановки предложения, и запись принимают
- **THEN** принятие отказывает, называя, что файл изменился с момента предложения, запись остаётся открытой, а файл — нетронутым

#### Scenario: Файл появился до принятия

- **WHEN** предложено создание файла, а к моменту принятия такой файл уже создан руками
- **THEN** принятие отказывает той же причиной, а созданный руками файл не перезаписывается

### Requirement: Решённая запись остаётся следом, а отклонённое не предлагается заново

Решённая запись SHALL оставаться в каталоге очереди со своим состоянием и моментом решения, а не стираться. Постановка предложения с той же целью и тем же содержимым, что у уже отклонённой записи, MUST быть отказом с названной причиной — сравнение MUST идти по содержимому, а не по тексту причины. Уборка решённых записей MUST оставаться делом человека: движок MUST не стирать их ни по сроку, ни по числу.

#### Scenario: Повторная миграция не просится дважды

- **WHEN** пайплайн миграции запущен второй раз и предлагает виджету ровно то, от чего человек отказался
- **THEN** постановка отказывает, называя отклонённую запись, и очередь новых открытых записей не получает

#### Scenario: Исправленное предложение принимается

- **WHEN** повторное предложение той же цели несёт другое содержимое
- **THEN** оно встаёт в очередь открытой записью

#### Scenario: След решения сохраняется

- **WHEN** запись принята или отклонена
- **THEN** её файл остаётся в каталоге очереди с состоянием и моментом решения

### Requirement: Состав очереди идёт потоком событий

Наблюдатель демона SHALL держать каталог очереди своей частью отпечатка, а поток `GET /api/events` MUST нести состав очереди отдельным событием по тому же правилу, что `backlog`, `widgets` и `dashboards`: только когда состав отличается от отправленного прежде. Событие MUST нести только состав очереди: содержимое записей в поток MUST не идти — его отдаёт маршрут чтения, который экран перечитывает по событию. Предложение, записанное идущим прогоном, MUST появляться в открытой витрине без перезагрузки страницы.

#### Scenario: Запись от идущего прогона появляется сама

- **WHEN** прогон ставит предложение, пока витрина открыта
- **THEN** поток несёт новый состав очереди, и запись появляется на экране без перезагрузки

#### Scenario: Неизменившаяся очередь события не порождает

- **WHEN** такт наблюдателя не нашёл изменений в каталоге очереди
- **THEN** события состава очереди в потоке не появляется

#### Scenario: Поток не несёт содержимого записей

- **WHEN** поток событий отдал состав очереди с открытой записью
- **THEN** запись в событии названа целью и состоянием, а содержимого файла в ней нет

### Requirement: Очередь не делает дерево проекта грязным

`stepcast init` SHALL вносить каталог очереди в `.gitignore` проекта, а документация MUST называть ту же строку для проекта, заведённого раньше. Каталог очереди MUST оставаться игнорируемым для проверки чистоты дерева и для предиката границ правок, чтобы первое же предложение не останавливало пайплайн, требующий чистого дерева.

#### Scenario: Заведённый проект игнорирует очередь

- **WHEN** проект заведён командой `stepcast init`
- **THEN** `.gitignore` проекта несёт строку каталога очереди

#### Scenario: Предложение не делает дерево грязным

- **WHEN** в очередь встала запись, а затем проверяется чистота дерева
- **THEN** дерево считается чистым
