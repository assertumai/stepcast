## Why

Состав плагинов сегодня — **список, в который можно только дописать**.

Ключ `plugins` (`src/core/config/schema.ts:369`) — массив строк-модулей;
между слоями списки **объединяются** (`UNION_LIST_KEYS`, `:403`), то есть
проектный слой вправе добавить строку к домашнему, но не вправе ни заменить
её, ни убрать. Встроенное недоступно и вовсе: бэкенд `claude` регистрируется
прямо в `createBuiltinKernel` (`src/core/plugins/builtin.ts:55`), конфигурацией
не назван, а плагин, объявивший бэкенд с тем же именем, получает отказ по
конфликту имён — «переопределение вклада не предусмотрено»
(`src/core/plugins/kernel.ts`). У строки нет и имени: `pluginDeclarations`
(`src/core/plugins/load.ts:51`) различает строки по спецификатору модуля, а
спецификатор — это путь, то есть сказать «заменить вот эту строку другим
модулем» нечем.

`cordis-kernel-daemon` сделал регистрацию обратимой: снятие области плагина
снимает его вклады и освобождает имена. Механизм замены есть — нет того, чем
её **объявляют**. Пока состав плагинов выражается плоским списком путей,
пользователь не может ни подменить встроенный вклад своим, ни отключить
чужой, ни поставить свой раньше соседа; а дальше по группе `ui-runtime` на это
опираются все: `builtin-pages-as-plugins` («отключение встроенного экрана
патчем»), `user-plugins-from-files` («плагин с ошибкой показан в `stepcast
plugins --dump`»), `plugin-introspection` («`stepcast plugins --dump` из
`config-patch-layers` печатает дерево»).

В deepseek-harness это решено деревом строк с идентификаторами и патчами
поверх него: слой заменяет строку по id целиком либо вставляет новую с
позицией, а `dsh --dump-config` печатает итог. Та же форма нужна здесь — с
тремя слоями, как у скиллов OpenClaw: встроенное описание пакета, домашний
каталог, проект.

## What Changes

- **Состав плагинов — дерево именованных строк.** Строка: `id` (слаг,
  уникальный в дереве), `use` (модуль — путь, пакет либо `stepcast:<имя>` для
  поставляемого пакетом) и `enabled`. Порядок строк дерева — порядок загрузки.
- **Дерево собирается тремя слоями снизу вверх:** встроенное описание пакета,
  домашний слой, проектный слой. Каждый слой — последовательность операций над
  деревом, накопленным предыдущими.
- **Патч слоя — файл `plugins.patch.yml`** (`~/.stepcast/plugins.patch.yml` и
  `.stepcast/plugins.patch.yml`, `kind: plugins-patch`). Строка патча с
  **известным id заменяет** одноимённую строку **целиком** — незаполненные поля
  не наследуются от заменяемой; строка с **новым id вставляется** на место,
  названное `before`/`after`, по умолчанию — в конец слоя.
- **Ключ `plugins` конфигурации остаётся сокращением** и не меняет ни
  синтаксиса, ни разрешения путей: каждая его строка — вставка в конец своего
  слоя, id такой строки — сам спецификатор модуля. Складывание списков между
  слоями (`UNION_LIST_KEYS`) при этом и есть «каждый слой дописывает своё».
- **Встроенное описание — строки того же формата.** Бэкенд `claude` становится
  строкой `backend-claude` встроенного слоя; заменённая пользователем строка
  встроенного слоя **не применяется вовсе**, поэтому конфликта имён у замены не
  возникает. Авторство вкладов встроенной строки остаётся «встроенный» — она
  применяется на области ядра, а не как плагин (иначе поменялись бы тексты
  отказов и раздел «Плагины» отчёта `stepcast config`).
- **Отключение — `enabled: false`, а не изъятие строки.** Отключённая строка
  остаётся в дереве видимой, её модуль не импортируется и вкладов не вносит.
- **Новая команда `stepcast plugins --dump`** печатает итоговое дерево: порядок,
  id, слой, давший строку (и файл, если слой файловый), модуль и состояние.
  Отказ загрузки одной строки эту команду не заслоняет: дерево печатается, а
  строка-виновница называется причиной (код возврата остаётся ошибкой
  конфигурации).
- **Правка патча действует без перезапуска демона.** Ключ кеша ядер
  (`declarationsEqual`, `src/ui/pipelines.ts:318`) сравнивает строки дерева, а
  не строки ключа `plugins`: правка патча расходится с закешированным, старое
  ядро снимается вместе со вкладами своих строк, новое поднимается.
- **Формат патча публикуется JSON Schema** `schema/plugins-patch.schema.json`
  из той же zod-схемы, что его и проверяет.
- **`docs/config.md` и `docs/plugins.md`** описывают слои, формат строки,
  формат патча и `stepcast plugins --dump`.

## Capabilities

### New Capabilities

- `plugin-tree`: дерево плагинов как конфигурация — из чего состоит строка,
  какие три слоя и в каком порядке его собирают, что делает патч с известным и
  с новым id, чем отключается строка, как встроенная строка заменяется
  пользовательской, что печатает `stepcast plugins --dump` и чем отказывает
  неверный патч.

### Modified Capabilities

- `plugin-contributions`: входом загрузчика становится дерево строк, а не
  объединённый список ключа `plugins`; у строки появляется id, а ключ `plugins`
  объявляется его сокращённой формой. Разрешение модуля (путь от файла
  объявления, пакет от корня проекта) и поведение отказа загрузки не меняются.
- `stepcast-configuration`: слой конфигурации получает второй документ —
  `plugins.patch.yml`; отчёт `stepcast config` перестаёт быть единственным
  ответом на вопрос «что загружено» и отсылает к `stepcast plugins --dump` за
  слоями и порядком.
- `ui-daemon`: добавляется требование о правке патча на работающем демоне —
  вклады строки, ушедшей из дерева, сняты, вклады появившейся действуют,
  перезапуск не нужен.

## Impact

- Изменяется: `src/core/plugins/tree.ts` (новый) — модель строки, разбор патча,
  свёртка слоёв; `src/core/plugins/load.ts` — `pluginDeclarations` уступает
  место разрешению дерева, загрузка идёт по строкам;
  `src/core/plugins/builtin.ts` — встроенные вклады описываются строками и
  применяются по дереву; `src/core/config/schema.ts` и `resolve.ts` — схема
  патча, чтение второго документа слоя, `Config.plugins` как проекция дерева;
  `src/cli/main.ts` и `src/cli/commands/plugins.ts` (новый) — команда и её показ
  дерева при отказе загрузки; `src/ui/pipelines.ts` — сравнение строк дерева в
  ключе кеша ядер; `scripts/schema-targets.ts` — новая цель схемы.
- Не изменяется: контракт плагина (`contract.ts`), ядро (`kernel.ts`) и реестр
  (`registry.ts`) — дерево решает, **что** применять, а не **как**; плагин
  Codex и любой сторонний плагин правок не требуют.
- Тесты: новый `test/plugin-tree.test.ts` — свёртка трёх слоёв, замена по id
  целиком, вставка с `before`/`after`, отключение, отказы неверного патча,
  замена встроенной строки пользовательской; `test/plugins-command.test.ts` —
  печать дерева со слоями и печать при отказе загрузки;
  `test/ui-server.test.ts` — правка патча на работающем демоне выгружает старую
  строку и загружает новую; `test/schema-generated.test.ts` подхватывает новую
  цель сам.
- Документация: `docs/config.md` (раздел «Плагины» — слои и патч),
  `docs/plugins.md` (дерево, id строки, замена встроенного, команда осмотра).
- Не входит в изменение (`design.md`, Non-Goals): значения настройки строки
  (`with:`), чтение плагинов из каталогов и перезагрузка по правке файла модуля
  (`user-plugins-from-files`), машинный формат вывода и экран витрины
  (`plugin-introspection`), слои маршрутов и дашбордов, запись id и слоя строки
  в манифест прогона.
