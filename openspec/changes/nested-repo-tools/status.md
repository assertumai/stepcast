## Работает

- **Инструменты вложенного репозитория объявляет он сам**: объектная форма элемента `project.nested_repos` принимает ключ `tools` — той же моделью, что `project.tools` (непустой список непустых строк, пробел внутри значения допущен). В отличие от `check` и `spec`, которые репозиторий объявляет вместо корневых, перечень складывается с корневым: корневые впереди, повторы схлопнуты. `git` и `npm`, объявленные корнем, верны в любом дереве, а `./gradlew` — только там, где лежит обёртка, и репозиторий, объявивший своё замещением, потерял бы право, которого у него никто не отнимал. Репозиторий без ключа получает ровно корневой перечень — поведение, бывшее до ключа.
- **`stepcast project repos` отдаёт дорожке инструменты её репозитория**: блок `repo` заполненной дорожки несёт `tools` — действующий перечень выбранного репозитория. Ключ необязателен: дерево, не объявившее инструментов ни корнем, ни репозиторием, отвечает без него, а не пустым списком, который в элементе `allow` дал бы ноль записей. Отсутствие инструментов отказом команды не является — они нужны только той работе, которая на них ссылается.
- **Списочное значение размножает элемент списка и на позднем раскрытии**: правило действует одинаково на обоих этапах — при разборе документа и перед исполнением работы, — так что `allow: ["Bash(${jobs.slots.output.lanes.a.repo.tools} *)"]` даёт по праву на инструмент. Иначе перечень, посчитанный работой прогона, в список не попадает ничем: параметры работы скалярны по модели, и `with:` кладёт в параметр неразвёрнутый текст отложенной подстановки. Довод про снимок, которым позднее раскрытие было из-под правила выведено, не подтвердился: до раскрытия `pipeline.lock.yml` несёт на этом месте саму подстановку, а не значение, и числа записей не обещает ни с правилом, ни без него. Молчания правило не допускает и здесь: пустой список — отказ, две списочные подстановки в элементе — отказ, списочное значение в скалярном поле — прежняя ошибка «непредставимое строкой».
