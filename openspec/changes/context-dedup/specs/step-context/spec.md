## ADDED Requirements

### Requirement: Повторно объявленный путь включается в контекст один раз

Система SHALL включать файл, разрешённый при сборке контекста более одного раза, в собранный контекст единственной записью — независимо от того, объявлен он на разных уровнях, дважды на одном уровне или получен один раз явным путём, а другой раз раскрытием глоба.

Тождество записей MUST определяться разрешённым путём файла, приведённым к абсолютному виду, а не текстом объявления. Склеенная запись MUST занимать место первого объявления в порядке сборки «выходы предшественников, пайплайн, работа, шаг», а её содержимое MUST читаться один раз. Записи `text` MUST NOT склеиваться между собой: пути у них нет, и одинаковый текст на двух уровнях остаётся двумя записями.

#### Scenario: Один файл объявлен на пайплайне и на работе

- **WHEN** и `context` пайплайна, и `context` работы называют `CLAUDE.md`
- **THEN** содержимое `CLAUDE.md` включается в контекст один раз, в разделе уровня пайплайна

#### Scenario: Повтор внутри одного уровня

- **WHEN** `context` работы называет `AGENTS.md` дважды
- **THEN** файл включается в контекст один раз

#### Scenario: Глоб пересекается с явным путём

- **WHEN** пайплайн объявляет `docs/plan.md`, а работа — глоб `docs/*.md`, совпадающий в том числе с `docs/plan.md`
- **THEN** `docs/plan.md` включается один раз, а остальные файлы, пойманные глобом, включаются как обычно

#### Scenario: Повтор пути выхода предшественника

- **WHEN** работа объявляет в `context` тот же файл выхода, что уже вошёл в блок выходов предшественников
- **THEN** файл включается один раз, в блоке выходов предшественников

#### Scenario: Одинаковый текст на двух уровнях

- **WHEN** пайплайн и работа объявляют записи `text` с совпадающим содержимым
- **THEN** обе записи входят в контекст

### Requirement: Способ передачи склеенной записи выбирается по силе объявления

Система SHALL выбирать способ передачи для записи, объявленной несколько раз, по самому сильному из объявлений, а не по уровню объявления и не по порядку их обхода.

Порядок силы: `mode: inline` сильнее вставки, полученной из `auto` по размеру меньше `context.inline_threshold`, а любая вставка сильнее передачи путём (`mode: reference` либо `auto` сверх порога). При равной силе исход MUST совпадать с исходом первого объявления. Объявление `mode: inline` на любом из уровней MUST делать склеенную запись непонижаемой при превышении предела размера — наравне с записью, объявленной так однажды.

#### Scenario: Явная вставка снизу побеждает передачу путём сверху

- **WHEN** пайплайн объявляет файл с `mode: reference`, а работа — тот же файл с `mode: inline`
- **THEN** содержимое файла вставляется в контекст

#### Scenario: Передача путём не отменяет явную вставку

- **WHEN** пайплайн объявляет файл с `mode: inline`, а шаг — тот же файл с `mode: reference`
- **THEN** содержимое файла остаётся вставленным

#### Scenario: Крупный файл, объявленный вставкой на одном из уровней

- **WHEN** файл сверх порога вставки объявлен на пайплайне как `auto`, на работе — как `inline`, и предел размера контекста превышен
- **THEN** запись не понижается на передачу путём

## MODIFIED Requirements

### Requirement: Состав контекста фиксируется и наблюдаем

Для каждого агентского шага система SHALL записывать в `context.json` перечень
вошедших записей с указанием уровня-источника, способа передачи и размера в
токенах. Отправленный текст MUST сохраняться в `prompt.txt`.

Запись, объявленная на нескольких уровнях, MUST присутствовать в перечне один
раз и MUST называть все уровни, на которых она была объявлена, — отдельным
полем со списком уровней в порядке сборки. Уровнем-источником такой записи
MUST оставаться тот, на месте которого она вошла в контекст, чтобы разрез по
уровням оставался разрезом собранного текста. Запись, объявленная однажды,
списка уровней MUST NOT нести: её называет уровень-источник.

#### Scenario: Разбор по источникам

- **WHEN** шаг исполнен
- **THEN** `context.json` содержит для каждой записи её источник — блок выходов, пайплайн, работа или шаг — способ передачи и размер

#### Scenario: Запись, объявленная дважды

- **WHEN** один и тот же файл объявлен и на пайплайне, и на работе
- **THEN** `context.json` содержит его одной записью с источником «пайплайн» и списком уровней объявления, называющим пайплайн и работу

#### Scenario: Запись без повторов

- **WHEN** файл объявлен ровно на одном уровне
- **THEN** списка уровней у его записи в `context.json` нет

### Requirement: Суммарный размер контекста ограничен

Собранный контекст шага SHALL проверяться на соответствие пределу
`context.max_tokens` до отправки бэкенду. Размер MUST оцениваться локально, без
обращения к модели, и трактоваться как оценка. Оценка MUST считаться по составу
контекста после склейки повторно объявленных путей: запись, вошедшая в контекст
один раз, MUST учитываться в оценке один раз. При превышении предела система
MUST понижать записи в режиме `auto` с вставки содержимого на передачу путём,
начиная с самой крупной, пока оценка не уложится в предел. Записи с явным
`mode: inline` и записи `text` MUST NOT понижаться. Если после всех понижений
оценка остаётся выше предела, шаг MUST завершаться отказом до отправки.

#### Scenario: Неудачный глоб собрал слишком много

- **WHEN** запись контекста в режиме `auto` раскрылась в набор файлов, превышающий предел
- **THEN** самые крупные записи передаются путём вместо содержимого
- **AND** в журнал событий пишется запись о каждом понижении

#### Scenario: Явная вставка не понижается

- **WHEN** предел превышен, а часть записей объявлена с `mode: inline`
- **THEN** эти записи остаются вставленными содержимым, а понижаются только записи в режиме `auto`

#### Scenario: Предел недостижим понижениями

- **WHEN** после понижения всех записей `auto` оценка всё ещё выше предела
- **THEN** шаг завершается отказом до запуска бэкенда
- **AND** сообщение называет оценку, предел и три самые крупные записи

#### Scenario: Проверка до отправки

- **WHEN** контекст шага превышает предел
- **THEN** процесс бэкенда не запускается, и расход по этому шагу равен нулю

#### Scenario: Повтор не расходует предел дважды

- **WHEN** файл объявлен и на пайплайне, и на работе, а его размер таков, что двойной учёт вывел бы контекст за предел
- **THEN** оценка учитывает файл один раз, и шаг исполняется без понижений и без отказа
