## Why

Stepcast разрабатывается вручную: человек выбирает следующее ограничение из
`docs/status.md`, заводит OpenSpec-изменение, доводит его до зелёной сборки и
архивирует. Это ровно тот класс работы, ради которого движок и написан —
топология объявлена, гейт дешевле самой работы (`npm run check`), результат
проверяется контрактом, — но сам движок к себе не применён.

Ценность не только в экономии рук. Пайплайн, который улучшает собственный
движок, — самая честная проверка формата: он упирается в те же ограничения,
что и любой пользователь, и упирается первым. Первые два пункта его бэклога —
предикат `judge` и `on_exceed: wait` — нужны в первую очередь ему самому:
без `judge` шаг исправления находок ревью держится на слове модели, без
`on_exceed: wait` ночной прогон умирает на лимите подписки вместо того, чтобы
дождаться сброса. Петля замыкается: каждый успешный проход делает следующий
проход лучше.

## What Changes

- **Очередь улучшений — отдельный `backlog.md` в корне репозитория.** Файл
  ведёт единственную вещь: какие улучшения решено сделать и в каком они
  состоянии (`pending`, `in_progress`, `done`, `failed`). Заголовок пункта —
  kebab-case слаг, он же имя будущего OpenSpec-изменения, он же стабильный
  идентификатор.
- **`docs/status.md` очередью не становится.** Он остаётся описанием
  реальности и служит источником кандидатов для человека, пополняющего бэклог,
  но состояние работ в нём не хранится. Три причины: его правит сама работа
  `implement` (перенося строку из «Пока нет» в «Работает»), и добавление туда
  же пометок очереди столкнуло бы три работы на одном файле; у его записей нет
  ни идентификаторов, ни единиц работы, а проза с болдовыми лидами хрупка к
  переформулировке тем же агентом; часть его ограничений — сознательные
  не-цели («Проверка сознательно не вводится»), и очередь из них порождала бы
  задачи, которые решено не делать.
- **Пайплайн `self-improve` из семи работ**: `propose` → `plan` → `implement`
  → `review` → `fix-review` → `verify` → `finalize`. Каждая — отдельный файл
  работы в `.stepcast/jobs/`, подключаемый через `uses`.
- **`review` — отдельная работа, а не шаг внутри `implement`.** Ревьюер должен
  смотреть на диф свежим взглядом, а не из диалога, в котором сам же и писал
  этот код. Граница работы даёт независимую сессию по устройству формата
  («именованная сессия живёт в пределах одной работы»), без ручной настройки.
  Находки доезжают до `fix-review` штатным механизмом выходов
  предшественников — `artifacts/review.json` попадает в его контекст
  автоматически.
- **Коммит после каждого успешного улучшения.** `finalize` коммитит рабочее
  дерево одним коммитом на улучшение — исходники, документацию, OpenSpec-
  изменение и отметку `done` в `backlog.md` вместе. История получается по
  коммиту на пункт бэклога, и откат улучшения — обычный `git revert`.
- **При отказе не коммитится ничего.** Сломанные правки остаются в рабочем
  дереве нетронутыми: стирать работу агента автоматически движок не вправе, а
  разбор отказа — это ровно то, ради чего её сохраняют.
- **Петля отказывается стартовать на грязном дереве.** `propose` проверяет
  `git status` до первого потраченного токена и завершается отказом, если есть
  незакоммиченные изменения. Это закрывает сразу три дыры: незавершённая правка
  человека не попадёт в автоматический коммит; отказ предыдущего прогона
  останавливает петлю до вмешательства человека, а не наслаивает на сломанный
  код следующее улучшение; граница «что изменило это улучшение» остаётся
  однозначной.
- **Пункт, зависший в `in_progress`, признаётся протухшим и берётся заново.**
  Прогон, оборванный по `Ctrl-C`, крашу или бюджету, оставляет пункт помеченным
  в работе. `propose` считает такой пункт свободным, если `started_at` старше
  порога, — иначе одна отменённая ночь блокировала бы пункт навсегда, а увидеть
  это можно только открыв файл руками.
- **`finalize` выполняется при любом исходе** — `needs: all` и `on: always`.
  Только так пункт получает конечное состояние и при отмене, и при остановке по
  бюджету; обычная зависимость в этих случаях не сработала бы, и пункт остался
  бы в `in_progress` до протухания.
- **Бэклог засевается пятью пунктами**, отсортированными по тому, насколько
  каждый улучшает следующий проход самой петли: `judge`, `on_exceed: wait`,
  подстановка в числовые поля, триггер по расписанию, наследование рабочего
  дерева зависимой работой.

Сознательно вне объёма: изменения самого движка — все пять пунктов бэклога
становятся отдельными OpenSpec-изменениями, которые петля и заведёт; выбор
пункта агентом по произвольному критерию (`propose` берёт первый свободный
сверху — порядок задаёт человек); автоматический `push`; параллельные прогоны
петли; откат неудачного улучшения автоматикой.

**BREAKING**: нет. Изменение не трогает ни одной строки движка — добавляются
только файлы пайплайна, бэклог и вспомогательный скрипт.

## Capabilities

### New Capabilities

- `improvement-backlog`: формат очереди улучшений и её машина состояний —
  структура записи, переходы `pending` → `in_progress` → `done` | `failed`,
  выбор следующего пункта, протухание зависших, требование чистого дерева.
- `self-improvement-loop`: топология пайплайна — состав и связи семи работ,
  независимость сессии ревью, передача находок в исправление, гейт сборки,
  коммит по успеху и его отсутствие по отказу, поведение при отмене и
  исчерпании бюджета.

### Modified Capabilities

(нет — движок не меняется; пайплайн собран из существующих возможностей
формата: `uses`/`with`, `needs`/`on`, `until`, `output`, `changed_only`,
`workspace.mode: cwd`)

## Impact

- Новые файлы пайплайна: `.stepcast/pipelines/self-improve.yml`;
  работы `.stepcast/jobs/{propose,plan,implement,review,fix-review,verify,finalize}.yml`;
  промпты `.stepcast/prompts/*.md`; схемы `.stepcast/schemas/*.json`.
- Новый `backlog.md` в корне репозитория — очередь с пятью засеянными пунктами.
- Новый `scripts/backlog.mjs` — разбор и правка `backlog.md` для командных
  шагов `propose` и `finalize`. Node без зависимостей: формат заведомо простой,
  а тянуть парсер markdown ради пяти полей несоразмерно.
- Изменяется: `docs/status.md` — таблица «Работает» пополняется строкой о
  пайплайне саморазвития; `README.md` — упоминание петли в разделе о статусе.
- Зависимости: ни одной новой.
- Движок: не затрагивается. Ни один файл в `src/` не меняется.
- Рабочее дерево: `workspace.mode: cwd` обязателен — изолирующие режимы дают
  каждой работе снимок от исходного `HEAD`, и `review` не увидел бы правок
  `implement`. Следствие — `concurrency: 1` и отсутствие песочницы; снятие
  этого ограничения и есть пятый пункт бэклога.
