# Задачи

Порядок — из плана миграции `design.md`: движок учится ключам и подстановке
раньше, чем `.stepcast/` начинает ими пользоваться. Иначе проверка на
промежуточном дереве упадёт на разборе собственного пайплайна петли: её
`dist/` пересобирается той же командой, которую эта правка и трогает. Каждая
задача — код **и** тест; тест обязан падать до правки.

Границы `changed_only` этого захода: `.stepcast/prompts/**` в них есть, поэтому
файл правил заводится там (задача 4.1) — `.stepcast/spec-rules.md` завести
нельзя, он вне границ. Объявление садится в пайплайн, рядом с `project.check`
(задача 4.2). Расширение границ подстановкой `${project.spec.rules}` (задача
4.3) действует со следующего прогона: предикат фиксируется вместе с раскрытым
пайплайном. `backlog.md` не правится.

Удалять ничего не нужно и нечем: у работы нет прав на удаление файлов. Всё
переносится правкой текста, а не переносом файлов.

## 1. Ключи конфигурации

- [x] 1.1 `src/core/config/schema.ts` — модель относительного пути репозитория
      рядом с `CheckCommandSchema`: непустая после обрезки строка, не
      абсолютный путь, без сегмента `..`. Непустота выражена и образцом, чтобы
      дойти до публикуемой JSON Schema. Тест: принимается
      `openspec/changes`, отклоняются `""`, `"   "`, `/tmp/changes`,
      `../changes`.
- [x] 1.2 `src/core/config/schema.ts` — `RawSpecSchema` (`dir`, `rules`,
      `tool`, `.strict()`) внутри `RawProjectSchema`; `dir` и `rules` —
      моделью задачи 1.1, `tool` — непустой строкой. Каждый ключ
      необязателен: слои сливаются по листьям. Тест: принимается полная
      группа и любая её часть, `spec: { folder: … }` отклоняется как
      неизвестный ключ.
- [x] 1.3 `src/core/config/resolve.ts` — `spec` в поле `project` типа
      `Config`, каждый ключ `string | undefined`. Встроенных умолчаний в
      `BUILTIN_CONFIG` нет и не заводится. Тест: без объявления конфигурация
      разрешается и значения отсутствуют; объявленные значения видны в отчёте
      `stepcast config` с файлом-источником.
- [x] 1.4 `schema/config.schema.json` — перегенерировать
      (`test/schema-generated.test.ts` сверяет файл с моделью и уронит
      проверку, если забыть).

## 2. Запрет глобального слоя на вложенных ключах

- [x] 2.1 `src/core/config/merge.ts` — хвостовая форма `**` в
      `matchesKeyPattern`: шаблон, оканчивающийся на `**`, совпадает с самим
      ключом и со всем, что под ним; в середине пути `**` не допускается.
      Тест: `project.**` ловит `project.check` и `project.spec.dir` и не
      ловит `defaults.model`; форма с `**` посередине отклоняется.
- [x] 2.2 `src/core/config/schema.ts` — `PROJECT_ONLY_KEYS = ['project.**']`
      с комментарием о причине: сегодняшний `project.*` требует равного числа
      сегментов и вложенный ключ пропускает молча. Тест:
      `project.spec.dir` в `~/.stepcast/config.yml` — отказ, называющий ключ
      и `.stepcast/config.yml`; тот же ключ в проектном конфиге — успех;
      `project.check` в глобальном по-прежнему отклоняется.

## 3. Объявление в пайплайне и подстановки

- [x] 3.1 `src/core/pipeline/schema.ts` — группа `spec` в `ProjectSchema`
      документа пайплайна, теми же моделями значений, что в конфигурации
      (модель одна на оба документа, а не копия). Тест: документ с группой
      разбирается; пустой `dir`, абсолютный путь и неизвестный ключ внутри
      группы отклоняются.
- [x] 3.2 `src/core/pipeline/expand.ts` — действующее значение группы:
      пайплайн поверх конфигурации, по ключу, а не по группе целиком; ни один
      слой не обязателен. Разрешается один раз, оба потребителя
      (`pipelineScope` и `bodyScope`) берут посчитанное. Тест: перекрытие,
      объявление только в пайплайне, только в конфиге, частичное объявление в
      обоих.
- [x] 3.3 `src/core/pipeline/expand.ts` — `PROJECT_NAMES` пополняется
      составными именами `spec.dir`, `spec.rules`, `spec.tool`; объяснение
      необъявленного называет конкретный ключ и оба места объявления, а имя
      вне состава — перечень доступных. Тест: два разных сообщения на две
      разные ошибки (проверка «есть слово spec» прошла бы на обеих ветках —
      тест обязан их различать).
- [x] 3.4 Раскрытие в местах, которыми пользуется петля. Тест: путь контекста,
      элемент `changed_only`, запись `permissions.allow`, текст промпта — всё
      в работе, подключённой через `uses`, то есть в `bodyScope`; снимок
      `pipeline.lock.yml` содержит значения, а не подстановки.
- [x] 3.5 `test/lint.test.ts` — настоящие `stepcast lint` и `stepcast run` на
      документе со ссылкой без объявления: отказ, называющий ключ и оба места;
      `run` не заводит каталога прогона.
- [x] 3.6 `schema/pipeline.schema.json` — перегенерировать.

## 4. Перевод петли

- [x] 4.1 `.stepcast/prompts/spec-rules.md` — новый файл правил этого
      репозитория: `openspec new change "<слаг>"`, артефакты по
      `openspec instructions <artifact> --change "<слаг>" --json`, порядок
      зависимостей из `openspec status --change "<слаг>" --json`, проверка
      `openspec validate "<слаг>" --strict`, правило про `SHALL` в первой
      физической строке описания требования. Всё это дословно переезжает из
      `.stepcast/prompts/propose.md`.
- [x] 4.2 `.stepcast/pipelines/self-improve.yml` — группа `spec` в верхнем
      ключе `project` рядом с `check`: `dir: openspec/changes`,
      `rules: .stepcast/prompts/spec-rules.md`, `tool: openspec`. Комментарий
      объясняет слой (почему пайплайн, а не `.stepcast/config.yml`, и что
      перенос возможен одной правкой).
- [x] 4.3 `.stepcast/jobs/implement.yml` и `.stepcast/jobs/fix-review.yml` —
      `openspec/changes/**` в `changed_only` заменяется на
      `${project.spec.dir}/**`, добавляется `${project.spec.rules}` с
      комментарием: правила спецификации — часть петли, править их должен
      уметь заход. Расширение действует со следующего прогона.
- [x] 4.4 `.stepcast/jobs/propose.yml` — `Bash(openspec *)` заменяется на
      `Bash(${project.spec.tool} *)`; в контекст добавляется
      `path: ${project.spec.rules}` в режиме `inline`; `changed_only` —
      `${project.spec.dir}/**`; описание и комментарий работы перестают
      называть OpenSpec.
- [x] 4.5 `.stepcast/jobs/plan.yml` — четыре пути контекста заменяются одним
      глобом `${project.spec.dir}/${params.change}/**/*.md`. Комментарий: имён
      документов работа не знает, а путь без глоба обязан существовать —
      перечень требовал бы `design.md` от каждого изменения.
- [x] 4.6 `.stepcast/jobs/implement.yml` — контекст: один вход
      `${project.spec.dir}/${params.change}/**/*.md` в режиме `reference`.
      Комментарий объясняет режим: вставлять по имени больше нечего, а порог
      `context.inline_threshold` и так переводил крупные документы в ссылки.
- [x] 4.7 `.stepcast/jobs/review.yml` — контекст:
      `${project.spec.dir}/${params.change}/**/*.md` вместо глоба по `specs/`.
- [x] 4.8 `.stepcast/prompts/propose.md` — остаётся портируемая часть:
      завести описание изменения по правилам репозитория (они в контексте,
      файл `${project.spec.rules}`), документы лежат в
      `${project.spec.dir}/<слаг>/`, слаг пункта становится именем изменения,
      обоснование и признак выполненности — вход, а не готовый текст, ничего
      не реализовывать, `backlog.md` не трогать.
- [x] 4.9 `.stepcast/prompts/plan.md`, `implement.md`, `review.md`,
      `fix-review.md` — имена документов и путь `openspec/changes/…`
      заменяются на `${project.spec.dir}/${params.change}/` и на «чек-лист
      задач изменения»; промпт `implement` прямо велит начинать с него, раз

- [x] 4.10 `.stepcast/schemas/propose.json` — описание поля `slug`
      перестаёт называть OpenSpec; `change_dir` описывается как каталог
      документов изменения.
- [x] 4.11 `test/loop-portability.test.ts` — новый файл, четыре проверки:
      (а) в `.stepcast/jobs/**` и в промптах петли, кроме файла правил, нет
      ни `openspec`, ни имён документов OpenSpec; (б) настоящие файлы петли,
      раскрытые против чужого объявления (`dir: docs/changes`,

- [x] 4.12 Проверка руками: `stepcast lint .stepcast/pipelines/self-improve.yml`

## 6. Находки ревью

- [x] 6.1 `.stepcast/prompts/implement.md` и `propose.md` — имя документа
      внутри каталога изменения (`status.md`), команда `npm run status:build`
      и ссылка на `docs/status.md` переезжают в файл правил; промпт называет
      только сам файл правил. `.stepcast/jobs/implement.yml` получает файл
      правил контекстом вставкой — иначе правило до реализующего не доходит.
      Тест: `status.md` и `status:build` пополняют перечень запрещённых
      литералов в `test/loop-portability.test.ts`.
- [x] 6.2 `required: true` у записи контекста: ключ в схеме документа и в
      модели, отказ сборки контекста на записи без совпадений, объявление у
      глоба по каталогу изменения в `plan`, `implement` и `review`. Переход с
      перечня путей на глоб снял гарантию существования — работы шли дальше с
      пустым контекстом. Тесты: `test/context.test.ts` (три ветки),
      `test/expand.test.ts` (доезжает до раскрытой записи),
      `test/loop-portability.test.ts` (сквозной прогон в дереве без каталога
      изменения роняет первую же работу, а не завершается успехом).
- [x] 6.3 `src/core/lint.ts` — путь, все подстановки которого принадлежат
      `${project.*}`, проверяется на существование: опечатка в объявлении
      `project.spec.rules` иначе не видна ни линту, ни тестам. Пути с
      `inputs`, `params` и отложенными пространствами пропускаются как
      прежде — ими адресуют ещё не созданное. Тесты: `test/lint-paths.test.ts`
      (обе ветки) и `test/loop-portability.test.ts` (файл, названный
      объявлением петли, лежит на диске).
- [x] 6.4 `src/core/pipeline/interpolate.ts` — обращение к группе без листа
      (`${project.spec}`) объясняется составом пространства, а не сообщением о
      непредставимом строкой значении: подсказку даёт то же `scope.explain`,
      что и у неопределённого имени. Тест: `test/expand.test.ts`.
- [x] 6.5 Спеки изменения и `status.md` фрагмента приведены в соответствие:
      `required` и правило проверки путей из `${project.*}` — в
      `pipeline-definition` (второе — правкой существующего требования),
      запрет на имена документов, заводимых по итогам реализации, и
      обязательность глоба — в `self-improvement-loop`.
