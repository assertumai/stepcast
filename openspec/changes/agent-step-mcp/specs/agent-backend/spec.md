## ADDED Requirements

### Requirement: Трансляция объявленных MCP-серверов

Адаптер SHALL транслировать действующее для шага объявление MCP-серверов в параметры запуска бэкенда, и делать это только внутри сборки запуска.

Ни одна часть движка вне адаптера MUST NOT знать имён параметров, которыми
серверы передаются бэкенду: движок несёт объявление как данные — от документа
через раскрытый пайплайн до вызова адаптера. Шаг без действующего объявления и
без жёсткого режима MUST запускаться теми же параметрами, что и до появления
этой возможности.

Режим применения политики доступа MUST менять смысл объявления. При `enforce:
inherit` объявленные серверы **добавляются** к тем, что бэкенд поднимает по
своим настройкам. При `enforce: strict` объявление MUST быть полным списком:
адаптер собирает запуск так, что бэкенд не поднимает ни одного сервера сверх
объявленных, включая объявленные файлами репозитория. Шаг со `strict` и без
объявления MUST оставаться без серверов вовсе — то есть отсечение MUST
собираться и для него, а не только для шага, назвавшего хоть один сервер.

Параметры MCP — и объявление, и отсечение — MUST собираться только для
бэкенда, о котором возможность работы с серверами объявлена. Бэкенду без неё
адаптер MUST NOT добавлять ни того, ни другого: ни линт, ни ворота прогона тут
не заступятся, потому что шаг со `strict` серверов не объявляет и проверок о
возможности не запускает.

Объявление сервера MUST NOT разрешать вызовы его инструментов само по себе: в
жёстком режиме инструмент, не названный в `allow`, отклоняется независимо от
того, каким сервером он предоставлен. Состав инструментов сервера задан вне
репозитория и меняется без правки пайплайна, поэтому объявление говорит о
доступности, а список прав — о дозволенности.

#### Scenario: Объявленные серверы доходят до бэкенда

- **WHEN** агентский шаг с действующим объявлением двух серверов исполняется
- **THEN** собранный запуск содержит параметры, несущие оба объявленных сервера

#### Scenario: Шаг без объявления и без жёсткого режима

- **WHEN** агентский шаг серверов не объявляет и `enforce: strict` не действует
- **THEN** собранный запуск не содержит параметров, относящихся к MCP

#### Scenario: Жёсткий режим делает объявление полным списком

- **WHEN** шаг с `enforce: strict` объявляет один сервер
- **THEN** собранный запуск объявляет этот сервер единственным и отсекает серверы из прочих конфигураций бэкенда

#### Scenario: Жёсткий режим без объявления отсекает чужие серверы

- **WHEN** шаг с `enforce: strict` серверов не объявляет
- **THEN** собранный запуск несёт отсечение серверов прочих конфигураций и ни одного объявленного

#### Scenario: Бэкенд без объявленной возможности MCP

- **WHEN** запуск собирается для бэкенда, о котором возможность работы с MCP-серверами не объявлена
- **THEN** он не содержит ни параметров объявления, ни параметра отсечения — даже при `enforce: strict`

#### Scenario: Мягкий режим добавляет к своим

- **WHEN** шаг с `enforce: inherit` объявляет один сервер
- **THEN** собранный запуск добавляет объявленный сервер, не отсекая поднимаемых бэкендом самостоятельно

#### Scenario: Права не выдаются объявлением

- **WHEN** шаг с `enforce: strict` объявляет сервер, ни одного инструмента которого нет в `allow`
- **THEN** собранный запуск не содержит разрешений на инструменты этого сервера

### Requirement: Объявленный сервер, не поднявшийся у бэкенда, отказывает попытке

Система SHALL сличать состав поднятых бэкендом MCP-серверов, сообщённый при инициализации, с объявленным для шага, и отказывать попытке, если объявленный сервер не поднялся.

Причина отказа MUST называть сервер и MUST быть видна в записи попытки и в
потоке событий. Отказывает попытка, а не шаг целиком: повторы и эскалация
применяются к нему как ко всякому другому отказу. Бэкенд, не сообщающий состава
серверов, MUST оставлять шаг без этой проверки, а не отказывать ему: несообщённое
MUST NOT толковаться как отсутствие сервера.

Состав, сообщённый в виде, которого адаптер не понимает, MUST толковаться как
несообщённый. Форма этой части записи не документирована и меняется вместе с
бэкендом; истолковать непонятое как «сервера нет» значило бы уронить каждую
попытку каждого шага с объявлением, назвав причину, которой не было.

#### Scenario: Объявленный сервер не поднялся

- **WHEN** бэкенд сообщает при инициализации, что объявленный шагом сервер не подключён
- **THEN** попытка отказывает с причиной, называющей этот сервер

#### Scenario: Все объявленные серверы поднялись

- **WHEN** бэкенд сообщает о подключении всех объявленных серверов
- **THEN** попытка исполняется обычным порядком

#### Scenario: Бэкенд состава не сообщает

- **WHEN** запись инициализации не содержит сведений о серверах
- **THEN** попытка исполняется обычным порядком, а сличение не выполняется

#### Scenario: Состав сообщён в непонятом виде

- **WHEN** запись инициализации несёт состав серверов в форме, которой адаптер не понимает
- **THEN** попытка исполняется обычным порядком, а сличение не выполняется

#### Scenario: Неподнявшийся сервер, шагом не объявленный

- **WHEN** бэкенд сообщает о неподнявшемся сервере, которого шаг не объявлял
- **THEN** попытка не отказывает по этой причине

### Requirement: Вызовы инструментов MCP учитываются наравне со встроенными

Система SHALL записывать вызовы инструментов MCP-серверов в журнал попытки и учитывать их расход тем же порядком, что и вызовы встроенных инструментов бэкенда.

Особого пути для них MUST NOT быть: имя инструмента, предоставленного сервером,
движок MUST толковать как всякое другое имя. Отказ бэкенда в разрешении на
вызов такого инструмента MUST попадать в поток событий наравне с прочими
отказами в разрешении.

#### Scenario: Вызов инструмента сервера в журнале

- **WHEN** агент вызывает инструмент объявленного сервера
- **THEN** вызов виден в потоке попытки, сохранённом в директории шага, и в разборе этого потока витриной

#### Scenario: Расход сообщения с вызовом инструмента сервера

- **WHEN** бэкенд сообщает расход сообщения, содержащего вызов инструмента сервера
- **THEN** этот расход входит в расход попытки

#### Scenario: Отказ в разрешении на инструмент сервера

- **WHEN** бэкенд отказывает в разрешении на вызов инструмента объявленного сервера
- **THEN** в потоке событий есть запись об отказе, называющая инструмент

## MODIFIED Requirements

### Requirement: Объявление возможностей адаптера

Каждый адаптер SHALL объявлять поддерживаемые возможности, включая продолжение сессий, структурированный вывод и работу с MCP-серверами. При отсутствии поддержки сессий режим `session: shared` MUST деградировать до `per_step` с предупреждением на старте прогона, а не приводить к отказу.

Отсутствие поддержки MCP-серверов MUST NOT деградировать: шаг, для которого
действует объявление серверов, на бэкенде без этой возможности MUST
останавливать прогон до первого шага. Молча исполнить такой шаг значило бы
оставить пайплайн с инструментами, которых нет. Спрашивается возможность самого
адаптера, а не флаг в конфигурации: флаг — то, что о бэкенде объявили,
возможность — то, что он умеет, и расходиться они могут.

Пустое объявление (`mcp: {}`, снимающее унаследованное) MUST NOT требовать этой
возможности ни от адаптера, ни от конфигурации: серверов у такого шага не будет
ни при каком бэкенде, и останавливать прогон не за что.

#### Scenario: Бэкенд без поддержки сессий

- **WHEN** пайплайн объявляет `session: shared`, а адаптер не поддерживает продолжение сессий
- **THEN** на старте выводится предупреждение, а шаги исполняются каждый в своей сессии

#### Scenario: Бэкенд без поддержки MCP

- **WHEN** для шага действует объявление серверов, а его адаптер такой возможности не объявляет
- **THEN** прогон останавливается до первого шага с ошибкой, называющей шаг и бэкенд

#### Scenario: Бэкенд с поддержкой MCP

- **WHEN** для шага действует объявление серверов, а его адаптер эту возможность объявляет
- **THEN** прогон идёт обычным порядком

#### Scenario: Снятие серверов не требует возможности

- **WHEN** шаг снимает унаследованные серверы пустым объявлением, а его адаптер возможности работать с MCP не объявляет
- **THEN** прогон идёт обычным порядком
