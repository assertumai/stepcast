## Why

Условие сходимости работы (`until.check`) исполняется **без окружения**.
Вычислитель предикатов получает `env: {}`, а команда запускается через
`execaSync` с `extendEnv: false` — то есть пустой набор означает буквально
пустой: ни `PATH`, ни `HOME`, ни чего-либо ещё.

Практически это делает `until` непригодным с любой реальной проверкой:

```
predicate: cmd  passed: False
npm run check:
/bin/sh: npm: command not found
```

Шаговые предикаты при этом получают полное окружение через `stepEnv`, так что
одна и та же команда в `expect` шага работает, а в `check` работы — нет.

Документация обещает обратное: «Окружение процесса наследуется целиком:
агентский CLI и сборочные инструменты нуждаются в `JAVA_HOME`, `NVM_DIR`,
`SSH_AUTH_SOCK`, прокси и десятке других переменных, и отсечение по списку
ломает первый же реальный шаг».

Цена дефекта наблюдалась на живом прогоне: работа с циклом честно исчерпала
четыре итерации, каждый раз выполняя агентскую работу заново и каждый раз
упираясь в проверку, которая не могла пройти ни при каком коде. Отказ при этом
выглядел как «check не пройден», то есть указывал на код, а не на окружение.

## What Changes

- **Проверка цикла получает окружение работы** — то же, что её шаги: окружение
  процесса, `env_files`, `env` пайплайна и работы, внедряемые `STEPCAST_*`,
  за вычетом `env_deny`.
- **Переменные уровня шага проверке не объявляются.** `STEPCAST_STEP` и
  `STEPCAST_STEP_DIR` пропускаются: проверка шагом не является, и объявлять их
  означало бы называть несуществующее.

**BREAKING**: нет. Меняется поведение там, где проверка не работала вовсе.

## Impact

- Изменяется: `src/core/run/runner.ts` — окружение работы собирается и
  передаётся вычислителю; `src/core/exec/env.ts` — шаг и его каталог в
  внедряемых переменных становятся необязательными.
- Тесты: команда проверки находит инструменты из `PATH`; переменные пайплайна
  и работы доходят; переменная уровня шага не объявляется; непройденная
  проверка по-прежнему исчерпывает итерации.
