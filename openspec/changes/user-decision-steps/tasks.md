- [x] 1.1 `src/core/plugins/contract.ts`: поле `waits?: true` в `StepKindContribution` с комментарием о том, почему гонка с `step.timeoutMs` для такого вида снимается (design.md, решение 6), и `decision?: StepKindDecisions` во `StepKindInput` — способность объявить ожидание и дождаться решения, даваемая только виду с `waits` (решение 1, 5).
- [x] 1.2 `src/core/plugins/contract.ts`: типы запроса и результата ожидания — перечень эффектов (`continue`, `reject`, `restart`) с подписью, срок, исход по умолчанию, вопрос; результат — исход, эффект, автор (`user` | `deadline`), причина, шаг перезапуска. Закрытость набора эффектов — типом, а не строкой (решение 1).
- [x] 1.3 `src/core/plugins/contract.ts`: тип отказа обещания, которым движок отдаёт исход, решающий судьбу прогона, — узнаваемый по своему типу, а не по тексту (решение 5); комментарий о защёлке, которую вклад не в силах отменить.
- [x] 1.4 `src/plugin.ts`: реэкспорт новых типов и экспорт `parseDuration` из `src/core/units.ts` с комментарием о единственном диалекте длительностей (решение 7).
- [x] 1.5 `src/core/plugins/context.ts`: типизация `waits` в публикуемом типе регистратора видов шага; `StepKindContributionSchema` принимает `waits` только значением `true` и отказывает названной причиной на любом другом. ## 12. Правки по ревью

- [x] 12.1 Решение, записанное прогону с мёртвым процессом, доживает до возобновления: новый `src/core/run/decisionCarry.ts` собирает по журналу исходного прогона объявленные, но не применённые ожидания вместе с лежащими на диске записями, `runner.ts` переносит их в новый прогон событием `decision.carried`, а `decisionWait.ts` пробует перенесённое решение первым же тактом и ровно один раз (следующая итерация `until` спрашивает человека заново). Сценарии «Решение ждёт возобновления» и «Возобновление применяет лежащее решение» покрыты в `test/run-decision.test.ts` и `test/decision-wait.test.ts`.
- [x] 12.2 Ожидание решения больше не спорит с пределом ожидания окна лимита: `UsageAccumulator.recordWait` получил повод (`window` | `decision`), `totalWaitMs()` и `wouldExceedMaxWait` считают только `window`, а из `elapsedMs()` и длительности областей вычитаются оба. Восьмичасовое терпение человека не отказывает ближайшему сну до сброса окна — `test/budget.test.ts`.
- [x] 12.3 Негодная запись решения отвергается один раз, а не каждым тактом опроса: `decisionWait.ts` помнит текст уже отвергнутой записи и повторяет событие `decision.refused` только на изменившемся содержимом (исправленную запись ожидание обязано рассмотреть заново); отдельной защёлкой снят и повтор отказа по негодному объявлению срока.
- [x] 12.4 Звено цепочки перезапуска слушает тот же сигнал отмены, что и первый прогон: `continueRestartChain` принимает `AbortSignal`, `stepcast run` и `stepcast resume` передают в него `controller.signal` своих обработчиков SIGINT/SIGTERM. Ctrl-C на звене, стоящем на шаге решения, прерывает ожидание — `test/resume-chain.test.ts`.
- [x] 12.5 `selectAwaiting` не решает за первое совпадение: голое имя шага, ждущего в двух работах, отвергается перечнем полных адресов тем же приёмом, что и несколько ожиданий без `--step`; полный адрес `работа/шаг` разводит одноимённые шаги — `test/decision.test.ts`, `test/decide.test.ts`.
- [x] 12.6 Исход по истечении срока проходит ту же `validateDecision`, что и решение человека: `on_expire` с эффектом `reject` получает причину, названную самим сроком, вместо записи без причины и остановки прогона с висящим тире; негодное объявление срока отвергается событием, не отказывая прогон. Путь из `examples/decision/stepcast.yml` покрыт тестом.
- [x] 12.7 `test/resume-chain.test.ts` снимает слепок файлов исходного прогона ДО возобновления и перезапускает не с первой работы, а с середины — так проверены сценарии `run-resume` «Шаги выше точки переиспользованы»; «Успешное решение переиспользовано» (возобновление не переспрашивает решение успешного шага) покрыто в `test/run-decision.test.ts`.
