## 1. Помощник рабочих деревьев: заведение и адресное снятие

- [x] 1.1 Новый файл `src/core/run/worktrees.ts` — единственное место, где движок зовёт `git worktree`. Свой помощник `git` того же вида, что в `src/core/run/workspace.ts` (`core.quotePath=false`, `maxBuffer`, `stdio`), без копии комментария к нему: комментарий остаётся в одном месте, здесь — ссылка.
- [x] 1.2 `addWorktree({ repoDir, path })` — `git -C <repoDir> worktree add --detach --quiet <path> HEAD`; каталог-родитель заводится до вызова. Ошибка git уходит наружу как есть: причину формулирует вызывающий, у которого есть контекст (корень это или часть).
- [x] 1.3 `removeWorktree({ repoDir, path, runDir })` — адресное снятие: сначала `git -C <repoDir> worktree remove --force <path>`; при отказе — `rmSync` каталога и удаление учётной записи по указателю самого дерева (файл `<path>/.git`, строка `gitdir: …`). Возвращает исход (снято / каталог снят, а запись осталась) — вызывающий решает, что с ним делать.
- [x] 1.4 Защита указателя: запись удаляется, только если разобранный путь существует и его родительский каталог называется `worktrees`. Не совпало — запись не трогается, исход «запись осталась» с причиной. Комментарий объясняет, почему путь резервный и почему проверка именно такая.
- [x] 1.5 Инвариант каталога: `removeWorktree` отказывает `StepcastError`, если `path` не лежит внутри `runDir`. Комментарий называет то, что защищается: рабочее дерево части в проекте и корневое дерево проекта лежат вне директории прогона по устройству, и ошибка в вычислении пути обязана стать отказом, а не снесённым деревом.
- [x] 1.6 `git worktree prune` не вызывается ни здесь, ни где-либо ещё: убрать вызов из `discardWorkspaceDir` (`src/core/run/workspace.ts`), переведя её на `removeWorktree`. В комментарии — почему слепой prune снят: он снимает всякую осиротевшую запись чужого репозитория, а не только свою.
- [x] 1.7 Тесты `test/worktrees.test.ts` на стенде из репозитория и его worktree внутри временного каталога прогона: снятие убирает и каталог, и запись; снятие уже снесённого каталога убирает запись по указателю; путь вне `runDir` — отказ, каталог цел; чужая запись того же репозитория переживает снятие.

## 2. Заведение частей при подготовке дерева

- [x] 2.1 `src/core/run/workspace.ts`: `PrepareOptions` получает объявленный состав (`nestedRepos`), `PreparedWorkspace` — перечень материализованных частей (`nested: { dir, repo }[]`, канонический порядок).
- [x] 2.2 В ветке `workspace.mode === 'worktree'` после корневого `addWorktree` завести часть на каждый объявленный каталог: репозиторий — `join(cwd, relDir)`, путь — `join(dir, relDir)`, состояние — `HEAD` репозитория части. Комментарий объясняет выбор `HEAD` части (не gitlink корня, не её рабочее дерево) — решение 2 design.md.
- [x] 2.3 Атомарность: отказ на любой части снимает заведённые части в обратном порядке, затем корневое дерево (через ту же `discardWorkspaceDir`), и пробрасывает исходную причину. Отказ доезжает до вызывающего прежним `spawn_failed`, новой причины остановки не заводится.
- [x] 2.4 Продолжение цепочки (`source.kind === 'continue'`) частей не заводит и в перечень их не пишет: каталог предшественника уже с ними, а перечень принадлежит той работе, которая деревья завела.
- [x] 2.5 Развилка (`source.kind === 'seed'`): дерево заводится полностью — корень и части, — и только потом приводится `anchorer.restore`. Отказ приведения снимает всё заведённое тем же путём, что и сегодня.
- [x] 2.6 Тесты `test/workspace.test.ts`: часть материализована и является рабочим деревом собственного репозитория; незакоммиченная правка части в дерево не попала; рабочее дерево части в проекте и корневое дерево проекта не изменились (`status --porcelain`, `HEAD`, индекс); отказ на второй части не оставляет ни каталогов, ни учётных записей; режим `cwd` при том же составе ведёт себя как прежде.

## 3. Предстартовые проверки и статическая диагностика

- [x] 3.1 `checkWorkspaceAvailability`: отказ изолированным режимам при объявленном составе сузить до `copy` — своё сообщение, своя причина (копия не содержит `.git`, часть в ней была бы каталогом без репозитория).
- [x] 3.2 Там же: при работе в режиме `worktree` и объявленном составе требовать коммит в каждой части независимо от игнорирования корнем — сегодняшнее послабление (`hasCommit` только при `!ignoredByRoot`) относится к корневому `add -A` и на `worktree add … HEAD` не распространяется. Сообщение называет каталог и причину.
- [x] 3.3 Там же: отказ, если корневой репозиторий отслеживает файлы по пути части (`git -C <корень> ls-files -- <relDir>/` непусто) — выкладка корня займёт каталог. Сообщение называет каталог и причину; на gitlink и на игнорируемую часть отказ не распространяется.
- [x] 3.4 `src/core/lint.ts`: та же тройка статически — `copy` при объявленном составе, часть без коммита и занятый путь при `worktree`, — с файлом работы и путём `jobs.<id>.workspace.mode`. Формулировки совпадают с отказами прогона.
- [x] 3.5 Тесты `test/workspace.test.ts` и `test/lint.test.ts`: каждый отказ срабатывает до первой работы и называет своё; `worktree` при пригодном составе больше не отказывает; в режиме `cwd` часть без коммита, игнорируемая корнем, по-прежнему допустима.

## 7. Сквозной сценарий

- [x] 7.1 Стенд: корневой репозиторий, две объявленные части (одна игнорируемая корнем, одна отслеживаемая gitlink'ом), пайплайн из двух работ в режиме `worktree` с `lane`.
- [x] 7.2 Проверка дерева: обе части материализованы, у каждой своя база объектов и свой `HEAD`; правка внутри части даёт путь с префиксом в `changed_only` и в `diff.patch`; работы не видят правок друг друга ни в корне, ни в частях.
- [x] 7.3 Проверка радиуса: правки в двух частях и в корне, приведение путей одной части — остальные правки целы; рабочие деревья проекта (корень и обе части) не тронуты за весь прогон.
- [x] 7.4 Проверка уборки: после удаления прогона в обоих репозиториях частей и в корневом не осталось записей этого прогона, а заведённая посторонним рабочим деревом запись цела.
- [x] 7.5 Проверка наследования: работа-продолжение видит части предшественника с его правками; работа-развилка получает части, приведённые к состоянию источника.
- [x] 7.6 Регрессия режима `cwd`: прогон в том же дереве в режиме каталога запуска даёт те же идентификаторы состояния, тот же способ фиксации и ту же форму записей, что до изменения.
