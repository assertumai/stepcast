## Why

Имя модели во всём репозитории существует только как строка, которую кто-то
однажды напечатал. Страница «Агенты» (`ui/src/pages/Agents.tsx`) принимает
свободным вводом и модель по умолчанию, и каждый из пяти tier'ов (`max`,
`deep`, `balance`, `fast`, `mini`); проверка на стороне демона —
`ModelNameSchema` (`src/core/config/schema.ts:8`) — требует лишь непустой
строки. Опечатка сохраняется молча и становится видна отказом бэкенда уже
внутри захода петли: у codex это `turn.failed` со `status: 400` (запись
`test/fixtures/codex/run3.jsonl` снята ровно на `-m no-such-model-xyz`), то
есть ценой попытки агентского шага.

Ни витрина, ни движок не знают, какие модели у агента вообще есть. Весь
«список моделей» репозитория — два литерала: `default_model: 'sonnet'`
(`src/core/config/defaults.ts`) и `default_model: 'gpt-5.6-terra'`
(`src/backends/codex/index.ts`). Устарело умолчание плагина или нет — нельзя
узнать, не сверяясь с CLI руками, и с приходом пяти tier'ов таких значений
стало по шесть на каждого агента.

Спрашивать про модели у витрины неправильно: набор моделей — свойство агента,
и место ему там же, где живут флаги его CLI, — во вкладе бэкенда, рядом с
`defaults`. Витрине остаётся показать распознанное и не потерять уже
сохранённое.

Отдельно мешает то, что выбранное имя приходится переносить в `model:`
пайплайна или работы (`schema/pipeline.schema.json`) перепечатыванием с
экрана — тот же источник опечаток, ради которого затевается распознавание.

**Оговорка к признаку выполненности.** «Распознавание работает для claude и
codex» упирается в то, что CLI действительно умеет ответить. Проверено
2026-09-09 на машине разработчика: `claude --help` не содержит ни подкоманды
перечисления моделей, ни флага вроде `--list-models`; единственное место, где
CLI сам называет модели, — описание `--model` в его же справке (псевдонимы
`fable`, `opus`, `sonnet`, пример полного имени `claude-fable-5`). Поэтому
изменение вводит перечисление как объявляемое свойство бэкенда с честным
«не распознано» вместо выдуманного списка: адаптер, которому CLI ответить
нечем, пробы не объявляет, и страница говорит это словами, а не притворяется
знающей. Константный список моделей в коде адаптера отвергнут прямо: это та
самая гниль, из-за которой пункт заведён (разбор — в `design.md`).

**Что из признака выполненности осталось незакрытым.** Половина «распознавание
работает для claude и **codex**» не сделана: вклад codex перечисления не
объявляет. Причина — не свойство CLI, а ограничение исполнителя: запуск
`codex` любой подкомандой отклоняется политикой песочницы всех сессий, в
которых велась работа над пунктом (проверено на этапе `propose`, при
реализации и ещё раз при разборе ревью — `codex --help` отвечает «This command
requires approval»). Снять справку неоткуда, а сочинять её флаги запрещено
практикой репозитория. Доделывается это в среде, где запуск `codex` разрешён:
одной пробой во вкладе `src/backends/codex/index.ts` и снятой фикстурой, не
трогая ни контракт, ни движок, ни витрину — то есть отдельным пунктом очереди с
собственным признаком выполненности, а не переписыванием этого.

## What Changes

- **Вклад бэкенда объявляет перечисление моделей.** У `BackendContribution`
  появляется необязательное поле `models` рядом с `defaults`: запуск-проба
  (`LaunchSpec` по действующей записи `backends.<имя>`) и разбор её вывода в
  список имён. Флаги и формат ответа конкретного CLI остаются во вкладе, как
  и всё остальное про CLI; поле публично и документируется в `docs/plugins.md`.
- **Пробу исполняет движок, а не плагин.** Новый модуль
  `src/core/backend/models.ts` запускает пробу тем же надзираемым `runProcess`,
  что и шаги: без оболочки, с отфильтрованным окружением бэкенда и с
  собственным небольшим таймаутом. Плагин не заводит своего `spawn`.
- **Отказ распознавания — назван, а не проглочен.** Результат перечисления —
  либо список, либо одна из различимых причин: бэкенд не объявил пробы, CLI не
  установлен, не ответил за отпущенное время, ответил отказом (сюда попадает и
  неавторизованность — текстом CLI как есть), ответил неразбираемым выводом,
  а также сорвавшееся исключением перечисление самого вклада. Пустой разбор
  означает «не распознано», а не «моделей нет».
- **Витрина спрашивает список отдельным маршрутом.** `GET /api/models`
  отдаёт по каждому известному агенту его список либо причину отказа;
  `/api/settings` остаётся прежним и отрисовывается, не дожидаясь дочерних
  процессов. Демон держит распознанное, пока жив, и обновляет по явному
  требованию страницы — кнопкой «перечислить заново», которой чинится и
  застывший отказ.
- **Страница «Агенты» выбирает модель из списка.** Модель по умолчанию и
  каждый из пяти tier'ов выбираются из распознанного списка своего агента.
  Сохранённое значение, которого в списке нет, остаётся выбранным и помечается
  как значение вне списка. Ручной ввод остаётся доступен всегда — распознанный
  список неполон по устройству и не становится ни запретом, ни валидацией
  сохранения.
- **Рядом с каждым полем модели — копирование значения.** Кнопка кладёт имя
  модели в буфер, чтобы вставить его в `model:` пайплайна или работы; отказ
  буфера обмена сообщается, а не проглатывается.
- **BREAKING**: нет. Поле `models` необязательно: существующие адаптеры
  плагинов работают без правок, а бэкенд без пробы ведёт себя на странице так
  же, как сегодня, — свободным вводом с объяснением.

## Capabilities

### New Capabilities

(нет — перечисление принадлежит уже объявленной способности `agent-backend`,
страница «Агенты» — `ui-dashboard`)

### Modified Capabilities

- `agent-backend`: вклад бэкенда объявляет способ перечислить доступные ему
  модели; пробу исполняет движок под надзором и с таймаутом, а её недоступность
  различима по причине и не является отказом.
- `ui-dashboard`: страница «Агенты» выбирает модель по умолчанию и модель
  каждого tier'а из распознанного списка, не теряет сохранённое значение вне
  списка, переживает недоступность распознавания и даёт скопировать имя
  модели.

## Impact

- Изменяется: `src/core/plugins/contract.ts` — поле `models` вклада и его
  проверка формы при загрузке; `src/plugin.ts` — публичный экспорт типов
  перечисления; `src/core/backend/types.ts` — формы `BackendModel` и вывода
  пробы; `src/core/backend/claude.ts` и `src/backends/codex/index.ts` — пробы
  двух бэкендов; `src/ui/server.ts`, `src/ui/routes.ts` — маршрут `/api/models`;
  `ui/src/api.ts`, `ui/src/pages/Agents.tsx`, `ui/src/styles.css` — выбор из
  списка и копирование.
- Добавляется: `src/core/backend/models.ts` — запуск пробы, классификация
  отказа, кэш распознанного для демона.
- Не изменяется: `src/core/config/schema.ts` и `schema/config.schema.json` —
  нового ключа конфигурации изменение не заводит; `ModelNameSchema` остаётся
  прежней, распознанный список не валидирует сохранение (обоснование — в
  `design.md`); `src/core/backend/registry.ts` — контракт `BackendAdapter` не
  меняется.
- Тесты: `test/backend-models.test.ts` (новый) — разбор вывода пробы,
  неразбираемый вывод, отсутствующая команда, зависшая команда, ненулевой код
  возврата; `test/backend.test.ts` и `test/codex-adapter.test.ts` — проба
  собирается из команды и окружения записи `backends.<имя>`;
  `test/plugin-surface.test.ts` и `test/plugin-load.test.ts` — новое поле
  вклада на публичной поверхности и его проверка формы; `test/ui-server.test.ts`
  — `/api/models`, отказ пробы не роняет `/api/settings`. Фикстуры вывода
  снимаются с установленных CLI по практике `test/fixtures/codex/README.md`:
  сочинённых записей в тестах не заводится.
- Документация: `docs/plugins.md`, раздел «Бэкенд» — объявление перечисления и
  его необязательность; `docs/config.md`, раздел «Агенты и модели» — откуда
  берётся список на странице, что значит «вне списка» и почему ручной ввод
  остаётся.
