## 1. Слой модели в раскрытии

- [x] 1.1 `src/core/pipeline/model.ts`: тип `ModelOrigin` — пять различимых
      исходов (`step`, `pipeline`, `config` с источником, `backend` с именем
      бэкенда, `none`) и поле `modelOrigins: ReadonlyMap<string, ModelOrigin>`
      в `ExpandedPipeline`. Ключ карты — `<job>/<step>`. Комментарий у поля
      называет, почему слой не лежит в `Step`: `computeStepKey` хеширует `Step`
      целиком, и справочное поле обнулило бы переиспользование шагов прошлых
      прогонов (design.md, Решение 1).
- [x] 1.2 `src/core/pipeline/expand.ts`: `toStep` возвращает вместе с шагом
      звено, давшее модель, — там же, где считается `raw.model ??
      defaults.model ?? backend?.defaultModel`. Различение `step` и `pipeline`
      берётся у уже посчитанных `doc.defaults?.model` и `config.defaults.model`
      (строка 751), а не сравнением строк: одинаковые значения на разных слоях
      обязаны остаться различимыми.
- [x] 1.3 Слой `config` файла не называет, и `ExpandOptions` провенансом не
      обрастает: файл подписывает витрина из своего `resolveConfig` по корню
      проекта (design.md, Решение 1). Проверить, что ни один вызов
      `expandPipeline` менять не пришлось.
- [x] 1.4 `expandPipeline` собирает карту по всем работам и шагам и кладёт её в
      результат. Командные шаги в карту не попадают вовсе — у них модели нет.
- [x] 1.5 Убедиться, что `src/core/pipeline/lock.ts` (`pipelineToPlain`,
      `jobLockHash`) и `src/core/run/stepKey.ts` правки не потребовали. Если
      потребовали — слой попал в `Pipeline`, и это ошибка реализации, а не
      повод менять ключ.
