## MODIFIED Requirements

### Requirement: Применение бюджета

Бюджеты SHALL объявляться на уровнях пайплайна, работы и шага и быть
необязательными. Бюджет пайплайна MUST накапливаться по всему прогону, бюджеты
работы и шага MUST ограничивать свою область. Величина токенов MUST считаться
как сумма входных и выходных токенов, записи в кеш и чтения из кеша с весом,
заданным для бэкенда. При превышении любого из действующих потолков текущий шаг
MUST прерываться. Исход превышения MUST определяться режимом `on_exceed` той
области, чей потолок упёрся первым: при `stop` соответствующая область MUST
получать статус `budget_exceeded`, при `wait` система MUST ожидать сброса окна
лимита и продолжать прогон.

Режим `wait` MUST приводить к ожиданию только при превышении потолка
`rate_limit_pct` и только когда бэкенд сообщил момент сброса окна. Превышение
потолка токенов или времени MUST останавливать область со статусом
`budget_exceeded` при любом режиме, поскольку эти потолки не сбрасываются.
Отсутствие сообщённого момента сброса и момент сброса, отстоящий дальше
объявленного предела ожидания, MUST приводить к остановке со статусом
`budget_exceeded`, а причина MUST называть, почему ожидание не состоялось.

Время, проведённое в ожидании, MUST NOT засчитываться в потолки `wallclock`
действующих областей. Попытка шага, прерванная ожиданием, MUST NOT расходовать
объявленное число попыток, а расход, снятый с неё, MUST оставаться учтённым.
После пробуждения прерванный шаг MUST исполняться заново.

#### Scenario: Превышение бюджета шага

- **WHEN** шаг превысил объявленный для него потолок токенов
- **THEN** его процесс прерывается, а шаг получает статус `budget_exceeded`

#### Scenario: Накопление по прогону

- **WHEN** сумма расхода всех работ достигла потолка пайплайна
- **THEN** прогон останавливается со статусом `budget_exceeded` и кодом возврата 3

#### Scenario: Чтение кеша учитывается с весом

- **WHEN** бэкенд сообщил чтение из кеша, а для него задан вес
- **THEN** в потолок засчитывается взвешенная величина, а в отчёте видна и исходная

#### Scenario: Бюджет не объявлен

- **WHEN** ни один уровень не объявляет бюджет
- **THEN** прогон исполняется без ограничения по расходу, а `stepcast lint` предупреждает об этом

#### Scenario: Ожидание сброса окна лимита

- **WHEN** область с `on_exceed: wait` превысила `rate_limit_pct`, а бэкенд
  сообщил момент сброса окна в пределах допустимого ожидания
- **THEN** текущий шаг прерывается, прогон ожидает до сообщённого момента и затем
  исполняет прерванный шаг заново
- **AND** прогон не получает статус `budget_exceeded`

#### Scenario: Ожидание не расходует попытки

- **WHEN** попытка шага прервана ожиданием сброса окна
- **THEN** число израсходованных попыток шага не увеличивается
- **AND** её расход остаётся учтённым в потолках всех действующих областей

#### Scenario: Ожидание не съедает потолок времени

- **WHEN** прогон с потолком `wallclock` провёл часть времени в ожидании сброса окна
- **THEN** это время не засчитывается в потолки `wallclock` прогона, работы и шага

#### Scenario: Момент сброса неизвестен

- **WHEN** область с `on_exceed: wait` превысила `rate_limit_pct`, но бэкенд не
  сообщил момента сброса окна
- **THEN** область получает статус `budget_exceeded`, а причина называет отсутствие момента сброса

#### Scenario: Сброс слишком далёк

- **WHEN** сообщённый момент сброса отстоит дальше объявленного предела ожидания
- **THEN** область получает статус `budget_exceeded`, а причина называет и предел, и сообщённый момент

#### Scenario: Режим wait не спасает от потолка токенов

- **WHEN** область с `on_exceed: wait` превысила потолок токенов
- **THEN** она получает статус `budget_exceeded` без ожидания

### Requirement: Поток событий

Система SHALL вести журнал событий построчно, по одной записи на событие, в
формате, допускающем чтение по мере поступления. Записи MUST включать начало и
завершение работ и шагов, попытки, непройденные предикаты, исключения по
запретам окружения и путей, предупреждения и остановки по бюджету, уход в
ожидание сброса окна лимита и пробуждение из него, обнаружение зависшего шага.

Запись об уходе в ожидание MUST называть область, измерение, порог, сообщённый
момент сброса и рассчитанную длительность ожидания, а запись о пробуждении —
фактическую длительность.

#### Scenario: Чтение на лету

- **WHEN** прогон исполняется
- **THEN** содержимое журнала событий доступно для чтения до его завершения

#### Scenario: Запись об исключении по запрету

- **WHEN** переменная окружения или путь контекста исключены по запрету
- **THEN** в журнале есть запись с именем и сработавшим шаблоном

#### Scenario: Запись об ожидании и пробуждении

- **WHEN** прогон ушёл в ожидание сброса окна лимита и затем продолжился
- **THEN** в журнале есть запись об уходе в ожидание с моментом сброса и запись о пробуждении с фактической длительностью

#### Scenario: Отменённое ожидание отличимо от завершённого

- **WHEN** спящий прогон отменён пользователем
- **THEN** в журнале есть запись об уходе в ожидание без парной записи о пробуждении

### Requirement: Состояние достаточно для продолжения

Файл `status.json` SHALL содержать идентификатор прогона, имя пайплайна, входы,
статус каждой работы, для упавшей работы — идентификатор шага, номер попытки,
непройденные предикаты, выдержку из вывода и путь к полному журналу, а также
израсходованную и предельную величины бюджета. Для прогона, полученного
возобновлением, состояние MUST содержать идентификатор исходного прогона. Для
каждой работы состояние MUST содержать режим и путь её рабочей директории, а
для завершённых шагов — якорь состояния дерева. Команда возобновления в
состоянии MUST указывать точку, с которой имеет смысл продолжать.

Прогон, уходящий в ожидание сброса окна лимита, MUST дописывать своё состояние
на диск до начала ожидания, и это состояние MUST содержать момент пробуждения.
Момент пробуждения MUST исчезать из состояния после продолжения прогона.

#### Scenario: Отказ описан полностью

- **WHEN** работа завершилась отказом
- **THEN** `status.json` позволяет назвать упавший шаг, непройденный предикат и путь к его логу без обращения к другим файлам

#### Scenario: Состояние дописывается при прерывании

- **WHEN** прогон прерван
- **THEN** `status.json` содержит статусы всех работ на момент прерывания

#### Scenario: Происхождение возобновлённого прогона

- **WHEN** прогон создан возобновлением
- **THEN** `status.json` содержит идентификатор исходного прогона

#### Scenario: Рабочая директория работы описана

- **WHEN** работа исполнялась в изолированном режиме
- **THEN** `status.json` содержит режим и путь её рабочей директории

#### Scenario: Спящий прогон отличим от зависшего

- **WHEN** прогон ожидает сброса окна лимита
- **THEN** `status.json` уже содержит момент пробуждения, и он доступен для чтения во время ожидания
