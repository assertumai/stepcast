## MODIFIED Requirements

### Requirement: Состав директории прогона

Директория прогона SHALL содержать манифест `run.json`, зафиксированный
`pipeline.lock.yml`, состояние `status.json`, поток событий `events.ndjson`,
сводку расхода `usage.json`, каталог `artifacts/` и каталог `jobs/` с
покаталожной раскладкой работ и шагов. Раскладка шагов работы с циклом MUST
содержать промежуточный уровень итерации; раскладка работы без цикла MUST
оставаться без него.

#### Scenario: Раскладка шага

- **WHEN** шаг исполнен
- **THEN** его каталог содержит `step.json`, `expect.json`, `stdout.log`, `stderr.log`, а для агентского шага дополнительно `context.json`, `prompt.txt` и `output.json`

#### Scenario: Нумерация и адресация шагов

- **WHEN** работа содержит несколько шагов
- **THEN** их каталоги упорядочены числовым префиксом, а адресация в командах и состоянии выполняется по идентификатору шага

#### Scenario: Уровень итерации

- **WHEN** работа объявляет цикл и выполнила несколько итераций
- **THEN** каталоги шагов сгруппированы по итерациям, а номер итерации входит в адресацию шага

#### Scenario: Изменение шага в рабочем дереве

- **WHEN** шаг изменил рабочее дерево
- **THEN** его каталог содержит `diff.patch`

### Requirement: Состояние достаточно для продолжения

Файл `status.json` SHALL содержать идентификатор прогона, имя пайплайна, входы,
статус каждой работы, для упавшей работы — идентификатор шага, номер попытки,
непройденные предикаты, выдержку из вывода и путь к полному журналу, а также
израсходованную и предельную величины бюджета. Для прогона, полученного
возобновлением, состояние MUST содержать идентификатор исходного прогона. Для
каждой работы состояние MUST содержать режим и путь её рабочей директории, а
для завершённых шагов — якорь состояния дерева. Команда возобновления в
состоянии MUST указывать точку, с которой имеет смысл продолжать.

#### Scenario: Отказ описан полностью

- **WHEN** работа завершилась отказом
- **THEN** `status.json` позволяет назвать упавший шаг, непройденный предикат и путь к его логу без обращения к другим файлам

#### Scenario: Состояние дописывается при прерывании

- **WHEN** прогон прерван
- **THEN** `status.json` содержит статусы всех работ на момент прерывания

#### Scenario: Происхождение возобновлённого прогона

- **WHEN** прогон создан возобновлением
- **THEN** `status.json` содержит идентификатор исходного прогона

#### Scenario: Рабочая директория работы описана

- **WHEN** работа исполнялась в изолированном режиме
- **THEN** `status.json` содержит режим и путь её рабочей директории

### Requirement: Ключ шага вычисляется, записывается и определяет переиспользование

Для каждого шага система SHALL вычислять ключ от нормализованного определения
шага, развёрнутых промпта и контекста, идентификатора и версии бэкенда, модели,
выходов работ выше по графу и отпечатка входов шага, и записывать его в
`step.json`. Вычисленный ключ SHALL быть единственным основанием для решения о
переиспользовании результата шага из другого прогона. Отпечаток входов и его
происхождение MUST записываться рядом с ключом, чтобы решение о валидности
можно было объяснить без повторного вычисления.

#### Scenario: Одинаковые условия дают одинаковый ключ

- **WHEN** шаг исполняется дважды на неизменном рабочем дереве с теми же входами
- **THEN** вычисленные ключи совпадают

#### Scenario: Изменение промпта меняет ключ

- **WHEN** изменён файл промпта шага
- **THEN** вычисленный ключ отличается от предыдущего

#### Scenario: Изменение рабочего дерева меняет ключ

- **WHEN** между прогонами изменён файл, входящий в отпечаток входов шага
- **THEN** вычисленный ключ отличается от записанного в прошлом прогоне

#### Scenario: Совпадение ключа — основание для переиспользования

- **WHEN** ключ шага совпал с ключом успешного шага исходного прогона
- **THEN** шаг признан валидным и его результат берётся из исходного прогона

#### Scenario: Решение объяснимо по записи

- **WHEN** шаг признан невалидным
- **THEN** его запись содержит отпечаток входов и его происхождение, достаточные, чтобы назвать причину

## ADDED Requirements

### Requirement: Переиспользованный шаг отличим от исполненного

Запись переиспользованного шага SHALL содержать признак переиспользования и
идентификатор прогона-источника. Расход и протокол попыток такого шага MUST
браться из источника и MUST NOT учитываться повторно в расходе нового прогона.

#### Scenario: Признак и источник

- **WHEN** шаг переиспользован из прошлого прогона
- **THEN** его запись содержит признак переиспользования и идентификатор источника

#### Scenario: Расход не удваивается

- **WHEN** прогон переиспользовал шаги
- **THEN** сводка расхода нового прогона показывает расход переиспользованных шагов отдельно и не включает его в израсходованный бюджет

### Requirement: События возобновления и итераций

Поток событий SHALL содержать записи о переиспользовании шага, о восстановлении
рабочего дерева по якорю, о начале и завершении итерации цикла и о результате
предикатов `check` итерации.

#### Scenario: Событие переиспользования

- **WHEN** шаг переиспользован
- **THEN** в потоке событий есть запись с идентификаторами шага и прогона-источника

#### Scenario: Событие восстановления дерева

- **WHEN** рабочее дерево восстановлено по якорю
- **THEN** в потоке событий есть запись с якорем и путём рабочей директории

#### Scenario: События итерации

- **WHEN** работа с циклом выполнила итерацию
- **THEN** в потоке событий есть записи о её начале, завершении и исходе предикатов `check`
