## Why

Три команды объявлены в формате с самого начала (`docs/run-layout.md` перечисляет их в общем CLI-разделе), но ни одна не зарегистрирована — `stepcast gc`, `stepcast init`, `stepcast context` завершаются «неизвестная команда». Это три разных недостатка обкатки одного и того же инструмента:

без `gc` каталог `~/.stepcast/runs/` растёт без предела — рабочие деревья `worktree`/`copy` и логи каждого шага копятся вечно, а инструмент, задуманный для частых повторных прогонов при отладке пайплайна, штрафует именно за частое использование;

без `init` порог входа в новый проект — вручную писать `stepcast.yml` и файл работы, сверяясь с `docs/pipeline-format.md`, вместо одной команды;

без `context` пользователь не может проверить состав и размер контекста до запуска — единственный способ узнать, что глоб в `context:` подхватил лишнее, это заплатить за отправку и увидеть `context.json` уже после того, как бюджет списан.

Все три — независимые, некрупные команды, не требующие новой инфраструктуры: работают поверх уже существующих `core/journal/`, `core/context/assemble.ts` и формата пайплайна. Идут одним изменением, потому что каждая — маленький, самодостаточный кусок работы над одним и тем же пробелом «команда объявлена, но не реализована», а не потому что они архитектурно связаны.

Четвёртая объявленная команда, `stepcast ui`, сознательно не входит: она требует SQLite-индекса поверх файлового журнала, локального веб-сервера и фронтенда — на порядок больше по объёму и заслуживает отдельного design-обсуждения, а не довеска к трём CLI-утилитам.

## What Changes

- **`stepcast gc [--older-than <duration>]`** — удаляет прогоны целиком: рабочие деревья (`workspace/`), каталог шагов (`jobs/`, включая логи, промпты, `context.json`, `expect.json`), `artifacts/`, служебные файлы якоря (`anchors/`), `pipeline.lock.yml`, `events.ndjson`. Сохраняет `run.json`, `status.json`, `usage.json` — минимум, достаточный для того, чтобы прогон остался виден в истории и в `stepcast usage`. Без `--older-than` — только отчёт (кандидаты и сколько места освободится), ничего не удаляет; с `--older-than` — реально удаляет прогоны старше указанного возраста, посчитанного по времени завершения прогона (`finished_at` из `run.json`). Без интерактивных подтверждений: у CLI нет ни одного прецедента чтения stdin для диалога с пользователем, и `gc` не станет первым — явный флаг важнее скрытого prompt'а.
- **`stepcast init`** — создаёт `stepcast.yml` в текущем каталоге по минимальному рабочему шаблону (командный шаг, без зависимости от агентского бэкенда — чтобы `stepcast init && stepcast run stepcast.yml` работал сразу после установки) и отдельный файл примера работы, подключаемый через `uses`, — чтобы показать оба способа описания работы, а не только «на месте». Отказывается перезаписывать существующий `stepcast.yml` без явного согласия.
- **`stepcast context [--job <job>] [--step <step>]`** — печатает состав и размер контекста, который получил бы указанный шаг, без запуска пайплайна и без обращения к бэкенду: выходы предшественников, уровень пайплайна, уровень работы, уровень шага, итог — тот же четырёхуровневый разрез, что уже пишется в `context.json` при живом прогоне. Выходы предшественников оцениваются по `artifacts/<job>.json` последнего прогона проекта, если он есть; при его отсутствии уровень помечается как неизвестный, а не нулевой — молчаливый ноль выглядел бы как «предшественник ничего не публикует», что неверно.

Сознательно вне объёма: `stepcast ui`, `stepcast runs` (список прогонов — используется `gc` внутри через уже существующий `listRuns`, но отдельной командой не становится в этом изменении).

**BREAKING**: нет. Все три команды сегодня не зарегистрированы; добавление новых команд не меняет поведения существующих.

## Capabilities

### New Capabilities

- `run-cleanup`: команда `stepcast gc`, отбор прогонов по возрасту, минимальный набор файлов, переживающих уборку, отчёт без действия при отсутствии `--older-than`.
- `project-init`: команда `stepcast init`, шаблон пайплайна и файла работы, защита от перезаписи существующего `stepcast.yml`.
- `context-preview`: команда `stepcast context`, отчёт о составе и размере контекста без запуска пайплайна, источник данных о выходах предшественников.

### Modified Capabilities

- `run-journal`: требование о минимальном наборе файлов, переживающих уборку (`run.json`, `status.json`, `usage.json`), фиксируется как часть контракта директории прогона — раньше только упоминалось в `docs/run-layout.md`, не было проверяемым требованием.

## Impact

- Новый код: `src/cli/commands/gc.ts`, `src/cli/commands/init.ts`, `src/cli/commands/context.ts`, регистрация в `src/cli/main.ts`.
- Переиспользуется без изменений: `core/journal/reader.ts` (`listRuns`, `resolveRun`, `readManifest`), `core/journal/paths.ts` (`RunPaths`), `core/context/assemble.ts` (`assembleContext`), `core/units.ts` (`parseDuration`), `core/pipeline/expand.ts` (для `context` — нужно раскрытие пайплайна без запуска).
- Файловая система: `gc` удаляет каталоги внутри `~/.stepcast/runs/<project>/<run>/`; `init` создаёт `stepcast.yml` и файл работы в текущем каталоге. Обе операции необратимы с точки зрения пользователя, поэтому обе требуют явного намерения флагом: `gc` без `--older-than` только отчитывается и ничего не удаляет; `init` поверх существующего `stepcast.yml` отказывается без `--force`.
- Документация: `docs/status.md` — три строки уезжают из «Пока нет» в «Работает»; `docs/run-layout.md` уже описывает `gc` и его семантику, `docs/pipeline-format.md` уже показывает пример вывода `stepcast context` — существенных правок по существу не требуется, только снятие статуса «не реализовано».
