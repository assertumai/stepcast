## ADDED Requirements

### Requirement: Директория прогона вне проекта

Каждый прогон SHALL создавать собственную директорию в корне прогонов,
сгруппированную по проекту. Ключ проекта MUST вычисляться от реального пути его
корня, а соответствие ключа и пути MUST сохраняться в общем указателе. Журнал
прогона MUST лежать вне рабочей директории проекта независимо от режима её
выбора.

#### Scenario: Изоляция прогонов разных проектов

- **WHEN** прогоны запускаются из двух разных проектов
- **THEN** их директории лежат под разными ключами проекта

#### Scenario: Указатель на проект

- **WHEN** прогон создан
- **THEN** указатель проектов содержит соответствие ключа и реального пути корня проекта

#### Scenario: Права доступа

- **WHEN** директория прогона создана
- **THEN** права дерева ограничены владельцем

### Requirement: Состав директории прогона

Директория прогона SHALL содержать манифест `run.json`, зафиксированный
`pipeline.lock.yml`, состояние `status.json`, поток событий `events.ndjson`,
сводку расхода `usage.json`, каталог `artifacts/` и каталог `jobs/` с
покаталожной раскладкой работ и шагов.

#### Scenario: Раскладка шага

- **WHEN** шаг исполнен
- **THEN** его каталог содержит `step.json`, `expect.json`, `stdout.log`, `stderr.log`, а для агентского шага дополнительно `context.json`, `prompt.txt` и `output.json`

#### Scenario: Нумерация и адресация шагов

- **WHEN** работа содержит несколько шагов
- **THEN** их каталоги упорядочены числовым префиксом, а адресация в командах и состоянии выполняется по идентификатору шага

### Requirement: Состояние достаточно для продолжения

Файл `status.json` SHALL содержать идентификатор прогона, имя пайплайна, входы,
статус каждой работы, для упавшей работы — идентификатор шага, номер попытки,
непройденные предикаты, выдержку из вывода и путь к полному журналу, а также
израсходованную и предельную величины бюджета.

#### Scenario: Отказ описан полностью

- **WHEN** работа завершилась отказом
- **THEN** `status.json` позволяет назвать упавший шаг, непройденный предикат и путь к его логу без обращения к другим файлам

#### Scenario: Состояние дописывается при прерывании

- **WHEN** прогон прерван
- **THEN** `status.json` содержит статусы всех работ на момент прерывания

### Requirement: Поток событий

Система SHALL вести журнал событий построчно, по одной записи на событие, в
формате, допускающем чтение по мере поступления. Записи MUST включать начало и
завершение работ и шагов, попытки, непройденные предикаты, исключения по
запретам окружения и путей, предупреждения и остановки по бюджету, обнаружение
зависшего шага.

#### Scenario: Чтение на лету

- **WHEN** прогон исполняется
- **THEN** содержимое журнала событий доступно для чтения до его завершения

#### Scenario: Запись об исключении по запрету

- **WHEN** переменная окружения или путь контекста исключены по запрету
- **THEN** в журнале есть запись с именем и сработавшим шаблоном

### Requirement: Логи пригодны для чтения и сравнения

Стандартные потоки шага SHALL сохраняться построчным текстом без управляющих
последовательностей. Команда `scarp logs` MUST показывать логи указанного шага
или всего прогона и MUST поддерживать подключение к исполняющемуся прогону.

#### Scenario: Логи завершённого шага

- **WHEN** пользователь запрашивает логи конкретного шага
- **THEN** выводится содержимое его стандартных потоков

#### Scenario: Подключение к идущему прогону

- **WHEN** пользователь запрашивает логи с сопровождением во время прогона
- **THEN** новые строки появляются по мере их записи

### Requirement: Ключ шага вычисляется и записывается

Для каждого шага система SHALL вычислять ключ от нормализованного определения
шага, развёрнутых промпта и контекста, идентификатора и версии бэкенда, модели,
выходов работ выше по графу и отпечатка рабочего дерева, и записывать его в
`step.json`.

#### Scenario: Одинаковые условия дают одинаковый ключ

- **WHEN** шаг исполняется дважды на неизменном рабочем дереве с теми же входами
- **THEN** вычисленные ключи совпадают

#### Scenario: Изменение промпта меняет ключ

- **WHEN** изменён файл промпта шага
- **THEN** вычисленный ключ отличается от предыдущего

### Requirement: Непрерывный учёт расхода

Расход SHALL сниматься по мере поступления данных от бэкенда, а не только по
завершении попытки. Запись расхода MUST вестись на каждую попытку и
агрегироваться по шагам, работам и прогону в `usage.json`.

#### Scenario: Учёт до завершения шага

- **WHEN** агентский шаг исполняется и бэкенд сообщил промежуточный расход
- **THEN** израсходованная величина в состоянии прогона обновлена до завершения шага

#### Scenario: Агрегация

- **WHEN** прогон завершён
- **THEN** `usage.json` содержит суммы по попыткам, шагам, работам и прогону целиком

### Requirement: Отчёт о расходе

Команда `scarp usage` SHALL показывать расход прогона с разбивкой по работам и
шагам и распределением по номеру попытки. Измерения, не сообщаемые бэкендом,
MUST помечаться как отсутствующие.

#### Scenario: Шаги, проходящие не с первой попытки

- **WHEN** пользователь запрашивает отчёт о расходе
- **THEN** видно, какие шаги завершались успехом не с первой попытки и сколько это стоило

#### Scenario: Неполный учёт помечен

- **WHEN** бэкенд не сообщает одно из измерений расхода
- **THEN** отчёт помечает это измерение как несообщаемое, а не выводит ноль

### Requirement: Применение бюджета

Бюджеты SHALL объявляться на уровнях пайплайна, работы и шага и быть
необязательными. Бюджет пайплайна MUST накапливаться по всему прогону, бюджеты
работы и шага MUST ограничивать свою область. Величина токенов MUST считаться
как сумма входных и выходных токенов, записи в кеш и чтения из кеша с весом,
заданным для бэкенда. При превышении любого из действующих потолков текущий шаг
MUST прерываться, а соответствующая область MUST получать статус
`budget_exceeded`.

#### Scenario: Превышение бюджета шага

- **WHEN** шаг превысил объявленный для него потолок токенов
- **THEN** его процесс прерывается, а шаг получает статус `budget_exceeded`

#### Scenario: Накопление по прогону

- **WHEN** сумма расхода всех работ достигла потолка пайплайна
- **THEN** прогон останавливается со статусом `budget_exceeded` и кодом возврата 3

#### Scenario: Чтение кеша учитывается с весом

- **WHEN** бэкенд сообщил чтение из кеша, а для него задан вес
- **THEN** в потолок засчитывается взвешенная величина, а в отчёте видна и исходная

#### Scenario: Бюджет не объявлен

- **WHEN** ни один уровень не объявляет бюджет
- **THEN** прогон исполняется без ограничения по расходу, а `scarp lint` предупреждает об этом
