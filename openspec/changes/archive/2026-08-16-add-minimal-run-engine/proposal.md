## Why

Формат и модель данных stepcast зафиксированы в `docs/`, но кода нет, и два
несущих допущения дизайна проверить нечем: действительно ли агентский бэкенд
продолжает сессию по идентификатору между шагами, и что показывает
`cache_read_input_tokens` на втором шаге общей сессии. От первого зависит вся
модель сессий, от второго — единственный оставшийся источник экономии на
контексте. Оба проверяются только живым прогоном.

Нужен тонкий вертикальный срез: пайплайн из нескольких работ, исполняемый
последовательно в текущем каталоге, с настоящим вызовом Claude Code через pipe,
записью прогона на диск и учётом расхода. Он делает продукт запускаемым, снимает
неопределённость по обоим допущениям и задаёт скелет, в который остальные
возможности добавляются по одной.

## What Changes

- CLI `stepcast` на Node + TypeScript: `lint`, `run`, `status`, `logs`, `usage`,
  `config`. Коды возврата по контракту из `docs/run-layout.md`.
- Разбор `stepcast.yml` и файлов работ, раскрытие `uses`/`with`, наследование
  `defaults`, подстановка `${inputs.*}`, `${params.*}`, `${jobs.*.output.*}`,
  `${run.*}`, `${env.*}`.
- Статическая валидация: циклы и неизвестные идентификаторы в `needs`, `needs`
  и `on`/`if`/`with` внутри файла работы, необязательные и лишние ключи в
  `with`, подстановка вывода модели в строковую форму `run`, переменная в `env`
  под запретом `env_deny`, превышение `limits`, нераскрываемые `uses`.
- Исполнение графа работ **последовательно**: топологический порядок, `needs`,
  `on`, `if`, `needs: all`, `fail_fast`, статусы работ и шагов.
- Шаги двух типов: `run` (argv и строка) и `agent` для бэкенда Claude Code
  через pipe со `stream-json`. Таймаут шага, детектор тишины, попытки с
  эскалацией.
- Сессии агента внутри работы: `shared` (умолчание), `per_step`, именованные
  алиасы. Унаследованный контекст уходит в первое сообщение сессии.
- Сборка контекста трёх уровней с автоматическим блоком выходов предшественников
  и режимами `inline`/`reference`/`auto`.
- Выход работы: структурированный JSON из указанного шага в `artifacts/<job>.json`.
- Предикаты `expect`: `exit_code`, `file_exists`, `schema`, `matches`,
  `not_matches`, `cmd`.
- Директория прогона: `run.json`, `status.json`, `events.ndjson`, `usage.json`,
  покаталожная раскладка шагов с `prompt.txt`, `context.json`, логами и
  `expect.json`.
- Непрерывный учёт расхода из потокового вывода и остановка по бюджету
  (`on_exceed: stop`).
- Конфигурация двух уровней с разрешением и объяснением происхождения значений.

Сознательно вне объёма этого изменения, чтобы срез остался обозримым:
`until`-циклы, режимы `worktree` и `copy`, `stepcast apply`, якорь дерева `tree_id`,
`resume`, `diff`, `gc`, `init`, `ui`, параллелизм, предикаты `judge` и
`changed_only`, бэкенд Codex, триггеры, секреты, `--budget` и `--resolve`
у линта. Каждое становится отдельным изменением поверх готового скелета.

**BREAKING**: нет, проект новый.

## Capabilities

### New Capabilities

- `stepcast-configuration`: разрешение конфигурации из глобального и проектного
  файлов, флагов и встроенных умолчаний; складывающиеся снизу запреты
  `env_deny` и `context.deny`; потолки `limits`; отчёт о происхождении значений.
- `pipeline-definition`: формат пайплайна и файла работы, раскрытие `uses` и
  `with`, наследование умолчаний, грамматика подстановок и единиц, правила
  разрешения путей, статическая валидация и её диагностика.
- `pipeline-execution`: построение графа работ, порядок исполнения, вычисление
  `on` и `if`, `needs: all`, `fail_fast`, отмена, итоговые статусы работ и
  прогона.
- `step-execution`: исполнение шагов `run` и `agent`, сборка окружения,
  таймаут и детектор тишины, попытки и эскалация, границы дочерних процессов.
- `agent-backend`: контракт адаптера агентского бэкенда — запуск через pipe,
  промпт через stdin, структурированный вывод по схеме, продолжение сессии по
  идентификатору, извлечение расхода и объявление собственных возможностей.
- `step-context`: сборка контекста трёх уровней, автоматический блок выходов
  предшественников, детерминированный порядок, `inline`/`reference`/`auto`,
  отказ от наследования, запреты по путям.
- `result-contract`: предикаты `expect` и их семантика, структурированный выход
  работы и его публикация в `artifacts/`.
- `run-journal`: раскладка директории прогона, `status.json` как достаточное
  состояние, поток событий, логи, ключ шага, учёт расхода и применение бюджета.

### Modified Capabilities

Нет — `openspec/specs/` проекта пуст, все возможности вводятся впервые.

## Impact

- Новый код: весь исходный код проекта, до сих пор в репозитории только
  документация и примеры.
- Зависимости: Node 22+, TypeScript, `zod` как единственный источник правды для
  схем и типов, `yaml`, `execa`, `ajv` для пользовательских схем вывода.
  Нативных зависимостей нет — запуск только через pipe, `node-pty` не нужен.
- Внешние: Claude Code CLI на машине разработчика; работа по подписке,
  учётные данные берёт сам CLI.
- Документация: `docs/pipeline-format.md`, `docs/run-layout.md` и
  `docs/config.md` описывают целевое состояние шире этого среза — по итогам
  реализации в них нужно пометить, что реализовано, а что ещё нет.
- Пример `examples/openspec-change.yml` использует `until` и потому этим срезом
  не запустится; понадобится вариант без цикла как проверочный.
