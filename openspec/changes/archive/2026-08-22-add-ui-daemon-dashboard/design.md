## Context

Источник правды по прогонам — файлы под `~/.stepcast/runs/`:

```
runs/
  projects.json          # ключ проекта → { path, last_run }
  <projectKey>/
    latest -> <runId>
    <runId>/
      run.json  pipeline.lock.yml  status.json  events.ndjson  usage.json
      artifacts/<job>.json
      jobs/<job>/steps/<NN-id>/{step,context,output,expect}.json prompt.txt *.log diff.patch
```

Всё это уже читается функциями `core/journal/reader.ts` (`readStatus`,
`readManifest`, `readUsage`, `readEvents`, `findStepDir`, `follow`). Две вещи,
которых там нет и которые нужны наблюдателю:

- **Читателя `projects.json` не существует** — файл только пишется
  (`RunJournal.updateProjectIndex`). Без него по корню прогонов не
  сориентироваться: ключ проекта — `sha256(realpath)[0:12]`, необратим, и по
  каталогу `a3f19c2b7e40/` нельзя сказать, какому проекту он принадлежит.
- **`listRuns(runsRoot, projectRoot)` требует путь проекта** и сам его хеширует,
  то есть отвечает на вопрос «прогоны вот этого проекта». Наблюдателю нужен
  обратный обход: «все проекты, какие есть в корне».

`follow()` уже даёт построчное чтение дописываемого файла опросом по таймеру —
на нём строится живое обновление, новой инфраструктуры не требуется.

Ограничение стиля, которое здесь придётся сознательно нарушить: в CLI сегодня
нет ни одного фонового процесса — каждая команда синхронна и завершается кодом
возврата, а единственная долго живущая команда (`stepcast logs --follow`)
блокирует терминал. Демон — первый фоновый процесс в инструменте, и именно
поэтому его жизненный цикл описан явно, а не оставлен на «запустится как-нибудь».

## Goals / Non-Goals

**Goals:**

- Один демон, поднятый однажды, наблюдает за всеми прогонами всех локальных
  проектов и подхватывает новые прогоны по мере появления, ничего не зная о
  том, кто и из какого терминала их запустил.
- Дашборд живёт без перезагрузки страницы: статусы, события и новые прогоны
  приезжают сами.
- По каждой работе видно вход (выходы предшественников, разрез контекста) и
  выход (`artifacts/<job>.json`), а файл журнала можно раскрыть и прочитать.
- Жизненный цикл демона предсказуем: запуск идемпотентен, остановка явная,
  осиротевший pid-файл не ломает следующий запуск.
- Демон только читает журнал: ничего не изменяет и не удаляет.

**Non-Goals:**

- Запуск, отмена, `resume` прогона из интерфейса — только наблюдение.
- Аутентификация, доступ по сети, наблюдение за чужими машинами.
- SQLite-индекс поверх журнала.
- Автозапуск браузера: команда печатает URL, открывает его пользователь.
- Применение `runs.keep`: настройка резолвится, но ретенцию сегодня никто не
  исполняет (уборка — дело `stepcast gc`), и демон её не начинает исполнять.
- Графики расхода во времени и агрегаты по истории — обзор показывает то, что
  записано, без аналитики.

## Decisions

### `up` и `down` вместо объявленного `ui`

Объявленное в `docs/run-layout.md` имя `ui` заменяется парой глаголов.
Основание — закономерность, уже сложившаяся в этом CLI: глаголы (`run`, `lint`,
`apply`, `resume`, `init`, `gc`) что-то делают, существительные (`config`,
`status`, `logs`, `context`) печатают и выходят. Команда, поднимающая процесс на
часы, — действие, и имя у неё должно быть глагольным.

Форма — `stepcast up` / `stepcast down`, а не подкоманды `ui start|stop`:
`parseArgs` в `src/cli/args.ts` не знает подкоманд, позиционные аргументы у него
просто строки, и ни одна команда сегодня не ветвится по позиционному глаголу.
Заводить эту ветвь ради одной команды дороже, чем две записи в `COMMANDS`.

Третьей команды — состояния демона — не заводится: `stepcast up` при уже
поднятом демоне печатает ровно эти сведения (URL, pid, время старта). Имя
`status` для этого недоступно и не должно быть занято: команда с таким именем
существует, реализована и означает состояние *прогона*; подмешивать к ней
демона значит заставить одну команду отвечать на два несвязанных вопроса и
изменить её сегодняшнее поведение без флагов.

### Демон по умолчанию, `--foreground` — по требованию

`stepcast up` порождает отсоединённый процесс (`spawn(process.execPath,
[bin, 'up', '--foreground'], { detached: true, stdio: ['ignore', log, log] })`
плюс `unref()`), печатает URL и завершается кодом 0. Причина простая: смысл
наблюдательного пункта в том, что он поднят всегда, а команда, занимающая
терминал, этому противоречит — её закрывают вместе с окном.

Отсоединённый процесс — заметный след на машине пользователя, поэтому он
уравновешен тремя вещами: явной остановкой (`stepcast down`), pid-файлом, по которому
процесс всегда можно найти, и тем, что демон ничего не пишет в журнал и не
слушает никого, кроме `127.0.0.1`.

`stepcast up --foreground` — тот же сервер в текущем терминале. Он же
используется как внутренняя точка входа для отсоединённого запуска: детей
порождает не отдельный скрипт, а та же команда с флагом, поэтому расхождения
между «как оно работает в фоне» и «как оно работает при отладке» не возникает.

### Pid-файл `~/.stepcast/ui.pid`, повторный запуск идемпотентен

Файл содержит `{ pid, port, started_at }`. Проверка живости —
`process.kill(pid, 0)`: сигнал 0 ничего не посылает, а только сообщает, есть ли
такой процесс и доступен ли он.

- Файла нет, либо процесс из него мёртв → файл (пере)записывается, демон
  поднимается. Осиротевший pid-файл после `SIGKILL` или перезагрузки машины
  не должен требовать ручной уборки — это ровно тот случай, где инструмент
  обязан справиться сам.
- Процесс жив → команда печатает URL и завершается кодом 0. Не ошибка: человек,
  набравший `stepcast up` дважды, хочет открыть дашборд, а не узнать, что
  он уже открыт. Печатаются URL, pid и время старта — этим повторный запуск
  закрывает потребность в отдельной команде о состоянии демона.
- Порт занят **не нашим** процессом (pid-файла нет, а `listen` даёт
  `EADDRINUSE`) → внятный отказ с указанием порта и настройки `ui.port`. Молча
  выбирать соседний порт нельзя: пользователь пойдёт по напечатанному URL, а
  прошлый демон продолжит висеть на настроенном.

### Один наблюдатель на демон, а не на подключение

Наблюдатель (`src/ui/watcher.ts`) запускается один раз при старте сервера и
раздаёт обновления всем подключённым клиентам. Альтернатива — свой опрос на
каждое SSE-соединение — умножает работу на число открытых вкладок при том, что
данные у всех одни и те же.

Наблюдатель опрашивает корень прогонов по таймеру (1 с — каталоги, в отличие
от `follow()` с его 200 мс на строку лога, меняются редко):

1. `readdirSync(runsRoot)` → ключи проектов; `projects.json` → человекочитаемые
   пути.
2. Для каждого проекта `readdirSync` → идентификаторы прогонов; новый каталог,
   которого не было в прошлом проходе, — это новый прогон.
3. Для каждого прогона `statSync(status.json).mtimeMs`; `status.json`
   перечитывается и разбирается только если mtime изменился. Без этого демон
   парсил бы весь журнал каждую секунду ради данных, которые почти всегда те же.

Изменение любого из трёх пунктов рождает новый обзор, который уходит клиентам
SSE-сообщением. Пересчёт целиком, а не диффинг по полям: файлы небольшие,
а «посчитать заново» вместо «кешировать и инвалидировать по частям» — уже стиль
движка (`stepcast gc` так считает размеры).

### Список проектов: каталоги — про существование, указатель — про имя

Что показывать, решают каталоги на диске; как это назвать — `projects.json`.
Указатель может отстать или быть повреждён (писатель это допускает: при
непрочитавшемся указателе он начинает с пустого), а каталог прогона существует
независимо от него.

Каталог проекта, которого нет в указателе, показывается своим ключом с явной
пометкой, что путь неизвестен, — не скрывается и не подписывается догадкой.
Обратное (запись в указателе без каталога) просто не показывается: прогонов
у такого проекта нет. Это та же линия, что уже проведена в `stepcast context`
для выходов предшественников: неизвестность не маскируется под данные.

### Адресация прогона в API — `<projectKey>/<runId>`

Идентификаторы прогонов содержат отметку времени и случайный хвост и на
практике не сталкиваются, но принадлежность прогона проекту — часть его
адреса, и API не должен полагаться на глобальную уникальность там, где
раскладка на диске её не гарантирует.

### Детальный снимок: `status.json` + мягкий разбор `pipeline.lock.yml` + файлы шага

`status.json` даёт исполнение (статусы, попытки, `reason`, `cause`).
`pipeline.lock.yml` даёт определение — промпт агентского шага, команду
командного, объявленный контекст, `needs`, `output`, — то, что нужно показать
как «вход» независимо от того, дошло ли дело до исполнения. Файлы шага дают
фактические данные: `context.json`, `output.json`, `artifacts/<job>.json`.

Лок разбирается мягко: `yaml.parse` в `unknown` и точечный доступ к полям по
имени, без Zod-схемы. Обратного парсера лока в проекте нет — есть только
сериализатор `pipelineToPlain`; заводить строгую схему ради витрины значит
расширять эту возможность далеко за её задачу. Неожиданное или отсутствующее
поле даёт пустое место в интерфейсе, а не отказ демона.

### Прогон, убранный `stepcast gc`, остаётся видимым

После уборки от прогона остаются `run.json`, `status.json`, `usage.json` —
ровно тот минимум, который `run-journal` объявляет достаточным, чтобы прогон
был виден в истории. Дашборд обязан показывать такой прогон в обзоре и
объяснять при раскрытии, что подробностей больше нет, — а не падать на
отсутствующем `pipeline.lock.yml` или `jobs/`. Это прямая проверка контракта,
зафиксированного изменением `add-gc-init-context-commands`.

### Просмотр файла: путь резолвится от каталога прогона, потолок 1 МБ

`GET /api/file?run=<projectKey>/<runId>&path=<относительный>`. Путь приходит от
самого сервера (в снимке), но проверяется всё равно: `path.resolve(runDir,
requested)` обязан остаться внутри `runDir`, иначе — код 400. Обработчик,
доверяющий пути «потому что мы его сами выдали», перестаёт быть верным ровно в
тот день, когда снимок начнут строить из чего-то ещё.

Потолок — 1 МБ: `stdout.log` агентского шага бывает крупным, и отдавать его
браузеру целиком незачем. Сверх потолка — первый мегабайт и признак усечения,
который интерфейс показывает явно.

### Только `127.0.0.1`, без аутентификации

Сервер слушает петлевой интерфейс. Это не полная защита — GET на `localhost`
может уйти с любой открытой вкладки, — но убирает грубый случай: демон,
доступный всей сети. Полноценная защита (токен в URL, проверка `Origin`) не
входит в v1 сознательно: инструмент локальный, однопользовательский и
исключительно читающий. Ограничение фиксируется в `docs/status.md` как
известное, а не остаётся молчаливым пробелом.

### Страница без бандлера, ассеты — строковой константой

Один HTML со встроенными CSS и vanilla JS. Обоснование то же, что у
собственного разборщика аргументов в `src/cli/args.ts`: страница простая
(список, раскрытия, `<pre>`), а фронтенд-фреймворк со сборкой — несоразмерный
довесок к пакету, который должен ставиться одной командой.

Ассеты живут строковыми константами в `src/ui/assets.ts`, а не отдельными
файлами, по причине сугубо технической: `npm run build` — это голый `tsc`, он
не копирует нескомпилируемые файлы в `dist/`. Заводить шаг копирования ради
одной страницы дороже, чем держать её в `.ts`, который компилируется сам. Тот
же приём уже применён для шаблонов `stepcast init`.

## Risks / Trade-offs

**Отсоединённый демон переживает терминал и может быть забыт** → Смягчение:
`stepcast down`, pid-файл с портом и временем старта, только чтение,
только петлевой интерфейс. Демон не переживает перезагрузку машины и не
прописывается в автозапуск.

**Опрос каталогов вместо уведомлений файловой системы** → Осознанный повтор
решения, уже принятого в `follow()`: уведомления приходят не на всех файловых
системах, включая сетевые, а секундный опрос десятков каталогов с
mtime-отсечкой обходится дешевле, чем ошибка «прогон не появился, потому что
уведомление не пришло».

**Демон видит прогоны всех проектов пользователя, включая посторонние** → Это
и есть его задача, но следствие стоит назвать: в дашборде окажутся имена
проектов и пути, которые пользователь мог не собираться показывать. Смягчение —
петлевой интерфейс и отсутствие какого-либо исходящего трафика.

**Мягкий разбор лока может показать пустоту там, где формат разошёлся** →
Приемлемо для витрины: строгую проверку по-прежнему дают `stepcast lint` и
`stepcast status`, а UI — дополнительный способ посмотреть, не единственный.

**Гонка на pid-файле при одновременном запуске двух `stepcast up`** → Проигравший
получит `EADDRINUSE`; поскольку к этому моменту pid-файл уже принадлежит
победителю, проигравший завершится с сообщением о занятом порте. Блокировки
файла не вводится: цена ошибки — одно понятное сообщение, а не порча данных.

## Migration Plan

Миграции нет: новая команда, новый читатель указателя, поведение существующих
команд не меняется, включая `stepcast status`. После реализации
`docs/status.md` — строка `stepcast ui` заменяется на `stepcast up` /
`stepcast down` и уезжает из «Пока нет» в «Работает» с оговоркой об отсутствии
аутентификации; в CLI-разделе `docs/run-layout.md` `stepcast ui` заменяется той
же парой, и уточняется, что наблюдение охватывает все проекты и работает без
SQLite.

## Open Questions

- Автозапуск браузера (`open`/`xdg-open`/`start`) — сейчас решено печатать URL,
  чтобы не тащить платформенную развилку; добавляется отдельно, если печати
  окажется мало.
- Нужна ли отдельная команда о состоянии демона (жив ли, на каком порту, с
  какого времени) помимо повторного `stepcast up`, который эти сведения уже
  печатает. Имя `status` занято состоянием прогона и освобождено не будет;
  свободное docker-подобное имя — `ps`, но оно конфликтует по смыслу с
  объявленным в документации `stepcast runs`. Заводится, только если на
  реализации найдётся случай, где повторного `up` не хватает.
- Поведение при смене `ui.port` в конфигурации при уже поднятом демоне: сейчас
  предполагается, что порт берётся из pid-файла, а не из конфигурации, — иначе
  команда напечатает URL, по которому никого нет. Проверяется на реализации.
