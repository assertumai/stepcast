## Context

`UsageAccumulator` хранит `startedAt` — момент своего создания, совпадающий с
началом прогона, — и отдаёт `elapsedMs()` как разницу с текущим моментом.
Проверка бюджета перебирает области от узкой к широкой и для каждой сравнивает
`elapsedMs()` с её `wallclock`. Токены при этом считаются по своей области
корректно; расходится только время.

## Goals / Non-Goals

**Goals:**

- Каждая область меряет своё время.
- Прогон продолжает мерить прогон.

**Non-Goals:**

- Считать время работы как сумму длительностей её шагов: `wallclock` — это
  именно календарное время, и промежутки между шагами из него не выпадают.
- Раздельный отсчёт по итерациям цикла: потолок работы ограничивает работу
  целиком, иначе четыре итерации по часу уложились бы в часовой потолок.

## Decisions

### Момент начала передаёт вызывающий, а не хранит учёт

Рассматривалось запоминать начало области в самом учёте — при первой проверке
по данному ключу. Отвергнуто: момент первой проверки не совпадает с началом
области, а для шага внутри цикла ключ повторяется на каждой итерации, и
«первая проверка» стала бы неопределённой.

Исполнитель знает моменты точно: начало работы — до подготовки первой итерации,
начало шага — перед его запуском. Он их и передаёт.

### Отсутствие момента означает прогон

Область прогона момента не несёт: он совпадает с созданием учёта. Так же
трактуется область, момент которой не передан, — это сохраняет прежнее
поведение для вызывающих, не знающих о новом поле.

## Risks / Trade-offs

**Работа с циклом получает больше времени, чем раньше** → раньше она получала
не больше, а неверно: остаток от времени прогона. Объявленный потолок начинает
означать объявленное.

**Пайплайн полагался на прежнее поведение как на общий дедлайн** → для этого
есть потолок прогона, и он работает именно так.
