# Задачи

Порядок — из плана миграции `design.md`: ядро и команды заводятся рядом с
работающими скриптами, тесты переписываются на движок до удаления скриптов, а
работы петли переводятся на команды в том же коммите, что и удаление, — петля
сводит саму себя этим же заходом и не имеет права остаться с работами,
зовущими исчезнувшие файлы. Каждая задача — код **и** тест; тест обязан падать
до правки.

Границу `changed_only` захода расширять не нужно: `src/**`, `test/**`,
`docs/**`, `scripts/**`, `.stepcast/jobs/**` и `openspec/changes/**` уже в ней.
`backlog.md` в границу не входит и в этом изменении не правится.

## 1. Ядро сведения дорожек

- [x] 1.1 `src/core/lanes/lanes.ts` — годность дорожки по `status.json`:
      разбор работ по метке `lane`, исход дорожки (годна / негодна с перечнем
      работ и их статусов / незаполненный слот, когда все работы `skipped`) и
      перечень дорожек, известных прогону. Критерий: ни одного сравнения
      идентификатора работы со строкой и ни одного суффикса имени; функция
      чистая — на входе запись состояния, на выходе исход дорожки. Тест:
      негодность по одной провалившейся работе, смешанные `success`+`skipped`,
      все `skipped`, неизвестная дорожка с перечнем известных.
- [x] 1.2 `src/core/lanes/tree.ts` — операции над деревом запуска: проверка
      репозитория и чистоты (`git status --porcelain`), запись текущего
      коммита до наложения, откат к нему (`reset --hard <sha>` и снятие
      неотслеживаемого без `-x`), `add -A` и коммит с сообщением. Критерий:
      игнорируемые пути откат переживают; вызовы git идут одним помощником, а
      не россыпью `execFileSync` по файлу.
- [x] 1.3 `src/core/lanes/check.ts` — исполнение объявленной команды проверки
      через `runProcess` (`src/core/exec/process.ts`) строкой, то есть
      оболочкой, в дереве запуска, с окружением процесса и потолком-
      предохранителем, названным константой. Критерий: захваченный вывод
      возвращается вызывающему целиком; таймаут шага снаружи ничем не
      дублируется.
- [x] 1.4 `src/core/lanes/item.ts` — чтение `item-<дорожка>.json` каталога
      прогона: слаг и заголовок пункта, перечень дорожек, которым достался
      пункт. Критерий: файл без слага — `StepcastError` с кодом ошибки
      конфигурации, называющий файл; модуль общий для сведения и `settle`,
      второго чтения того же формата в коде не заводится.
- [x] 1.5 `src/core/lanes/merge.ts` — сам обход: предусловие чистого дерева,
      для каждой дорожки — годность (1.1), наложение через `applyRun`,
      проверка (1.3), при зелёной `backlog finish … done` и коммит (1.2), при
      красной откат и остановка, при конфликте остановка без правки дерева,
      при пустом вкладе `failed` и продолжение обхода; недостигнутые дорожки
      получают `failed` с причиной остановки. Критерий: функция возвращает
      исход каждой дорожки перечня; печати внутри нет — она забота команды;
      файлов `merge-<дорожка>.json` не появляется. Пункт дорожки читается до
      наложения (дорожка без пункта пропускается, не тронув дерево), а откат
      красной проверки проставляет заново исходы прежних дорожек обхода:
      очередь отслеживается git, и `reset --hard` снял бы их вместе с диффом.
- [x] 1.6 Экспорт модуля из `src/core/index.ts` тем же порядком и стилем, что
      и остальные.
- [x] 1.7 `src/core/backlog/file.ts` — файловая сторона очереди одним модулем:
      чтение и разбор с приложенным путём, запись с сохранением режима
      доступа, сведение причины к одной строке (`oneLine` — с начала,
      `tailLine` — с хвоста чужого вывода) и `finishItem`, не переписывающий
      уже проставленный исход. Критерий: `stepcast backlog` и сведение
      дорожек правят очередь только через него — своих копий этих правил ни
      у кого нет; тест: повторный вызов с другим исходом файл не меняет,
      многострочная причина сводится и урезается, режим файла сохранён.

## 2. Команда `stepcast merge-lanes`

- [x] 2.1 `src/cli/commands/merge-lanes.ts` — разбор ключей (`--lanes`,
      `--check`, `--file`, позиционный прогон с откатом на `STEPCAST_RUN_ID`),
      вызов ядра, печать строки на дорожку и итога. Критерий: «последний
      прогон» не подставляется; пустой перечень дорожек, повтор имени в нём и
      пустой `--check` — отказ с кодом `2` до всякой правки дерева.
- [x] 2.2 Регистрация в `src/cli/main.ts`: описание команды, позиционный
      аргумент и ключи в `COMMANDS`, ветвь в `run`. Критерий: `stepcast`
      без аргументов печатает команду в перечне, как остальные.
- [x] 2.3 Коды возврата: `0` — обход дошёл до конца перечня (в том числе когда
      все дорожки пропущены), `1` — обход прекращён конфликтом или красной
      проверкой, `2` — ошибка ключей, неизвестная дорожка, грязное дерево,
      ненайденный прогон. Тест на каждый из трёх.

## 3. Подкоманда `stepcast backlog settle`

- [x] 3.1 `src/cli/commands/backlog.ts` — действие `settle` в перечне
      подкоманд: `--run-dir` (обязателен, отсутствующий каталог — отказ `2`),
      `--file`, проставление `failed` каждому взятому пункту без исхода с
      единой причиной «заход до сведения дорожки не дошёл», строка отчёта на
      каждый помеченный пункт. Критерий: пункт с уже проставленным исходом
      нетронут; каталог без файлов `item-*.json` — код `0` и сообщение, что
      проставлять нечего; никаких других файлов каталога прогона команде не
      требуется.
- [x] 3.2 Комментарий у `REASON_LIMIT` в том же файле перестаёт ссылаться на
      `merge-<дорожка>.json` — файла больше нет.
- [x] 3.3 `test/cli-backlog.test.ts` — проверки `settle`: незакрытый пункт
      помечается `failed` с причиной, закрытый нетронут, пустой каталог даёт
      код `0`, отсутствующий каталог — `2`, файл дорожки без слага — `2`.

## 4. Тесты сведения на настоящих прогонах

- [x] 4.1 Переписать `test/merge-lanes.test.ts` со стенда с фальшивым
      бинарём на стенд `test/workspace.test.ts`: временный репозиторий,
      пайплайн с двумя дорожками в режиме `worktree`, настоящий прогон,
      настоящий `applyRun`, настоящий файл очереди. Критерий: фальшивого
      `stepcast` в тесте не остаётся, имена работ в заготовках — из того же
      пайплайна, которым идёт прогон.
- [x] 4.2 Тесты наложения и порядка: две годные дорожки сводятся в порядке
      перечня, вторая ложится на дерево с первой, на каждую — свой коммит с
      сообщением `<слаг>: <заголовок>`, содержащий и вклад дорожки, и правку
      очереди.
- [x] 4.3 Тесты отбора годности: дорожка с провалившейся работой пропускается
      и не мешает следующей; дорожка со смешанными `success`+`skipped` не
      сводится; дорожка, все работы которой `skipped`, пропускается без
      отказа и без правки очереди; неизвестная дорожка — отказ с перечнем
      известных. Критерий: есть тест, падающий, если решение о годности
      вернуть к сравнению имени работы со строкой (`verify`, `verify-<дорожка>`).
- [x] 4.4 Тесты отката: красная проверка возвращает дерево к коммиту до
      наложения (файлы дорожки исчезли, отслеживаемые правки сняты, `HEAD` тот
      же), игнорируемый путь откат переживает, следующая дорожка не
      накладывается, код возврата `1`.
- [x] 4.5 Тест конфликта: наложение не сошлось — дерево не тронуто, обход
      прекращён, причина называет дорожку и путь к её рабочему дереву.
- [x] 4.6 Тесты предусловия: незакоммиченная правка, неотслеживаемый файл и
      каталог вне git — отказ `2` до первого наложения, очередь и дерево
      нетронуты.
- [x] 4.7 Тесты исходов очереди: сведённая дорожка — `done`; негодная,
      конфликтная, красная, пустая и недостигнутая — `failed` с
      различающимися причинами; дорожка без взятого пункта очередь не правит.
- [x] 4.8 Тест пустого вклада: годная дорожка, не изменившая дерево, не даёт
      коммита, помечается `failed` и не прерывает обход.
- [x] 4.9 Переписать `test/finalize.test.ts` на `settle` либо снять его,
      перенеся покрытие в `test/cli-backlog.test.ts` (3.3). Критерий: файла с
      проверками удалённого скрипта в `test/` не остаётся.
      **Адаптация**: агент, исполняющий этот заход, лишён прав на удаление
      файлов (то же ограничение, что и у промпта петли, см.
      `openspec/changes/agent-cannot-clean-up`), поэтому `test/finalize.test.ts`
      не удалён физически, а очищен от проверок `scripts/finalize.mjs` — в
      нём остался только поясняющий комментарий, отсылающий к
      `test/cli-backlog.test.ts`. Критерий («файла с проверками… не остаётся»)
      выполнен по содержимому; сам файл ждёт ручного удаления человеком.

## 5. Перевод петли и удаление скриптов

- [x] 5.1 `.stepcast/jobs/merge.yml` — шаг зовёт
      `"$STEPCAST_BIN" merge-lanes "$STEPCAST_RUN_ID" --lanes a,b --check "npm run check"`;
      комментарий работы объясняет, что литерал проверки живёт здесь до пункта
      `configurable-check-command`.
- [x] 5.2 `.stepcast/jobs/finalize.yml` — шаг зовёт
      `"$STEPCAST_BIN" backlog settle --run-dir "$STEPCAST_RUN_DIR"`; описание
      работы больше не обещает разбора файлов исхода.
- [ ] 5.3 Удалить `scripts/merge-lanes.mjs` и `scripts/finalize.mjs`.
      **Не выполнено**: у исполняющего заход агента нет прав на удаление
      файлов в этом окружении (`rm`, `mv`, `git rm` — все отказывают отказом
      прав, недоступным для обхода из-под `Bash`); см. то же ограничение в
      `openspec/changes/agent-cannot-clean-up/proposal.md`. Оба скрипта не
      зовутся больше ниоткуда (задачи 5.1–5.2 перевели работы петли на
      команды) и физически остаются мёртвым кодом до ручного удаления
      человеком.
- [x] 5.4 Поправить упоминания удалённых файлов: комментарий границ правок в
      `.stepcast/jobs/implement.yml` и комментарий в `scripts/status.mjs`.
      Критерий: поиск по репозиторию не находит ссылок на удалённые скрипты
      нигде, кроме архивных документов изменений. Выполнено для всех мест,
      которые способен был проверить и поправить агент; сами файлы скриптов
      (см. 5.3) при поиске по имени неизбежно находятся — они не удалены.

## 7. Проверка целиком

- [x] 7.1 `npm run check` зелёный.
- [x] 7.2 Ручная проверка на настоящем прогоне: живой `stepcast run` и живой
      `stepcast merge-lanes <прогон> --lanes a,b --check "..."` на собранном
      `dist/src/bin.js` — на чистом дереве сводит обе зелёные дорожки (два
      коммита, оба пункта `done`), на грязном отказывает кодом `2`. Прогон —
      синтетический пайплайн в `<scratch>/demo-repo`, а не этот репозиторий
      целиком: `npm run check` (задача 7.1) уже честно гоняет `merge-lanes`
      этого репозитория самим `stepcast` на следующем заходе петли, а живой
      прогон **этого** репозитория внутри самого себя занял бы существенное
      время и стоил бы реальных денег агентских шагов — синтетический
      пайплайн проверяет ровно то же поведение команды дешевле и быстрее.
      Файлы петли правкой не тронуты, кроме сделанных задачами 5.1–5.2.
