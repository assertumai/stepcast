## Context

Пять импортов держат нынешнюю двустороннюю связь ядра плагинов с доменом:

| откуда | куда | чем |
| --- | --- | --- |
| `plugins/kernel.ts:4` | `pipeline/schema.js` | значение: два перечня ключей документа |
| `plugins/builtin.ts:1` | `backend/claude.js` | значение: адаптер и перечисление моделей |
| `plugins/builtin.ts:7` | `pipeline/expand.js` | значение: регистрация четырёх встроенных видов шага |
| `plugins/builtin.ts:8` | `../../steps/decision/index.js` | значение: вклад вида шага `decision` |
| `plugins/contract.ts:4` | `backend/types.js` | тип: `BackendAdapter`, `ModelDiscovery` |

Обратный ход тоже есть: `pipeline/expand.ts:16`, `core/lint.ts:12`,
`run/runner.ts:53`, `backend/registry.ts:3` и `config/resolve.ts:9` читают
`plugins/builtin.js`. Пара `builtin.ts ↔ expand.ts` — настоящий цикл модулей,
живой только потому, что оба обращения отложены до вызова функции.

Ограничения, в которых делается работа:

- Публикуемая поверхность `stepcast/plugin` (`src/plugin.ts`) реэкспортирует
  доменные типы напрямую (`BackendAdapter`, `Permissions`, `EvaluationInput`,
  `Usage`) и меняться в этом шаге не должна: её разделение — шаг 8 плана.
- `npm run check` включает `typecheck:plugin` по трём образцам плагинов в
  `examples/plugins/**`, которые компилируются против `dist` как сторонний
  автор. Любая правка публикуемых объявлений видна там немедленно.
- Плоский конфиг ESLint **не сливает** опции одноимённого правила: последний
  совпавший блок заменяет их целиком. Про это предупреждает комментарий в
  начале `eslint.config.js`, и ровно ради этого написан
  `test/eslint-config.test.ts`.

## Goals / Non-Goals

**Goals:**

- Ни один модуль `src/core/plugins/**` не импортирует `core/pipeline/**`,
  `core/backend/**`, `core/run/**`, `src/steps/**` — значением или типом, — с
  единственным объявленным в правиле исключением (`contract.ts` →
  `backend/types.js`, только тип).
- Запрет проверяется линтером, а сам линтер — тестом.
- Перечни занятых имён и перечень строк поставки объявлены доменом и доходят
  до ядра параметром.
- Поведение дефолтного бинаря, тексты отказов и состав дерева не меняются.

**Non-Goals:**

- Разделение публикуемой поверхности на `stepcast/plugin` и
  `stepcast/pipeline` (шаг 8 плана) — отсюда единственное исключение правила.
- Переезд `backends`, `predicates`, `commands`, `steps` из служебных сервисов
  ядра в сервисы строки `pipeline` (шаг 7). `KERNEL_RESERVED_NAMES` и
  объявление `declare module 'cordis'` остаются в ядре как есть.
- Соглашение о строке `row.ts` и декларация состава дефолта в `bin.ts`
  (шаг 3). Здесь заводится только каталог `src/parts/`, куда шаг 3 положит
  первые `row.ts`.
- Разрыв цикла `parts/builtin.ts ↔ pipeline/expand.ts` (см. Риски).
- Граница для `src/core/config/**`: `config/resolve.ts` по-прежнему читает
  `BUILTIN_ROW_IDS` для семени дерева. Это домен, читающий поставку, — ход
  правильный, и правило на `plugins/**` его не касается.

## Decisions

### Решение 1. Проверка имени — вызываемая проверка в параметре сборки ядра, а не перечень данных

`createKernel` принимает необязательные проверки по виду вклада:

```ts
export type ContributionNameGuard = (name: string) => void;

export interface KernelOptions {
  /** Проверка имени вклада перед регистрацией — по виду вклада. */
  readonly nameGuards?: Partial<Record<ContributionKind, ContributionNameGuard>>;
}
```

`ContributionService.register` зовёт проверку своего вида перед проверкой
занятости имени и только для вклада, поданного не областью ядра:

```ts
if (owner !== BUILTIN_OWNER) this.nameGuard?.(name);
```

Сегодня то же место написано условием `this.kind === 'steps'` и прямым вызовом
`assertStepKindNameAvailable`. После правки ядро о видах шага здесь не
упоминает вовсе, а поведение тождественно: проверка подаётся только для
`steps`, и подаёт её домен.

Функция `assertStepKindNameAvailable` переезжает в `src/core/pipeline/schema.ts`
целиком, оба текста и обе подсказки — дословно. Там уже объявлены
`STEP_COMMON_KEYS` и `BUILTIN_STEP_KIND_KEY_OWNERS`, и комментарий у первого
(«Список общий с `plugins/kernel.ts`») становится верным без оговорок: второго
читателя перечней в репозитории не остаётся.

*Почему проверка, а не перечень занятых имён.* Второй вариант — ядро принимает
`readonly reservedStepKindNames: readonly string[]` и отказывает само. Отказов
здесь два, с разными текстами и разными подсказками («ключи общей части (id,
env, …) не могут стать именем вида шага» против «выберите другое имя: ключи
встроенных видов…»), и второй ещё называет виды-владельцы ключа. Перечень
пришлось бы превратить в записи «имя + сообщение + подсказка», то есть
протащить в ядро тот же доменный текст, только данными. Проверка оставляет
текст там, где живёт знание, и ядру не достаётся ни одного доменного слова.

*Почему правило «встроенный вклад мимо проверки» остаётся в ядре.* Оно про
область регистрации, а не про документ: встроенные виды регистрируются под
теми же именами (`run`, `agent`), и это не конфликт, а определение. Ядро
отличает свою область по идентичности фибера — знание сугубо ядерное, домену
его не передать.

*Почему `nameGuards` необязательны.* `createKernel()` без аргументов зовут
тесты (`test/backend-models.test.ts`, `test/plugins-introspect.test.ts`),
которым проверка имени не нужна. Обязательное поле заставило бы каждый такой
вызов назвать домен — ровно то, от чего шаг избавляется. Цена — ядро без
проверки принимает любое имя; она названа требованием и закрыта сценарием:
это и есть доказательство, что перечня в ядре нет.

### Решение 2. Встроенный слой уезжает в `src/parts/`, а не в соседний файл ядра

`src/core/plugins/builtin.ts` → `src/parts/builtin.ts`, содержимое без правок.

Имя каталога взято из `docs/microkernel-target.md` («Финальная структура
кода»): `parts/` — строки встроенного слоя, «пакет их несёт, ядро — нет».
Шаг 3 кладёт туда `row.ts`, шаг 5 — виды шага, шаг 10 переносит остальное.
Заводить промежуточное имя (`src/core/builtin.ts`) — значит завести переезд,
который придётся делать дважды.

Альтернатива «оставить файл в `plugins/`, но вычистить импорты» невозможна:
импорты `builtin.ts` — это и есть его содержание, таблица `id → фабрика`
существует ровно затем, чтобы назвать `claude` и `decision`.

Следствие, принятое сознательно: `src/core/**` начинает импортировать
`src/parts/**` (`pipeline/expand.ts`, `lint.ts`, `run/runner.ts`,
`backend/registry.ts`, `config/resolve.ts`). Направление выглядит
перевёрнутым только при нынешней раскладке каталогов: в целевой все пять
модулей сами лежат в `parts/pipeline/`. Хуже, чем сегодня, не становится — те
же пять модулей уже читают `plugins/builtin.js`.

Тип `BuiltinRow` (`{ id, apply(kernel) }`) доменно пуст и остаётся в ядре, в
`load.ts`, рядом с `LoadOptions.builtinRows`, который им типизирован. Витрина
(`src/ui/screens/rows.ts`, `registry.ts`) импортирует его оттуда.

### Решение 3. Загрузчик обходит дерево на поданном ядре; состав дефолта — в `src/parts/`

Ядро (`src/core/plugins/load.ts`):

```ts
export function applyPluginTree(kernel: Kernel, resolved: ResolvedConfig, options: LoadOptions): Promise<LoadResult>;
export function walkPluginTree(kernel: Kernel, resolved: ResolvedConfig, options: LoadOptions): Promise<{ outcomes; introspection }>;
```

Обе — нынешние тела `loadPlugins` и `inspectPluginTree` без первой строки
(`createKernelShell(...)`). `applyTreeRow` ищет фабрику строки только в
`options.builtinRows`; `findBuiltinRow` и `BUILTIN_ROW_IDS` из ядра уходят —
причём `findBuiltinRow` не переезжает, а исчезает: без единственного
вызывающего он ведёт мимо настоящего пути разрешения.

Состав дефолта (`src/parts/load.ts`) сохраняет прежние имена и сигнатуры:

```ts
export interface DefaultLoadOptions extends LoadOptions {
  readonly builtinCommands?: readonly CommandContribution[];
}

export function loadPlugins(resolved, options: DefaultLoadOptions) {
  const { builtinCommands, ...rest } = options;
  return applyPluginTree(createKernelShell(builtinCommands ?? []), resolved, {
    ...rest,
    builtinRows: [...BUILTIN_ROWS, ...(options.builtinRows ?? [])],
  });
}
```

*Почему `builtinCommands` объявлено обёрткой, а не ядерной парой.* Поле
читает только сборка ядра, то есть обёртка; оставленное в `LoadOptions`, оно
компилировалось бы и в прямом вызове `applyPluginTree(kernel, resolved, {
projectRoot, builtinCommands })` — и молча не вносило бы ни одной команды.
Это ровно та тихая деградация, ради которой у ядерной пары другие имена
(ниже): разные имена делают ошибкой компиляции выбор не того модуля, разные
опции — выбор не того поля.

Порядок слагаемых обязателен: подсказка отказа о несуществующей встроенной
строке перечисляет строки в порядке `builtinRows`, и сегодня это «строки
движка, затем строки вызывающего» (`load.ts:326`). Обратный порядок сменил бы
текст отказа, который проверяет `test/plugin-tree.test.ts:436`.

`resolveWithPlugins` переезжает туда же (`src/parts/resolve.ts`) — целиком, без
правок: он зовёт `loadPlugins` и потому принадлежит составу дефолта, а не ядру.

*Почему у ядерной пары другие имена.* Одинаковые имена в двух модулях дают
самый неприятный из возможных отказов: импорт из «не того» модуля
компилируется, а дерево молча собирается без встроенного слоя. Разные имена
делают такую ошибку ошибкой компиляции.

*Почему обёртка, а не обязательные поля у всех вызывающих.* Второй вариант —
сделать `kernel` и `builtinRows` обязательными полями `LoadOptions` и заставить
каждого вызывающего назвать состав. Это честнее по духу («состав дефолта
называет точка входа»), но правит по существу около сорока мест, из которых
тридцать — тесты, зовущие `loadPlugins(config, { projectRoot })`. Шаг 3 плана
всё равно вводит декларацию состава в `bin.ts`; до него обёртка сохраняет
нынешний вид вызова, и весь диф сводится к строке импорта. Решение «обязательно
называть состав» принимается там, где оно и осмысленно, — вместе с самой
декларацией.

### Решение 4. Граница — блок `no-restricted-imports` на `src/core/plugins/**`, плюс отдельный блок для поверхности

```js
const kernelBoundaryPatterns = [
  {
    group: [
      '**/core/pipeline/**', '**/core/backend/**', '**/core/run/**',
      '**/steps/**', '**/backends/**', '**/parts/**', '**/ui/**',
    ],
    message: 'Ядро плагинов не зависит от домена: перечень и вклад приходят параметром или регистрацией (docs/microkernel-target.md, шаг 2).',
  },
];
```

Три детали, каждая — причина отказа, если о ней забыть:

1. **Блок обязан повторить прежние запреты.** На `src/core/plugins/**` уже
   действует блок `src/core/**/*.ts` с `paths: enginePaths` и
   `patterns: coreBoundaryPatterns`. Новый блок на более узком наборе файлов
   заменит его опции целиком, и оба прежних запрета молча исчезнут с файлов
   ядра плагинов. Поэтому запись — `{ paths: enginePaths, patterns: [...coreBoundaryPatterns, ...kernelBoundaryPatterns] }`.
2. **Запрещённые деревья шире четырёх названных в пункте.** `src/parts/**`
   добавлено затем, чтобы Решение 3 нельзя было откатить обратным импортом
   таблицы строк; `src/backends/**` и `src/ui/**` — по тому же основанию, что
   и `src/steps/**`.
3. **Тип запрещён наравне со значением.** Базовое правило
   `no-restricted-imports` (в конфиге используется именно оно, не версия
   typescript-eslint) не различает `import` и `import type` и ловит обе формы,
   а также `export … from`. Проверяется сценарием.

Исключение для поверхности — вторым блоком, на одном файле:

```js
{
  files: ['src/core/plugins/contract.ts'],
  rules: { 'no-restricted-imports': ['error', { paths: enginePaths, patterns: [
    ...coreBoundaryPatterns,
    { group: ['**/core/pipeline/**', '**/core/run/**', '**/steps/**', '**/backends/**', '**/parts/**', '**/ui/**'], message: … },
    { group: ['**/core/backend/**', '!**/core/backend/types.js'], message: … },
  ] }] },
}
```

Отдельный блок, а не отрицание внутри общего: `files`/`ignores` плоского
конфига — механизм, на который тест уже опирается, а поведение отрицания в
`group` зависит от версии правила. Если отрицание в установленной версии
работает (проверяется тем же тестом), блоки допустимо слить — текст требования
этого не запрещает, оно требует лишь, чтобы исключение было названо в правиле и
проверялось.

Как и вышло: отрицание установленная версия понимает, и исключение выражено
им — группой `['**/backend/**', '!**/backend/types.js']` внутри блока
`contract.ts`. Отдельная она потому, что исключение действует в ней одной:
внесённое в общую группу доменных деревьев, отрицание сняло бы запрет и с
прочих. Комментарий в конфиге обязан говорить именно это, а не «отрицание не
используется» — иначе он противоречит коду под собой.

Переезд `builtin.ts`/`resolve.ts` в `src/parts/` выводит их из-под блока
`src/core/**/*.ts`, а значит — из-под границы ядра и поверхности: единственный
блок, под который `src/parts/**` попадает сам собой, несёт только
`paths: enginePaths`. Поэтому заводится ещё один блок — `src/parts/**/*.ts` с
`{ paths: enginePaths, patterns: coreBoundaryPatterns }`. Без него изменение,
чья цель — заменить соглашения машинной проверкой, попутно вернуло бы одно из
них в соглашения: `createBuiltinKernel` принимает `commands` параметром ровно
потому, что зависеть от `src/cli` нельзя, — и этот запрет обязан пережить
переезд файла.

Тест (`test/eslint-config.test.ts`) добавляет случаи по образцу уже написанных:
модуль ядра плагинов, импортирующий `pipeline/expand.js` типом и значением;
`contract.ts` с разрешённым `backend/types.js` и с запрещённым
`backend/claude.js`; и обязательный случай «оба прежних запрета сработали на
файле ядра плагинов» — тот самый, ради которого тест и написан.

### Решение 5. Тексты отказов закрепляются тестом до переноса, а не после

Ни один тест сегодня не читает текст «Имя вида шага … занято ключом…». Порядок
работ в `tasks.md` поэтому такой: сперва тесты на нынешнем коде, потом
перенос. Тест, написанный после переноса, доказывает лишь то, что код
согласован сам с собой.

## Risks / Trade-offs

- **Цикл `parts/builtin.ts ↔ pipeline/expand.ts` переживает этот шаг.**
  `builtin.ts` берёт из `expand.ts` регистрацию встроенных видов шага, а
  `expand.ts` из `builtin.ts` — умолчание `builtinRegistry()`. → Цикл
  перестаёт проходить через ядро и становится внутренним делом одной будущей
  строки `pipeline`, где ему и место. Разрывается он шагом 5 плана, когда
  четыре встроенных вида станут строками и `registerBuiltinStepKinds` исчезнет
  вовсе; ломать его сейчас пришлось бы отменой умолчания `registry` у
  `expandPipeline`, `lint` и `runner` — правка, чья цена не связана с целью
  этого шага.
- **Ядро, собранное без проверки имени, примет вид шага `expect`.** →
  Проверку подаёт `createKernelShell`, то есть единственная дорога к
  дефолтному дереву; голый `createKernel()` живёт только в тестах ядра. Риск
  закрыт сценарием, который требует прежнего отказа именно от встроенного
  ядра.
- **Переезд трогает около сорока файлов правкой пути импорта.** → Правка
  механическая и целиком проверяется компилятором: `verbatimModuleSyntax` и
  `NodeNext` не прощают ни забытого расширения, ни несуществующего пути.
  Опасность не в ней, а в соблазне заодно «поправить рядом»; `tasks.md`
  разводит переезд и правки поведения по разным задачам.
- **Новый блок конфига линтера способен снять чужие запреты.** → Это уже
  случившаяся в репозитории ошибка, ради которой существует
  `test/eslint-config.test.ts`; сценарий «оба запрета сработали в одном файле»
  обязателен для новых файлов наравне с прежними.
- **Исключение для `contract.ts` может пережить шаг 8.** → Оно названо в
  требовании вместе с условием снятия и стоит отдельным блоком конфига: снять
  его — удалить блок, и тест немедленно покажет, что исключения больше нет.

## Migration Plan

Совместимость наружу не нарушается: публикуемые подпути (`stepcast`,
`stepcast/plugin`, `stepcast/step`, `stepcast/backends/codex`) не меняют ни
одного экспорта, схемы в `schema/` не пересобираются. Внутренние вызывающие
правятся в том же коммите, что и переезд, — промежуточных реэкспортов
(`export * from '../../parts/builtin.js'` в старом месте) не заводится: они бы
оставили ядру тот самый импорт, ради удаления которого всё делается.

Прежние пути остаются пустыми заглушками (`export {}` с комментарием о
переезде), а не исчезают с диска: право удалять файлы у агента — намеренный
Non-Goal (design.md `agent-cannot-clean-up`), а `unlinkSync` на
git-отслеживаемом файле заводит расхождение индекса и рабочего дерева, которое
здесь нечем починить. Существенное свойство при этом соблюдено и проверяется
компилятором: импорт из старого места — ошибка, реэкспорта нет. Физическое
удаление двух пустых модулей делается тем, у кого есть право на `git rm`.

## Open Questions

- Нужен ли `src/parts/index.ts` как единая точка состава дефолта. Пока
  вызывающие берут `builtinRegistry` и `loadPlugins` из разных модулей
  каталога; собирать их в один фасад имеет смысл вместе с декларацией состава
