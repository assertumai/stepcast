## Context

Три вида вкладов, которые открывает изменение, сегодня устроены по-разному:

- **Бэкенды.** Контракт `BackendAdapter` (`launch`, `parseLine`,
  `capabilities`) чист; конфигурация `backends.<имя>` — произвольная карта, и
  `buildBackends` собирает `BackendConfig` для любого имени. Единственное
  закрытое место — `resolveAdapter`, `switch` по имени. Раннер держит
  `adapterFor` для подмены в тестах, судья берёт адаптер той же функцией.
- **Предикаты.** Литералы в четырёх местах: `PredicateSchema` (zod-объединение
  однoключевых объектов), тип `Predicate`, `toPredicate` в `expand.ts`,
  `switch` в `evaluatePredicates`. Первый проход синхронный (`execaSync` в
  `cmd`), судья — отдельный асинхронный проход. Линт знает `schema` (путь) и
  `judge` (бэкенд), плюс два предупреждения о составе `expect`.
- **Команды.** `COMMANDS: Record<string, CommandSpec>` для разбора аргументов
  и `switch` по имени в `run()` для диспетчеризации; каждая команда — функция
  `(args, write, cwd)`.

Ограничения, которые задают форму решения:

- `resolveConfig` синхронна, а загрузка модуля — `import()` — асинхронна.
  Значит плагины загружаются не внутри разрешения конфигурации, а после него,
  отдельным шагом, и всё, что зависит от реестра (схема документа, линт,
  раннер), принимает реестр параметром.
- Публикуемые JSON Schema генерируются из zod-моделей статически
  (`scripts/schema-targets.ts`, тест свежести). Схема документа с плагинными
  предикатами статичной быть не может.
- Ключ шага (`stepKey.ts`) и `pipeline.lock.yml` фиксируют раскрытое
  определение; предикат плагина попадает туда своим именем и значением.
  Семантика вычислителя в ключ не входит — как не входит и версия `claude`.
- Раннер не должен знать, встроенный предикат или плагинный: `runner.ts` и
  так 2338 строк.

## Goals / Non-Goals

**Goals:**

- Второй бэкенд, свой предикат и своя подкоманда добавляются пакетом без
  правки ядра.
- Всё, что плагин объявил, проверяется до первого токена: конфликт имён при
  загрузке, форма значения предиката при разборе документа, статические
  условия плагина в `stepcast lint`.
- Прогон с плагинными вкладами воспроизводим: манифест называет плагины.
- Тесты движка не зависят от внешних пакетов: поддельный плагин лежит в
  `test/`.

**Non-Goals:**

- Виды шагов, якоря, триггеры, витрина, маршруты `/api` — закрыты как прежде.
- Автообнаружение по имени пакета или топику.
- Изоляция плагина (песочница, ограничение прав): плагин — код, которому
  доверяют так же, как самому движку, и это сказано в документации.
- Горячая перезагрузка: реестр собирается на вызов команды и живёт столько же.
- Вклад плагина в конфигурацию за пределами умолчаний своего бэкенда.

## Decisions

### 1. Явное объявление в `plugins`, оба слоя, объединение

Список `plugins` допустим и в `~/.stepcast/config.yml`, и в
`.stepcast/config.yml`; слои объединяются, как `env_deny`. Глобальный слой
нужен для машинного (адаптер бэкенда, установленный на этой машине),
проектный — для того, от чего зависит пайплайн репозитория. Дубликат модуля
между слоями — не ошибка, загрузка одна. Обратный вариант — только
проектный — лишил бы адаптер бэкенда естественного места: `backends.*.command`
и так только глобальный.

Элемент — строка. Начинается с `./` или `../` — путь от файла объявления;
иначе — спецификатор пакета, разрешаемый от корня проекта
(`createRequire(join(projectRoot, 'package.json')).resolve`), а при неудаче —
от каталога самого движка (глобальная установка плагина рядом с глобальным
stepcast). Объектная форма с параметрами плагина не заводится: параметры
своему бэкенду плагин читает из `backends.<имя>`, а предикату — из значения
в документе.

### 2. Контракт: объект по умолчанию, вклады — данные, не вызовы

```ts
export interface StepcastPlugin {
  readonly name: string;      // слаг kebab-case, уникален среди загруженных
  readonly version?: string;
  readonly backends?: Readonly<Record<string, BackendContribution>>;
  readonly predicates?: readonly PredicateContribution[];
  readonly commands?: readonly CommandContribution[];
}
```

Плагин ничего не вызывает у движка при загрузке — он экспортирует описание,
а движок его читает. Так конфликт имён и валидность формы проверяются
целиком до того, как исполнится хоть одна строка плагина сверх импорта, и
загрузка не зависит от порядка. Альтернатива по образцу Cordis
(`apply(ctx)` с `ctx.provide`) даёт больше свободы, но именно её и не
нужно: у движка нет долгоживущего контекста, в который стоило бы вешать
эффекты.

Модуль обязан экспортировать объект по умолчанию (`export default`), а
загрузчик валидирует его zod-схемой `StepcastPluginSchema`: неверная форма —
отказ с именем модуля и путём поля.

### 3. Реестр — один объект, собранный на команду

```ts
interface Registry {
  readonly backends: ReadonlyMap<string, BackendContribution>;
  readonly predicates: ReadonlyMap<string, PredicateContribution>;
  readonly commands: ReadonlyMap<string, CommandContribution>;
  readonly plugins: readonly LoadedPlugin[];   // { name, version, source }
}
```

`builtinRegistry()` — встроенные вклады, `loadPlugins(config, …)` добавляет
к нему вклады из модулей.

**Бэкенды и команды описаны контрактом полноценно.** Встроенный `claude`
создаётся своей фабрикой-вкладом, встроенные команды диспетчеризуются как
вклады. Это не симметрия ради симметрии: единственный способ проверить, что
контракта достаточно, — выразить через него то, что уже работает. Если
через вклад нельзя выразить `claude`, через него нельзя выразить и Codex.

**Предикаты — исключение, и оно осознанное.** Встроенные предикаты в реестре
представлены только именами (`BUILTIN_PREDICATE_NAMES`), а не вкладами с
`evaluate`. Причина в модели: `Predicate` — размеченное объединение с
типизированными полями (`{ kind: 'changed_only', globs }`), и вычисление —
`switch` по `kind`, который TypeScript проверяет на полноту. Обернуть их в
вклад с сигнатурой `evaluate(value: unknown, …)` значило бы заменить девять
проверенных компилятором ветвей на девять непроверенных приведений типа —
ровно тот обмен, которого изменение избегает. Реестру от встроенных нужны
две вещи: их имена для перечня в диагностике и их ветви для схемы документа;
обе даёт перечень имён, а ветви остаются в `schema.ts`, где и были.

Следствие честно ограничивает обещание: плагин добавляет предикат, но не
переопределяет и не заменяет встроенный — имя из перечня занято, и вклад с
таким именем отклоняется тем же конфликтом, что и вклад, спорящий за
`claude`.

Конфликт имён — отказ загрузки, называющий вид вклада, имя и обоих
претендентов (`встроенный` или имя плагина). Переопределение встроенного не
предусмотрено: подмена `claude` плагином с тем же именем сделала бы
`stepcast config` лжецом.

`Config` реестр не несёт — он передаётся рядом: `ExpandOptions.registry`,
`LintOptions.registry`, `RunOptions.registry`. Без значения — встроенный:
тесты и внешние потребители `stepcast` как библиотеки не меняются.

### 4. Бэкенд плагина: фабрика плюс умолчания конфигурации

```ts
interface BackendContribution {
  create(config: BackendConfig): BackendAdapter;
  readonly defaults?: Partial<RawBackend>;   // command, sessions, …
}
```

`resolveAdapter(name, config, registry)` берёт `registry.backends.get(name)`
и зовёт `create(config.backends[name])`. Требование «бэкенд настроен и
включён» остаётся: имя без записи в `backends` — прежняя ошибка с перечнем
настроенных; настроенное имя без вклада — ошибка «адаптер не предоставлен ни
встроенно, ни плагином», с перечнем доступных.

Умолчания плагина ложатся слоем между `builtin` и глобальным конфигом —
источник `plugin:<имя>` в происхождении, видимый в `stepcast config`. Но
слой можно применить только после загрузки плагинов, а `resolveConfig` уже
отработала (она же и назвала плагины). Поэтому разрешение конфигурации
становится двухфазным: `resolveConfig` читает слои и список `plugins`, а
`applyPluginDefaults(resolved, registry)` вставляет слой и пересобирает
`backends`. Пересборка касается только `backends.<имя плагина>`; всё прочее
неизменно, и тест это утверждает.

Отвергнутая альтернатива — требовать полной записи `backends.<имя>` от
пользователя — работает, но каждый пользователь плагина копировал бы одни и
те же `sessions: true, structured_output: true` из его README.

### 5. Предикат плагина: схема значения — JSON Schema, вычислитель асинхронный

```ts
interface PredicateContribution {
  readonly name: string;                   // ключ в expect
  readonly schema: JsonSchema;             // форма значения
  readonly hard?: boolean;                 // по умолчанию true
  evaluate(value: unknown, input: EvaluationInput): PredicateResult | Promise<PredicateResult>;
  lint?(value: unknown, at: LintSite): readonly Diagnostic[];
}
```

**JSON Schema, а не zod.** У плагина своя версия zod, и объект другой версии
в объединении схем документа — источник неотлаживаемых отказов. JSON Schema —
данные, `ajv` уже зависимость движка (предикат `schema`), и она же печатается
в отчёте `stepcast config`.

**Схема документа собирается из реестра.** `PredicateSchema` перестаёт быть
константой: `predicateSchema(registry)` строит объединение встроенных ветвей и
по ветви на плагинный предикат — `z.object({ [name]: z.unknown() }).strict()`
с последующей проверкой значения через ajv в `toPredicate`. Отказ ajv —
`StepcastError` с путём поля и сообщением ajv, как у `schema:` в `expect`.
Ключ, не известный ни встроенно, ни плагином, — отказ с перечнем доступных.

**Модель.** `Predicate` получает вариант
`{ kind: 'plugin'; name: string; value: unknown }`. Раннер, ключ шага,
`pipeline.lock.yml` и журнал видят его как данные. `evaluatePredicates`
получает реестр и на `plugin` зовёт `evaluate`; `PredicateResult.predicate`
— имя из реестра, чтобы `stepcast status` и витрина показывали его как
`exit_code` или `cmd`.

**Асинхронность.** `evaluatePredicates` становится `async`; три вызова в
раннере получают `await`. Встроенные вычислители остаются синхронными внутри
— `cmd` по-прежнему `execaSync`, менять его не надо. Порядок результатов —
объявленный, вычисление последовательное: параллельность предикатов не
обещана и в документации не появится.

**Генерируемая схема.** `schema/pipeline.schema.json` генерируется из
`predicateSchema(builtinRegistry())` и плагинных ключей не знает. Это
известное ограничение, записанное в `status.md` и `docs/plugins.md`.

### 6. Команда плагина: тот же `CommandSpec`, диспетчеризация по реестру

```ts
interface CommandContribution {
  readonly name: string;
  readonly spec: CommandSpec;
  run(args: ParsedArgs, io: CliIo, env: CommandEnv): Promise<ExitCodeValue>;
}
```

`CommandEnv` — `{ cwd, config, registry }`. `main.ts` собирает `COMMANDS`
из `registry.commands` и вызывает `run` найденного вклада; `switch`
исчезает, встроенные команды становятся вкладами встроенного реестра.
Разбор аргументов (`parseArgs`) не меняется. Имя команды — слаг, конфликт с
встроенной — отказ загрузки.

Порядок в `main.ts`: `resolveConfig` → `loadPlugins` → `applyPluginDefaults`
→ `parseArgs` по полному перечню → диспетчеризация. Отказ загрузки плагина
печатается тем же `reportError`, что и прочие ошибки конфигурации, с кодом
`configError`; команда до диспетчеризации не доходит, включая `stepcast
config` — иначе отчёт печатал бы конфигурацию, которой не будет.

### 7. Манифест прогона называет плагины

`run.json` получает `plugins: [{ name, version?, source }]` — пустой список,
если плагинов нет. `source` — разрешённый путь модуля. Читатель журнала без
плагина видит имя предиката в результатах и путь к модулю, которого у него
нет, — достаточно, чтобы понять, чего не хватает для воспроизведения.

### 8. Публикуемый подпуть `stepcast/plugin`

`package.json` → `exports["./plugin"]: "./dist/src/plugin.js"` — типы
контракта и ровно те функции, без которых адаптер не написать: `runProcess`,
`emptyUsage`, `mergeUsage`, `sumUsage`, `describeRefusal`. Остальное ядро
плагину недоступно намеренно: что экспортировано, то и обещано.

## Risks / Trade-offs

- [Плагин — произвольный код с правами процесса движка] → В документации
  сказано прямо; проектный конфиг в ревью, и список `plugins` виден там же,
  где `project.check`. Песочницы нет и не обещано.
- [Плагинный предикат меняет поведение, а ключ шага этого не видит] →
  Манифест называет версию плагина; сравнение прогонов `stepcast diff`
  печатает различие в списке плагинов. Семантика встроенных предикатов тоже
  меняется с версией движка — та же природа.
- [`import()` пакета из корня проекта тянет `node_modules` репозитория] →
  Это и есть требуемое поведение: плагин — зависимость проекта. Разрешение
  от каталога движка — запасное, для глобальных установок.
- [Асинхронный первый проход меняет три места раннера] → Замена синхронного
  вызова на `await` без изменения порядка; тесты `expect.test.ts` и
  `run.test.ts` покрывают порядок и правило отмены судьи.
- [Плагин с зависимостью от другой версии stepcast] → Контракт типов из
  `stepcast/plugin`; несовместимость формы ловится валидацией при загрузке.
  Версионирование контракта отдельным полем не заводится, пока нет второй
  версии.
- [Умолчания бэкенда плагина ложатся слоем после `resolveConfig`] →
  Пересобирается только `backends.<имя>`; тест утверждает неизменность
  остальных значений и происхождения.
