## Context

Правило «унаследованный контекст уходит в первое сообщение сессии» собрано из
трёх мест `src/core/run/runner.ts`:

1. `runJobSteps` заводит `const contextSent = new Set<string>()` (строка 1043) —
   один набор на вызов, то есть на работу и на итерацию цикла;
2. набор передаётся в `runAgentStep` (строка 1174) и оттуда — в замыкание
   `buildPrompt`, где `const first = !contextSent.has(step.session)` решает
   судьбу уровней (строки 1616–1617);
3. `assembleContext` получает `pipeline: first ? pipeline.context : []`, то же
   для `job.context` и для блока выходов предшественников, и результат сборки
   тут же уходит в `journal.writeContextReport(stepDirPath, …)`.

Что из этого следует по границам:

- **Сессия.** Ключ — `step.session`. `expandPipeline` (строка 341) даёт `default`
  всем шагам работы при `session: shared` и `step.id` при `per_step`; явный
  псевдоним шага побеждает оба.
- **Работа.** Набор создаётся внутри `runJobSteps`, поэтому две работы с
  псевдонимом `default` друг о друге не знают — и это верно: реестр сессий
  (`createSessionRegistry`) там же и тоже свой.
- **Итерация.** Цикл `until` зовёт `runJobSteps` заново на каждой итерации
  (строка 593), значит новая итерация получает и новый реестр сессий, и пустой
  `contextSent`: сессия начинается заново, унаследованный контекст уходит снова.
- **Попытка.** `executeAgentStep` зовёт `buildPrompt` на каждой попытке
  (`src/core/exec/agentStep.ts:135`), а сессию берёт через
  `sessions.acquire(step.session)` — тот же идентификатор с `resume: true`.
  Значит вторая попытка — второе сообщение той же сессии, и контекст ей не
  повторяется.

Существующий тест (`test/backend.test.ts`, `describe('step-context: контекст и
общая сессия')`) не связан ни с одним из этих мест: он зовёт `executeAgentStep`
напрямую и держит собственные `contextSent` и `buildPrompt`. Проверяемая им
логика написана в нём самом.

Наблюдать отправленное снаружи движка есть чем: `context.json` шага пишется
самой сборкой промпта и содержит `entries[].origin` из перечня `upstream |
pipeline | job | step` (`ContextEntryReportSchema`,
`src/core/journal/schema.ts:73`). Шаг, не получивший унаследованного, записей с
`origin` кроме `step` не имеет. Промпт сохраняется рядом: `prompt.txt` для
первой попытки, `prompt.<номер>.txt` для последующих
(`src/core/exec/agentStep.ts:149`).

Ограничения, в которые проверка обязана вписаться:

1. **Ничего в `src/`.** Изменение описывает и проверяет существующее поведение.
   Правка движка «чтобы тест было удобнее писать» превратила бы проверку в
   проверку правки.
2. **`context.json` один на шаг.** `writeContextReport` пишет в тот же путь на
   каждой попытке, поэтому у шага с двумя попытками сохранится состав второй.
   Разделять файл по попыткам — правка журнала, то есть правка `src/`.
3. **Поддельный бэкенд умеет сессии.** `createFakeBackend` объявляет
   `capabilities.sessions: true` (`src/core/backend/fake.ts:49`), иначе
   `session: shared` деградировал бы событием `backend.degraded`.
4. **Тесты гоняет сам stepcast.** Петля саморазвития исполняет `npm run check`
   внутри прогона, поэтому пайплайны-образцы берут окружение через
   `testBaseEnv()` там, где окружение вообще важно, и работают в проекте из
   `makeProject`.

## Goals / Non-Goals

**Goals:**

- Однократность унаследованного контекста проверяется на том же пути, каким
  идёт настоящий прогон: `runPipeline` → `runJobSteps` → `runAgentStep` →
  `assembleContext` → `context.json`.
- Снятие отметки `contextSent` из `runner.ts` роняет проверку — это
  сформулированный признак годности, а не побочное свойство.
- Границы отметки — сессия, работа, итерация цикла, попытка шага — покрыты
  каждая своей проверкой и записаны в спеку.
- В репозитории не остаётся второго, самодостаточного теста того же правила.

**Non-Goals:**

- Правка движка. Ни `src/core/run/runner.ts`, ни сборка контекста, ни журнал не
  меняются: изменение не вводит поведения.
- Починка отправки контекста на бэкенде без поддержки сессий. Дефект найден при
  разборе и назван дефектом в `status.md`, откуда его берёт в очередь человек:
  починка меняет поведение прогона (`contextSent` обязан спрашивать
  `adapter.capabilities.sessions`), а изменение обязалось движок не трогать —
  иначе проверять оно будет собственную правку. Заводить пункт `backlog.md`
  здесь тоже нельзя: очередь ведёт петля.
- Разделение `context.json` по попыткам. Тот же довод: это правка журнала, её
  цена — схема, витрина и `stepcast diff`.
- Проверка того, что бэкенд действительно продолжает сессию (`resumeSession`,
  идентификатор сессии в запуске). Это про `agent-backend`, и покрыто отдельно.
- Замена или расширение остальных проверок `test/backend.test.ts`: удаляется
  ровно один `describe`.

## Decisions

### Решение 1. Наблюдать по `context.json`, а не по промпту

Утверждения строятся по `entries[].origin` в `context.json` шага: у первого шага
общей сессии есть записи `pipeline` и `job`, у второго — только `step`.

Почему не по тексту промпта: совпадение подстроки отвечает на вопрос «встретился
ли этот текст», а не «какие уровни вошли в сборку». Файл уровня, случайно
совпавший содержимым с шагом, дал бы ложный зелёный, а `origin` — прямой ответ
движка о составе. Промпт остаётся вторым, независимым пробником там, где
`context.json` не различает: у повторной попытки (Решение 3).

Уровни пайплайна-образца объявляют записи `text` с узнаваемым текстом
(«контекст пайплайна», «контекст работы», «контекст шага <id>») — как это уже
сделано в `test/context.test.ts`. Текстовые записи не склеиваются между собой и
не зависят от рабочего дерева, поэтому уровень виден в `context.json` ровно
там, где объявлен. Пути тоже годятся, но требуют разных файлов на разных
уровнях: один и тот же путь склеился бы в одну запись (изменение
`context-dedup`) и смазал бы картину.

### Решение 2. Один пайплайн-образец на границу, а не один на всё

Границы проверяются раздельными пайплайнами и раздельными прогонами: общая
сессия, `per_step`, `until` с двумя итерациями, шаг с двумя попытками, две
работы с псевдонимом `default`. Соблазн собрать всё в один пайплайн отвергнут:
упавшая проверка должна называть границу, а не «что-то в контексте не то», а
`until` и `attempts` в одной работе ещё и путают номера каталогов шага.

Каталог шага ищется `findStepDir(result.journal.paths, job, step, iteration)` —
той же функцией, что уже используют тесты итераций
(`test/iteration-context.test.ts`), с номером итерации там, где итераций больше
одной.

### Решение 3. Повторная попытка проверяется парой промптов, а `context.json` — как подтверждение

`context.json` шага с двумя попытками содержит состав второй: файл
перезаписывается на каждой сборке. Поэтому у шага с `attempts.max: 2`, где
первая попытка не проходит предикат, а вторая проходит:

- `prompt.txt` (попытка 1) содержит текст записи уровня пайплайна,
  `prompt.2.txt` (попытка 2) — не содержит: прямое свидетельство, что второе
  сообщение сессии унаследованного контекста не получило;
- `context.json` записей с `origin: pipeline` не содержит — согласуется с тем же
  выводом.

Альтернатива — читать состав попытки из `context.json` — недоступна без правки
журнала (Non-Goal). Поэтому в этой единственной проверке сравниваются промпты,
и в тесте это сказано комментарием, чтобы следующий читатель не счёл несходство
с остальными проверками небрежностью.

### Решение 4. Признак годности — мутация, выполняемая руками

Автоматической мутационной проверки в репозитории нет, заводить её ради одного
правила — несоразмерно. Вместо этого задача сформулирована как действия с
проверяемым исходом; каждая мутация сдвигает отметку через свою границу, и
роняет ровно те проверки, что эту границу стерегут:

- **(а) отметки нет вовсе** — `contextSent` убран, `first` всегда `true`.
  Обязаны упасть проверки общей сессии (обе) и блока выходов предшественников:
  унаследованное уходит в каждое сообщение сессии. Проверка повторной попытки
  падает заодно — она о том же первом сообщении.
- **(б) отметка сужена до шага** — `contextSent` заведён внутри
  `runAgentStep`. Это случавшийся регресс. Обязаны упасть проверки общей сессии
  и блока выходов предшественников. Проверки соседней работы и итерации остаются
  зелёными по устройству: сужение границы наружу не выходит.
- **(в) отметка расширена до прогона** — `contextSent` живёт вне
  `runJobSteps` и общий у всех работ и итераций прогона. Обязаны упасть
  проверки соседней работы и новой итерации `until` — те самые границы, которых
  первые две мутации не задевают, — и вместе с ними блок выходов
  предшественников: у `consumer` первый шаг перестаёт быть первым в прогоне.

Мутация (в) заведена именно потому, что «отметка живёт в работе» и «итерация
начинает сессию заново» ни (а), ни (б) не проверяются: проверка соседней работы
утверждает наличие унаследованных записей у каждой работы, а обе первые мутации
унаследованное только добавляют или оставляют на месте. Без (в) две из четырёх
объявленных границ остались бы объявленными и не проверенными.

Исход каждой мутации записывается в задаче списком упавших проверок, а не
остаётся в голове исполнителя. После каждой код возвращается, и чистота
`git status` по `src/` — часть задачи.

### Решение 5. Отдельный файл `test/session-context.test.ts`

Проверки не кладутся ни в `test/backend.test.ts` (там уровень `executeAgentStep`
и поддельные бэкенды — уровнем ниже нужного), ни в `test/context.test.ts` (там
`assembleContext` без движка), ни в `test/iteration-context.test.ts` (там
предмет — выдержка о прошлой итерации). Отдельный файл называет предмет
и удерживает пайплайны-образцы рядом с проверками, которые их читают.

## Risks / Trade-offs

- **Проверка через `runPipeline` медленнее и шире по площади: упасть она может
  от чужой поломки.** → Пайплайны-образцы минимальны: поддельный бэкенд, шаги
  без побочных действий, предикаты только `exit_code`. Диагностику даёт
  сообщение утверждения, называющее шаг и найденные уровни.
- **`origin` записи — деталь формата журнала: изменится схема — сломается
  проверка.** → Это приемлемо и отчасти желательно: `context.json` объявлен
  наблюдаемым составом контекста (`step-context`), и его молчаливая смена формы
  должна быть замечена. Проверки читают `entries[].origin`, не полагаясь ни на
  порядок записей, ни на `total_tokens`.
- **`prompt.2.txt` — не названное спекой имя.** → Изменение называет его:
  требование о наблюдаемости состава дополняется тем, что промпт каждой попытки
  сохраняется отдельно. Проверка опирается на объявленное поведение, а не на
  подсмотренное.
- **Удаление старого `describe` уменьшает число тестов и выглядит потерей
  покрытия.** → Покрытие им и не создавалось: он зелёный при любом состоянии
  движка. Замена происходит в одном изменении, поэтому промежутка без проверки
  нет.
