## Why

`.stepcast/jobs/implement.yml` и `.stepcast/jobs/fix-review.yml` разрешают
агенту ровно шесть команд, и три из них — `Bash(npm *)`, `Bash(npx *)`,
`Bash(node *)` — записаны литералом. Это устройство npm-репозитория внутри
файла, объявленного переносимым: остальные три (`git status*`, `git diff*`,
`git log*`) принадлежат не проекту, а самому движку — он и сам требует git для
рабочих деревьев и якорей.

Репозиторий, забравший `.stepcast/` себе, получает агента, который не может
запустить собственную сборку. Для Go нужно `Bash(go *)`, для Gradle —
`Bash(./gradlew *)`, для Python — `Bash(uv *)` или `Bash(pytest *)`. Правки
внутри скопированных файлов при этом требуются только здесь: `project.check`
уже объявляет команду проверки, `project.spec` — практику спецификации,
`stepcast:<имя>` — схемы движка. Инструменты, которыми объявленная команда
исполняется, остались последним, что работы знают о репозитории буквально.

Хуже того, привязка молчалива в обе стороны. Чужой репозиторий получает
неприменимые права (`npm` там нет вовсе) и не получает нужных — а `enforce:
strict` в этих работах означает, что отказ будет не предупреждением, а
отклонённым вызовом инструмента: `permission.denied` в журнале и потраченная
попытка. Ни `stepcast lint`, ни прогон об этом не скажут: движок политику
доступа не разбирает, и `Bash(npm *)` в дереве без npm для него неотличимо от
рабочего права.

Это последнее, что осталось от `configurable-check-command`: команду проверки
объявили настройкой, а инструменты, которыми она исполняется, — нет.

**Чего изменение не обещает.** Пункт очереди ссылается на отказы прав в
журналах заходов. Отказы там есть — в двух просмотренных прогонах петли по 22
события `permission.denied` на прогон, — но их причина по большей части
другая, и объявление инструментов её не снимет:

- **составные команды.** `npm run typecheck 2>&1 | tail -20`,
  `node dist/src/bin.js lint …; echo "exit=$?"`, `cd .stepcast && for f in …`,
  heredoc с `python3` — бэкенд сопоставляет с шаблоном команду целиком, и
  `Bash(npm *)` такую строку не покрывает, хотя первое слово в ней разрешено.
  Это большинство отказов и в `implement`, и в `fix-review`;
- **работа `review` не имеет права ни на один инструмент.** В её списке только
  `git`, а шаг раз за разом пробует `npm run check` и `npm run typecheck`.
  Выдать ей инструменты — правка поведения петли этого репозитория, а признак
  выполненности пункта требует обратного («работает с прежним набором прав без
  правок поведения»); отдельный вопрос — отдельным пунктом.

То есть ценность изменения — переносимость и одно место объявления, а не
исчезновение отказов. Обещать второе было бы неправдой.

## What Changes

- **Секция `project` пополняется ключом `tools` — объявлением инструментов
  репозитория.** Список непустых строк; каждая — имя команды, которой в этом
  репозитории собирают, проверяют и запускают код:

  ```yaml
  # .stepcast/pipelines/self-improve.yml (или .stepcast/config.yml)
  project:
    check: npm run check
    tools: [npm, npx, node]      # go; ./gradlew; uv, pytest
  ```

  Слой, запреты и умолчания — те же, что у `project.check` и `project.spec`:
  ключ допустим только в `.stepcast/config.yml` (в `~/.stepcast/config.yml`
  отклоняется уже действующим шаблоном `project.**`), документ пайплайна может
  объявить его сам и перекрыть конфигурацию, встроенного умолчания нет.
  Пустой список отклоняется разбором — как и пустая строка у `check`: он не
  «инструментов нет», а «объявление есть, но ничего не объявляет».

- **Пространство подстановки `project` получает первое списочное имя.**
  `${project.tools}` пополняет состав `check`, `spec.dir`, `spec.rules`,
  `spec.tool`; правила отказа те же — необъявленное имя называет оба места
  объявления, имя вне состава перечисляет доступные.

- **Списочное значение раскрывается в списке — по элементу на значение.**
  Элемент списка, целиком являющийся строкой, в которой ровно одна подстановка
  даёт список строк, MUST заменяться на столько элементов, сколько значений в
  списке: окружающий текст применяется к каждому. Так `- Bash(${project.tools} *)`
  становится тремя записями `Bash(npm *)`, `Bash(npx *)`, `Bash(node *)`, а
  форма права остаётся в файле работы — там, где ей и место: движок синтаксис
  `allow`/`deny` не разбирает и разбирать не начинает.

  Вне списка списочное значение по-прежнему непредставимо строкой — прежняя
  ошибка с уточнённой подсказкой. Две списочные подстановки в одном элементе —
  отказ разбора: декартово произведение никто не заказывал.

- **Работы `implement` и `fix-review` берут права из объявления.** Три
  литерала в каждой заменяются одной строкой `Bash(${project.tools} *)`.
  Литералов `npm`, `npx` и `node` в правах работ петли не остаётся; в
  `.stepcast/pipelines/self-improve.yml` они остаются — это и есть место
  объявления (`check: npm run check` уже там).

- **Свойство закрепляется проверкой движка.** `test/loop-portability.test.ts`
  уже обходит настоящие файлы петли: к перечню запрещённых литералов
  добавляется имя инструмента в праве (`Bash(npm …`, `Bash(npx …`,
  `Bash(node …`), а сквозной прогон против чужого объявления получает
  `tools: [make]` и проверяет, что `implement` и `fix-review` уходят в бэкенд
  с `Bash(make *)`, а не с сегодняшними тремя.

Ломающих изменений нет: `project.tools` — новый необязательный ключ,
размножение элемента списка срабатывает только там, где подстановка даёт
список, а сегодня списочных значений в пространстве `project` не бывает вовсе.

## Capabilities

### New Capabilities

Новых нет: и объявление свойств проекта, и переносимость петли уже описаны
существующими возможностями.

### Modified Capabilities

- `stepcast-configuration`: секция `project` получает ключ `tools` — список
  имён инструментов репозитория, с теми же слоями, запретом глобального слоя и
  отсутствием умолчаний, что у `check` и `spec`.
- `pipeline-definition`: состав пространства `project` пополняется именем
  `tools`; правила подстановок получают раскрытие списочного значения в
  элемент списка.
- `self-improvement-loop`: работы петли, которым нужны инструменты
  репозитория, берут права из объявления проекта, а не из литерала.

## Impact

Код движка:

- `src/core/config/schema.ts` — `RawProjectSchema` пополняется `tools`;
  модель значения (непустой список непустых строк) заводится рядом с
  `CheckCommandSchema` и переиспользуется документом пайплайна;
- `src/core/config/resolve.ts` — `Config['project'].tools`;
- `src/core/pipeline/schema.ts` — `ProjectSchema` документа пайплайна;
- `src/core/pipeline/expand.ts` — `PROJECT_NAMES`, `resolveProjectValues`;
- `src/core/pipeline/interpolate.ts` — размножение элемента списка в
  `interpolateTree`, уточнённая подсказка в `renderValue`.

Публикуемые схемы `schema/config.schema.json` и `schema/pipeline.schema.json`
перегенерируются (`npm run schema`); `test/schema-generated.test.ts` сторожит
расхождение.

Файлы петли: `.stepcast/pipelines/self-improve.yml` (объявление),
`.stepcast/jobs/implement.yml` и `.stepcast/jobs/fix-review.yml` (права).

Документация: `docs/config.md` — раздел об инструментах рядом с «Команда
проверки проекта» и «Практика спецификации»; `docs/pipeline-format.md` —
состав пространства `project` и правило раскрытия списочного значения;
фрагмент `openspec/changes/job-tools-declaration/status.md` и пересборка
`docs/status.md`.

Не затрагивается: витрина (`src/ui/pipelines.ts` отдаёт секцию `project`
целиком и новый ключ подхватывает сам), команды `backlog`, `merge-lanes`,
формат журнала.
