## MODIFIED Requirements

### Requirement: Подстановки

Система SHALL раскрывать подстановки вида `${...}` в значениях пайплайна, файлов
работ и файлов промптов. Доступны пространства `inputs`, `params`, `project`,
`run`, `env` и `jobs.<id>`. Последовательность `$${` MUST давать литерал `${`.
Обращение к неизвестному пространству или имени MUST быть ошибкой.

Пространства `inputs`, `params` и `project` раскрываются при раскрытии
пайплайна. Пространства `jobs`, `run` и `env` — отложенные: их значения известны
только по ходу прогона, и система SHALL раскрывать их перед исполнением работы,
целиком по её определению.

Отказ на неизвестном пространстве или неопределённом имени MUST называть
документ, в котором стоит ссылка: у работы, подключённой через `uses`, это её
файл, а не пайплайн, где работа только подключена. Точечный путь поля
указывает место внутри документа и сам документ не называет.

#### Scenario: Подстановка входа пайплайна

- **WHEN** значение содержит `${inputs.change}`, а прогон запущен с `--input change=foo`
- **THEN** в раскрытом пайплайне на этом месте стоит `foo`

#### Scenario: Неизвестное имя

- **WHEN** значение содержит `${inputs.missing}`, не объявленное в `inputs`
- **THEN** `stepcast lint` завершается ошибкой

#### Scenario: Отказ называет файл подключённой работы

- **WHEN** файл работы, подключённой через `uses`, ссылается на неопределённое
  имя
- **THEN** отказ называет этот файл, а не файл пайплайна

#### Scenario: Экранирование в промпте

- **WHEN** файл промпта содержит `$${params.x}`
- **THEN** в отправленном тексте стоит `${params.x}`

#### Scenario: Отложенная подстановка доезжает через параметр

- **WHEN** работа подключена с `with: { change: "${jobs.plan.output.slug}" }`, а
  её файл использует `${params.change}` в пути контекста
- **THEN** к началу исполнения работы путь содержит значение поля `slug` выхода
  работы `plan`

#### Scenario: Отложенная подстановка в аргументах командного шага

- **WHEN** командный шаг объявлен как `run: [echo, "${run.id}"]`
- **THEN** процесс получает аргументом идентификатор прогона, а не литерал

#### Scenario: Обращение к незавершённой работе

- **WHEN** значение содержит `${jobs.later.output.slug}`, а работа `later` к
  моменту исполнения не завершилась
- **THEN** работа завершается отказом, а сообщение называет выражение и причину

#### Scenario: Обращение к выходу упавшей работы

- **WHEN** значение содержит `${jobs.broken.output.slug}`, а работа `broken`
  завершилась отказом
- **THEN** работа завершается отказом: выход упавшей работы не публикуется

## ADDED Requirements

### Requirement: Объявление project в пайплайне перекрывает конфигурацию

Документ пайплайна SHALL принимать верхний ключ `project` того же состава, что
и одноимённая секция конфигурации, и объявленное там значение MUST перекрывать
конфигурацию — тем же порядком слоёв, каким пайплайн перекрывает `defaults` и
`context`. Порядок разрешения: пайплайн, затем проектный конфиг; ни один слой
не обязателен.

Требования к значению MUST быть теми же, что в конфигурации: непустая строка,
иначе разбор документа завершается ошибкой.

#### Scenario: Пайплайн перекрывает конфигурацию

- **WHEN** проектный конфиг объявляет `project.check: "npm run check"`, а пайплайн — `project: { check: "make check" }`
- **THEN** `${project.check}` во всех документах прогона раскрывается в `make check`

#### Scenario: Пайплайн — единственный слой объявления

- **WHEN** конфигурация секции `project` не содержит, а пайплайн объявляет `project.check`
- **THEN** подстановка раскрывается значением из пайплайна

#### Scenario: Пустая команда в пайплайне

- **WHEN** пайплайн объявляет `project: { check: "" }`
- **THEN** `stepcast lint` завершается ошибкой, называя ключ

### Requirement: Состав пространства project

Пространство `project` SHALL содержать единственное имя `check` — действующую
команду проверки репозитория, объявленную пайплайном либо конфигурацией
проекта. Значение SHALL раскрываться при разборе документа
наравне с `inputs` и `params`: оно известно до запуска прогона, и раскрытый
пайплайн MUST содержать его строкой, а не подстановкой.

Подстановка `${project.check}` в документе, разбираемом без объявленного ключа,
MUST быть отказом разбора, а не пустой строкой; сообщение MUST называть
`.stepcast/config.yml` как место объявления. Обращение к другому имени
пространства MUST быть отказом, называющим доступные имена.

Наличие ключа MUST NOT требоваться само по себе: документ, не ссылающийся на
`${project.check}`, разбирается и исполняется без него.

#### Scenario: Команда проверки в цикле until

- **WHEN** файл работы объявляет `until.check: [{ cmd: "${project.check}" }]`, а проектный конфиг — `project.check: "npm run check"`
- **THEN** предикат сходимости исполняет `npm run check`

#### Scenario: Команда проверки в тексте промпта

- **WHEN** файл промпта содержит `${project.check}`
- **THEN** агент получает текст с объявленной командой на этом месте

#### Scenario: Раскрытое значение попадает в снимок пайплайна

- **WHEN** пайплайн с `${project.check}` раскрыт
- **THEN** `pipeline.lock.yml` содержит на этом месте объявленную команду, а не подстановку

#### Scenario: Ссылка без объявления

- **WHEN** документ содержит `${project.check}`, а `project.check` не объявлен ни пайплайном, ни конфигурацией
- **THEN** `stepcast lint` завершается ошибкой, называющей оба места объявления
- **AND** `stepcast run` не начинает прогон

#### Scenario: Имя вне состава пространства

- **WHEN** документ содержит `${project.name}`
- **THEN** разбор завершается ошибкой с перечнем доступных имён пространства

#### Scenario: Документ без ссылки на команду проверки

- **WHEN** ни пайплайн, ни его работы, ни промпты не ссылаются на `${project.check}`, а ключ не объявлен
- **THEN** пайплайн разбирается и исполняется без ошибки
