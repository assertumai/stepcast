## Why

Объективный гейт — единственное, на чём держится качество петли: агент пишет
код, а решает не он, а команда проверки. Эта команда сегодня не объявлена
нигде — она размножена литералом `npm run check` по всей петле:

- `.stepcast/jobs/verify.yml` — четыре шага `npm run typecheck|lint|build|test:only`;
- `.stepcast/jobs/implement.yml` — `until.check[].cmd: npm run check`;
- `.stepcast/jobs/fix-review.yml` — то же в своём `until`;
- `.stepcast/jobs/merge.yml` — `--check "npm run check"` в аргументах `merge-lanes`;
- `.stepcast/prompts/implement.md` и `.stepcast/prompts/fix-review.md` — словами
  в правилах: «если проверка `npm run check` упала…»;
- `.stepcast/pipelines/self-improve.yml` — абзац `context`, объясняющий агенту,
  чем проверяется этот репозиторий.

Семь литералов в шести файлах. Движок к этому моменту от репозитория уже
отвязан: очередь переехала в `stepcast backlog` (`portable-backlog-format`),
сведение — в `stepcast merge-lanes` (`builtin-merge-lanes`), и команда проверки
там честно приходит ключом. Осталась последняя привязка — сама строка. Для Go
проверка — `go vet ./... && go test ./...`, для Gradle — `./gradlew check`, у
репозитория документации её нет вовсе; пока строка вшита, петлю нельзя
перенести, а можно только переписать в семи местах, ничего не забыв.

Цена размножения уже видна: копии разошлись. `npm run check` этого репозитория
— это `typecheck && typecheck:ui && lint && build && test:only && status:check`,
а `verify` гоняет четыре шага из шести: `typecheck:ui` и `status:check` в
финальную проверку не входят. То есть работа, чей исход решает судьбу
улучшения, проверяет не то же, что цикл `until` двумя работами раньше, — и
узнать об этом можно было, только сверив два файла глазами.

## What Changes

- **Команда проверки объявляется один раз — в конфигурации проекта.** Новая
  секция `project` с единственным пока ключом `check`:

  ```yaml
  # .stepcast/config.yml
  project:
    check: npm run check
  ```

  Ключ проектный: в `~/.stepcast/config.yml` он отклоняется с ошибкой — команда
  проверки принадлежит репозиторию, а не машине, и одна на все репозитории
  машины бессмысленна. Это зеркало уже существующего `GLOBAL_ONLY_KEYS`
  (`runs.root`, `backends.*.command`), которым проектный конфиг защищён от
  машинно-зависимых путей. Пустая строка и строка из пробелов отклоняются
  разбором: проверка, которая ничего не проверяет, хуже отсутствующей.

- **Пайплайн может объявить `project` сам.** Верхний ключ `project: { check: … }`
  в документе пайплайна перекрывает конфигурацию — тем же порядком слоёв, каким
  пайплайн уже перекрывает `defaults`, `context` и `env` («пайплайн перекрывает
  оба конфига», docs/config.md). Репозиторий выбирает один слой: конфигурация —
  когда пайплайнов несколько, пайплайн — когда он один. Этому репозиторию
  доступен пока только второй, и по причине, названной ниже.

- **Пространство подстановки `${project.check}`.** Раскрывается при разборе
  документа — наравне с `inputs` и `params`, а не отложенно: значение известно
  до запуска, и его видно в `pipeline.lock.yml` прогона. Доступно в пайплайне,
  файлах работ и файлах промптов; состав пространства — одно имя `check`,
  обращение к другому имени называет доступные, как это уже сделано для `run`.

- **Необъявленное — отказ, а не пустота.** Документ, ссылающийся на
  `${project.check}` там, где `project.check` не объявлен, отклоняется
  `stepcast lint` и `stepcast run` до запуска, с подсказкой, называющей
  `.stepcast/config.yml`. Репозиторий, которому проверять нечем (документация),
  просто не ссылается на подстановку — обязательным ключ не становится.

- **Работа `verify` — один шаг вместо четырёх.** `run: ${project.check}` в
  строковой форме, оболочкой. Побочный и желаемый эффект: финальная проверка
  начинает гонять ровно объявленную команду, то есть в этом репозитории
  дополнительно `typecheck:ui` и `status:check`, которые четыре шага упускали.
  Ценой — гранулярность журнала: имя упавшей части читается из вывода шага, а
  не из его идентификатора.

- **Циклы `until` работ `implement` и `fix-review`, аргумент `--check` работы
  `merge`, оба промпта и абзац `context` пайплайна** называют проверку
  подстановкой. Литералов `npm run check` в `.stepcast/` не остаётся.

- **Границы правок `implement` и `fix-review` пополняются
  `.stepcast/config.yml`.** Сегодня список `changed_only` перечисляет
  `.stepcast/jobs/**`, `prompts/**`, `pipelines/**`, `schemas/**` — но не
  конфигурацию проекта, которой в этом репозитории пока нет. Пока её нет в
  границах, ни один заход петли не может её завести.

- **Объявление этого репозитория живёт в пайплайне, а не в
  `.stepcast/config.yml`.** Причина не вкусовая: предикат `changed_only`
  фиксируется вместе с раскрытым пайплайном в начале прогона, поэтому
  расширение границ, сделанное заходом, действует только со следующего
  прогона, — заход, который завёл бы `.stepcast/config.yml` сейчас, разбился бы
  о собственную границу. Пайплайн в границах уже есть. Перенести объявление в
  конфигурацию можно любым последующим заходом, одной строкой; на устройство
  работ и промптов слой объявления не влияет вовсе.

- **Поведение петли этого репозитория не меняется:** `check` объявлен как
  `npm run check`, и все семь мест раскрываются в ту же строку, что стояла в
  них литералом.

## Capabilities

### New Capabilities

Новых возможностей изменение не вводит: и конфигурация, и подстановки, и петля
— возможности существующие, к которым добавляются требования.

### Modified Capabilities

- `stepcast-configuration`: добавляется секция `project` и ключ `project.check`
  — объявление команды проверки проекта, допустимое только в проектном
  конфиге. Дельта — `## ADDED Requirements`: разрешение слоёв, складывающиеся
  запреты и потолки изменение не переписывает.
- `pipeline-definition`: перечень пространств подстановки пополняется
  `project`, у пространства появляется собственный состав, а документ пайплайна
  — верхний ключ `project`, перекрывающий конфигурацию. Требование
  «Подстановки» переписывается целиком (`## MODIFIED Requirements`), состав
  пространства и объявление в пайплайне добавляются отдельными требованиями.
- `ui-dashboard`: витрина раскрывает пайплайн секцией `project` того проекта,
  которому файл принадлежит, а не конфигурацией каталога, откуда поднят демон.
  До этого изменения конфигурация не могла уронить раскрытие — у всех её
  значений есть встроенные умолчания; `project.check` первый, у которого
  умолчания нет, и одной конфигурации на все проекты корня прогонов стало
  недостаточно. Дельта — `## ADDED Requirements`.
- `self-improvement-loop`: работы петли берут команду проверки из настройки
  проекта, а не несут её литералом. Базовая спека возможности пока живёт в
  неархивированном изменении `self-improve-pipeline`, поэтому дельта здесь —
  `## ADDED Requirements`. Требованиям «Реализация до зелёной сборки» и
  «Финальная проверка», называющим `npm run check`, новое требование не
  противоречит: `project.check` этого репозитория и есть `npm run check`.

Возможность `lane-merge` изменение не трогает: `stepcast merge-lanes` уже
принимает команду ключом `--check` и о её происхождении ничего не знает —
подстановка раскрывается в файле работы, до того как команда запущена.

## Impact

- `src/core/config/schema.ts` — `RawProjectSchema`, поле `project` в
  `RawConfigSchema`, список `PROJECT_ONLY_KEYS`.
- `src/core/config/resolve.ts` — `project` в типе `Config`, проверка
  проектных ключей в глобальном слое (зеркало `rejectGlobalOnlyKeys`), отказ на
  пустой команде.
- `src/core/pipeline/schema.ts` — верхний ключ `project` документа пайплайна.
- `src/core/pipeline/expand.ts` — действующее значение (пайплайн поверх
  конфигурации), `project` в области видимости пайплайна и в области видимости
  тела работы (значит, и в промптах), объяснение для необъявленного ключа.
- `src/core/pipeline/interpolate.ts` — отказ подстановки называет документ,
  из которого пришла ссылка (`scope.file`): у подключённой работы это её файл.
- `src/ui/pipelines.ts`, `src/ui/server.ts` — секция `project` читается у
  каждого проекта своя; нечитаемая конфигурация проекта показывается ошибкой
  карточки.
- `schema/config.schema.json`, `schema/pipeline.schema.json` —
  перегенерируются из моделей (`test/schema-generated.test.ts` держит свежесть).
- `test/config-*.test.ts`, `test/pipeline-*.test.ts` — новые проверки:
  проектный ключ, отказ глобального слоя, отказ на пустой строке, перекрытие
  пайплайном, раскрытие в документе и в промпте, диагностика необъявленного.
- `.stepcast/jobs/implement.yml`, `.stepcast/jobs/fix-review.yml` — границы
  `changed_only` пополняются `.stepcast/config.yml`.
- `.stepcast/jobs/verify.yml`, `implement.yml`, `fix-review.yml`, `merge.yml`,
  `.stepcast/prompts/implement.md`, `.stepcast/prompts/fix-review.md`,
  `.stepcast/pipelines/self-improve.yml` — литералы заменяются подстановкой.
- `docs/config.md` (секция `project`), `docs/pipeline-format.md` (перечень
  пространств и таблица «когда что раскрывается»),
  `openspec/changes/configurable-check-command/status.md` — фрагмент состояния.
