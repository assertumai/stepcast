# Задачи

Порядок — из плана миграции `design.md`: движок учится ключу и подстановке
раньше, чем `.stepcast/` начинает ими пользоваться. Иначе проверка на
промежуточном дереве упадёт на разборе собственного пайплайна петли — её
собственный `dist/` пересобирается той же командой, которую эта правка и
трогает. Каждая задача — код **и** тест; тест обязан падать до правки.

Границы `changed_only` этого захода: `.stepcast/config.yml` в них **не входит**
и в этом заходе не заводится — расширение границ (задача 4.1) действует со
следующего прогона, потому что предикат фиксируется вместе с раскрытым
пайплайном. Объявление этого репозитория садится в пайплайн (задача 4.2), он в
границах есть. `backlog.md` не правится.

## 1. Ключ конфигурации

- [x] 1.1 `src/core/config/schema.ts` — `RawProjectSchema` с единственным
      ключом `check` (`.strict()`), поле `project` в `RawConfigSchema`.
      Значение — строка, непустая после обрезки пробелов: пустая команда даёт
      нулевой код возврата, то есть зелёный гейт на любом коде. Тест: ключ
      принимается, `check: "   "` отклоняется, `chek` отклоняется как
      неизвестный ключ.
- [x] 1.2 `src/core/config/schema.ts` — `PROJECT_ONLY_KEYS = ['project.*']`
      рядом с `GLOBAL_ONLY_KEYS`, с комментарием о причине: слой, общий всем
      репозиториям машины, не может объявлять команду одного из них.
- [x] 1.3 `src/core/config/resolve.ts` — `rejectProjectOnlyKeys` зеркально
      `rejectGlobalOnlyKeys`, применяется к глобальному слою; сообщение
      называет ключ, файл и предлагает `.stepcast/config.yml`. Тест: ключ в
      `~/.stepcast/config.yml` — отказ; тот же ключ в проектном — успех.
- [x] 1.4 `src/core/config/resolve.ts` — поле `project: { check: string |
      undefined }` в `Config`. Встроенного умолчания в `BUILTIN_CONFIG` нет и
      не заводится: подставленная за автора команда исполнялась бы в чужом
      репозитории. Тест: без объявления конфигурация разрешается, значение
      отсутствует; отчёт `stepcast config` печатает объявленное значение с
      файлом-источником.
- [x] 1.5 `schema/config.schema.json` — перегенерировать
      (`test/schema-generated.test.ts` сверяет файл с моделью и уронит
      проверку, если забыть).

## 2. Объявление в пайплайне

- [x] 2.1 `src/core/pipeline/schema.ts` — верхний ключ `project` документа
      пайплайна того же состава и с той же непустотой. Тест: документ с ключом
      разбирается, с пустой строкой — отклоняется, неизвестное поле внутри
      секции — отклоняется.
- [x] 2.2 `src/core/pipeline/expand.ts` — действующее значение: пайплайн
      поверх конфигурации, ни один слой не обязателен. Критерий: разрешение
      живёт в одном месте, оба потребителя (область пайплайна и область тела
      работы) берут уже посчитанное значение. Тест: перекрытие, объявление
      только в пайплайне, только в конфиге, ни там ни там.
- [x] 2.3 `schema/pipeline.schema.json` — перегенерировать.

## 3. Подстановка `${project.check}`

- [x] 3.1 `src/core/pipeline/expand.ts` — пространство `project` в области
      видимости пайплайна (`pipelineScope`) и в области видимости тела работы
      (`bodyScope`), то есть и в файлах промптов, которые читаются с той же
      областью. Пространство не отложенное: значение известно до запуска, и
      раскрытое значение обязано попасть в `pipeline.lock.yml`. Тест: раскрытие
      в `until.check[].cmd`, в строковой и массивной форме `run`, в тексте
      промпта, в абзаце `context`; снимок пайплайна содержит команду, а не
      подстановку.
- [x] 3.2 `src/core/pipeline/expand.ts` — объяснение для необъявленного:
      `${project.check}` без объявления даёт отказ разбора, называющий оба
      места объявления (пайплайн и `.stepcast/config.yml`), а не пустую
      строку. Обращение к имени вне состава (`${project.name}`) называет
      доступные имена — как `RUN_NAMES` для пространства `run`. Критерий: два
      разных сообщения, потому что это две разные ошибки. Тест: `stepcast lint`
      отказывает в обоих случаях; документ без ссылки на подстановку при
      необъявленном ключе разбирается без ошибки. (Проверки самих команд
      добавлены задачей 6.4: до неё тесты звали `expandPipeline` напрямую.)

## 4. Перевод петли

- [x] 4.1 `.stepcast/jobs/implement.yml` и `.stepcast/jobs/fix-review.yml` —
      `.stepcast/config.yml` в перечень `changed_only`, с комментарием, почему:
      конфигурация проекта — часть петли, и завести её должен уметь заход, а не
      человек. Расширение действует со следующего прогона.
- [x] 4.2 `.stepcast/pipelines/self-improve.yml` — верхний ключ
      `project: { check: "npm run check" }` с комментарием о слое (почему
      пайплайн, а не `.stepcast/config.yml`, и что перенос возможен в любой
      момент).
- [x] 4.3 `.stepcast/jobs/verify.yml` — четыре шага заменяются одним:
      `run: ${project.check}`, `timeout: 30m`, `expect: [{ exit_code: 0 }]`.
      Комментарий работы объясняет, почему шаг один: движок не разбирает чужую
      команду на части, а перечень, повторяющий её устройство, расходится с ней
      — что уже случилось (`typecheck:ui` и `status:check` в четыре шага не
      попали).
- [x] 4.4 `.stepcast/jobs/implement.yml` и `.stepcast/jobs/fix-review.yml` —
      `until.check[].cmd: ${project.check}`; описания работ (`description`) и
      комментарии перестают называть команду текстом.
- [x] 4.5 `.stepcast/jobs/merge.yml` — `--check "${project.check}"` вместо
      литерала; комментарий о том, что литерал ушёл в объявление, заменяет
      нынешнюю отсылку к этому пункту очереди.
- [x] 4.6 `.stepcast/prompts/implement.md` и `.stepcast/prompts/fix-review.md`
      — правила называют проверку подстановкой `${project.check}`.
- [x] 4.7 `.stepcast/pipelines/self-improve.yml` — абзац `context`: команда
      проверки называется подстановкой; репозиторные оговорки (`dist/` не
      трогать, `npm run build` и `npm test` напрямую не вызывать) остаются
      текстом — они о свойствах этого репозитория, а не о команде.
- [x] 4.8 Проверить, что литералов не осталось: поиск `npm run check` по
      `.stepcast/` даёт единственное вхождение — объявление задачи 4.2.

## 6. Правки по ревью

- [x] 6.1 Витрина раскрывает пайплайн секцией `project` того проекта, которому
      файл принадлежит (`src/ui/pipelines.ts`, `src/ui/server.ts`). До правки
      все проекты корня прогонов раскрывались одной конфигурацией — той, что
      резолвнута по каталогу запуска `stepcast up`; репозиторий, объявивший
      команду у себя (то есть ровно так, как советует `docs/config.md`),
      получал карточку с ошибкой «подстановка не определена». Нечитаемая
      конфигурация проекта показывается ошибкой карточки, а не подменяется
      чужой. Дельта спеки — `specs/ui-dashboard/spec.md`. Тесты в
      `test/ui-server.test.ts` на оба случая.
- [x] 6.2 Тесты на ветку `bodyScope`: работа, подключённая через `uses:`,
      раскрывает `${project.check}` в `until`, в шагах и в файле промпта, а
      ссылка без объявления даёт отказ, называющий файл работы. До правки
      второй области видимости не касался ни один тест — все звали работу,
      описанную на месте, где `bodyScope === pipelineScope`, — а петля целиком
      подключает работы файлами.
- [x] 6.3 Отказ подстановки называет документ, из которого пришла ссылка
      (`src/core/pipeline/interpolate.ts`): `scope.file` был известен, но в
      ошибку не попадал, и диагностика подключённой работы указывала только
      точечный путь поля. Требование добавлено в спеку `pipeline-definition`.
- [x] 6.4 `test/lint.test.ts` — проверки настоящими командами `stepcast lint`
      и `stepcast run` вместо прямого вызова `expandPipeline`: отказ в обоих
      случаях разными сообщениями, приём пайплайна с объявлением из
      `.stepcast/config.yml` проекта и то, что `run` не заводит каталога
      прогона. Сценарий спеки «`stepcast run` не начинает прогон» до этого не
      был покрыт вовсе.
- [x] 6.5 Различие двух диагностик держится тестом: проверка «есть слово
      check» проходила на обеих ветках `explainProject` и перепутанные ветки
      оставила бы зелёными.
- [x] 6.6 Непустота команды выражена и в публикуемой JSON Schema
      (`.regex(/\S/)` рядом с `.trim().min(1)`, `schema/*.json`
      перегенерированы): обрезку JSON Schema не переносит, и редактор принимал
      бы `check: "   "`, отклоняемое движком. Модель значения теперь одна на
      конфигурацию и документ пайплайна (`CheckCommandSchema`).
- [x] 6.7 Спека `self-improvement-loop` говорит о слое, на котором объявление
      стоит на самом деле: сценарий «Одно объявление доходит до всех работ»
      больше не требует `.stepcast/config.yml`, которого в репозитории нет, а
      перекрытие пайплайном и порядок переноса названы отдельными сценариями —
      заведённый позже конфиг молча ничего не изменит, и это записано.
