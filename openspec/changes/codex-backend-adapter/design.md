## Context

`first-real-backend-plugin` подготовило ядро и границу, но адаптера не дало:
`src/backends/` пуст. Теперь `codex-cli 0.149.0` установлен и аутентифицирован
(вход через ChatGPT), и три потока записаны вживую в этой сессии — новая нить со
схемой и вызовом инструмента, продолжение нити, отказ турна. Вся форма ниже
взята из них и из `codex exec --help` / `codex exec resume --help`, а не из
памяти.

Что установлено по записи:

- Запись потока: `{"type":"thread.started","thread_id":"<uuid>"}` первой
  строкой — и на новой нити, и на продолжении (тот же идентификатор). Далее
  `turn.started`, `item.started` / `item.updated` / `item.completed` с
  `item.type` ∈ {`agent_message`, `reasoning`, `command_execution`,
  `file_change`, `mcp_tool_call`, `collab_tool_call`, `web_search`,
  `todo_list`, `error`}, в конце `turn.completed` с `usage`
  {`input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`,
  `output_tokens`, `reasoning_output_tokens`} либо `turn.failed` с
  `error.message`; отдельно бывает `{"type":"error","message":…}` перед
  `turn.failed`. Расход приходит **один раз на турн**.
- Структурированный вывод при `--output-schema` — текст `agent_message`,
  причём схема применяется ко **всем** сообщениям турна, не только к
  последнему. Отдельного поля структурированного вывода нет.
- Отказ: `turn.failed.error.message` — строка с JSON ответа API вида
  `{"type":"error","status":400,"error":{"type":"invalid_request_error","message":"…"}}`;
  код возврата процесса 1.
- `codex exec resume` не принимает `-s`, `-C`, `--add-dir`; принимает `-c`,
  `-m`, `--output-schema`, `--json`, `--skip-git-repo-check`,
  `--ignore-user-config`, `--ignore-rules`. Промпт со stdin — аргумент `-`.
- CLI подгружает `~/.codex/config.toml` (MCP-серверы, навыки) без указаний:
  в записи видны ошибки подключения к пользовательскому MCP-серверу и чтение
  пользовательского навыка.

Ограничения прежнего дизайна сохраняются: `src/core` — запретная зона сверх
одной названной правки; `tsconfig.json` вне границ правок; движок петли
зафиксирован снимком, поэтому плагин в `.stepcast/config.yml` репозитория не
объявляется; автоматические тесты обходятся без сети и CLI.

## Goals / Non-Goals

**Goals:**

- Адаптер Codex как плагин пакета проходит агентский шаг, судью, общую сессию
  двух шагов и структурированный вывод на настоящем CLI.
- Всё, чему у Codex есть аналог возможностей `claude`, переведено; чему нет —
  отказывает до запуска процесса и названо в документации.
- Правка ядра ровно одна и названа: `sessionId` у события `init`.

**Non-Goals:**

- `enforce: strict` у Codex. У CLI есть `--ignore-user-config` и
  `--ignore-rules`, но нет ни пооперационного запрета, ни аналога
  `--strict-mcp-config`, а линт сверяет разрешающие режимы со списком Claude
  (`lint.ts:1436`). Поддержка потребовала бы второй правки ядра — отдельное
  изменение.
- Перевод петли репозитория на Codex и объявление плагина в его конфигурации.
- Пооперационные `allow`/`deny`: их у CLI нет.
- Разбор `collab_tool_call` и `web_search` во что-либо сверх `tool_use`.

## Decisions

### Решение 1. Одна правка ядра — `init` несёт `sessionId`

`parseLine` возвращает одно событие на строку и не имеет состояния: экземпляр
адаптера один на прогон (`adapterOf()`) и обслуживает одновременные шаги и
судей. `thread.started` у Codex — одновременно начало разговора и единственное
место, где назван идентификатор нити. Отдать только `session_started` нельзя:
движок распознаёт неоткрывшееся продолжение по отсутствию `init`
(`agentStep.ts`, ветка `onFailedContinuation`) и снял бы засев после любого
неудачного турна на продолженной нити — следующая попытка начинала бы новую
нить и теряла разговор. Отдать только `init` — потерять идентификатор.

Поэтому вариант `init` получает `readonly sessionId?: string`; `agentStep`
на `init` с `sessionId` делает то же, что на `session_started` (запоминает и
засевает). Вариант `session_started` не удаляется: бэкенд, у которого
идентификатор приходит отдельной записью, по-прежнему выражается им.

Альтернативы: очередь событий внутри адаптера (состояние на общем экземпляре
— гонка между одновременными шагами); `parseLine` возвращает массив (правка
контракта шире, чем нужно, и трогает все адаптеры и `fake.ts`); `init` без
идентификатора и чтение хранилища сессий Codex с диска (чужие внутренности).

### Решение 2. Песочница и подтверждения — через `-c`, одинаково для двух форм

У `resume` нет `-s`. Чтобы новая нить и продолжение собирались одним кодом, обе
формы получают `-c sandbox_mode="<режим>"` и `-c approval_policy="never"`
(значение — TOML-строка в кавычках, как требует `-c`). `permissions.mode`
принимает ровно словарь CLI: `read-only`, `workspace-write`,
`danger-full-access`. Без объявленного режима флаг песочницы не передаётся, и
действует умолчание CLI и пользовательской конфигурации — так же, как у
`claude` без `--permission-mode`. `approval_policy="never"` передаётся всегда:
неинтерактивный запуск обязан не ждать ввода (спека `agent-backend`, «Политика
доступа агента»).

`-C` не передаётся: рабочий каталог задаёт движок процессом, а `-C` у `resume`
нет. `--skip-git-repo-check` передаётся всегда: режим `copy` даёт дерево без
`.git`, и без флага CLI отказывает.

Альтернатива — `-s` на новой нити и `-c` на продолжении: две ветки под одно и
то же, и расхождение между ними никто не заметил бы до живого прогона.

### Решение 3. Результат — последний `agent_message`, структура — разбор его текста

Отдельного поля структурированного вывода в потоке нет. Каждый
`item.completed` с `agent_message` отдаётся событием `result` с `text` и,
если текст разбирается как JSON-объект или массив, со `structured`. Движок уже
берёт последнее (`agentStep.ts`: `text = event.text`, `structured =
event.structured`), а `output.json` пишет только у шага с `output_schema` — так
что промежуточное сообщение, которое случайно оказалось JSON, не вредит: его
перекроет последнее, а без схемы файл не пишется вовсе.

Адаптер не знает, была ли схема запрошена (у `parseLine` нет доступа к
`invocation`), и разбирать «на всякий случай» — единственный вариант без
состояния. Это названо в документации.

### Решение 4. Расход — одним событием `usage` на `turn.completed`, с приведением семантики

Поток несёт расход турна целиком и один раз; дельт по обращениям нет.
Адаптер отдаёт его событием `usage` без `messageId` — движок суммирует одну
величину, итог попытки верен. Следствие: потолок расхода не обрывает идущий
шаг Codex по ходу (`onUsage` → `abort.trigger` срабатывает лишь по
завершении турна). Это ограничение записано в спеке и `docs/plugins.md`; чинится
оно только полем возможностей «расход дельтой или итогом» — правкой ядра вне
объёма.

Семантика полей: у OpenAI `input_tokens` включает `cached_input_tokens`, у
Claude `input_tokens` кешированные не включает, а движок считает трафик как
`tokens_in + cache_read × cache_read_weight`. Чтобы одна и та же работа не
стоила у Codex вдвое, адаптер отдаёт `tokens_in = input_tokens −
cached_input_tokens` (не ниже нуля), `cache_read = cached_input_tokens`,
`cache_write = cache_write_input_tokens`, `tokens_out = output_tokens`
(рассуждения входят в него у OpenAI). `reasoning_output_tokens` в общую форму
не переносится. Стоимость и окна лимитов не сообщаются — поля отсутствуют.

Вычитать нарастающие итоги между записями запрещено, как и прежде.

### Решение 5. Отказы — по коду из JSON сообщения, затем по формулировке

`turn.failed.error.message` (и `error.message` записи `error`) — строка, внутри
которой JSON ответа API. Адаптер пытается разобрать её и берёт `status`:
429 → `rate_limit`, 401/403 → `unauthenticated`, другой код — обычный отказ
шага без классификации (`failed: true`). Не разобралось — закрытый перечень
формулировок (`rate limit`, `usage limit`, `quota`; `unauthorized`, `not
logged in`, `authentication`). `message` в `BackendRefusal` — строка CLI как
есть. Момент сброса — из полей ответа (`resets_at`, `resets_in_seconds`), если
они есть; иначе пустой. Живой записи 429 нет — README фикстур говорит это
прямо, а тест классификации подменяет код в записанном 400 и называет это в
имени теста.

Оба события — `turn.failed` и `error` — дают `result` с `failed: true`: они
несут одно и то же сообщение, второе перекрывает первое тем же содержанием, а
поток, оборванный между ними, всё равно даёт отказ. `item.completed` типа
`error` — предупреждение (в записи: неизвестные метаданные модели) и даёт
`ignored`.

### Решение 6. MCP — переопределениями `-c mcp_servers.*`, с проверкой вживую

Объявление шага переводится в ключи конфигурации Codex: `-c
mcp_servers.<имя>.command="…"`, `.args=[…]`, `.env={…}` для процесса; `.url="…"`
и `.http_headers={…}` для HTTP. Значения сериализуются TOML-совместимо (JSON
строк, массивов и плоских объектов TOML принимает). `init` идёт без
`mcpServers`: состав поднятых серверов в потоке не сообщается, сличения нет
(решение 7 `agent-step-mcp` это допускает), а сбой подключения виден только в
stderr и по поведению агента.

Это единственная часть, которую запись не подтверждает: живая проверка (задача
в разделе приёмки) — шаг с объявленным stdio-сервером, в потоке которого есть
`mcp_tool_call` с этим сервером. Если CLI переопределения не примет, вклад
объявляет `mcp: false`, гейт `requireMcpSupport()` отказывает до первой работы,
а причина ложится в `docs/plugins.md`. Ветвление одно и названо.

### Решение 7. Вызовы инструментов — на `item.completed`

Имена для `tool_use`: `command_execution` → `Bash` не подставляется — имя
инструмента у бэкенда своё, и движок сравнивает `observedInputs` с
объявлением шага по ним; отдаётся как есть: `command_execution`,
`file_change`, `web_search`, `collab_tool_call`, а `mcp_tool_call` —
`mcp__<server>__<tool>`, в форме, которую `docs/pipeline-format.md` уже
называет общей для MCP. Событие отдаётся на `item.completed`, не на
`item.started`: у части типов начала нет (в записи `agent_message` приходит
сразу завершённым), а двойной учёт одного вызова дал бы лишние `tool_use`.
`input` — сам объект `item` без `aggregated_output` (вывод команды не является
входом и раздувал бы `step.json`).

### Решение 8. Публичная поверхность растёт ровно на то, что понадобилось

`src/plugin.ts` получает `effectivePermissions`, `messagePrefix`,
`BACKEND_REFUSAL_PREDICATE`, тип `McpServerStatus` — перенесено из 3.2 старого
изменения. Что окажется лишним после написания адаптера, не экспортируется:
каждый экспорт объясняется комментарием на месте.

### Решение 9. Приёмка — во временном проекте, а старое изменение — вытеснено

Как и прежде (решение 8 старого дизайна): `examples/codex/` с README о запуске
из временного каталога с плагином по абсолютному пути к `dist/`. Старое
изменение остаётся в очереди до архивации этого; при архивации его спека
`codex-backend` заменяется этой, а `agent-backend` — объединяется. Его
незакрытые пункты не дублируются в двух местах: `tasks.md` старого получает
одну строку «остальное — в codex-backend-adapter».

### Решение 10 (по ходу реализации). Команды CLI берут конфигурацию из окружения точки входа

Живая приёмка показала: `stepcast config` печатал `backends.codex.*` источником
`plugin:codex`, а `stepcast lint` того же каталога отвечал «Неизвестный бэкенд
codex». Точка входа (`src/cli/main.ts`) разрешает конфигурацию через
`resolveWithPlugins()` и передаёт её командам в `env.config`, но `run`, `lint`
и `resume` звали `resolveConfig({ cwd })` заново — без слоя умолчаний
плагинов. Плагинный бэкенд с умолчаниями до этого дня ни разу не доходил до
`lint`/`run` живьём, и дефект был невидим — ровно то, ради чего заводился
настоящий адаптер.

Правка — в `src/cli`, не в ядре: три команды получают необязательный
параметр с уже разрешённой конфигурацией и берут его, когда он есть; прямой
вызов из тестов без него работает как прежде. Прочие команды с собственным
`resolveConfig` (`status`, `usage`, `gc`, `up`, …) к бэкендам не обращаются и
не правятся; это названо в `docs/plugins.md` как найденное.

### Решение 11 (по ходу реализации). Судья наследует окружение шага

Первый живой прогон: шаг со схемой прошёл (`output.json` записан, сессия равна
`thread_id`), а судья на том же бэкенде — «Процесс судьи не удалось запустить».
`callJudge()` запускал процесс с `env: launch.env ?? {}`, а `runProcess` не
наследует окружение родителя (`extendEnv: false`); без `PATH` поиск бинарника
идёт по системному умолчанию (`/usr/bin:/bin`), где `codex` из `~/.local/bin`
нет. Агентский шаг этого не видел: его окружение строит движок (`stepEnv`), а
поддельный бэкенд тестов зовёт узел абсолютным путём. Claude Code в стандартном
префиксе npm попадал в системный путь случайно — дефект был невидим до бэкенда
с другим местом установки.

Правка — вторая в ядре и той же природы, что первая: `JudgePassOptions.env`,
runner передаёт `stepEnv(...)` в обоих вызовах, `callJudge` собирает окружение
как `agentStep` — окружение шага, поверх — `launch.env` бэкенда. Раздел
«Единственная правка ядра» из proposal читать как «правки ядра ровно две, обе
названы».

## Risks / Trade-offs

- **Форма потока меняется с версией CLI** → фикстуры несут версию; неизвестная
  запись — `ignored`, неразбираемая — `unparsed`; ни одна не роняет шаг.
- **Схема применяется ко всем сообщениям турна** → агент, который между
  инструментами пишет пояснения, отдаёт их JSON-ом по схеме; последнее
  побеждает, движку безразлично. Пояснения в промптах для Codex лучше не
  просить.
- **Пользовательский `~/.codex/config.toml` подгружается всегда** → чужие
  MCP-серверы и навыки влияют на шаг; отсечь их нечем без `strict`, который вне
  объёма. Названо в документации.
- **`OPENAI_API_KEY` попадает под `env_deny` (`*_KEY`)** → пользователи с
  ключом вместо входа через ChatGPT получат `unauthenticated`. В `docs/config.md`
  — как разрешить точечно.
- **Живой прогон стоит квоты подписки** → пайплайн приёмки дёшев: короткие
  промпты, потолок токенов, `read-only`.
- **Обрыв потолком не срабатывает по ходу шага** → записано ограничением;
  `timeout` шага работает как прежде.
- **MCP не подтверждено записью** → решение 6 с ветвлением на `mcp: false`.

## Migration Plan

Ничего не мигрирует: плагин подключается только явным объявлением. Откат —
убрать объявление из `plugins`.
