## ADDED Requirements

### Requirement: Поток событий несёт действующие дашборды

Поток событий демона SHALL нести действующие дашборды отдельным событием — по каждому имя, файл, заголовок, сетку с ячейками и причину отказа сборки, если она была. Событие MUST отправляться первым же обменом при подключении и дальше только при отличии от отправленного прежде — тем же правилом, каким отправляются маршруты, виджеты и плагины. Каталоги дашбордов обоих слоёв MUST наблюдаться тем же единственным наблюдателем демона, отдельной частью его отпечатка, и MUST NOT перечитываться, когда изменилась лишь другая часть. Отказ сборки одного дашборда MUST NOT отменять остальные и MUST NOT гасить витрину.

#### Scenario: Дашборды пришли при подключении

- **WHEN** страница подключилась к потоку событий
- **THEN** она получает действующие дашборды первым же обменом

#### Scenario: Правка файла дашборда отражается в потоке

- **WHEN** файл дашборда изменён при открытой странице
- **THEN** событие приносит новое содержимое, а маршруты, состав экранов и виджеты не пересылаются

#### Scenario: Сломанный файл не отменяет остальные

- **WHEN** один файл дашборда перестал разбираться
- **THEN** событие несёт прочие дашборды и причину отказа по сломанному

#### Scenario: Неизменное не пересылается

- **WHEN** такт наблюдения прошёл без правки каталогов дашбордов
- **THEN** событие дашбордов не отправляется

### Requirement: Демон запускает прогон дочерним процессом по явному действию пользователя

Демон SHALL запускать прогон только по явному действию пользователя через объявленный маршрут API и MUST порождать его отдельным отсоединённым дочерним процессом с рабочим каталогом в корне названного проекта, а не исполнять прогон внутри себя. Маршрут MUST принимать ключ проекта и файл пайплайна и ничего сверх: проект MUST значиться в указателе проектов, файл MUST быть среди пайплайнов этого проекта, найденных тем же обходом, каким их перечисляет витрина, и любое иное значение MUST отклоняться ошибкой клиента с названной причиной. Ответ MUST подтверждать запуск, не обещая идентификатора прогона: прогон MUST появляться в обзоре обычным тактом наблюдателя. Незавершённый прогон того же пайплайна отменять запуск MUST NOT: нажатие равносильно запуску из терминала. Отказ самого порождения процесса MUST быть названной причиной в журнале демона и MUST NOT останавливать демон: он приходит после ответа об успешном приёме, и необработанным исключением гасил бы витрину целиком.

#### Scenario: Запуск известного пайплайна

- **WHEN** пользователь запускает пайплайн известного проекта через объявленный маршрут API
- **THEN** демон порождает дочерний процесс прогона в корне этого проекта и подтверждает запуск

#### Scenario: Неизвестный проект или пайплайн

- **WHEN** запрос называет проект, которого нет в указателе, либо файл, которого нет среди пайплайнов проекта
- **THEN** запрос отклоняется ошибкой клиента с названной причиной, и ни одного процесса не порождается

#### Scenario: Процесс прогона не породился

- **WHEN** порождение дочернего процесса отказало — исполняемого файла нет или он недоступен
- **THEN** отказ назван причиной в журнале демона, а сам демон продолжает отвечать витрине

#### Scenario: Прогон переживает остановку демона

- **WHEN** прогон запущен из витрины, и демон остановлен
- **THEN** прогон продолжает исполняться, а его файлы дописываются дочерним процессом

## MODIFIED Requirements

### Requirement: Наблюдение не изменяет журнал

Демон SHALL только читать файлы, за которыми наблюдает: он MUST NOT изменять, создавать или удалять файлы прогонов. Кроме корня прогонов демон читает файлы проектов, названных указателем `projects.json`, — очередь улучшений, каталог переиспользуемых шагов и каталог виджетов, — файлы маршрутов своих слоёв, каталоги дашбордов своих слоёв и каталоги плагинов своих слоёв, и это чтение MUST оставаться чтением: ни компиляция виджета, ни сборка браузерной половины плагина, ни кеш их результатов, ни наблюдение за файлом маршрутов или файлом дашборда MUST NOT записывать ничего ни в каталог проекта, ни в каталог плагина. Запись демона в каталог проекта или в домашний каталог SHALL быть только записью файла маршрутов слоя или файла дашборда слоя по явному действию пользователя через объявленный маршрут API; никакой другой файл проекта демон изменять MUST NOT, и встроенный файл маршрутов поставки MUST NOT изменяться никогда. Файлы прогона, появившиеся от прогона, который пользователь запустил через объявленный маршрут API, MUST создаваться его дочерним процессом, а не самим демоном. Собственное состояние демона (pid-файл и лог) MUST лежать вне каталогов прогонов, вне каталогов проектов и вне каталогов плагинов.

#### Scenario: Наблюдение оставляет файлы нетронутыми

- **WHEN** демон наблюдает за корнем прогонов, каталогами проектов, файлами маршрутов и каталогами дашбордов
- **THEN** ни один наблюдаемый файл не создаётся, не изменяется и не удаляется наблюдением

#### Scenario: Запись файла маршрутов по действию пользователя

- **WHEN** пользователь сохраняет маршрут через объявленный маршрут API витрины
- **THEN** демон пишет только файл маршрутов названного слоя, а прочие файлы проекта остаются нетронутыми

#### Scenario: Запись файла дашборда по действию пользователя

- **WHEN** пользователь сохраняет дашборд через объявленный маршрут API витрины
- **THEN** демон пишет только файл этого дашборда в названном слое, а прочие файлы проекта остаются нетронутыми

#### Scenario: Состояние демона вне наблюдаемых каталогов

- **WHEN** демон поднят
- **THEN** его pid-файл и лог лежат вне корня прогонов, вне каталогов проектов и вне каталогов плагинов
