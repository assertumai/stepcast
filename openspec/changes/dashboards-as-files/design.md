## Context

Витрина уже разобрана на части, между которыми этому изменению остаётся
положить одну сущность.

- **Маршрут** — строка файла со своим `id`, путём, целью и параметрами
  (`user-defined-routes`, `docs/routes.md`). Вид цели — ключ keyed-слота
  `route.target`; сегодня в нём два вкладчика, `screen` и `widget`, и оба
  внесены каркасом (`ui/src/plugins/shell.tsx`). Каркас прямо записан как
  место, которого третий вид не касается.
- **Экран** — строка состава с объявлением на демоне
  (`src/ui/screens/*/declaration.ts`) и браузерной половиной, вносящей вклад
  в keyed-слот `screen` (`builtin-pages-as-plugins`). Данные витрины
  раздаются вкладчику props, а к сервисам обращается только каркас
  (`cordis-kernel-browser`, Решение 10).
- **Виджет** — файл `<проект>/.stepcast/widgets/<id>.tsx`, который демон
  компилирует по запросу и отдаёт ES-модулем с версией в адресе
  (`ui-runtime-widget-spike`). Хост (`ui/src/widgetHost.tsx`) отрисовывает
  его **без аргументов**: ни параметров, ни данных. Вне слотов, вне ядра.
- **Наблюдатель** демона отпечатывает корень прогонов, очередь, виджеты,
  плагины и файлы маршрутов по частям и пересобирает только сдвинувшуюся
  часть; поток `GET /api/events` несёт каждую часть своим событием и только
  при отличии от отправленного прежде.
- **Запись** демона сегодня — ровно два файла по явному действию
  пользователя: файл маршрутов слоя и файл настроек. Ни одного процесса демон
  не порождает.

Пункт очереди требует, чтобы дашборд был содержимым без адреса, чтобы виджеты
для конструктора брались из keyed-слота по имени — встроенные и
пользовательские одинаково, — и чтобы среди встроенных виджетов был запуск
пайплайна. Последнее и есть единственное место, где изменение выходит за
границу «витрина только читает».

## Goals / Non-Goals

**Goals:**

- Дашборд описан файлом, читаемым и правимым руками, агентом и конструктором,
  и переносимым между проектами копированием файла.
- У дашборда нет адреса: он открывается маршрутом, и один дашборд стоит за
  несколькими маршрутами с разными параметрами.
- Виджет — вклад в один keyed-слот витрины, с манифестом параметров;
  встроенный и пользовательский пишутся и перечисляются одинаково.
- Параметры маршрута доезжают до виджетов дашборда подстановкой, приведённой
  к объявленному типу.
- Отказ локален: битая ячейка не гасит соседние, битый дашборд не гасит
  витрину, битый файл не переписывается сохранением.
- Правка файла применяется в открытой вкладке без перезагрузки.

**Non-Goals:**

- **Замена встроенного виджета чужим по тому же имени.** Пространства ключей
  разведены (Решение 4), и подмена имени поставки — отдельный вопрос вместе с
  патчем состава браузерных строк.
- **Слои у самих виджетов-файлов.** Виджет остаётся файлом проекта
  (`docs/widgets.md`); слои получает дашборд, а не виджет.
- **Снятие ограничений спайка виджетов**: проверка типов, локальные импорты,
  песочница, рост памяти вкладки при частой замене.
- **Очередь предложенных правок** дашбордов и виджетов агентом —
  `agent-edits-widgets`.
- **Отмена/повтор, перетаскивание мышью с инерцией, сетка с
  автораскладкой** — конструктор двигает ячейку по координатам сетки, история
  правок остаётся историей файла.
- **Планировщик и повторяемость запуска** из кнопки: `POST /api/run` — ровно
  один запуск, расписание — `schedule-trigger`.

## Decisions

### Решение 1. Дашборд — файл в каталоге, ключ — имя файла

`<проект>/.stepcast/dashboards/<id>.yml`, `<id>` — один безопасный сегмент
пути, тем же правилом, что и `<id>` виджета (`src/ui/widgets.ts`,
`resolveWidgetFile`). Каталог, а не один файл со списком дашбордов: дашборд
переносится между проектами копированием файла, а правка одного дашборда
конструктором не переписывает соседние — то же соображение, по которому
виджет живёт файлом, а не записью в реестре.

Альтернатива — `.stepcast/dashboards.yml` одним документом — отвергнута:
сохранение из витрины трогало бы чужие дашборды, а отказ разбора одного
скрывал бы все.

### Решение 2. Два слоя, перекрытие файлом целиком

Домашний `~/.stepcast/dashboards/` и проектный
`<корень демона>/.stepcast/dashboards/` — те же два пользовательских слоя,
что у маршрутов, и тот же корень проекта (каталог, в котором поднят демон).
Встроенного слоя нет: дашбордов поставки не существует, и заводить пустой
слой ради симметрии значило бы обещать файл, которого в пакете нет.

Перекрытие — целиком файлом, а не слиянием по листьям, каким сливаются
строки маршрутов. Строка маршрута — набор независимых полей одного адреса, и
«поменять только название пункта» осмысленно; дашборд — раскладка, и
слияние сеток дало бы ячейку домашнего слоя посреди проектной сетки,
которую перекрывающий не объявлял и не видит. Источник у дашборда поэтому
один — файл, и он называется рядом с заголовком.

### Решение 3. Вид цели `dashboard` — вклад в `route.target`, ключ вида

Маршрут получает третью форму цели: `target: { dashboard: <id> }`. Вклад в
keyed-слот `route.target` по ключу `dashboard` вносит новая браузерная
строка (`ui/src/plugins/dashboard.tsx`), а не каркас: `user-defined-routes`
(Решение 5) оставил слот именно под это, и файл каркаса изменение не трогает.

Отсюда бесплатно: адреса у дашборда нет; два маршрута на один `dashboard: run`
с разными `params` — обычное состояние; дашборд, на который не ведёт ни один
маршрут, — законный файл, просто не открытый (и видимый в конструкторе через
маршрут, который на него ведёт). Название пункта меню для цели-дашборда —
заголовок дашборда, тем же правилом «нет `nav.title` — берётся заголовок
цели».

### Решение 4. Виджет — вклад в keyed-слот `widget`; ключи разведены пространствами

Новый слот `WIDGET` (`keyed`) в поверхности `@stepcast/slots`. Ключ
встроенного виджета — голое имя (`runs`, `usage`), ключ виджета-файла —
`<projectKey>/<id>`, тот же составной ключ, каким виджет уже адресуется в
маршруте и в адресе модуля. Пространства не пересекаются по форме ключа, и
`duplicate-key` реестра слотов между поставкой и проектом невозможен без
злого умысла.

Плата: заменить встроенный виджет своим по тому же имени нельзя — первый по
`seq` выигрывает keyed-слот, а первым идёт поставка. Это Non-Goal, а не
недосмотр: подмена имени поставки — то же самое, что подмена строки состава,
и решается патчем дерева, когда браузерные строки научатся читаться с диска
(`user-plugins-from-files`).

### Решение 5. Манифест — регистрация в сервисе-каталоге, а не поле вклада

Каталог конструктора обязан знать по каждому виджету заголовок и параметры.
Дескриптор вклада (`Contribution`, `ui/src/slots.ts`) описывает **props,
которые слот раздаёт**, и добавить в него произвольные метаданные значило бы
завести третий параметр типа у `SlotDescriptor` и коснуться всех слотов
витрины ради одного.

Поэтому манифест регистрируется отдельно — сервисом `ctx.widgets` страницы,
тем же приёмом, каким серверная половина экрана регистрирует своё объявление
(`ctx.screens.register`, `src/ui/screens/registry.ts`): владелец определяется
по фиберу вызвавшего, регистрация снимается вместе с его областью. Слот
отвечает на «чем рисовать», каталог — на «что предложить в конструкторе и
как проверить параметры», и это то же разделение, что уже живёт между слотом
`screen` и сервисом `screens`.

Виджет, внёсший вклад без манифеста, считается виджетом без параметров: в
каталоге он есть, настраивать в нём нечего.

### Решение 6. Манифест виджета-файла приезжает с его модулем, а каталог грузит модули по требованию

У виджета-файла манифест — именованный экспорт модуля (`export const widget =
{ title, params }`), потому что единственный, кто его знает, — сам файл.
Значит, до первого `import()` параметры неизвестны.

Отвергнуто: разбор исходника демоном (обещал бы статический разбор
произвольного TypeScript и врал бы на первом же вычисляемом значении) и
сайдкар-файл рядом с `.tsx` (второй файл на виджет, который забудут
обновить).

Принято: ключ виджета-файла попадает в слот и в каталог сразу, как только
событие `widgets` его назвало, — поставить его на дашборд можно немедленно, а
строка каталога до загрузки честно говорит, что параметры ещё не прочитаны.
Конструктор, открыв каталог, импортирует модули, которых ещё не загружал;
дашборд импортирует те, что стоят в его ячейках. Отказ компиляции показывается
в каталоге той же карточкой, что и на дашборде, — хост уже умеет отличать её
от неразрешённого импорта.

Страница не импортирует все виджеты всех проектов на загрузке: у демона,
знающего десяток проектов, это была бы десятки модулей ради экрана, который,
возможно, не откроют.

### Решение 7. Виджет получает params и те же данные витрины, что экран

Props виджета — `{ params, overview, backlog, widgets, snapshot, navigate }`:
значения параметров плюс `LiveDataProps`, которые каркас и так раздаёт
экранам. Второго способа доставки данных витрина не заводит — иначе у неё
было бы два контракта на один вопрос «что видно вкладчику слота».

Виджету-файлу те же props уходят через хост, и это и есть ответ на
отложенный вопрос спайка. Что сверх — виджет берёт сам `fetch('/api/...')` со
своей же петлевой страницы: демон отдаёт те же данные, что показывают
встроенные экраны, и запрещать это было бы притворством (виджет исполняется
с правами страницы — `docs/widgets.md`, «Песочницы»).

### Решение 8. Значение параметра: подстановка, потом приведение к объявленному типу

В файле дашборда значение параметра — скаляр (строка, число, булево). Строка
проходит подстановку `${params.<имя>}` тем же языком, что и параметры цели
маршрута, где пространство `params` — параметры пути и параметры цели,
собранные разбором адреса. Приведение к типу манифеста — **после**
подстановки, тем же порядком, каким живут числовые поля пайплайна
(`numeric-field-substitution`): иначе `limit: "${params.limit}"` отклонялся бы
на разборе как «ожидалось число, получена строка».

Значение, не приводимое к объявленному типу, — причина на месте ячейки,
называющая виджет, параметр, полученное значение и, если оно пришло из
подстановки, само выражение.

### Решение 9. Форму файла проверяет демон, смысл ячейки — витрина

Демон проверяет то, для чего достаточно самого документа: схему (`Zod` →
`schema/dashboard.schema.json`), уникальность `id` ячеек, попадание ячейки в
объявленное число колонок, отсутствие наложений. Всё это — свойства файла, и
отказ здесь — отказ сборки дашборда целиком, с именем файла и места.

Знание о том, какие виджеты существуют и какие у них параметры, живёт только
в браузере (Решение 5): у демона нет ни слотов, ни манифестов. Поэтому
неизвестный виджет, лишний параметр, недостающий обязательный и неверный тип
проверяются на странице и показываются **на месте одной ячейки** — тем же
приёмом, каким маршрут показывает цель без действующего вклада
(`docs/routes.md`). Битая ячейка соседей не гасит.

Это то же разделение, что уже принято маршрутами: демон собирает таблицу и
не знает, есть ли у цели вкладчик.

### Решение 10. Живое применение — своя часть отпечатка и своё событие

Наблюдатель отпечатывает два каталога дашбордов (`mtime` и размер каждого
файла) отдельной частью и пересобирает дашборды только по её сдвигу: правка
дашборда не заставляет перечитывать очередь, виджеты, маршруты или прогоны, и
наоборот. Поток несёт событие `dashboards` первым обменом и дальше только при
отличии от отправленного — то же правило, что у `routes`, `widgets` и
`plugins`.

Отказ сборки одного дашборда не отменяет остальные и не гасит витрину:
действующим остаётся последнее собранное содержимое, причина едет вместе с
ним и показывается на месте того дашборда, который сломан.

### Решение 11. Конструктор — режим правки той же цели, а не отдельный экран

Правка живёт в том же вкладе `route.target`, что и показ: у дашборда нет
своего адреса, а значит, и «экрану-конструктору» неоткуда взяться, кроме как
из адреса самого дашборда. Переключатель правки, каталог виджетов, панель
параметров выбранной ячейки — состояние страницы; сохранение — `POST
/api/dashboards` с именем дашборда, слоем (`home` либо `project`) и
документом.

Пишет демон, документом `yaml` (`Document`), как и файл маршрутов:
комментарии, порядок ячеек и форматирование пользователя переживают правку.
Файл, который не разбирается, не перезаписывается: одно сохранение из витрины
не должно стирать то, что пользователь не успел починить.

Маршрут, ведущий на несуществующий дашборд, показывает причину и предлагает
создать файл в названном слое — иначе первый дашборд заводился бы только
руками, а конструктор был бы недостижим из витрины.

### Решение 12. Сетка — явные координаты, а не поток

`grid.columns` (умолчание 12) и `at: { column, row, width, height }` у каждой
ячейки. Явные координаты, потому что конструктор двигает ячейку, а порядок
строк в файле после этого не должен решать, что где стоит: иначе перестановка
двух ячеек мышью переписывала бы весь список, а правка руками — двигала бы
раскладку незаметно для автора. По той же причине `id` ячейки обязателен:
им адресуется ячейка в диагностике и в правке, а выдуманный движком ключ
менялся бы под пользователем при каждой перестановке.

Наложение ячеек — отказ (Решение 9), а не «кто последний, тот и сверху»:
скрытый под соседом виджет неотличим от пропавшего.

### Решение 13. Запуск прогона — отсоединённый дочерний процесс, а не работа внутри демона

Кнопка запуска требует от демона первого в его жизни порождения процесса.
Прогон исполняется **не в демоне**: агентский шаг длится часами, единственный
поток демона он бы занял целиком, а остановка демона убила бы прогон. `POST
/api/run` с ключом проекта и файлом пайплайна проверяет, что проект есть в
`projects.json`, а файл — среди пайплайнов проекта (тем же обходом
`listPipelineFiles`, каким их перечисляет экран «Пайплайны»), и запускает
`stepcast run` дочерним отсоединённым процессом с `cwd` в корне проекта.

Ответ — 202 и ничего о прогоне: идентификатор известен не раньше, чем
дочерний процесс напишет журнал, а прогон и так приедет в обзор обычным
тактом наблюдателя. Живой прогон того же пайплайна запуск не отменяет — в
отличие от планировщика (`schedule-trigger`), где срабатывает расписание, а
не человек: нажатие кнопки равносильно `stepcast run` в терминале, и
запрещать его значило бы решать за пользователя.

Свойство «демон только читает» этим не отменяется в той части, ради которой
оно вводилось: сам демон в корень прогонов не пишет ни байта — файлы прогона
создаёт дочерний процесс, как и при запуске из терминала.

### Решение 14. Пять встроенных виджетов — те же данные, что у экранов, с параметрами вместо зашитых значений

`runs` (список прогонов; `project`, `pipeline`, `status`, `limit`),
`pipeline` (состояние пайплайна: его последний либо названный прогон;
`project`, `pipeline`, `run`), `usage` (расход за период; `days`, `project`),
`run-pipeline` (кнопка запуска; `project`, `pipeline`, `label`),
`step-output` (вывод шага; `project`, `run`, `job`, `step`, `attempt`).

Данные берутся из тех же источников, что у нынешних экранов: обзор и снимок
прогона — из props витрины, расход и вывод шага — своими запросами к уже
объявленным маршрутам API. Новых маршрутов чтения изменение не заводит:
встроенный виджет, которому понадобился бы свой, — признак того, что он не
виджет, а экран.

## Risks / Trade-offs

- **Каталог виджетов исполняет чужой код при открытии** (Решение 6) → это тот
  же код, который уже исполняется, когда виджет открыт на экране «Виджеты»
  или стоит на дашборде, и тот же файл самого пользователя; ограничение
  «песочницы нет» остаётся записанным в `docs/widgets.md`.
- **Запуск прогона из витрины — процесс, порождённый по HTTP** (Решение 13)
  → демон слушает только петлю, проект обязан значиться в `projects.json`, а
  файл пайплайна — быть найденным обходом проекта: произвольную команду через
  этот маршрут не выполнить. Аргументов сверх имени пайплайна маршрут не
  принимает вовсе.
- **Правка руками и правка конструктором могут разойтись** — вкладка,
  открытая на дашборде, сохранит то, что видела до правки файла → сохранение
  отправляет отпечаток документа, от которого правка началась; разошедшийся
  отпечаток — отказ с причиной «файл изменился с момента открытия», а не
  молчаливая перезапись.
- **Приведение типов после подстановки прощает больше, чем строгая схема**
  (Решение 8) → ошибка не исчезает, а переезжает на ячейку и называет
  выражение, которое дало значение; тот же обмен уже принят числовыми полями
  пайплайна.
- **Два слоя без встроенного** (Решение 2) означают, что «сбросить дашборд к
  поставке» нечем → сбрасывать не к чему: поставка дашбордов не приносит, а
  удаление файла проектного слоя возвращает домашний.
- **Пять встроенных виджетов повторяют куски четырёх экранов** → общие части
  выносятся в компоненты, которыми пользуются оба (таблица прогонов, карточка
  расхода); повторение вёрстки в двух местах — та самая цена, ради ухода от
  которой экраны и разбирались на слоты.

## Migration Plan

1. Формат, схема и чистый модуль подстановок — без единого потребителя;
   `npm run schema` печатает `schema/dashboard.schema.json`, тест свежести
   схем держит его в согласии с моделью.
2. Слот `WIDGET`, каталог и манифесты; пять встроенных виджетов; хост
   виджета-файла начинает передавать props. Виджеты спайка продолжают
   работать: компонент, не объявивший манифеста, получает props и вправе их
   игнорировать (`examples/widgets/clock.tsx` не меняется).
3. Вид цели `dashboard`, чтение слоёв, событие потока, часть отпечатка —
   дашборд открывается по маршруту, правится только руками.
4. Конструктор и запись; `POST /api/run` и виджет запуска.
5. Документация: `docs/dashboards.md`, снятые Non-Goals в `docs/widgets.md` и
   `docs/routes.md`.

Откат — снятие двух строк состава (`ui-dashboards`, `ui-run-launch`) и вклада
`dashboard` в `route.target`: файлы дашбордов остаются на диске неоткрытыми,
маршрут на них показывает «вид цели не знаком составу» — ровно то состояние,
в котором витрина живёт сегодня.

## Open Questions

- **Нужен ли дашборду свой перечень в витрине** — экран «Дашборды» со списком
  файлов обоих слоёв? Сегодня дашборд виден только через маршрут, ведущий на
  него; файл без маршрута не показан нигде. Отложено до первого случая, когда
  это помешает: перечень маршрутов уже показывает цель `dashboard`, и
  дашборд-сирота заметен по отсутствию в нём.
- **Ячейка с виджетом, которого нет в этом проекте** (`<projectKey>/<id>`
  чужого проекта) показывается причиной; стоит ли позволить дашборду
  ссылаться на виджет проекта, отличного от того, чей дашборд открыт, — или
  это признак того, что дашборд скопировали не туда? Пока разрешено:
  ключ виджета уже несёт проект, и запрет был бы правилом без нужды.
- **Заголовок карточки ячейки против заголовка манифеста**: сейчас ячейка
  вправе перекрыть заголовок виджета своим. Не станет ли это способом
  запутать — две карточки «Прогоны» с разными фильтрами? Оставлено
  пользователю: он и различает их подписями.
