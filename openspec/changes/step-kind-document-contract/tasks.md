## 3. Разбор и схема документа

- [x] 3.1 `src/core/pipeline/expand.ts`: синтез формы документа из имени и
  `fields` для вклада без `document` (`test`, `keys`, `schema`, `parse`) —
  одной функцией, которой пользуются и разбор, и сборка схемы.
- [x] 3.2 `matchStepKind`: обход реестра без ветви по происхождению —
  `test` берётся у внутренней формы, у объявленной или у синтезированной.
  Правило «побеждает первый по порядку регистрации» зафиксировать
  комментарием (design.md, Решение 8).
- [x] 3.3 `toStep`: единственная оставшаяся ветвь — `isNativeStepKind`;
  результат разбора вклада кладётся в `PluginStep.fields` тем же кодом, каким
  сегодня это делает `toPluginStep`.
- [x] 3.4 `toPluginStep`: раскрытие подстановок по занятым ключам (а не по
  одному ключу имени), затем `document.schema` через `ajv`, затем `parse`,
  затем `fields` через `ajv`; пропуск проверок при отложенной подстановке —
  прежним правилом. Исключение `parse` оборачивается `StepcastError` с
  именем вида, адресом шага и владельцем.
- [x] 3.5 `src/core/pipeline/schema.ts`: `PluginStepSchema` обобщается с
  одного ключа на перечень занятых; `assertStepKindNameAvailable` принимает
  вклад и уже занятые вклады, проверяя каждый объявленный ключ против
  `STEP_COMMON_KEYS`, `BUILTIN_STEP_KIND_KEY_OWNERS` и чужих занятых ключей.
- [x] 3.6 `src/core/plugins/kernel.ts`: `ContributionNameGuard` расширяется до
  `(name, contribution: unknown, taken: ReadonlyMap<string, unknown>)`. Ядро
  доменного типа не узнаёт — комментарием сослаться на границу
  `kernel-domain-free-imports`; проверить, что линт границы
  (`no-restricted-imports` на `src/core/plugins/**`) остаётся зелёным.
- [x] 3.7 `src/core/plugins/registry.ts`: `pluginStepKindNames` отдаёт имена и
  занятые ключи видов, приносящих свою ветвь схемы, — без вопроса о
  происхождении.

## 6. Находки ревью

- [x] 6.1 `src/core/pipeline/schema.ts`: при объявленном `document` имя вида
  не проверялось на занятость вовсе — `assertStepKindNameAvailable` спрашивал
  только `document.keys`. Имя проверяется наравне с занятыми ключами (в
  занятые ключи ветви схемы при этом не попадая), а отказ на занятом ключе
  называет вид, которому этот ключ принадлежит; прежние дословные тексты
  отказа на имени сохранены. Покрыто `test/plugin-step-kind.test.ts`.
- [x] 6.2 Там же, `PluginStepSchema`: `z.unknown()` в zod 4 — обязательный
  ключ, и ветвь делала обязательными **все** объявленные ключи, отклоняя
  форму `uses:` + `with:` дампом объединения. Ветвь собирается объединением
  по каждому занятому ключу — обязателен ровно один, остальные
  необязательны, — а обязательность объявляет `document.schema` вклада, её
  словами и отказывая. Покрыто `test/step-kind-document-form.test.ts`.
- [x] 6.3 `src/core/pipeline/published-schema.ts`: в схему проекта
  вкладывались только подсхемы ключей из `document.schema.properties`, а
  `required`, `oneOf` и прочее содержание терялось молча. Теперь `properties`
  и `required` переносятся в узел-метку, остаток схемы — целиком отдельным
  `allOf`, `additionalProperties`/`unevaluatedProperties` отбрасываются как
  уже подразумеваемые узлом, а ключи состава объекта — с названной причиной
  в `notes`. Покрыто `test/published-schema.test.ts`.
- [x] 6.4 `src/core/pipeline/late.ts`: позднее раскрытие собирало адрес как
  `…steps.<n>.<имя вида>` и для вклада с формой документа называло путь,
  которого в файле нет. Адрес — адрес шага (Решение 6); реестр приходит
  необязательным параметром, `runner.ts` его передаёт. Покрыто
  `test/step-kind-document-form.test.ts`.
- [x] 6.5 `src/core/pipeline/expand.ts`: `stepKindTest` читал поле `native`
  по одному его наличию — вклад, внесённый `ctx.steps.register` и случайно
  несущий это имя, ронял чтение документа голым TypeError. Вопрос —

- [x] 6.6 `test/plugin-load.test.ts`: тест запрета поля утверждал снятое
