## ADDED Requirements

### Requirement: Вид шага определяется ключом из реестра видов

Разбор документа SHALL определять вид шага ключом, объявленным реестром видов шага, а не закрытым перечислением, и MUST собирать ветви схемы шага из действующего реестра. Ключ, не объявленный ни одним видом шага, MUST быть отказом разбора с перечнем доступных видов — встроенных и плагинных вместе, — а не молча пропущенным полем. Значение под ключом плагинного вида MUST проверяться JSON Schema вклада тем же валидатором и с той же диагностикой, что и значение плагинного предиката: отказ MUST называть путь поля и причину. Шаг, вид которого распознан, MUST попадать в раскрытую модель именем вида и полями, и движок MUST обращаться с ними как с данными.

#### Scenario: Шаг плагинного вида раскрывается

- **WHEN** в реестре есть вид шага `http`, и шаг объявляет ключ `http` с полями по схеме вклада
- **THEN** шаг попадает в раскрытый пайплайн именем вида и его полями

#### Scenario: Неизвестный ключ вида шага

- **WHEN** шаг объявляет ключ, которого не знает ни один вид шага действующего реестра
- **THEN** разбор отказывает, называя ключ и перечень доступных видов шага

#### Scenario: Поля не по схеме вклада

- **WHEN** значение под ключом вида шага не проходит схему вклада
- **THEN** разбор отказывает, называя путь поля и причину, и называет плагин, объявивший схему

#### Scenario: Документ без плагинных видов разбирается как прежде

- **WHEN** пайплайн объявляет только шаги `agent`, `run`, `script` и `uses`
- **THEN** разбор, его диагностика и раскрытая модель совпадают с прежними

### Requirement: Поля вида шага раскрываются типизированно и проверяются перед исполнением

Поля плагинного вида шага SHALL раскрываться типизированным проходом подстановок — тем же, каким раскрывается объявленный вход шага `script`, — чтобы подстановка на объект или список не превращалась в строку. Схема полей MUST проверяться дважды: при раскрытии — по тому, что известно статически, и перед исполнением шага — по окончательным значениям, потому что до позднего раскрытия поле могло нести отложенную подстановку. Замок раскрытого пайплайна MUST печатать вид шага и его поля в объявленном виде, с нераскрытыми отложенными подстановками, а статическая проверка MUST звать хук вклада и печатать его диагностики наравне со своими.

#### Scenario: Отложенная подстановка в поле

- **WHEN** поле вида шага объявлено подстановкой на выход работы выше по графу, дающей объект
- **THEN** шаг получает объект, а не его строковое представление

#### Scenario: Значение после позднего раскрытия не по схеме

- **WHEN** поле, проверенное при разборе, после позднего раскрытия перестало соответствовать схеме вклада
- **THEN** шаг отказывает названной причиной до исполнения, а не посреди него

#### Scenario: Замок печатает вид шага

- **WHEN** раскрытый пайплайн зафиксирован в замке
- **THEN** шаг записан именем своего вида и полями в объявленном виде

#### Scenario: Диагностика вклада печатается статической проверкой

- **WHEN** хук статической проверки вклада вернул предупреждение по полю шага
- **THEN** проверка печатает его с файлом и путём поля наравне со своими диагностиками
