## Context

Сегодня вид шага — не понятие движка, а совпадение семи независимых
перечислений. Документ различает виды присутствием ключа (`prompt`, `run`,
`script`, `uses`) в объединении строгих zod-объектов
(`src/core/pipeline/schema.ts:354`); раскрытие разбирает их четырьмя `if`
(`expand.ts:1008—1081`); модель хранит объединение трёх интерфейсов
(`model.ts:325`); исполнение выбирает между двумя функциями тернарником
(`runner.ts:1661`); замок печатает три ветки (`lock.ts:64—132`); журнал знает
`z.enum(['agent', 'run', 'script'])` (`journal/schema.ts:165`); витрина
собирает карточку дюжиной `step.kind === '…'` (`ui/pipelines.ts:179—204`,
`ui/snapshot.ts:61`). Добавить вид шага значит пройти все семь мест, и
пользовательскому плагину это недоступно вовсе.

Образец уже есть, и он свежий. `plugin-contributions` открыл ровно так же
закрытое объединение предикатов: ветвь `z.object({ [name]: z.unknown() })` в
схеме документа, проверка значения JSON Schema вклада через `ajv` при
раскрытии (`expand.ts:520—545`), вариант `{ kind: 'plugin', name, value }` в
модели, хук `lint(value, site)`, вызов `evaluate` из общего прохода
(`expect/evaluate.ts:350`), имя предиката в журнале. Ничего из этого не
пришлось изобретать заново — и здесь не придётся: вид шага отличается от
предиката двумя вещами, которых у предиката нет, — исполнителем и
отображением.

`cordis-kernel-daemon` дал недостающее: ядро — корневой контекст, служебный
сервис вида вклада (`ContributionService`, `kernel.ts:68`) умеет регистрацию
эффектом области вызвавшего, конфликт имён именованным отказом и вывод
владельца из области. Четвёртый сервис — это тридцать строк, а не новая
архитектура.

Потребитель назван очередью: `user-decision-steps` — шаг ожидания решения
человека — объявлен первым плагинным видом шага, и его `done_when` прямо
ссылается на реестр из этой работы. Второй и третий (ожидание события, запрос
к базе) названы в обосновании самого пункта.

## Goals / Non-Goals

**Goals:**

- Вид шага — вклад в контекст ядра: имя, схема полей, схема выхода, линт,
  исполнитель, название для витрины.
- Разбор, линт, исполнение, замок, журнал, опубликованная схема и витрина
  собираются из реестра, а не из перечислений.
- Встроенные `agent`, `run`, `script`, `uses` регистрируются тем же сервисом
  и тем же вызовом, не меняя ни строки своего поведения.
- Снятие области плагина снимает вид шага; отказ после снятия называет и вид,
  и плагина.
- Пример без подпроцесса (`http`) написан только через публикуемую
  поверхность — как доказательство, что контракта достаточно.

**Non-Goals:**

- Исполнение пользовательских скриптов внутри процесса движка. Файл
  пользователя исполняется подпроцессом и только им (`script-step-runners`).
- Сборка контекста (`context`) для плагинного вида шага: её некому
  потреблять.
- Сессии, продолжение диалога, эскалация моделей и выбор модели для
  плагинного вида — это свойства агентского шага.
- Песочница для исполнителя. Её нет у плагина вообще (`docs/plugins.md`), и
  вид шага не заводит исключения.
- Открытие якорей состояния дерева и триггеров.
- Вид шага, вносимый браузерной половиной витрины: карточка собирается по
  данным реестра демона, свой компонент на вид шага — отдельная работа.

## Decisions

### Решение 1. Четвёртый служебный сервис, а не поле в трёх существующих

Вид шага заводится сервисом `steps` рядом с `backends`, `predicates`,
`commands` — тем же классом `ContributionService`, с тем же
`register(имя, вклад)`. Имя `steps` пополняет `KERNEL_RESERVED_NAMES`.

Альтернатива — «вид шага как разновидность команды» либо «как предикат с
исполнителем» — отвергнута: и то и другое дало бы две сущности под одним
именем сервиса, а `owners`, диагностика конфликта и `stepcast plugins` строят
свои сообщения по виду вклада («Имя предиката X занято»). Четвёртый сервис
обходится ровно в один элемент перечня, одну карту в `Registry`, одну строку
в `KIND_NAMES` и один ключ в `owners`; ничего сверх.

### Решение 2. Встроенные виды регистрируются тем же вызовом, но несут zod-ветвь, а не JSON Schema

Вклад вида шага несёт ветвь разбора в одной из двух форм:

- `fields` — JSON Schema значения под ключом вида. Это единственная форма,
  которую публикует `stepcast/plugin`; из неё движок сам строит ветвь
  документа (`z.object({ [name]: z.unknown() }).strict()` поверх общей части)
  и сам проверяет значение `ajv` при раскрытии, отдавая `PluginStep`;
- `document` — готовая zod-ветвь и типизированный разбор, отдающий
  типизированный `Step`. Форма внутренняя: в публикуемой поверхности её нет.

Встроенные `agent`, `run`, `script` и `uses` регистрируются второй формой.
Это и есть обещанное «зарегистрированы тем же способом»: тот же сервис, тот же
вызов, тот же владелец, та же обратимость, тот же обход при разборе, линте,
исполнении и печати схемы. Отличается язык ветви — и только он.

Альтернатива — перевести встроенные виды на `fields` — отвергнута тем же
доводом, каким `plugin-contributions` отказался делать вкладами встроенные
предикаты (`builtin.ts:23—35`): ветви встроенных видов — строгие объекты с
объединениями, отказами по месту (`declaredByManifest`) и разбором, читающим
файлы (`prompt: file:`, `uses`, `script`), а модели — типизированные
интерфейсы, полноту разбора которых проверяет компилятор. Обмен четырёх
проверенных ветвей на четыре приведения `unknown` ухудшил бы движок ради
симметрии, которой никто не пользуется: пользовательский вид шага пишется
`fields`, и второй формы автор плагина не видит.

Асимметрия названа прямо и в `docs/plugins.md`: контракт публикует `fields`,
внутри есть вторая форма для встроенного, и это не «приватный API для своих»,
а следствие того, что у встроенных видов есть типы, а у плагинных — нет.

### Решение 3. Вид шага занимает ровно один ключ документа — своё имя

Плагинный вид шага объявляется единственным ключом, равным имени вклада; все
его поля живут под ним:

```yaml
- id: ping
  http:
    url: https://example.org/health
    expect_status: 200
  expect:
    - exit_code: 0
```

Альтернатива — позволить вкладу объявить несколько ключей верхнего уровня,
как у встроенного `run` (`run`, `on_fail`, `output_schema`) — отвергнута.
Схема документа строгая, и это её главная ценность: `titile` и `exit_cod`
отклоняются разбором. Несколько ключей на вид означают, что различение вида
перестаёт быть однозначным (какой ключ дискриминирует?), что два плагина
могут занять пересекающиеся наборы и что опечатка в одном ключе превращает
шаг в шаг другого вида с непонятным отказом. Один ключ снимает всё это
конструктивно.

Из того же решения следует запрет на регистрации: имя вида шага не вправе
совпадать ни с одним ключом общей части шага (`id`, `env`, `context`,
`context_inherit`, `context_exclude`, `context_max_tokens`, `timeout`,
`budget`, `expect`, `attempts`) и ни с одним ключом встроенных видов
(`prompt`, `agent`, `model`, `model_tier`, `session`, `run`, `script`, `uses`,
`with`, `args`, `runner`, `on_fail`, `input`, `output_schema`, `permissions`,
`mcp`). Отказ выдаётся при регистрации, называя имя и то, чем оно занято, —
до того, как исполнится хоть один разбор.

### Решение 4. Модель — `PluginStep`, данные и ничего кроме

```ts
export interface PluginStep extends StepCommon {
  readonly kind: 'plugin';
  /** Имя вида из реестра — оно же ключ шага в документе. */
  readonly name: string;
  /** Значение под ключом, уже проверенное схемой вклада при раскрытии. */
  readonly fields: unknown;
}
export type Step = AgentStep | RunStep | ScriptStep | PluginStep;
```

Буквально то же, чем `Predicate` получил свой вариант `plugin`. Движку не
нужно знать, что значат поля: `computeStepKey` хеширует `step` целиком и
потому чувствителен к правке любого поля бесплатно; `lock.ts` печатает
`{ [name]: fields }`; журнал несёт имя; витрина показывает поля.

Второй `kind` на каждый плагинный вид (`kind: 'http'`) отвергнут: `kind` —
дискриминант размеченного объединения TypeScript, и открытое множество
литералов в нём не выражается, а `switch` по нему перестал бы проверяться на
полноту. Имя вида живёт полем, как у предиката.

### Решение 5. Поля проходят позднее раскрытие типизированным проходом

`fields` — JSON-дерево, и раскрывается оно тем же типизированным проходом,
каким раскрывается `input` шага `script` (`late.ts`, `omitLateSkipped`): общий
`interpolateTree` превратил бы `${jobs.plan.output.item}` в строку и упал бы на
объекте и списке. Значит `omitLateSkipped` снимает `fields` наравне с `input`
и `uses`, а `resolveLate` возвращает их раскрытыми типизированно.

Схема вклада проверяется дважды по той же причине и тем же образцом, что
`uses.paramsSchema` (`runner.ts:2131`): при раскрытии — по тому, что известно
статически, и перед исполнением — по окончательным значениям, потому что до
позднего раскрытия поле могло нести `${jobs.*}`, непроверимый заранее.

### Решение 6. Исполнитель получает попытку, а не шаг

```ts
export interface StepKindInput {
  readonly fields: unknown;
  readonly step: { readonly id: string; readonly index: number; readonly timeoutMs: number };
  readonly job: { readonly id: string };
  readonly attempt: number;
  readonly env: Readonly<Record<string, string>>;
  readonly cwd: string;
  /** Каталог шага в журнале: файлы попытки пишутся только сюда. */
  readonly stepDir: string;
  readonly signal: AbortSignal;
  /** Журнал попытки: событие и файл рядом с `stdout.log` попытки. */
  readonly log: StepKindLog;
  /** Контекст ядра прогона — им исполнитель достаёт сервис своего плагина. */
  readonly ctx: Context;
}

export interface StepKindOutcome {
  /** Умолчание `0`. Предикат `exit_code` читает его же. */
  readonly exitCode?: number;
  /** Текст результата: пишется в `stdout.log` попытки, питает `matches` и судью. */
  readonly text?: string;
  /** Структурированный выход: проверяется схемой `output` вклада, доступен `${jobs.*.output}`. */
  readonly structured?: unknown;
  /** Расход, если вид шага его несёт, — копится тем же счётчиком, что расход судьи. */
  readonly usage?: Usage;
}
```

Исполнителю не отдаётся ни `Step`, ни `Job`, ни `RunContext`: они тянут за
собой всю модель движка в публикуемую поверхность и сделали бы любое их
изменение ломающим для плагинов. Отдаётся то, чем исполняется попытка, —
ровно как `BackendAdapter` получает не шаг, а описание вызова.

`ctx` — контекст **процесса, исполняющего прогон**, а не демона. Демон прогон
внутри себя не исполняет — он порождает дочерний процесс
(`dashboards-as-files`, «Демон запускает прогон дочерним процессом»), — и
ядро этого процесса собрано из того же дерева плагинов. Обещать исполнителю
«сервисы демона» было бы ложью: сервис, заведённый плагином, живёт в каждом
процессе свой.

Исключение исполнителя — непройденная попытка с названной причиной, а не
крушение шага. Тот же выбор и та же формулировка, что у `evaluate`
плагинного предиката.

### Решение 7. Попытки, предикаты, таймаут и бюджет — общий путь, не второй

Плагинный вид шага исполняется новой функцией `runPluginStep`
(`src/core/exec/pluginStep.ts`), но цикл попыток берётся тот же
(`exec/attempts.ts`, `runAttempts`), проход предикатов тот же
(`evaluatePredicates`), учёт бюджета, отмена и события журнала — те же, что у
`runCommandStep`. Второго цикла попыток в движке не заводится: он уже один раз
был обобщён «до шага, у которого есть argv» (`exec/runStep.ts:17`), и второй
разошёлся бы с первым на первом же исправлении.

Таймаут применяется движком: исполнение гонится с `step.timeoutMs`, по
истечении попытка отказывает предикатом `timeout` тем же текстом, что у
командного шага, и сигнал отмены взводится. Но исполнитель при этом **не
убивается**: убивать внутри своего процесса нечего — см. риски.

### Решение 8. Снятое имя помнит прежнего владельца, пока живо ядро

`ContributionService` запоминает владельца имени, снятого вместе с областью,
на время жизни ядра. Это нужно ровно для одного сообщения: пайплайн, который
минуту назад раскрывался, после выгрузки плагина обязан отказать не «неизвестный
ключ `http`», а «вид шага `http` снят вместе с плагином `http-steps`».

Память ограничена именами и живёт не дольше ядра; в новом процессе (плагин
убран из конфигурации между запусками) её нет, и отказ называет вид шага и
перечень доступных — это названо ограничением в `docs/plugins.md`.

Альтернатива — «надгробие» в замке или в конфигурации — отвергнута: она
пережила бы правку, ради которой вид шага и убирали, и начала бы врать.

### Решение 9. Схема выхода вклада проверяется движком

Вклад вправе объявить `output` — JSON Schema структурированного выхода. Если
объявлена, движок проверяет ей `outcome.structured` и при несовпадении
отказывает попытке жёстким предикатом `step_output` с тем же текстом, каким
отказывает `output_schema` шага `script` (`runner.ts:2100`).

Это и есть «выход» в карточке витрины: схема — данные, и по ней же строится
подпись выхода. Альтернатива «`output` только для показа» отвергнута: схема,
которую никто не проверяет, расходится с действительностью молча.

### Решение 10. `http` — встроенная строка дерева, написанная контрактом плагина

Пример поставляется строкой `step-http` перечня `BUILTIN_ROWS`, а модуль
живёт в `src/steps/http/` и импортирует только `stepcast/plugin` и встроенные
модули Node — та же механическая дистанция, что у `src/backends/codex`
(правило `no-restricted-imports` и `test/plugin-surface.test.ts`).

Встроенной строкой, а не объявляемым плагином, как Codex: строка дерева
отключается и заменяется патчем (`config-patch-layers`), и это даёт дешёвый
сквозной тест снятия вклада — отключённая строка снимает вид шага `http` без
единой строки тестовой заглушки.

Секрет в поле вида шага — отдельная забота: поля печатаются в замок как
объявлены и в `jobs/<job>/resolved.json` — раскрытыми. Поэтому `http` берёт
токен **именем переменной окружения** (`auth_env: GITHUB_TOKEN`), а не
значением: движок читает переменную в исполнителе, и в журнал попадает имя, а
не секрет. Это же правило записывается в `docs/plugins.md` как указание
автору вклада.

### Решение 11. Витрина строит карточку из реестра, а незнакомый вид — из замка

Демон уже держит реестр на корень проекта (`docs/plugins.md`, «Витрина»), и
карточка шага плагинного вида собирается из него: название вклада, подписи
полей — из `fields` (`title`/`description` свойств, тем же выводом, каким
`ui/steps.ts:75` строит параметры манифеста), признак и схема выхода.

Шаг, чьего вида действующий реестр не знает (прогон снят плагином, которого
больше нет), показывается именем вида и полями из замка с названной причиной.
Пустая карточка и «неизвестный шаг» одинаково запрещены: журнал
самодостаточен, и витрина обязана показывать то, что в нём записано.

Карточка **прогона** при этом реестр не спрашивает вовсе: снимок строится по
журналу, который вправе пережить плагин, и вопрос «знает ли вид действующий
реестр» для прошлого прогона не имеет верного ответа — плагин мог быть снят,
переименован или подменён другим с тем же именем. Поэтому имя вида и поля
берутся из замка, плагин, внёсший вид **в этом прогоне**, — из записи шага
(`plugin_step.plugin`), а причина, объясняющая, чем показанные поля являются и
откуда взяты, стоит на такой карточке всегда, а не только когда вид пропал.
Карточка пайплайна — противоположный случай: там реестр действующий, и
незнакомый вид называет причину именно как отсутствие вклада.

## Risks / Trade-offs

- **Исполнитель работает в процессе движка и не убивается таймаутом.** →
  Движок взводит `AbortSignal` и перестаёт ждать, попытка отказывает по
  таймауту, но зависший `while(true)` во вкладе остаётся в процессе. Названо
  ограничением в `docs/plugins.md`; смягчение — только дисциплина автора
  вклада (уважать `signal`) и то, что пользовательские скрипты сюда не
  попадают вовсе.
- **Плагинный вид шага исполняется с правами процесса движка.** → Песочницы
  нет и не обещано, ровно как у остальных вкладов; список плагинов лежит в
  конфигурации репозитория и попадает в ревью там же, где `project.check`.
- **Поведение исполнителя не входит в ключ шага.** → Смена поведения вклада
  при той же версии не инвалидирует успешный шаг. То же ограничение, что у
  плагинного предиката; версия плагина видна в манифесте прогона.
- **Секрет, записанный значением поля, попадает в замок и `resolved.json`.** →
  Правило «поле несёт имя переменной, а не её значение» в документации и в
  примере `http`; движок за автора вклада этого не решает.
- **Четвёртая ветвь в схеме документа расширяет публикуемую JSON Schema.** →
  Проект без плагинных видов обязан получать файл, побайтово совпадающий с
  поставляемым пакетом; это фиксируется тестом, как уже зафиксировано для
  предикатов.
- **`kind: 'plugin'` в журнале — новая величина для старых читателей.** →
  Читатель журнала прошлой версии встретит незнакомый `kind`;
  `journal-reader-version-skew` уже описывает это поведение, и запись остаётся
  самодостаточной (имя вида и плагина в ней есть).
- **Обход `registry.steps` на разборе делает схему документа зависящей от
  состава плагинов сильнее, чем раньше.** → Пересборка схемы уже происходит
  на каждый вызов `buildDocumentSchemas`; добавляется одна ветвь на вид, и
  кеша не заводится — измерять нечего, пока видов единицы.

## Migration Plan

Ломающих изменений формата нет: документ без плагинных видов шага
раскрывается, исполняется и печатается ровно как прежде, и это проверяется
существующими тестами без правки.

Порядок: сервис и контракт → регистрация встроенных видов без изменения
поведения (здесь зелёная полная проверка обязательна: она и есть
доказательство, что переезд ничего не сломал) → плагинная ветвь разбора и
модель → исполнитель → журнал, замок, схема → витрина → `http` →
документация.

Откат — снятие строки `step-http` из `BUILTIN_ROWS` и возврат объединения;
промежуточных состояний формата, требующих миграции файлов, изменение не
создаёт.

## Open Questions

- Нужен ли виду шага собственный отпечаток поведения (версия вклада в ключе
  шага), чтобы правка исполнителя инвалидировала успешные шаги? Сегодня
  ответ — нет, тем же доводом, что у предиката; вопрос вернётся, если
  окажется, что виды шага правят чаще, чем предикаты.
- Должен ли плагинный вид шага уметь объявлять `on_fail` (разбор неуспеха
  агентом), как `run` и `script`? Отложено: у первых потребителей
  (`user-decision-steps`, `http`) разбирать нечего, а ключ верхнего уровня
  противоречит решению 3 и потребовал бы отдельного места в общей части.
