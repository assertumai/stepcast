## Context

Учёт расхода в движке полный, показа нет.

Что уже снимается и куда ложится:

- `UsageAccumulator` (`src/core/budget/accumulator.ts`) держит счётчики по
  ключу `job/step#attempt`, по работе и по прогону, а несообщённые бэкендом
  измерения копит в `unreported`. Расход приходит нарастающим итогом, поэтому
  `record()` заменяет, а не прибавляет.
- `status.json` содержит `jobs[].steps[].attempts[].usage` целиком —
  `backend`, `model`, четыре величины токенов (каждая `number | null`),
  `wallclock_ms`, окна лимитов и необязательный `reported_cost_usd`.
- `usage.json` пишется один раз, в конце прогона (`src/core/run/runner.ts`),
  из `accumulator.report()`. По шагу в нём остаются только
  `billable_tokens`, `wallclock_ms` и `attempts: number`.
- `stepcast gc` сохраняет `run.json`, `status.json`, `usage.json` и сносит
  остальное.

Показа нет нигде: команды `usage` в `COMMANDS` нет, `src/ui/` `usage.json` не
читает, `stepcast status` печатает одну строку из `status.budget`.

## Goals / Non-Goals

**Goals:**

- `stepcast usage <run-id>` — разбивка по работам, шагам и номерам попыток, с
  бэкендом и моделью каждой попытки.
- Расход прогона в обзоре витрины и расход работы и шага в снимке прогона.
- Несообщённое измерение видно как несообщённое на всех трёх поверхностях.
- Отчёт живёт на убранном прогоне.

**Non-Goals:**

- Не меняется, что именно считается billable-токеном и как применяется
  бюджет: изменение показывает уже снятые величины.
- Не вводится оценка стоимости в деньгах. `reported_cost_usd` печатается,
  когда бэкенд его сообщил, и не досчитывается по прайсу — прайса движок не
  знает и знать не должен.
- Не вводится сравнение расхода двух прогонов: это дело `stepcast diff`, и
  отдельного решения.
- Не вводится новая точка HTTP-API витрины.
- Не мигрируются `usage.json` уже завершённых прогонов.

## Decisions

### Отчёт собирается из `status.json` и `usage.json`, не из каталогов шагов

Попытки со своим `usage` есть в `status.json`; `step.json` содержит те же
записи. Выбор в пользу `status.json`: он один файл, а не обход
`jobs/*/steps/*/`, и он переживает `gc`. Отчёт на убранном прогоне —
не побочная приятность, а требование: расход интересен ровно тогда, когда
рабочие деревья уже не нужны и прогон убран.

`usage.json` при этом остаётся источником двух вещей, которых в `status.json`
нет: `unreported` за прогон целиком и суммарного `billable_tokens` (взвешенное
чтение кеша считает аккумулятор, и пересчитывать вес в команде значило бы
завести второе место, где живёт эта формула).

Альтернатива — собирать всё из одного `usage.json`, дописав в него бэкенд и
модель попытки. Отвергнута: `usage.json` пишется только в конце прогона, и
`stepcast usage` на идущем прогоне не показал бы ничего. `status.json`
обновляется непрерывно, поэтому команда работает и на живом прогоне —
с оговоркой ниже.

### Идущий прогон: показывается то, что уже записано

`usage.json` может ещё не существовать. Тогда отчёт строится по одному
`status.json`, а строки, которые считает аккумулятор, — итоговый
billable-токен и список несообщённых измерений — заменяются пометкой «прогон
идёт, агрегат будет записан по завершении». Отказ вместо отчёта здесь был бы
хуже: расход идущего прогона — самый частый вопрос.

### `attempts` в `usage.json` становится перечнем записей

```json
"steps": {
  "implement": {
    "billable_tokens": 412300, "wallclock_ms": 940000,
    "attempts": [
      { "attempt": 1, "backend": "claude", "model": "opus",
        "billable_tokens": 180100, "wallclock_ms": 402000 },
      { "attempt": 2, "backend": "claude", "model": "opus",
        "billable_tokens": 232200, "wallclock_ms": 538000 }
    ]
  }
}
```

Число попыток из перечня выводится, обратное — нет. Аккумулятор уже хранит
расход попоточно по ключу `job/step#attempt`; разбивка теряется ровно в
`report()`, при свёртке ключей. Бэкенд и модель попытки аккумулятору
известны — они приходят в `Usage` каждого `record()`.

**BREAKING** для читателей `usage.json`: тип поля меняется. Совместимость не
держится: файл читают только сам движок и человек, версии формата у прогона
нет, а `UsageReportSchema` строгая — старый файл нового читателя не пройдёт.
Отсюда — решение о старых прогонах ниже.

Переисполнение одной и той же попытки (аккумулятор отличает их
`sealCounter`) в перечне схлопывается в одну запись с суммарной величиной:
номер попытки — то, что видит пользователь, и две строки с одним номером
читались бы как ошибка.

### Несообщённое — прочерк, а не ноль

`Usage` держит несообщённое как `null`, `usage.json` — списком имён полей в
`unreported`. Отчёт печатает в такой ячейке `—`; витрина — то же самое.
В конце отчёта перечисляются измерения из `unreported` с явной формулировкой,
что учёт по ним за этот прогон неполон. Правило то же, что уже принято в
`UsageSchema`: ноль означал бы «израсходовано нисколько», а не «не сообщено».

Взвешенный billable-токен при этом считается по тому, что сообщено, — иначе
несообщённое одно поле обнулило бы весь отчёт. Пометка неполноты и есть та
оговорка, которая не даёт принять неполную сумму за полную.

### Форма вывода — те же колонки, что у `status`

`formatColumns` из `src/cli/output.ts`, `formatTokens` и `formatDuration` из
`src/core/units.ts`. Иерархия — отступом, как в `stepcast status`: прогон,
работа, шаг, попытка. Ни JSON-режима, ни флагов у команды нет: JSON уже лежит
на диске двумя файлами, а флаг `--json` над ним был бы третьим представлением
тех же данных.

Распределение моделей по работам отдельной таблицей не печатается: модель
стоит в строке каждой попытки, и работа с двумя моделями видна на месте.

### Витрина берёт расход из тех же двух файлов

`overview.ts` уже читает `status.json` каждого прогона — расход прогона
берётся оттуда же, без второго прохода по диску; `usage.json` дочитывается
там же, где определяется `swept`. `snapshot.ts` уже держит записи работ и
шагов из `status.json` — расход работы и шага собирается из них.

Точка API не добавляется: `/api/overview` и `/api/run` отдают те же
структуры, дополненные полями расхода, и клиент в `assets.ts` рисует их на
месте. Витрина остаётся на чтение.

### Старые прогоны отчёт не ломают

`readUsage` на `usage.json` старой формы упрётся в строгую схему и бросит
«Сводка расхода повреждена». Для команды это неприемлемо: пользователь ничего
не портил. Поэтому чтение агрегата в команде и в витрине обрабатывает неудачу
разбора так же, как отсутствие файла, — отчёт строится по `status.json`, а
итог и неполнота помечаются как недоступные с указанием причины. Миграции
файлов на диске не будет: прогон — журнал случившегося, и переписывать его
задним числом движок не вправе.

## Risks / Trade-offs

- **Смена типа `attempts` ломает внешних читателей `usage.json`** → формат
  ещё не имеет версии и не объявлен стабильным; деградация чтения старых
  файлов описана выше, `docs/run-layout.md` показывает новую форму.
- **Отчёт на идущем прогоне неполон по построению** → неполнота названа в
  выводе, а не замаскирована; сумма без агрегата не выдумывается.
- **Расход в обзоре витрины требует читать `usage.json` по каждому прогону**
  → обзор и так собирается целиком на каждый запрос и уже читает по прогону
  манифест и состояние; третий небольшой файл порядок стоимости не меняет.
- **Взвешенный billable-токен и сырые токены в одной таблице путают** →
  колонки названы раздельно, и итоговая строка billable подписана как та
  величина, к которой применяется бюджет.
