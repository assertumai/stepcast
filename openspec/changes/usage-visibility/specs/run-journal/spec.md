## MODIFIED Requirements

### Requirement: Непрерывный учёт расхода

Расход SHALL сниматься по мере поступления данных от бэкенда, а не только по завершении попытки. Запись расхода MUST вестись на каждую попытку и агрегироваться по шагам, работам и прогону в `usage.json`. Запись шага в `usage.json` MUST содержать перечень попыток, в котором у каждой указаны её номер, бэкенд, модель, величина токенов, идущая в бюджет, и затраченное время; число попыток MUST выводиться из этого перечня, а не храниться отдельным счётчиком.

#### Scenario: Учёт до завершения шага

- **WHEN** агентский шаг исполняется и бэкенд сообщил промежуточный расход
- **THEN** израсходованная величина в состоянии прогона обновлена до завершения шага

#### Scenario: Агрегация

- **WHEN** прогон завершён
- **THEN** `usage.json` содержит суммы по попыткам, шагам, работам и прогону целиком

#### Scenario: Разбивка шага по номерам попыток

- **WHEN** шаг завершился успехом со второй попытки
- **THEN** запись шага в `usage.json` содержит две записи попыток с номерами `1` и `2`, и у каждой указаны бэкенд, модель, токены и время

#### Scenario: Переисполнение той же попытки

- **WHEN** одна и та же попытка шага исполнялась заново, например после ожидания сброса окна лимита
- **THEN** в перечне попыток ей соответствует одна запись с суммарным расходом, а не две записи с одним номером

### Requirement: Отчёт о расходе

Команда `stepcast usage <run-id>` SHALL показывать расход прогона с разбивкой по работам, шагам и номерам попыток, называя у каждой попытки её бэкенд и модель. Отчёт MUST строиться из состояния прогона и сводки расхода, без обхода каталогов шагов, и MUST работать на прогоне, убранном `stepcast gc`. Идентификатор прогона MUST разрешаться так же, как у остальных команд журнала, включая сокращённую запись и умолчание «последний прогон». Измерения, не сообщённые бэкендом, MUST помечаться как несообщённые и MUST NOT показываться нулём.

#### Scenario: Шаги, проходящие не с первой попытки

- **WHEN** пользователь запрашивает отчёт о расходе
- **THEN** видно, какие шаги завершались успехом не с первой попытки и сколько это стоило

#### Scenario: Распределение моделей по работам

- **WHEN** работы прогона исполнялись разными моделями
- **THEN** отчёт называет модель у каждой попытки, и распределение моделей по работам видно без обращения к файлам журнала

#### Scenario: Неполный учёт помечен

- **WHEN** бэкенд не сообщает одно из измерений расхода
- **THEN** отчёт печатает в этой ячейке прочерк и отдельно перечисляет измерения, по которым учёт за прогон неполон

#### Scenario: Отчёт по убранному прогону

- **WHEN** запрошен расход прогона, у которого после уборки остались только `run.json`, `status.json` и `usage.json`
- **THEN** отчёт строится и показывает разбивку по работам, шагам и попыткам, не отказывая из-за отсутствия каталога работ

#### Scenario: Отчёт по идущему прогону

- **WHEN** расход запрошен у прогона, который ещё идёт и не записал `usage.json`
- **THEN** отчёт строится по уже записанным попыткам, а величины, которые даёт только сводка, помечены как ещё не подведённые

#### Scenario: Сводка прежней формы

- **WHEN** `usage.json` прогона не проходит текущую схему сводки
- **THEN** отчёт строится по состоянию прогона, называет сводку непрочитанной и не завершается ошибкой
