## Context

Три изменения группы `nested-repos` уже сделаны: состав объявляется
(`project.nested_repos`), состояние многорепного дерева считается составным
якорем, чистота проверяется по каждому репозиторию, а дорожка получает части
настоящими рабочими деревьями. Остался гейт: то, чем правка признаётся
годной.

Сегодня он один на весь заход. `${project.check}` и `${project.spec.*}`
раскрываются в `expandPipeline` — при разборе документа, до первой работы, —
и `verify` любой дорожки исполняет команду корня. Слой объявления (документ
пайплайна поверх конфигурации) на это не влияет: раскрытие в обоих случаях
происходит раньше, чем `slots` выбрала пункт.

Опоры, на которые ложится изменение:

- отложенная подстановка переживает передачу параметром: `with: { change:
  "${jobs.propose-a.output.slug}" }` кладёт в `params.change` литерал
  `${jobs…}`, а `resolveLate` раскрывает его перед исполнением работы
  (`src/core/pipeline/late.ts`). Значение из выхода работы доезжает так до
  любого поля работы — команды шага, предиката `cmd`, пути контекста, записи
  прав;
- `stepcast backlog pick --lanes` уже печатает документ с дорожками и уже
  публикует данными работы заголовки взятых пунктов, а её ответ проверяется
  поставляемой схемой `stepcast:backlog-slots`;
- `stepcast assert-clean` — образец команды, заведённой ровно потому, что
  файлу работы неоткуда прочитать объявление конфигурации: состав
  `nested_repos` сознательно не публикуется подстановкой;
- ключ шага считается по **нераскрытому** определению работы и по выходам
  работ выше по графу (`computeStepKey`, `upstreamOutputs`).

Ограничение, о которое спотыкается прямолинейное решение: `changed_only`
объявляется списком, а списочная подстановка размножается в элементы списка
только при разборе документа — на позднем раскрытии это запрещено сознательно
(`resolveListExpansion`), потому что значение приходит из произвольного JSON
выхода работы и молча меняло бы границы правок уже после фиксации
`pipeline.lock.yml`. Значит границы правок по репозиторию этим механизмом не
передаются вовсе — и в это изменение не входят.

## Goals / Non-Goals

**Goals:**

- Пункт очереди называет репозитории, которых касается, а необъявленное имя —
  отказ, а не тихий корень.
- Вложенный репозиторий объявляет свою команду проверки и свою практику
  спецификации там же, где объявлен сам.
- Выход `slots` несёт объявления выбранного репозитория по каждой заполненной
  дорожке.
- `verify`, `implement` и `fix-review` гоняют проверку и инструмент
  спецификации выбранного репозитория **в его каталоге**.
- Пункт без объявленного репозитория ведёт заход ровно как сегодня.
- Риск переиспользования шага при возобновлении назван документацией.

**Non-Goals:**

- Границы правок (`changed_only`) по репозиторию: механизм передачи списка на
  позднем раскрытии отсутствует сознательно (см. Context), и без него правка
  кода во вложенном репозитории по-прежнему упирается в жёсткий предикат.
  Отдельная возможность, названная в статусе.
- Сведение и коммит по каждому затронутому репозиторию — `merge-lanes-per-repo`.
- Несколько репозиториев у одного пункта: одна дорожка — одна проверка,
  большее требует другого устройства `verify` и другого сведения.
- `project.tools` и `project.edit_paths` по вложенным репозиториям.
- Обнаружение репозиториев обходом дерева: состав по-прежнему объявляется.

## Decisions

### 1. Объявления читает команда движка, а не `backlog pick`

`stepcast backlog` — команда, чей единственный вход файл очереди: ни
пайплайна, ни `.stepcast/`, ни конфигурации проекта ей не нужно, и это
записано требованием со сценарием «работа в каталоге без проекта».
Разрешение репозитория требует ровно конфигурации, и добавить его в `pick`
значило бы сделать переносимую команду зависимой от устройства проекта —
пусть и по флагу.

Поэтому заводится вторая команда, `stepcast project repos`, которая берёт
готовый ответ `pick` и дополняет его. Обе остаются при своём: очередь знает
про очередь, конфигурация — про репозитории. Головной шаг петли соединяет их
конвейером в одном шаге:

```
"$STEPCAST_BIN" backlog pick --lanes a --run-dir "$STEPCAST_RUN_DIR" \
  | "$STEPCAST_BIN" project repos
```

Отказ первого звена доезжает отказом второго: пустой либо неразбираемый ввод
— отказ разбора у `project repos`, а значит ненулевой код шага. Полагаться на
`set -o pipefail` не приходится (POSIX `sh` его не обязан знать).

Альтернативы:

- **флаг `--repos` у `pick`** — один процесс вместо двух, но платой идёт то
  самое свойство переносимости, и отменить его пришлось бы правкой
  требования;
- **отдельная работа на дорожку** (`repo-a`, `repo-b` с `needs: [slots]`) —
  два лишних узла графа на каждую дорожку, а признак выполненности пункта
  прямо требует, чтобы объявления нёс выход `slots`;
- **чтение `item-<дорожка>.json`, записанных `pick --run-dir`** — тогда
  перечень дорожек называется дважды (в `pick` и в `project repos`), и форма
  ответа собирается в двух местах.

### 2. Блок `repo` несёт склеенные пути и отдельный каталог

Заполненная дорожка получает

```json
"repo": {
  "dir": "backend",
  "check": "./gradlew check",
  "spec": { "dir": "backend/docs/changes", "rules": "backend/docs/spec-rules.md", "tool": "openspec" }
}
```

Пути практики склеены от корня рабочего дерева, а `dir` остаётся отдельным
полем. Так каждый потребитель получает готовое значение: путь контекста и
границы правок — путь от корня, рабочий каталог проверки — `dir`. Корень
даёт `dir: "."` и пути без приставки (`openspec/changes`), то есть ровно
сегодняшние значения — однорепозиторный заход не меняется ни на знак.

Склейка делается движком, а не в файле работы (`${params.repo_dir}/${params.spec_dir}`),
по двум причинам: у корня такое склеивание дало бы `./openspec/changes`, а
`changed_only` сопоставляет шаблоны с путями вида `openspec/changes/…`, где
`./` не совпадёт; и место склейки должно быть одно, иначе шесть работ склеят
по-разному.

`check` остаётся строкой, не разбираемой на части, — тем же решением, каким
`verify` перестала повторять устройство команды перечнем шагов.

### 3. Проверка исполняется в каталоге репозитория, без нового поля шага

`cd "${params.repo_dir}" && ${params.check}` — и в строковой форме `run`
работы `verify`, и в предикате `cmd` циклов `until` (оба исполняются
оболочкой в рабочем каталоге работы). Поля `cwd` у шага движок не заводит:
одна возможность формата ради одного потребителя, тогда как остальные шаги
работы обязаны остаться в корне дерева — агент правит и корень, и часть.

У корня это разворачивается в `cd "." && npm run check` — тождественно
сегодняшнему.

Строковая форма `run` с подстановкой из выхода работы — то, что `stepcast
lint` запрещает правилом «вывод модели не идёт в командную строку». Правило
смотрит на применённые подстановки поля, и через `params` значение проходит
мимо него. Это не дыра, а разные источники: в командную строку попадает
значение, объявленное в `.stepcast/config.yml` — файле репозитория, который
ревьюится наравне с кодом, — а пункт очереди приносит только **имя**
каталога, и необъявленное имя отказывает до первого шага дорожки. Расширять
правило линта на текст поля нельзя: оно запретило бы этот законный путь и
ничего не сказало бы про источник.

### 4. Пункт называет каталоги, `.` — корень

Значение поля `repos` — перечень через запятую из объявленных каталогов
(`backend`), где `.` называет корень дерева. Имена, а не команды: пункт
очереди пишет человек или агент, и приносить оттуда исполняемую строку
недопустимо. Отсутствующее поле означает корень — иначе все сегодняшние
пункты пришлось бы править разом.

Перечень (а не одно значение) — потому что межрепозиторный пункт формату
нужен: `merge-lanes-per-repo` будет накладывать и коммитить по каждому
затронутому. Но проверить сегодня можно один, и `project repos` отказывает
на двух и более, называя пункт и причину. Формат при появлении многорепной
проверки останется прежним.

### 5. Отказ вместо подстановки корня

`project repos` отказывает кодом ошибки конфигурации, когда: названный
каталог не объявлен составом и не `.`; названо больше одного; у названного
репозитория (включая корень) не объявлены `check` либо `spec.dir`,
`spec.rules`, `spec.tool`. Последнее — потому что все четыре потребляются
работами петли, и обнаружиться нехватка обязана в головной работе, а не на
`verify` последней работой дорожки, когда потрачен весь заход.

Пункт к этому моменту уже помечен `in_progress`, а исход ему проставит
`stepcast backlog settle` работой `finalize` — тем же путём, каким сегодня
закрывается всякая недоведённая дорожка. Это осознанная цена того, что
`pick` конфигурации не читает и проверить имя заранее не может.

### 6. Объявления этого репозитория переезжают в `.stepcast/config.yml`

`project repos` читает конфигурацию (`resolveConfig`), а пайплайновый слой
`project` не видит — команда о документе не знает и знать не должна. Значит
объявление, которое обязано быть видно и команде, живёт в конфигурации;
пайплайновый слой остаётся для `${project.*}` и никуда не девается.
Расхождение двух слоёв не молчит: репозиторий, объявивший `check` только в
пайплайне, получит от команды отказ «объявите в `.stepcast/config.yml`».

Пайплайн петли этого репозитория держит секцию `project` у себя с оговоркой
«перенос в конфигурацию возможен любым следующим заходом, одной строкой»;
изменение этот перенос и делает. Работы и промпты не затрагиваются: они видят
действующее значение, а не слой, на котором оно объявлено.

### 7. Объектная форма элемента `nested_repos`, а не вторая секция

Состав дерева и объявления его частей — про одни и те же каталоги. Второй
список рядом (`project.parts: { backend: … }`) заводил бы способ
рассогласовать два объявления; поэтому элемент состава получает вторую форму:
строка (как сейчас) либо объект `{ dir, check, spec }`. Читатели состава
(составной якорь, проверка чистоты, изоляция дорожки) продолжают получать
перечень каталогов — приведение обеих форм делается один раз при разрешении
конфигурации.

Объявления вложенных, как и сам состав, подстановкой `${project.*}` не
публикуются: пространство одно на документ, а тут значений по числу
репозиториев — выбрать из них нечем, пока пункт не выбран.

### 8. Работы получают значения параметрами с места подключения

Дорожку знает только пайплайн: файл работы общий для обеих. Поэтому
`with:` на месте подключения передаёт `${jobs.slots.output.lanes.<дорожка>.repo.*}`
в параметры работы — тем же приёмом, каким уже передаются `change` и `lane`.
Параметров у работы столько, сколько значений она потребляет: `verify` —
каталог, команду и инструмент; `implement` и `fix-review` — их же плюс пути
документов; `plan` и `review` — путь документов.

Передать блок одним параметром нельзя: подстановка раскрывается в строку, а
объект строкой непредставим.

## Risks / Trade-offs

- **Возобновление переиспользует шаг, снятый на другом репозитории.** → Ключ
  шага считается по нераскрытому определению, и `${jobs.slots.output…}` в нём
  — текст, одинаковый для любого репозитория. Спасает другая составляющая
  ключа: выходы работ выше по графу, куда `slots` входит транзитивно у каждой
  работы дорожки, — сменившийся выбор пункта (а с ним и репозитория) делает
  ключи невалидными и переисполняет шаги. `resume --from` это правило
  обходит по своему назначению — переиспользовать всё выше точки, — и на
  прогоне другого репозитория такой ключ означает чужой результат. Обе
  стороны записываются в `docs/run-layout.md` и в фрагмент статуса.

- **Путь, объявленный через `params`, выпадает из статической проверки
  линта.** → `stepcast lint` проверяет существование путей, все подстановки
  которых принадлежат `${project.*}`; пути с `params` пропускаются
  сознательно (значение известно только в прогоне). Перевод контекстных путей
  петли с `${project.spec.dir}` на `${params.spec_dir}` эту проверку с них
  снимает. Взамен объявление проверяется командой `project repos` в головной
  работе — раньше, чем дорожка начата, — и неполное объявление называется
  там.

- **Заход отказывает на неизвестном имени репозитория после того, как пункт
  помечен `in_progress`.** → Исход проставит `backlog settle` работой
  `finalize`, как всякой недоведённой дорожке; отказ виден в головной работе
  с именем пункта и перечнем объявленных каталогов.

- **Межрепозиторный пункт всё ещё не доводится до конца.** → Границы правок
  остаются корневыми (Non-Goals), и правка кода во вложенном репозитории
  упрётся в `changed_only`. Изменение снимает гейт проверки, а не весь путь;
  оставшееся названо в статусе явно, чтобы не выглядело работающим.

- **Конвейер в шаге `pick-lanes` скрывает код возврата первого звена.** →
  Пустой и неразбираемый ввод — отказ `project repos`, поэтому отказ `pick`
  доезжает ненулевым кодом шага; сценарий закрепляется проверкой.

## Migration Plan

Изменение обратно совместимо по формату: строковая форма элемента
`nested_repos` и пункт без поля `repos` работают как прежде. Единственный
разрыв — объявления самого репозитория переезжают из
`.stepcast/pipelines/self-improve.yml` в новый `.stepcast/config.yml`; оба
файла правятся одним изменением, и раскрытые значения остаются теми же.
Прогоны, записанные раньше, не читаются иначе: форма журнала не меняется.

## Open Questions

- Стоит ли позже публиковать объявление выбранного репозитория ещё и данными
  работы (`stepcast data`), чтобы витрина показывала его в карточке `slots`.
  На поведение петли это не влияет и в изменение не входит.
