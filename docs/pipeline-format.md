# Формат пайплайна

`stepcast.yml` в корне репозитория — пайплайн по умолчанию. Несколько пайплайнов
живут в `.stepcast/pipelines/<name>.yml`, работы — в `.stepcast/jobs/<name>.yml`.

| Где | Что описано |
|---|---|
| файл работы | что она делает: шаги, параметры, сессии, бюджет, условие сходимости |
| пайплайн | как работы связаны: зависимости, условия, окружение, аргументы, рабочая директория |

Ключи `needs`, `on`, `if`, `with` внутри файла работы отклоняются линтером.

## Разрешение путей

Два правила, и они разные:

- `uses:`, `prompt: file:…`, `schema:` — от файла, в котором объявлены. Правило
  для `schema:` одинаково во всех трёх местах, где он встречается:
  `output_schema` шага, `output.schema` работы и предикат `schema` в `expect`
  и в `until.check`;
- `context:`, `output:`, пути в `run:` — от корня рабочей директории работы. По
  этому же правилу разрешается `file_exists`: файл создаёт шаг, и появляется он
  в рабочей директории, а не рядом с определением работы.

Значение `schema:`, начинающееся с `stepcast:<имя>` (например
`stepcast:backlog-slots`), путём не считается: это ссылка на схему,
поставляемую пакетом stepcast — `schema/<имя>.schema.json` — и разрешается она
от расположения самого движка, а не от файла объявления. Каталог запуска и
способ установки движка (исходники, `dist/`, `node_modules` целевого
репозитория, глобальная установка) на разрешение не влияют. Имя — слаг в
kebab-case; `/`, `.` и `..` в имени, а также имя, которого пакет не везёт, —
отказ разбора с перечнем поставляемых имён, а не диагностика линта. Форма
действует только в местах объявления схемы, перечисленных выше: `uses:`,
`prompt: file:…` и `context:` её не понимают и читают `stepcast:…` как обычный
путь — движок не публикует ни работ, ни промптов, ни контекстов.

## Верхний уровень

```yaml
version: 1
kind: pipeline
name: implement-change

inputs:
  change: { type: string, required: true }
  skip_review: { type: bool, default: false }

workspace:
  mode: cwd                      # cwd | worktree | copy

env:
  NODE_ENV: test
env_files: [.env.test]
env_deny: ["AWS_*"]

context:
  - AGENTS.md

project:                         # необязателен, перекрывает project.* конфигурации
  check: npm run check
  tools: [npm, npx, node]
  spec: { dir: openspec/changes, rules: .stepcast/prompts/spec-rules.md, tool: openspec }
  edit_paths: [src/**, test/**, docs/**, package.json]

defaults:
  agent: claude
  session: shared

budget:                          # необязателен
  tokens: 2M
  wallclock: 2h
  rate_limit_pct: 80
  on_exceed: wait                # wait | stop

concurrency: 1
fail_fast: true

jobs: { ... }
```

## Рабочая директория

Задаётся на уровне пайплайна, работа может переопределить.

```yaml
workspace:
  mode: cwd | worktree | copy
  path: ./build/stepcast            # только для copy, по умолчанию внутри прогона
  inherit: <job> | none             # только на работе, только в worktree/copy
```

**`cwd`** — умолчание. Работы выполняются прямо в каталоге, из которого запущен
пайплайн. Ничего не копируется, результат сразу на месте, ничего возвращать не
нужно. Изоляции нет: параллельные работы делят одно дерево, поэтому линтер
предупреждает при `concurrency > 1` в этом режиме.

**`worktree`** — на каждую работу свой git worktree от текущего `HEAD`.
Незакоммиченные изменения в него не попадают. Параллельные работы не мешают
друг другу. При объявленных `project.nested_repos`
([config.md](config.md#вложенные-репозитории)) каждая часть выкладывается тем
же способом — своим worktree от `HEAD` своего репозитория, — и остаётся
настоящим рабочим деревом git внутри дерева дорожки.

**`copy`** — рабочее дерево копируется в `<run_dir>/workspace/<job>/`, минуя
игнорируемые пути. Единственный режим, работающий вне git и с
незакоммиченными изменениями. Дороже остальных по диску и времени старта.

Логи и состояние прогона в любом режиме лежат вне проекта, в
`~/.stepcast/runs/...` — рабочая директория и журнал прогона не смешиваются.

### Наследование рабочего дерева

В `worktree` и `copy` работа, у которой есть зависимости, начинает не с
исходного состояния, а с результата предшественника — состояния,
зафиксированного якорем его последнего шага. Работа без зависимостей
начинает, как и раньше: `worktree` — от `HEAD`, `copy` — с копии каталога
запуска. В режиме `cwd` наследовать нечего: дерево там одно на прогон.

Раскладка каталогов зависит от формы графа, а не от того, что работы
фактически сделали:

- **Линейная цепочка** — у работы ровно один предшественник, и она у него
  единственный потомок в графе — продолжается в его же каталоге. Ничего не
  копируется и не восстанавливается, а неотслеживаемое содержимое (кеши
  сборки, установленные зависимости) переходит по цепочке само — вместе с
  частями, объявленными `project.nested_repos`: они уже заведены в этом
  каталоге, и заводить их заново нечего.
- **Развилка** — у предшественника несколько потомков — каждый получает
  собственный каталог, подготовленный как обычно (включая объявленные части)
  и сразу приведённый к якорю предшественника — части приводятся к своему
  состоянию наравне с корнем. Неотслеживаемое и игнорируемое содержимое в
  такой каталог не попадает: якорь его не хранит.

При единственной зависимости источник очевиден и объявлять его не нужно. При
нескольких — `workspace.inherit` называет одну из них по идентификатору, либо
`none`, чтобы вернуть исходное поведение (начало от `HEAD`/каталога запуска).
Без `inherit` в этом случае `stepcast lint` отказывает: молча выбрать одно из
разошедшихся деревьев значило бы иногда тихо терять работу целой зависимости.

Если выбранный источник не исполнялся — пропущен условием — или его дерево
засеять нечем, наследование переходит к его собственному источнику, и так далее
до исходного состояния проекта. Отсутствие дерева у источника само по себе не
отказ зависимой работы. Продолжение каталога цепочки якоря не требует вовсе:
файлы предшественника уже лежат на месте, и неудача учёта у него наследника не
касается.

**Развилка и git.** Приведение каталога к чужому состоянию возможно только
там, где состояние зафиксировано средствами git. Внутри репозитория это верно
для обоих изолирующих режимов — рабочая копия `copy` не содержит `.git`, но её
состояние фиксируется базой объектов проекта, — и для составного якоря при
объявленных `project.nested_repos`: он приводит корень и каждую часть
средствами их собственных репозиториев, при условии что все части в
приводимом каталоге на месте (это верно для `worktree` — единственного
изолированного режима, где состав материализуется). Вне репозитория состояние
фиксируется хеш-манифестом: он отвечает, изменилось ли дерево, но содержимого
не хранит, и засеять им каталог развилки нечем. Пайплайн с развилкой вне git
отклоняется до первой работы — с предложением оставить работе одну зависимость
(тогда она продолжит её каталог) или объявить `inherit: none`.

Источник виден в состоянии прогона: запись работы несёт `inherited_from` —
работу, чьё дерево унаследовано, — и `continued`, если каталог продолжен, а не
заведён заново.

**Развилка не переносит неотслеживаемое содержимое источника.** Каталог
работы, получающей собственное дерево при наличии нескольких потомков у
предшественника, засевается его якорем — а якорь хранит только отслеживаемое
и не игнорируемое содержимое. Установленные зависимости, кеши сборки и прочий
неотслеживаемый след предшественника в такой каталог не попадают; для линейной
цепочки (единственный потомок) это не ограничение — она делит каталог
предшественника целиком, без засева.

**Пропущенное звено цепочки вне git обрывает наследование.** Если источник
пропущен условием, наследование ищет дерево дальше по цепочке — но вне
репозитория засеять им каталог нечем, и работа начинает с исходного
состояния, а не с результата предшественника предшественника. Внутри
репозитория такого нет.

**Возврат результата.** В режиме `cwd` он уже на месте. В `worktree` и `copy`
изменения остаются в стороне, и по завершении прогон печатает путь и команду:

```
stepcast apply <run-id> [--job <job>]     # наложить итоговый дифф на текущее дерево
```

Составному прогону (объявлен `project.nested_repos`) команда доступна так же:
`diff.patch` склеен из патчей разных баз объектов, по одному на репозиторий, и
наложение идёт тем же делением — по вызову на корень и на каждую часть, чьи
oid до и после различаются, каждый в её собственном каталоге. Конфликт на
любом репозитории возвращает все затронутые к состоянию до наложения.

**`stepcast apply --job` на работе из цепочки может не лечь на чужое дерево.**
Ограничение работой даёт вклад именно этой работы — дифф между её `tree_before`
и последним `tree_id`. Если работа продолжала каталог предшественника, этот
дифф предполагает уже применённые вклады предшествующих работ цепочки; наложить
его в одиночку, на дерево без них, обычно означает конфликт. Это ожидаемо и не
лечится: наложение всей цепочки (без `--job`) складывает вклады по порядку и
такого не имеет.

## Файл работы

```yaml
version: 1
kind: job
name: implement
description: Реализовать задачи из плана до зелёной сборки

params:
  change: { type: string, required: true }
  max_iterations: { type: int, default: 4 }

session: shared                  # shared | per_step

context:
  - openspec/changes/${params.change}/proposal.md

output:
  from: write-code               # чей структурированный вывод становится выходом
  schema: ./schemas/implement.json

budget:
  tokens: 500k
  wallclock: 30m

until:
  max_iterations: ${params.max_iterations}
  check:
    - cmd: npm test

steps: [ ... ]
```

Из значений, известных до запуска, работа адресует `${params.*}` и
`${project.*}` — `inputs` пайплайна ей недоступны: работа, привязанная к
входам одного пайплайна, перестаёт быть переиспользуемой, а команда проверки
принадлежит репозиторию и одна для всех его пайплайнов.

Итоговый статус: `success | failed | skipped | canceled | budget_exceeded`.

## Подключение работ

```yaml
jobs:
  plan:
    uses: ./jobs/plan.yml
    with: { change: ${inputs.change} }

  implement:
    uses: ./jobs/implement.yml
    with: { change: ${inputs.change} }
    needs: [plan]
    budget: { tokens: 900k }

  typecheck:                     # работу можно описать и на месте
    needs: [implement]
    steps:
      - id: tsc
        run: [npx, tsc, --noEmit]
        expect: [{ exit_code: 0 }]

  review:
    uses: ./jobs/review.yml
    needs: [typecheck]
    if: "not inputs.skip_review"

  archive:
    uses: ./jobs/archive.yml
    needs: [review]

  triage:
    uses: ./jobs/triage.yml
    needs: all
    on: failure
```

На месте подключения переопределяются `with`, `needs`, `on`, `if`, `env`,
`budget`, `workspace`, `context`, `lane`, `display`, `session_group`. Шаги — нет.

## Подпись работы (`display`)

```yaml
jobs:
  slots:
    uses: ./jobs/slots.yml
    display:
      title: ${jobs.slots.data.title}
```

`display` — карта произвольных имён в шаблоны. Витрина показывает значение
ключа `title` строкой прямо в узле графа, остальные ключи — в карточке
работы. Как `needs`, `on`, `if` и `lane`, блок объявляется только на месте
подключения работы и внутри файла работы отклоняется той же диагностикой, что
и остальная обвязка: подпись описывает роль работы в этом пайплайне, а не
саму работу.

Блок, а не плоское поле `title:` прямо в обвязке. Обвязка строгая, и
неизвестный ключ в ней отклоняется разбором — это ловит `titile`, `neds` и
`wokspace` на `stepcast lint`, до захода. Разрешить произвольные имена прямо
в обвязке значило бы потерять эту проверку для всей обвязки целиком; блок
сохраняет строгость снаружи и даёт полную свободу имён внутри.

**Раскрывается подпись позже всего остального** — в момент отрисовки, а не
перед исполнением работы (см. «Когда что раскрывается»). Отсюда и самоссылка
в примере: работа `slots` к отрисовке уже записала `title`, а к раскрытию
собственного определения ещё нет. Ссылка на собственные данные вне `display`
поэтому отклоняется линтом — не как опасная, а как заведомо не работающая.

Раскрытие здесь мягкое: ключа нет — поля просто нет, это не отказ. Правило
обратно строгому правилу полей, потребляемых шагом, потому что у подписи нет
потребителя ниже по течению: пустая строка в пути контекста ломает шаг тремя
шагами позже, а отсутствующая подпись не ломает ничего.

Доступно в подписи только пространство `${jobs.<работа>.data.<ключ>}` —
`run.*` и `env.*` принадлежат уже завершённому раскрытию, и ссылка на них
здесь отклоняется линтом.

## Данные работы (`jobs.<id>.data.*`)

Работа публикует произвольные значения по ходу исполнения:

```bash
stepcast data set title "Выбрано: Расход деньгами и токенами"
stepcast data merge --json '{"repo":"backend","slug":"nested-repo-anchor"}'
stepcast data get [<ключ>]
```

Хранятся они плоской картой строк в `<каталог прогона>/jobs/<работа>/data.json`
(см. [run-layout.md](run-layout.md)). Вложенности нет намеренно: в
`${jobs.x.data.a.b}` не различить вложенный объект и ключ с точкой, а
пространство подстановки обязано быть одноуровневым — поэтому и точка в имени
ключа отклоняется. Последняя запись по ключу побеждает; файл живёт на всю
работу, включая все её шаги и все итерации цикла `until`.

Целевая работа выводится из `STEPCAST_JOB_DIR` — переменной, которую движок
инжектирует в каждый шаг, — а не принимается аргументом, и путей команда не
принимает вовсе. Это три свойства устройства разом: единственный писатель на
файл, невозможность записать в чужую работу и невозможность записать в
рабочее дерево. Последнее существенно: файл внутри рабочего дерева попал бы в
`git add -A` при снятии якоря и вышел бы за границы `changed_only`. Вызов вне
шага прогона — внятный отказ.

`set` принимает **два позиционных аргумента**, а не пару `ключ:значение`:
значения содержат двоеточия штатно, и разбор пары либо терял бы хвост, либо
требовал экранирования на каждом вызове.

Читаются данные двумя способами:

- подстановкой `${jobs.<работа>.data.<ключ>}` из работы ниже по графу — строго,
  как `${jobs.<работа>.output.*}`: отсутствующий ключ даёт отказ с
  объяснением, а не пустую строку;
- блоком `display` — мягко, в момент отрисовки витрины.

Движок складывает содержимое `data.json` в запись работы в `status.json`
**после каждого шага**; сам подпроцесс `stepcast data` состояние прогона не
пишет — им владеет движок. Отсюда и живость витрины: она опрашивает корень
прогонов по времени изменения `status.json`. Следствие: данные, записанные в
середине долгого шага, появятся в витрине по его завершении, а не в момент
записи.

При `permissions.enforce: strict` право `Bash(stepcast data *)` добавляется
агентскому шагу неявно — узко на эту команду, не на `stepcast *`: там `run`,
`apply` и `gc`. Публикация же до рабочего дерева не дотягивается по
устройству.

При возобновлении данные работы, чьи шаги переиспользуются, переносятся из
исходного прогона — тем же правилом, что и выход работы.

## Дорожка (`lane`)

```yaml
jobs:
  propose-a:
    uses: ./jobs/propose.yml
    lane: a
    with: { lane: a }

  propose-b:
    uses: ./jobs/propose.yml
    lane: b
    with: { lane: b }
```

`lane` — метка обвязки, слаг в kebab-case, как и идентификатор работы.
Объявляется только на месте подключения работы — как `needs`, `on`, `if` — и
внутри файла работы отклоняется той же диагностикой, что и остальная
обвязка. На порядок исполнения графа не влияет: это чисто учётная метка,
группирующая работы одного прохода параллельной дорожки для сведения
расхода, журнала и последующего наложения.

Смежность дорожки объявляет автор пайплайна: движок не выводит её из needs
или workspace — работа несёт `lane`, только если она объявлена явно на месте
подключения.

Метка переносится в `pipeline.lock.yml`, в запись работы `status.json`
(`stepcast status`, `stepcast usage` — см. [run-layout.md](run-layout.md)) и
читается ключом `--lane` команды `stepcast apply` (там же).

Третья одновременная дорожка — правка самого пайплайна (третья цепочка
`propose → … → verify` с `lane: c`, третий слот в `stepcast backlog pick --lanes`,
третье имя в `--lanes` у `stepcast merge-lanes`), а не параметр движка. Одновременных
агентских сессий при этом становится больше, и прежде чем поднимать
`concurrency` пайплайна, поднимите на столько же `backends.claude.concurrency`
и, если денежный потолок захода упирается в потолок конфигурации, —
`limits.cost` в глобальном конфиге: сам пайплайн подняться выше него не
может.

**Смежность дорожек объявляет человек.** Движок не выводит `lane` из `needs`
или `workspace.inherit` — работа несёт дорожку, только если она объявлена
явно на месте подключения. Пропущенная в разводке пайплайна работа тихо
остаётся вне группировки расхода и вне `apply --lane`.

## Зависимости и условия

Два независимых ключа, оба должны выполниться. Разделение убирает главную
двусмысленность: `on` — про исход зависимостей, `if` — про данные.

```yaml
  needs: [typecheck]      # прямые зависимости; транзитивные подразумеваются
  on: success             # success | failure | always   (умолчание success)
  if: "not inputs.skip_review"
```

**`on: success`** — ни одна зависимость не завершилась отказом. Пропущенные
зависимости не блокируют: иначе один флаг `skip_review` тихо отменял бы и
архивацию. Если пропущены *все* зависимости, работа тоже пропускается.

**`on: failure`** — хотя бы одна зависимость завершилась отказом.
`budget_exceeded` считается отказом.

**`on: always`** — любой исход.

**`needs: all`** — после того как остальной граф завершился в любом исходе. Сама
работа в «остальной граф» не входит; работы с `needs: all` между собой не
упорядочены и друг друга не ждут. Вместе с `on: failure` это разбор отказа.

`if` вычисляется в момент готовности работы, когда все её зависимости уже
завершились, — не при построении графа.

### Выражения

`inputs.*`, `params.*`, `run.*`, `env.*`, `jobs.<id>.status`,
`jobs.<id>.output.*`, `jobs.<id>.data.*`. Сравнения, `and`, `or`, `not`,
обращение к полям. Всё
остальное выносится в `run`-шаг, печатающий результат в stdout.

Пространство `run.*`: `run.id`, `run.dir`, `run.workspace`, `run.scratch`.
Величины уровня шага им не предоставляются — на уровне работы у них нет
значения; каталоги работы и шага приходят переменными `STEPCAST_JOB_DIR` и
`STEPCAST_STEP_DIR`.

### Когда что раскрывается

Раскрытие идёт в три приёма, и каждое поле проходит ровно один из них.

**Разбор документа.** `inputs.*`, `params.*` и `project.*`: их значения
известны до запуска, и раскрытый пайплайн несёт их строкой, а не подстановкой.

**Перед исполнением работы.** `jobs.*`, `run.*` и `env.*` отложены: они
появляются только по ходу прогона и раскрываются один раз на работу, до
первого её шага и до первой итерации цикла, целиком по её определению — в
путях контекста, тексте промпта, аргументах командных шагов, значениях `env`
и путях схем. Раскрытое определение кладётся в `jobs/<работа>/resolved.json`.

**При отрисовке витрины.** Блок `display` не проходит ни через первый этап со
своими отложенными именами, ни через второй вовсе: его поля не потребляет ни
один шаг — их читает витрина. Они хранятся нераскрытыми (в том числе в
`pipeline.lock.yml`) и раскрываются в момент сборки снимка, против текущего
содержимого `data`. Поэтому самоссылка `${jobs.<сам>.data.*}` в `display`
работает, а вне его отклоняется линтом: на втором этапе работа ещё ничего не
публиковала, и такая ссылка застыла бы пустой навсегда.

Пространство `project.*` состоит из имени `check` — действующей команды
проверки репозитория, — имён `tools` и `edit_paths` — действующих списков
инструментов и границ правок репозитория (см.
[config.md](config.md#инструменты-репозитория) и
[config.md](config.md#границы-правок)) — и составных имён `spec.dir`,
`spec.rules`, `spec.tool` — действующего объявления практики спецификации (см.
[config.md](config.md#команда-проверки-проекта) и
[config.md](config.md#практика-спецификации)). Обращение к любому из них —
`${project.check}`, `${project.tools}`, `${project.edit_paths}`,
`${project.spec.dir}`, `${project.spec.rules}`, `${project.spec.tool}` — там,
где ключ не объявлен ни пайплайном, ни `.stepcast/config.yml`, — отказ
разбора, а не пустая строка: наличие ключа не обязательно само по себе,
обязательна только ссылка на него без объявления. Обращение к имени вне этого
состава (`${project.name}`, `${project.spec.folder}`) называет доступные
имена, включая составные.

`tools` и `edit_paths` — единственные на сегодня имена, раскрываемые списком:
прочие имена пространства `project`, а также `inputs`, `params`, `run` и `env`
ограничены скалярами. Раскрытие списочного значения подчиняется отдельному
правилу — см. ниже.

### Раскрытие списочного значения в элемент списка

Подстановка, дающая список строк (сегодня это `${project.tools}` и
`${project.edit_paths}`), раскрывается не в строку, а в несколько элементов
списка — по элементу на значение, в объявленном порядке. Правило действует
только внутри списка; окружающий текст элемента применяется к каждому значению
отдельно, а место исходного элемента и порядок соседей сохраняются:

```yaml
allow: [Read, "Bash(${project.tools} *)", "Bash(git log*)"]
# при project.tools: [npm, npx, node] →
allow: [Read, "Bash(npm *)", "Bash(npx *)", "Bash(node *)", "Bash(git log*)"]

expect:
  - changed_only: ["${project.edit_paths}", "${project.spec.dir}/**"]
# при project.edit_paths: [src/**, test/**] →
expect:
  - changed_only: ["src/**", "test/**", "${project.spec.dir}/**"]
```

**Ровно одна списочная подстановка на элемент.** Элемент с двумя (например,
`"${project.tools}-${project.tools}"`) — отказ разбора, называющий поле и оба
выражения: декартово произведение пришлось бы объявлять отдельным правилом, а
однозначного ответа на «сколько записей получится» здесь нет. Прочие
подстановки того же элемента раскрываются как обычно — по разу на каждую
копию; отложенная (`${jobs.*}`, `${run.*}`, `${env.*}`) остаётся текстом в
каждой копии и доезжает до позднего раскрытия.

**Списочное значение вне списка непредставимо.** `check: ${project.tools}` —
отказ разбора с подсказкой, что списочное значение раскрывается только в
элементе списка; движок не решает за автора, какой из нескольких инструментов
имелся в виду в скалярном поле.

**Пустой список — отказ, а не исчезнувший элемент.** Ноль значений удалил бы
элемент целиком: право, которого никто не отменял, или границу правок, которую
никто не снимал. Схема объявления пустой список и так не принимает; правило
раскрытия отказывает и там, где значение пришло мимо неё.

**Правило действует при разборе документа.** Отложенные пространства
(`${jobs.*}`, `${run.*}`, `${env.*}`) раскрываются перед исполнением работы и
не размножаются: выход работы — произвольный JSON, где список строк обычен, и
элемент вроде `"${jobs.build.output.changed_files}"` менял бы состав прав или
границ правок молча, уже после того как раскрытый пайплайн зафиксирован в
`pipeline.lock.yml`. На этом этапе списочное значение остаётся непредставимым
строкой — с объяснением про состав выхода работы.

Отложенная подстановка переживает передачу через параметр: `with: { change:
${jobs.plan.output.slug} }` кладёт в `params.change` неразвёрнутый текст, и
`${params.change}` внутри файла работы раскрывается в него же. К началу
исполнения на этом месте стоит значение.

Обращение к работе, которая к этому моменту не завершилась, и к выходу
работы, завершившейся отказом, — отказ с объяснением, а не пустая строка:
пустота дала бы путь вида `openspec/changes//proposal.md`, и разбираться
пришлось бы на три шага дальше от причины.

Из-за этого `pipeline.lock.yml` содержит отложенные подстановки
нераскрытыми — их значений на момент фиксации ещё не существует. Раскрытое
определение работы лежит в `jobs/<job>/resolved.json` каталога прогона.

## Порядок и отказы

Работы без взаимных зависимостей идут параллельно в пределах `concurrency`
(умолчание 1). При `fail_fast: true` (умолчание) первый отказ останавливает
запуск новых работ; уже идущие доводятся до конца, а не убиваются — агент мог
сделать половину полезного. Затем выполняются работы с `on: failure` и
`needs: all`. При `fail_fast: false` граф доигрывается целиком.

Работы с `needs: all` выполняются и при остановке по бюджету, и при отмене —
разбор нужнее всего именно тогда.

Параллелизм графа — не единственный предел: сколько вызовов одного бэкенда
может идти одновременно, задаёт отдельно `backends.<имя>.concurrency` (см.
[конфигурацию](config.md)). Он общий на прогон и работает поверх
`concurrency` пайплайна — граф может вести пять работ разом, а до бэкенда,
чей предел ниже, часть из них достучится с задержкой, дожидаясь места.

**Классов неустранимого отказа бэкенда ровно два.** Упор в окно лимита
подписки и отказ аутентификации — больше движок не различает. Кандидат на
классификацию — только запись результата, объявившая себя ошибкой и несущая
признак ошибки бэкенда (код состояния ответа либо `terminal_reason:
"api_error"`); класс решает сначала код состояния (429 → лимит, 401/403 →
аутентификация), а тело ответа смотрится лишь тогда, когда кода нет вовсе, и
только по закрытому перечню узнаваемых формулировок. Отказ, не совпавший ни с
одним классом, остаётся обычным отказом шага: попытка повторяется по
`attempts.max`, как при любой непройденной проверке, а не по правилам
неустранимого отказа. Момент сброса окна лимита разбирается только из двух
форм — настенного времени с часовым поясом (`resets 11pm (Asia/Nicosia)`,
ближайшее будущее наступление через `Intl.DateTimeFormat`) и метки ISO 8601 со
смещением или `Z`; нераспознанная форма, неизвестный часовой пояс и
отсутствие упоминания сброса дают отказ без момента сброса, а не угаданное
время.

## Результаты работ

Работа производит один структурированный JSON-выход. Движок забирает его из
шага, указанного в `output.from` (по умолчанию — последний агентский шаг), и
кладёт в `artifacts/<job>.json`. Файл пишет движок, агент его не трогает: схема
уходит бэкенду через его штатный механизм структурированного вывода.

```yaml
output:
  from: write-code
  schema: ./schemas/implement.json
```

**Выходы предшественников автоматически попадают в контекст последующих
агентских работ** — отдельным блоком, перед контекстом работы:

```
## Результаты предыдущих работ
plan       artifacts/plan.json        1 020 ток.   (вставлен ниже)
implement  artifacts/implement.json  18 400 ток.   (читай файл)
```

Мелкие выходы вставляются целиком, крупные — ссылкой на путь, порог тот же
`context.inline_threshold`. Управление:

```yaml
context_upstream: all            # all | none | [plan, review]
```

Умолчание `all` — все работы выше по графу, включая транзитивные. Перечень
отбирает из них: имя работы, которая предшественником не является, `stepcast
lint` отклоняет ошибкой — отобрать её выход всё равно не из чего. Выражением
`${jobs.plan.output.<field>}` можно достать конкретное поле в `if`, `with`,
`env` или `run`.

## Сессии

Агентские шаги одной работы по умолчанию идут **в общей сессии агента**: второй
шаг видит диалог первого, и не нужно перекладывать через файлы то, что и так
только что обсуждалось. Это же единственный способ получить попадания в кеш
промптов — см. [почему](run-layout.md#кеш-промптов).

```yaml
session: shared                  # умолчание: одна сессия на все агентские шаги
session: per_step                # каждому шагу своя
```

Точечное управление — именованными сессиями на шагах:

```yaml
steps:
  - id: read-specs
    agent: claude
    session: analysis
  - id: draft
    agent: claude
    session: writing
  - id: refine
    agent: claude
    session: writing             # продолжает сессию draft, не видит analysis
```

Шаг без явной `session` попадает в сессию по правилу работы. Именованная
сессия живёт в пределах одной работы и одной итерации `until`.

**Общий контекст отправляется один раз**, в первое сообщение сессии; следующие
шаги получают только своё. Это и дешевле, и честнее: повторять агенту то, что
он уже прочитал, незачем.

**Цена общей сессии — гранулярность возобновления.** Шаг внутри общей сессии
нельзя переисполнить в одиночку: его результат зависит от диалога. Поэтому при
`resume` единицей повтора становится работа целиком. Нужна пошаговая
гранулярность — `session: per_step`.

### Общая сессия нескольких работ (`session_group`)

Сессия по умолчанию замкнута на работу: её граница обрывает диалог, и
следующая работа читает репозиторий с нуля. Кто собирает пайплайн, объявляет
обратное — обвязкой, на месте подключения:

```yaml
jobs:
  propose:
    uses: ./jobs/propose.yml
    session_group: build

  plan:
    uses: ./jobs/plan.yml
    needs: [propose]
    session_group: build

  implement:
    uses: ./jobs/implement.yml
    needs: [plan]
    session_group: build
```

Работы с одинаковым именем группы продолжают один диалог агента: псевдонимы
их шагов живут в общем пространстве имён, и `session: shared` каждой из них
означает не «одна сессия на работу», а «одна на группу».

Ключ обвязки, а не поле работы, и это не мелочь записи: работа не знает, с кем
её поставят в один диалог, — знает только тот, кто собирает пайплайн. Внутри
файла работы `session_group` отклоняется разбором, как и прочая обвязка.

Отдельное имя, а не строка на `session`: там уже живёт перечисление
`shared | per_step`, и два вида значения на одном ключе различались бы только
формой.

**Контекст.** Свод правил пайплайна уходит один раз на диалог. Собственный
контекст работы и выходы её предшественников — один раз на работу внутри
диалога: для второй работы группы это новое знание, и умолчать о нём потому,
что диалог уже начат, значило бы отправить её работать по пустому месту. Если
предшественник — сосед по группе, его выход агент уже видел, и повтор
снимается объявлением `context_upstream: none` на месте подключения.

**Три условия, которые проверяет `stepcast lint`:**

| | |
|---|---|
| Порядок | работы группы упорядочены зависимостями: один диалог нельзя продолжать двумя работами одновременно |
| Цикл `until` | работе группы запрещён: его новая итерация начинает сессии заново, а сессия группы живёт дольше работы. Условие переносится в предикат `cmd` шага, повтор — в его `attempts` |
| Рабочее дерево | все работы группы в одном режиме, и ни одна, кроме первой, не заводит своё (`workspace.inherit: none`): иначе агенту посреди диалога сменился бы каталог |

**Цена — та же гранулярность возобновления, только шире.** Работа группы,
кроме первой, зависит от диалога, начатого до неё, и в одиночку не
переисполняется: единицей повтора становится группа.

**Что это стоит на деле.** Общая сессия не бесплатна, и решать стоит по замеру
своего пайплайна, а не по ожиданию. Замер на петле саморазвития этого
репозитория: время на единицу изменения не изменилось (3.20 минуты на сто
строк против базы 2.79–3.54), а стоимость выросла на треть ($1.73 против базы
1.24–1.30, плотной до ±2%). Причина в том, что́ наследуется: свежая сессия
вычитывает репозиторий выборочно, только нужное её задаче, а унаследованный
диалог тащит всё, чем занимался предшественник, — и тащит в префиксе каждого
следующего хода. Цена хода у работ, диалог унаследовавших, удвоилась вслед за
префиксом, а число ходов упало: ходов меньше, каждый дороже. Группа окупается
там, где предшественник дорого добывал знание, которым дальше пользуются
много и подряд, — а не там, где следующая работа и так прочла бы ровно нужное.

Требование к бэкенду: адаптер должен уметь продолжать сессию по идентификатору.
Если не умеет, `shared` деградирует в `per_step` с предупреждением на старте.

**На бэкенде без поддержки сессий унаследованный контекст не переотправляется — это дефект, а не устройство.** Отметка «контекст сессии уже отправлен» рассуждает так, будто бэкенд помнит предыдущие сообщения сессии, — а бэкенд без `sessions` в возможностях адаптера этого не делает: каждый его запуск получает лишь собственный промпт нового процесса, без истории. Движок не подстраивается под это различие: `session: shared` для такого бэкенда исполняется как `per_step` молча для промпта и с одним предупреждением `backend.degraded` на бэкенд в журнале, а второй шаг сессии на деле остаётся без свода правил пайплайна и работы, которые агент уже должен был прочитать в первом сообщении. Направление починки известно и невелико: отметка обязана спрашивать возможности адаптера и на деградировавшем бэкенде вести себя как при `per_step`. Пока она не сделана: пункт очереди на неё стоит отдельно.

## Шаги

### agent

```yaml
steps:
  - id: plan
    agent: claude
    model: opus
    session: analysis
    prompt: file:./prompts/plan.md
    context:
      - openspec/changes/${params.change}/tasks.md
    output_schema: ./schemas/plan.json
    permissions:
      mode: auto
      allow: ["Edit", "Bash(npm *)"]
      deny: ["Bash(rm *)"]
    timeout: 20m
    budget: { tokens: 120k }
    expect:
      - schema: ./schemas/plan.json
    attempts: { max: 3 }
```

Промпт передаётся через stdin, не аргументом: контекст легко перерастает
`ARG_MAX`. Файлы промптов шаблонизируются — `${params.*}`, `${inputs.*}`,
`${project.*}`, `${jobs.*}` подставляются; `$${` экранирует.

`permissions` транслируется адаптером в флаги бэкенда (`--permission-mode`,
`--allowedTools` у Claude Code, `--sandbox` у Codex). Без него агентский шаг
упрётся в отказ на первой же записи файла.

`permissions.enforce` объявляет режим применения этой политики — `inherit`
(умолчание) либо `strict`. Поле принимается в шаге, в работе и в конфигурации
бэкенда (`docs/config.md`); ближайшее объявление побеждает: шаг сильнее работы,
работа сильнее конфигурации. Списки при этом не складываются — блок нижнего
уровня заменяет верхний целиком, — а вот сам `enforce` берётся из ближайшего
уровня, который его **назвал**: блок `permissions` без `enforce` базовый режим
бэкенда не снимает. Ослабление остаётся возможным, но явное: `enforce: inherit`
на работе или шаге сильнее `strict` из конфигурации.

- `inherit` — сегодняшнее поведение без изменений: список `allow` **дополняет**
  правила, которые бэкенд читает из своих файлов настроек (в том числе
  пользовательского уровня, вне репозитория). Разрешающее правило машины
  (например, `Bash(*)` в `~/.claude/settings.json`) продолжает действовать
  поверх узкого списка шага.
- `strict` делает список границей, а не пожеланием: адаптер собирает запуск
  так, что настройки бэкенда вне репозитория не читаются вовсе, а инструмент,
  не названный в `allow`, отклоняется, а не разрешается молча. Разрешающее
  правило пользовательского уровня перестаёт давать доступ, которого список
  шага не называет.

```yaml
permissions:
  allow: ["Read", "Edit", "Bash(npm *)"]
  enforce: strict
```

Оговорка: в жёстком режиме бэкенд не читает настройки уровня пользователя
**целиком**, а не только их часть про права. Вместе с правилами доступа
перестают действовать и прочие настройки машины — пользовательский
`CLAUDE.md`, стили вывода и остальное из `~/.claude/settings.json`. Для
агентского шага, чей промпт целиком собирает движок, это способствует
воспроизводимости прогона, но поведение шага может неожиданно разойтись с
тем, что разработчик привык видеть локально.

`enforce: strict` рядом с режимом бэкенда, разрешающим неназванное по
умолчанию (у Claude Code — `auto`, `acceptEdits`, `dontAsk`,
`bypassPermissions`), — ошибка `stepcast lint`: оба поля описывали бы
противоположное. `enforce: strict` на бэкенде, не объявившем поддержку
жёсткого режима (`docs/config.md`), — тоже ошибка линта, до старта прогона: не
доделанная возможность отказывает явно, а не работает наполовину. Прогон,
запущенный в обход линта, проверяет то же сам: если адаптер возможности не
объявляет, он останавливается до первого шага.

**Синтаксис `allow`/`deny` остаётся бэкендовым.** Движок не разбирает и не
проверяет записи политики — опечатка в шаблоне (`Bash(npm*)` вместо
`Bash(npm *)`) в жёстком режиме превращается в неожиданный отказ, а не в
разрешение; причина видна в журнале как отказ в разрешении.

### run

```yaml
  - id: test
    run: [npm, test]             # список argv — предпочтительно
    timeout: 10m
    expect: [{ exit_code: 0 }]
    on_fail:
      analyze: claude
      prompt: file:./prompts/triage-tests.md
```

`run` принимает список argv или строку. Строка исполняется через `sh -c`
(`cmd.exe /c` на Windows). Подстановка `${jobs.*.output.*}` в строковую форму
отклоняется линтером: это данные, порождённые моделью, и место им в argv, а не
в командной строке.

Командный шаг с объявленным `output_schema` разбирает свой `stdout` как один
JSON-документ — строго: снимаются только пробелы по краям, без поиска первого
объекта в тексте и без склейки последней строки. Результат становится
структурированным выходом шага — теми же путями, что и у агентского шага:
доступен предикату `schema` в `expect`, и работа может опубликовать его через
`output.from`. Неразбираемый вывод — отказ попытки с причиной, называющей шаг
и то, что вывод не JSON; попытка подчинена обычному `attempts.max`. Без
`output_schema` командный шаг структурированного выхода не имеет вовсе.

```yaml
  - id: pick
    run: [node, scripts/pick.mjs]
    output_schema: ./schemas/pick.json
    expect:
      - schema: ./schemas/pick.json
```

`on_fail.analyze` не чинит и не повторяет — производит разбор в `analysis.md`
и завершает шаг отказом.

### Таймауты

`timeout` на шаге обязателен по существу: без него зависший агентский CLI
висит вечно, а бюджет проверяется по расходу, которого у молчащего процесса
нет. Умолчание берётся из конфига. По истечении — SIGTERM, через 30 секунд
SIGKILL, статус `failed`, причина `timeout`.

Дополнительно движок следит за тишиной: нет вывода дольше `stall_timeout` —
событие `step.stalled` в журнал, шаг продолжается.

## expect

| Предикат | Описание |
|---|---|
| `exit_code: 0` | код возврата |
| `file_exists: <path>` | файл создан |
| `schema: <path>` | структурированный вывод соответствует схеме |
| `matches: /re/` | текстовый результат содержит |
| `not_matches: /re/` | не содержит |
| `changed_only: [glob]` | изменения не вышли за границы |
| `cmd: "..."` | команда завершилась нулём |
| `judge: "..."` | оценка агентом-судьёй |

`matches` работает по текстовому результату шага: для агентского это поле
`result` ответа, для `run` — stdout.

`changed_only` сравнивает дерево с состоянием на начало шага; игнорируемые
git'ом пути не учитываются. Шаблоны: `**` пересекает разделители пути, `*` и
`?` — нет. Если состояние дерева снять не удалось, предикат помечается
невычисленным и статус шага не меняет: неудача внутреннего учёта не имеет права
становиться отказом пользователю. Предикат проверяет границы, но не факт работы —
шаг, не изменивший ничего, его проходит. Держать его единственным не стоит.

### judge

```yaml
      - judge: "План покрывает все требования из спеки"
        hard: true               # умолчание false — совещательный
        agent: claude            # умолчание из defaults
        model: sonnet
```

Судья — отдельный агентский вызов в своей сессии: свежий идентификатор,
политика доступа шага ему не передаётся, продолжением сессии шага он не
становится. Видит утверждение, задание шага, его текстовый и структурированный
вывод и результаты остальных предикатов этой попытки; контекст шага ему не
передаётся. Для шага командной строки место структурированного вывода в его
промпте занимает stdout. Отвечает только по фиксированной схеме `{ pass: bool,
reason: string }`, которую поставляет сама система, — свободный текст не
толкуется, а даёт непройденный предикат с причиной, называющей отсутствие
вердикта. Бэкенд судьи обязан поддерживать структурированный вывод; иначе
`stepcast lint` отклоняет пайплайн до запуска.

Каждый вызов ограничен `timeout` шага и наблюдается общим детектором тишины;
прерывание по времени тоже даёт непройденный предикат. Судья не вызывается,
если в этой попытке уже не прошёл жёсткий предикат, вычисляемый без обращения
к агенту, — платить за суждение о заведомо отклонённой попытке незачем; его
результат в этом случае помечается невычисленным, а не непройденным.

Его промпт, поток вывода, вердикт и расход лежат в `steps/<step>/judge-<n>/`
со сквозной нумерацией в пределах шага — счётчик растёт через попытки и через
несколько предикатов `judge` одного шага, не начинаясь заново на каждой
попытке. Токены и время судьи сливаются с расходом попытки и идут в бюджет
шага, работы и прогона наравне с расходом самого шага; `lint --budget` их
учитывает.

Умолчание «совещательный» неслучайно: если валидация дороже и менее надёжна,
чем сама работа, она даёт шум, а не сигнал. Ограничения в движке нет.

**Судья видит только вывод шага, а не его контекст, и не имеет его прав.**
Предикат `judge` получает утверждение, задание шага, его текстовый и
структурированный вывод и результаты остальных предикатов — но не контекст,
собранный шагу, и не его политику доступа. Вызов идёт в свежей сессии со
своими (или умолчальными) бэкендом и моделью. Из этого следует, что судья не
может свериться с файлами проекта или спекой напрямую — только с тем, что шаг
сам показал в своём ответе; утверждение стоит формулировать так, чтобы его
можно было проверить по выводу шага, не заглядывая дальше.

## attempts

```yaml
    attempts:
      max: 3
      escalation:                          # необязательно
        - include_failure: true
        - include_failure: true
          model: opus
```

`max` принимает и подстановку — `max: ${params.retries}` — по тем же правилам,
что и `until.max_iterations` ниже.

Ограничители — `attempts.max` и бюджеты. Проверки того, что попытка отличается
от предыдущей, нет. Каждая попытка пишется отдельной записью со своим расходом,
`stepcast usage` показывает распределение по номеру попытки: шаг, стабильно
проходящий с третьего раза, — диагноз промпта или спеки.

При `session: shared` неудачная попытка остаётся в диалоге, и следующая её
видит. Чтобы этого не было, нужен `per_step`.

## until

`until` — внешний цикл работы, `attempts` — внутренний цикл шага.

```yaml
until:
  max_iterations: 4
  check:
    - cmd: npm test
```

| | |
|---|---|
| Порядок | все шаги → `check` → если не прошёл и лимиты целы, новая итерация |
| Попытки | сбрасываются в начале каждой итерации |
| Провал шага | исчерпал `attempts` → работа падает, новой итерации нет |
| Контекст итерации | вывод непрошедшего `check` подмешивается шагам следующей |
| Сессии | в новой итерации сессии начинаются заново |
| Выход работы | берётся из последней выполненной итерации |
| Расход `check` | время идёт в бюджет работы, токены — только если `check` агентский |
| Исчерпание итераций | статус `failed`, причина `until_not_met` |

Худший случай работы = `Σ по шагам (бюджет шага × attempts.max) × max_iterations`,
ограниченный сверху бюджетом самой работы. Считается по уже раскрытому
значению `max_iterations` — в том числе когда оно получено подстановкой.

## Числовые поля и подстановки

`concurrency`, `until.max_iterations`, `attempts.max`, `budget.rate_limit_pct`
и `exit_code` в `expect`/`until.check` принимают подстановку наравне с числом:

```yaml
until:
  max_iterations: ${params.max_iterations}
```

Разбор документа проверяет только форму значения — строка или число, — а не
его вид. Приведение к нужному числу (целое, положительное, диапазон процента)
происходит позже, уже над раскрытым значением: строка `${params.n}` при
разборе документа не проходит целочисленную проверку ни при каком `n`,
поэтому проверка обязана ждать раскрытия.

Отсюда следствие: `${jobs.*}`, `${run.*}` и `${env.*}` в этих полях
недопустимы, хотя в остальных строковых полях работают. Эти три пространства
раскрываются только перед исполнением конкретной работы — числовое поле к
этому моменту уже должно быть числом, чтобы `until` и `attempts` определили
число итераций и попыток заранее, а не по ходу прогона. `${inputs.*}` и
`${params.*}` раскрываются при разборе пайплайна и годятся.

У этих полей нет суффиксов величин (`k`, `M`, `m`, `h`…) — те применимы только
к `tokens`, `cost` и `wallclock`. `max_iterations: 2k` — ошибка, а не 2000
итераций.

Выдержка о непройденном `check` укладывается в предел `context.note_max_tokens`
(см. [config.md](config.md#размер-контекста)). Если вывод непрошедших
предикатов не умещается, он усекается по границам строк с сохранением конца
вывода — начало отбрасывается, а не конец, — и на месте отброшенного встаёт
пометка с числом отброшенных строк. Несколько непрошедших предикатов делят
предел так, чтобы один многословный не вытеснил остальные из выдержки. Если
предел так мал, что читаемой доли не хватает всем, лишние предикаты сворачиваются
в одну строку с их числом: выдержка укладывается в предел при любой настройке и
не срывает сборку контекста.

## Бюджет

Три уровня — пайплайн, работа, шаг. Все необязательны; бюджет пайплайна
накапливается по всему прогону, бюджеты работ и шагов ограничивают свою
область. Связывает тот потолок, который упрётся первым.

В прогоне действуют три разных предела, названных похожими словами. Их не
стоит путать: исчерпание `budget.tokens` не означает переполнения контекста и
не вызывает сжатия — это разные величины с разными последствиями.

| Предел | Кто задаёт | Что при упоре |
|---|---|---|
| Трафик прогона | `budget.tokens` (пайплайн, работа, шаг) | сумма входных/выходных токенов, записи и чтения кеша по **всем** обращениям к API за область; шаг прерывается, область получает статус `budget_exceeded` |
| Собранный контекст шага | `context.max_tokens` (см. docs/config.md) | объём, который stepcast кладёт в промпт одного шага; проверяется **до** запуска, лишнее понижается до ссылки |
| Окно модели | никто из stepcast | сколько данных физически помещается в одно обращение; переполнение обрабатывает сам бэкенд (сжатие), а не движок |

Первый предел растёт быстрее прочих на порядок и более, потому что
`cache_read` — это префикс промпта, пересылаемый заново на **каждое**
обращение агентской сессии, а не то, что одновременно лежит в контексте (см.
формулу ниже). Величина одного обращения — «пик» — видна рядом с трафиком в
`stepcast usage` (docs/run-layout.md) и обычно на порядок меньше него.

`wallclock` тоже отсчитывается от начала своей области: у работы — от её
начала, включая все итерации цикла, у шага — от начала шага. Длительность
прогона на потолки работ и шагов не влияет, иначе работа с `needs: all` и
небольшим потолком была бы обречена в любом долгом прогоне.

```yaml
budget:
  tokens: 2M
  cost: 20                       # доллары США; допустимо и "$20", и "20.50"
  wallclock: 2h
  rate_limit_pct: 80
  on_exceed: wait                # wait | stop
```

**Считается непрерывно.** Расход снимается из потокового вывода бэкенда по мере
поступления, а не после завершения попытки. Превышение обрывает текущий шаг
(SIGTERM); дальше решает `on_exceed` области, чей потолок упёрся первым.

**Токены** — `tokens_in + tokens_out + cache_write + cache_read × вес`. Вес
`cache_read` задаётся в конфиге на бэкенд и по умолчанию мал: чтение кеша
дешевле обычного ввода примерно вдесятеро, и считать его наравне значило бы
объявлять катастрофой то, что на деле экономия.

`cache_read` в этой сумме — не однократный объём контекста, а сумма префиксов
по **всем** обращениям к API за область: агентская сессия пересылает заново
весь накопленный диалог на каждом ходу, и чтение кеша считается на каждом из
них. Поэтому трафик прогона растёт с числом обращений и оказывается на
порядок больше наибольшего отдельного обращения — этот наибольший префикс
показывает `stepcast usage` рядом с трафиком (docs/run-layout.md).

**Окна лимитов их два** — пятичасовое и недельное. `rate_limit_pct` применяется
к обоим, и ночной прогон обычно упирается именно в недельное.

**`stop`** — область получает статус `budget_exceeded`, прогон останавливается
и записывает команду возобновления.

**`on_exceed: wait`** ждёт сброса окна лимита вместо остановки. У этого ровно
два основания: измеренное превышение `rate_limit_pct` (и только когда бэкенд
сообщил `resets_at`) и упор самого бэкенда в окно лимита подписки — отказ,
который движок распознаёт по конверту результата независимо от того, объявлен
ли `rate_limit_pct` вообще (классы такого отказа названы выше, в «Порядок и
отказы»). Режим для второго основания берётся у ближайшей объявившей его
области — шаг → работа → пайплайн; ни одна не объявила — действует `stop`.
Объявившей считается та, где `on_exceed` написан: бюджет шага с одним лишь
`tokens` внешний `on_exceed: wait` не отменяет. Прерванный шаг переисполняется
заново целиком, не расходуя попытку из `attempts.max`; расход оборванной
попытки остаётся учтён в потолках. Время ожидания не входит ни в один потолок
`wallclock`.

Потолки `tokens` и `wallclock` режимом `wait` не спасаются: они не
сбрасываются, и упор в них останавливает прогон при любом `on_exceed`. Момент
сброса, который бэкенд не сообщил (ни в `resets_at`, ни в тексте отказа) или
назвал уже прошедшим, и
момент сброса, отстоящий дальше предела `defaults.max_wait` конфигурации
(умолчание — 6 часов), тоже вырождают `wait` в `stop` — причина называет
основание и, для отказа бэкенда, его класс и сообщение. Суммарная
длительность всех ожиданий за прогон ограничена тем же пределом.

`on_exceed: wait` — основной режим для длинных прогонов по подписке; объявлять
его можно и без `rate_limit_pct` — тогда он действует только на упор самого
бэкенда.

**Деньги.** `cost` — тот же трёхуровневый потолок, что и `tokens`, только в
долларах США: число (`20`) или строка с необязательным `$` (`"$20.50"`).
Хранится и сравнивается в микродолларах, печатается в отчётах двумя знаками
после запятой от доллара и четырьмя — для величин меньше доллара, чтобы
дешёвый шаг не выглядел бесплатным.

Цена приходит от бэкенда один раз, в финальной записи попытки (в отличие от
токенов, которые видны по ходу потока). Из этого следует:

- денежный потолок физически не может связать посреди попытки — только после
  неё; допустимый перерасход не больше цены одной попытки (и одного вызова
  судьи, если он есть в `expect`);
- `on_exceed: wait` на `cost` не действует — денежное превышение всегда ведёт
  в `stop`, ждать сброса окна лимитов по цене нечего;
- если бэкенд не сообщил цену ни разу за весь прогон, объявленный `cost` не
  применяется ни на одном уровне — прогон доводится до конца, а не
  останавливается вслепую, но и не даёт защиты, которую как будто обещал
  указанный потолок.

Сообщённая цена — это оценка бэкенда, а не счёт провайдера: она не обязана
совпадать с фактическим списанием и меняется вместе с тарифами. У прогона по
подписке она не расходует ничего реального — это оценка «сколько стоило бы по
API», полезная как мера объёма работы, а не как трата; от исчерпания
подписки защищает `rate_limit_pct`, а не `cost`.

Автору пайплайна: денежный потолок шага стоит объявлять с запасом на одну
попытку — граница проверки не даёт более точной остановки.

**Оценка до запуска:**

```
$ stepcast lint --budget stepcast.yml
ok: stepcast.yml
worst case: 2.9M токенов, ~78 мин
  implement   2.16M  (180k × 3 попытки × 4 итерации, потолок работы 900k → 900k)
  review        90k  (45k × 2 попытки)
  plan         120k
работы без бюджета: typecheck, archive — оценка неполна
```

**Денежный потолок под параллелизмом может немного отставать от факта.**
Проверка бюджета видит расход по завершённым попыткам; несколько работ,
упёршихся в потолок одновременно, каждая успевает потратить ещё до одной
попытки (и одного вызова судьи), прежде чем остановка их догонит, — тот же
допустимый перерасход, что и при последовательном исполнении, но кратный
числу работ, идущих в этот момент разом.

**Денежный потолок проверяется на границе попытки, не внутри неё.** Цена
приходит от бэкенда один раз, в финальной записи попытки — денежный потолок
не может связать раньше. Допустимый перерасход — не больше цены одной попытки
(и одного вызова судьи).

**Денежный потолок зависит от того, сообщает ли бэкенд цену.** Если ни одна
попытка за весь прогон цены не сообщила, объявленный `budget.cost` фактически
не применялся ни на одном уровне — прогон доводится до конца с прежним кодом
возврата, а не останавливается вслепую, но и не даёт защиты, которую как
будто обещал потолок. Частично сообщённая цена даёт частичную сумму: она
применяется по учтённой части, а число неучтённых попыток называется рядом.

**Денег в сводках прогонов прежней формы нет.** `usage.json` и `status.json`,
записанные до появления денежного потолка, не несут ни `cost_usd`, ни
`cost_used_usd` — поля читаются как отсутствующие, а не как ноль, и `stepcast
usage`/`status` показывают на их месте прочерк. Досчитать цену задним числом
неоткуда: старые записи попыток её не хранили.

**Пика в сводках прогонов прежней формы тоже нет.** Поле
`peak_prefix_tokens` появилось вместе с показом наибольшего префикса —
записи `usage.json`/`status.json`, снятые раньше, его не несут и читаются как
отсутствующее значение, а не ноль; `stepcast usage` печатает прочерк на их
месте. Досчитать пик задним числом неоткуда: пооткликовых данных в старом
журнале нет.

## Окружение

Цепочка склейки:

```
окружение процесса
  → env_files
    → env пайплайна
      → env на месте подключения
        → env в файле работы
          → env шага
            → STEPCAST_* (не переопределяются)
              → env_deny (вычёркивает)
```

Окружение процесса наследуется целиком: агентский CLI и сборочные инструменты
нуждаются в `JAVA_HOME`, `NVM_DIR`, `SSH_AUTH_SOCK`, прокси и десятке других
переменных, и отсечение по списку ломает первый же реальный шаг.

Фильтр — `env_deny`: глобы по именам, применяются последними, независимо от
того, как переменная попала в набор.

```yaml
env_deny: ["AWS_*", "*_PRIVATE_KEY"]
```

Списки из конфига, проектного конфига и пайплайна **объединяются и снизу не
отменяются**. Явно объявленная в `env` переменная, попадающая под запрет, — это
ошибка линтера, а не тихое вычёркивание в рантайме: человек написал намерение,
и молча его отменять нельзя.

Каждое срабатывание пишется в `events.ndjson` — именем переменной и шаблоном.

Осторожно с агентскими шагами: окружение наследуется всеми подпроцессами,
которые запустит агент.

Учётные данные бэкенда — забота адаптера. При работе по подписке CLI берёт их
из своего хранилища, а не из переменных.

### Инжектируемые

`STEPCAST_RUN_ID`, `STEPCAST_RUN_DIR`, `STEPCAST_BIN`, `STEPCAST_JOB`, `STEPCAST_JOB_DIR`,
`STEPCAST_STEP`, `STEPCAST_STEP_DIR`, `STEPCAST_ITERATION`, `STEPCAST_ATTEMPT`,
`STEPCAST_WORKSPACE`, `STEPCAST_ARTIFACTS`, `STEPCAST_SCRATCH`, `STEPCAST_PREV_FAILURE`.

`STEPCAST_BIN` — путь к точке входа исполняющего процесса stepcast
(`process.argv[1]`). Даёт шагу вызвать `stepcast` рекурсивно тем же движком,
которым он сам исполняется, — например, командный шаг, сводящий дорожки,
зовёт им `$STEPCAST_BIN apply --lane <имя> <run-id>`, не полагаясь на то, что
`stepcast` вообще есть в `PATH` шага.

`STEPCAST_SCRATCH` (и та же величина подстановкой `${run.scratch}`) — каталог
черновиков работы: общий на все её шаги и итерации, лежит вне рабочего дерева
при любом режиме `workspace` и потому не идёт против `changed_only`. Пустым не
сохраняется — движок снимает его сам по завершении работы.

Командному шагу каталог доступен всегда. Агентскому — насколько его пускает
бэкенд: под `permissions.enforce: strict` (см. шаг `agent`) движок объявляет
каталог доступным явно (адаптер Claude добавляет `--add-dir`), а вне жёсткого
режима границы записи ставит сам бэкенд по своим настройкам, и попытка писать
за пределы рабочей директории может упереться в его отказ. Агентскому шагу,
которому черновики нужны, объявляйте `enforce: strict`.

## Контекст

Три уровня, склейка сверху вниз: пайплайн → работа → шаг. Перед ними —
автоматический блок с выходами предшественников.

```yaml
context:
  - AGENTS.md                    # путь
  - "src/**/*.kt"                # глоб
  - text: |                      # текст
      Сгенерированные файлы в build/ не трогать.
  - path: reports/plan.json
    mode: inline                 # inline | reference | auto
  - path: "changes/${params.change}/**/*.md"
    required: true               # запись обязана дать хотя бы один файл
```

Порядок — от стабильного к изменчивому. Он нужен для детерминизма: записи идут
в порядке объявления, глобы раскрываются сортированными, поэтому одинаковый
вход даёт одинаковый промпт, `step_key` не плавает, а `stepcast diff` показывает
осмысленную разницу.

`mode: auto` (умолчание) вставляет файлы меньше `context.inline_threshold`
целиком, крупные передаёт путём — агент прочитает сам своими инструментами.

`required: true` (только у формы объектом) требует от записи хотя бы одного
файла: не нашедшая ничего запись роняет шаг до запуска бэкенда, называя путь.
Нужно это глобу — путь без глоба и так роняет сборку, когда файла нет, а глоб
без совпадений молча даёт пусто, и шаг уходит к агенту с контекстом беднее
объявленного. Умолчание прежнее: отсутствие совпадений не ошибка. Линт этого
не проверяет — на его этапе каталог, который наполняет работа выше по графу,
ещё и не обязан существовать.

Весь собранный контекст ограничен `context.max_tokens`, и проверка идёт **до**
запуска бэкенда: иначе один неудачный глоб отправит репозиторий целиком, и
бюджет заметит это уже после оплаты. При превышении записи режима `auto`
понижаются с вставки на путь, от самой крупной; `mode: inline` и `text` не
понижаются. Если и это не помогло — шаг падает, не запуская бэкенд. Предел
переопределяется ключом `context_max_tokens` на любом из трёх уровней.

Отказ от унаследованного:

```yaml
    context_inherit: false       # только собственный контекст
    context_exclude: ["src/**"]  # выбросить часть унаследованного
```

Пути, попадающие под `context.deny` из конфига, не включаются никогда.

Файл, разрешённый при сборке более одного раза — на разных уровнях, дважды на
одном уровне или явным путём вперемешку с глобом, — попадает в контекст одной
записью. Тождество считается по абсолютному пути после раскрытия, а не по
тому, как путь написан: `CLAUDE.md` на пайплайне и на работе — один и тот же
файл. Склеенная запись остаётся на месте первого объявления, в порядке
«выходы предшественников → пайплайн → работа → шаг», а читается файл один раз.
Способ передачи выбирается по самому сильному из объявлений: `mode: inline`
сильнее вставки, полученной из `auto` по порогу, а вставка сильнее передачи
путём (`mode: reference` либо `auto` сверх порога); при равной силе побеждает
первое объявление, так что исход не зависит от порядка уровней. `inline`,
объявленный на любом уровне, делает склеенную запись непонижаемой наравне с
записью, объявленной так однажды. `context.max_tokens` учитывает такую запись
один раз — двойного счёта нет. Записи `text` в склейке не участвуют: у них нет
пути, и совпадение текста на двух уровнях остаётся двумя записями.

При `session: shared` весь унаследованный контекст уходит в первое сообщение
сессии, а не повторяется на каждом шаге.

**Проектный контекст бэкенда.** Claude Code подгружает `CLAUDE.md`, автопамять,
хуки, MCP и плагины сам, и stepcast это не подавляет: работа по подписке важнее, а
проектный контекст полезен. Следствие, которое надо знать: `prompt.txt` в
журнале — только та часть, которую сформировал stepcast, а состав подгруженного
пишется отдельно в `step.json` из события инициализации бэкенда.

```
$ stepcast context --job implement --step write-code
выходы предшественников                       1 020 ток.
пайплайн                                      4 210 ток.
работа implement                             12 440 ток.
шаг write-code                                  610 ток.
итого                                        18 280 ток. в первое сообщение сессии

склеенные записи (объявлены на нескольких уровнях):
  CLAUDE.md                                  пайплайн, работа
```

Склеенная запись целиком относится к уровню своего места, поэтому уровень, где
она объявлена повторно, в разрезе её размера не содержит. Перечень склеенных
записей идёт следом за разрезом: без него ноль у уровня не отличить от «на этом
уровне ничего не объявлено». Те же уровни называет поле `declared_in` в
`context.json`.

**Выдержка о непройденной проверке усечена по `context.note_max_tokens`.** В
контекст следующей итерации попадает хвост вывода непрошедших предикатов, а не
он целиком; отброшенное начало помечается явно. Полный вывод из усечения не
теряется — он остаётся в логах шага проверки того прогона.

**Повтор между сообщениями общей сессии не склеивается.** При `session: shared` унаследованный контекст уходит в первое сообщение, а собственный контекст следующих шагов сессии собирается отдельным вызовом `assembleContext`, которому уже отправленные записи не видны. Файл, объявленный шагом сессии повторно, будет отправлен второй раз.

**`context.json` шага с несколькими попытками показывает состав только последней.** Запись — одна на шаг и перезаписывается каждой попыткой, тогда как промпт каждой попытки сохраняется отдельным файлом (`prompt.txt`, `prompt.2.txt`, …). Разбор состава по попытке, кроме последней, поэтому недоступен: узнать, что́ именно ушло агенту на первой попытке шага общей сессии, можно только по тексту `prompt.txt`, а не по `context.json`.

**`context.json` с `declared_in` не читается движком прежней версии.** Схема отчёта строгая: поле добавлено обратной совместимостью снизу вверх (запись без него по-прежнему читается как объявленная однажды), но откат движка под уже записанным таким журналом схема отклонит — та же оговорка, что и у `lane` в `status.json`.

## stepcast lint

Отклоняет:

- `needs`, `on`, `if`, `with`, `lane` внутри файла работы;
- `lane`, не являющийся слагом в kebab-case;
- циклы в `needs`, недостижимые работы, неизвестные идентификаторы;
- `if`, обращающийся к неопределённым `inputs` или к работе не выше по графу;
- обязательный `param`, не переданный через `with`; лишние ключи в `with`;
- обращение к работе, идентификатора которой в пайплайне нет, — как
  подстановку `${jobs.<id>...}` (в теле пайплайна, `with`, файле работы или
  файле промпта), так и `jobs.<id>` в `if`; подсказка называет похожие
  идентификаторы, если они есть;
- подстановку `${jobs.<id>.output.*}`, называющую работу вне числа
  предшественниц ссылающейся — прямых или транзитивных, — независимо от
  `concurrency`; кроме `needs: all` и ссылки работы на собственный выход;
- подстановку `${jobs.*.output.*}` в строковую форму `run`;
- переменную в `env`, попадающую под `env_deny`;
- неизвестный бэкенд, отсутствующий файл промпта или схемы — схема проверяется
  во всех трёх местах, где объявляется: `output_schema` шага, `output.schema`
  работы и предикат `schema` в `expect` и в `until.check`; ссылку
  `stepcast:<имя>` линт не проверяет вовсе — недопустимое или неизвестное имя
  отказывает разбором раньше, чем документ доходит до линта;
- отсутствующий файл контекста на любом из трёх уровней;
- `until` без `max_iterations`;
- превышение `limits` из конфига;
- нераскрываемые `uses:`.

Предупреждает:

- нет бюджета у пайплайна — повторы ограничены только `attempts`;
- `workspace.mode: cwd` при `concurrency > 1`;
- у шага нет структурных предикатов в `expect`;
- `changed_only` — единственный предикат шага;
- у работы есть `context`, но нет агентских шагов;
- транзитивная зависимость перечислена в `needs` явно;
- у шага нет `timeout` и не задано умолчание в конфиге;
- `if`, ссылающийся на существующую работу вне зависимостей, при
  `concurrency > 1` — исход названной работы к этому моменту может быть ещё не
  известен, но при `concurrency: 1` порядок исполнения определён объявлением, и
  предупреждения нет; подстановка `${jobs.<id>.output.*}` в том же положении
  этим предупреждением не ограничивается и отклоняется ошибкой (см. выше).

Пути с подстановками, пути-глобы и пути, производимые работами выше по графу,
статически не проверяются. Глобом считается путь с `*`, `?` или `[`: он
запрашивает совпадения, и их отсутствие не ошибка. Исключение — путь, целиком
собранный из `${project.*}`: это пространство объявляет то, что в репозитории
есть до прогона, поэтому такой путь проверяется наравне с литералом, и опечатка
в `project.spec.rules` видна линту, а не только отказом работы посреди прогона. Предикат `file_exists` не
проверяется тоже — он по смыслу указывает на файл, которого ещё нет. Полная проверка — `stepcast lint --resolve --input change=foo`.
