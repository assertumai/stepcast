# Формат пайплайна

Файл `scarp.yml` в корне репозитория — пайплайн по умолчанию. Несколько
пайплайнов живут в `.scarp/pipelines/<name>.yml`, работы — в
`.scarp/jobs/<name>.yml`.

Разделение ответственности жёсткое:

| Где | Что описано |
|---|---|
| файл работы | что она делает: шаги, параметры, бюджет, условие сходимости |
| пайплайн | как работы связаны: зависимости, условия запуска, окружение, аргументы |

Ключи `needs`, `when`, `with` внутри файла работы отклоняются линтером. Работа
не знает ни своих потребителей, ни своего места в графе.

## Верхний уровень

```yaml
version: 1
kind: pipeline
name: implement-change

inputs:                          # аргументы запуска
  change:
    type: string
    required: true
  skip_review:
    type: bool
    default: false

env:                             # окружение для всех работ
  NODE_ENV: test
env_inherit: minimal             # minimal | full
env_passthrough: [DOCKER_HOST]
env_files: [.env.test]
env_deny: ["AWS_*"]              # дополняет запреты из конфига

secrets:
  GITHUB_TOKEN: ${host.GH_TOKEN}

defaults:
  agent: claude
  workspace: worktree

budget:                          # обязателен
  tokens: 2M
  wallclock: 2h
  rate_limit_pct: 80
  on_exceed: pause

concurrency: 3

jobs: { ... }
```

## Файл работы

```yaml
# .scarp/jobs/implement.yml
version: 1
kind: job
name: implement
description: Реализовать задачи из плана до зелёной сборки

params:
  change:
    type: string
    required: true
  max_iterations:
    type: int
    default: 4

workspace: worktree              # repo | worktree | temp

env:
  RUST_BACKTRACE: "1"

budget:
  tokens: 500k
  wallclock: 30m

until:
  max_iterations: ${params.max_iterations}
  check:
    - cmd: npm test
    - cmd: npx tsc --noEmit

outputs:
  report: reports/implement.json

steps: [ ... ]
```

Параметры работы адресуются через `${params.*}` и не пересекаются с `inputs`
пайплайна. Работа не видит `inputs` — только то, что ей передали через `with`.

**`workspace`** — `repo` — общее рабочее дерево, `worktree` — отдельный git
worktree (изоляция параллельных работ без контейнеров), `temp` — чистая
директория. Контейнеры добавятся позже как ещё одно значение, формат не
изменится.

**`until`** — цикл живёт внутри работы, не между работами. После прохода
`steps` проверяется `check`; если он не прошёл и бюджет не исчерпан, цикл
повторяется, и вывод упавшей проверки попадает в контекст шагов следующей
итерации. `until` без `budget` и без `max_iterations` отклоняется линтером.

Итоговый статус: `success | failed | skipped | canceled | budget_exceeded`.

## Подключение работ

```yaml
jobs:
  plan:
    uses: ./.scarp/jobs/plan.yml
    with:
      change: ${inputs.change}

  implement:
    uses: ./.scarp/jobs/implement.yml
    with:
      change: ${inputs.change}
      max_iterations: 6
    needs: [plan]
    env:
      NODE_ENV: development      # оверрайд на месте подключения
    budget:
      tokens: 900k

  typecheck:                     # работу можно описать и на месте
    needs: [implement]
    steps:
      - id: tsc
        run: npx tsc --noEmit
        expect:
          - exit_code: 0

  review:
    uses: ./.scarp/jobs/review.yml
    needs: [typecheck]
    when: "not inputs.skip_review"

  archive:
    uses: ./.scarp/jobs/archive.yml
    needs: [review]
    when: all_ok

  triage:
    uses: ./.scarp/jobs/triage.yml
    needs: all
    when: any_failed
```

На месте подключения переопределяются `with`, `needs`, `when`, `env`,
`secrets`, `budget` и `workspace`. Шаги не переопределяются — иначе файл работы
перестаёт быть источником правды о том, что она делает.

Одна и та же работа подключается несколько раз под разными идентификаторами с
разными параметрами.

### Зависимости и условия

Перечисляются только **прямые** зависимости — транзитивные подразумеваются, и
линтер предупреждает об избыточных. Работы без взаимных зависимостей идут
параллельно в пределах `concurrency`. По умолчанию `when` — «все зависимости
завершились успехом».

`needs: all` — работа выполняется после того, как остальной граф завершился в
любом исходе. Нужна именно для разбора отказа: перечислять там все работы,
которые могли упасть, бессмысленно, потому что при раннем отказе поздние работы
просто не запускались.

Исходящей маршрутизации (`on_failure: <job>`) в формате нет.

### Выражения

Доступны `inputs.*`, `run.*`, `env.*`, `jobs.<id>.status`,
`jobs.<id>.outputs.*`, `jobs.<id>.usage.*`.

Без аргументов — значения, без скобок: `all_ok`, `any_failed`, `any_skipped`.
С аргументом — вызовы: `success(review)`, `failed(implement)`, `skipped(e2e)`,
`exceeded(implement)`. Скобки означают аргумент, и ничего больше.

Язык намеренно куцый: сравнения, `and/or/not`, обращение к полям. Всё, что
сложнее, выносится в `run`-шаг, который печатает результат в stdout.

## Окружение

Переменные объявляются на трёх уровнях и склеиваются по цепочке. Каждый
следующий уровень перекрывает предыдущий:

```
базовое окружение (env_inherit)
  → env_files
    → env пайплайна
      → env на месте подключения работы
        → env в файле работы
          → env шага
            → SCARP_* (инжектируются последними, не переопределяются)
              → env_deny (вычёркивает, что бы ни было выше)
```

```yaml
# в файле работы или в пайплайне
env:
  NODE_ENV: test
  API_BASE: ${inputs.api_base}

# только на уровне пайплайна
env_inherit: minimal
env_passthrough: [GH_TOKEN, DOCKER_HOST]
env_files: [.env.test]
env_deny: ["AWS_*", "*_PRIVATE_KEY"]
```

**`env_inherit: minimal`** (умолчание) пропускает из окружения процесса только
базовый набор: `PATH`, `HOME`, `USER`, `SHELL`, `LANG`, `TMPDIR`, системные
переменные платформы и `TERM=dumb`. Всё остальное отсекается — иначе состояние
машины разработчика протекает в прогон, и результат перестаёт воспроизводиться.
`full` пропускает всё, для отладки.

**Адаптер бэкенда добавляет свой список пропускаемого.** При работе по подписке
агентский CLI берёт учётные данные из собственного хранилища, а не из
переменных, поэтому адаптер сам объявляет, что ему нужно (свой конфиг-каталог,
`HOME`). Пользователю это настраивать не приходится.

**Осторожно с агентскими шагами.** Агент запускает собственные подпроцессы, и
окружение шага наследуется ими. Всё, что положено в `env` агентского шага,
доступно любой команде, которую агент решит выполнить.

### Запреты

`env_deny` — список шаблонов имён, которые вычёркиваются из окружения
последними, независимо от того, как переменная туда попала: наследованием,
`env_passthrough`, `env_files`, явным `env` любого уровня или адаптером
бэкенда.

```yaml
env_deny:
  - "AWS_*"
  - "*_PRIVATE_KEY"
  - "KUBECONFIG"
```

Шаблоны — глобы по имени, регистрозависимые. Правило одно: **запреты
складываются и никогда не вычитаются.** Список из глобального конфига,
проектного конфига и пайплайна объединяется; нижний уровень может только
ужесточить. Иначе запрет не был бы средством контроля — достаточно было бы
одного пайплайна, чтобы его обойти.

Базовый список запретов задан в конфиге и применяется ко всем прогонам —
см. [конфигурацию](config.md). При `env_inherit: minimal` большая часть
окружения и так отсекается, поэтому `env_deny` работает главным образом против
`env_passthrough`, `env_files` и режима `full`.

Каждое срабатывание пишется в `events.ndjson` (только имя переменной и
сработавший шаблон), чтобы «почему у меня в шаге нет `GH_TOKEN`» отвечалось
логом, а не догадками.

Если запрет перекрывает то, что запросил адаптер бэкенда, движок сообщает об
этом явно на старте прогона: заблокированная переменная может лишить агентский
CLI аутентификации в API-режиме.

### Инжектируемые переменные

Доступны всем шагам, переопределению не подлежат:

| | |
|---|---|
| `SCARP_RUN_ID` | идентификатор прогона |
| `SCARP_RUN_DIR` | директория прогона |
| `SCARP_JOB` / `SCARP_JOB_DIR` | текущая работа |
| `SCARP_STEP` / `SCARP_STEP_DIR` | текущий шаг |
| `SCARP_ITERATION` | номер итерации `until`, с 1 |
| `SCARP_ATTEMPT` | номер попытки, с 1 |
| `SCARP_WORKSPACE` | корень рабочего дерева работы |
| `SCARP_ARTIFACTS` | директория артефактов прогона |
| `SCARP_PREV_FAILURE` | путь к разбору прошлого отказа, если он есть |

### Секреты

Секреты — отдельная сущность, не переменные окружения, потому что `env`
целиком попадает в `pipeline.lock.yml` и `run.json`.

```yaml
secrets:
  GITHUB_TOKEN: ${host.GH_TOKEN}
  NPM_TOKEN:
    command: "op read op://dev/npm/token"
```

Объявляются один раз на уровне пайплайна, а получают их только те работы и
шаги, которые их запросили:

```yaml
  publish:
    uses: ./.scarp/jobs/publish.yml
    needs: [build]
    secrets: [NPM_TOKEN]
```

Значения разрешаются один раз в начале прогона, живут в памяти, не пишутся ни в
`pipeline.lock.yml`, ни в `run.json`, ни в `step.json`, и вычищаются из
`stdout.log` и `stderr.log` подстановкой `***` по совпадению значения.

В ключ шага секрет вносит только имя, но не значение: смена значения секрета не
инвалидирует шаг. Обход — `scarp run --no-reuse`.

## Шаги

### agent

```yaml
steps:
  - id: plan
    agent: claude                # claude | codex | ...
    model: opus
    prompt: file:./prompts/plan.md
    context:
      - openspec/changes/${params.change}/proposal.md
      - openspec/changes/${params.change}/tasks.md
    env:
      SCARP_HINT: "план должен быть исполняемым"
    output:
      file: reports/plan.json
      schema: ./schemas/plan.json    # передаётся бэкенду, если он это умеет
    expect:
      - file_exists: reports/plan.json
      - schema: ./schemas/plan.json
    attempts:
      max: 3
```

Шаг получает промпт, объявленный контекст, окружение и рабочую директорию.
Пайплайн ему не виден — он не знает ни о соседних шагах, ни о том, что дальше.

Запуск только через pipe, без псевдотерминала. Структурированный вывод берётся
из штатного headless-режима бэкенда, оттуда же приходит расход токенов.

### run

```yaml
  - id: test
    run: npm test
    env:
      CI: "1"
    expect:
      - exit_code: 0
    on_fail:
      analyze: claude
      prompt: file:./prompts/triage-tests.md
```

`on_fail.analyze` не чинит и не повторяет — он производит разбор в
`analysis.md` и завершает шаг отказом.

## expect

| Предикат | Тип | Описание |
|---|---|---|
| `exit_code: 0` | структурный | код возврата |
| `file_exists: <path>` | структурный | файл создан |
| `schema: <path>` | структурный | JSON-вывод соответствует схеме |
| `matches: /re/` | структурный | stdout содержит |
| `not_matches: /re/` | структурный | stdout не содержит |
| `changed_only: [glob]` | структурный | изменения не вышли за границы |
| `cmd: "..."` | структурный | команда завершилась нулём |
| `judge: "..."` | смысловой | оценка агентом-судьёй |

`judge` по умолчанию совещательный: результат пишется в отчёт, шаг не падает.
Жёстким гейтом делается явно:

```yaml
      - judge: "План покрывает все требования из спеки"
        hard: true
        agent: claude
```

Причина умолчания: если валидация дороже и менее надёжна, чем сама работа, она
даёт шум, а не сигнал. Ограничения в движке нет — есть умолчание.

## attempts

```yaml
    attempts:
      max: 3
      escalation:                          # опционально
        - include_failure: true            # 2-я: + вывод упавшей проверки
        - include_failure: true            # 3-я: + сильнее модель
          model: opus
```

Ограничителей ровно два: `attempts.max` и бюджет пайплайна. Проверки того, что
попытка чем-то отличается от предыдущей, нет — повтор с идентичным входом
разрешён.

`escalation` остаётся доступной, но не обязательной: если её нет, попытка
повторяется как есть.

Каждая попытка пишется в `step.json` отдельной записью со своим расходом.
`scarp usage` показывает шаги, проходящие не с первого раза, и распределение по
номеру попытки — это тот же диагноз промпта или спеки, только наблюдаемый, а не
блокирующий.

## Бюджет

Бюджет пайплайна обязателен: с тех пор как повторы ничем не ограничены по
содержанию, он единственный предохранитель. Линтер отклоняет пайплайн без него.

Бюджеты работ опциональны и работают как независимые потолки, а не как
выделенные квоты: сумма бюджетов работ может превышать бюджет пайплайна —
связывает тот потолок, который упрётся первым.

```yaml
budget:
  tokens: 2M            # tokens_in + tokens_out + cache_write
  wallclock: 2h
  rate_limit_pct: 80    # доля окна лимитов подписки
  on_exceed: pause      # pause | fail
```

Измерения бюджета — токены, время и окно лимитов. Денег среди них нет: при
работе по подписке биллингового сигнала не существует, а пересчёт токенов в
доллары требует таблицы цен, которая устаревает и различается по бэкендам и
режимам. Токены — то, что бэкенд действительно сообщает; на них и считаем.

**Токены.** В потолок идут `tokens_in + tokens_out + cache_write`. `cache_read`
учитывается и показывается, но не засчитывается один к одному — иначе длинные
сессии выглядят катастрофой при копеечной реальной цене. Вес настраивается в
адаптере бэкенда.

**Когда проверяется.** После каждой попытки — по факту. Перед шагом — по
остатку: если остаток меньше медианы прошлых прогонов этого шага, шаг не
запускается.

**При превышении** статус `budget_exceeded`. Для условий он отличим:
`exceeded(job)` истинно, `failed(job)` — тоже, так что `when: any_failed` его
ловит, а специальная обработка возможна.

При `on_exceed: pause` прогон не падает, а встаёт: пишет `status.json` с
командой возобновления и завершается нулём. Основной режим для окна лимитов
подписки — ночной прогон упирается в лимит, засыпает и продолжается после
сброса окна, а не теряет всю работу.

**Оценка до запуска.** `scarp lint --budget` считает верхнюю границу из
объявленных потолков, `max_iterations` и `attempts`:

```
$ scarp lint --budget scarp.yml
ok: scarp.yml
worst case: 4.2M токенов, ~92 мин
  implement   3.6M  (900k × 4 итерации)
  review      400k  (200k × 2 попытки)
  plan        160k  (80k × 2 попытки)
превышает budget.tokens пайплайна (1.5M) — прогон остановится по потолку
```

## scarp lint

Отклоняет до запуска:

- отсутствие `budget` на уровне пайплайна;
- превышение потолков из `limits` конфига;
- `needs`, `when` или `with` внутри файла работы;
- циклы в `needs`, недостижимые работы, ссылки на несуществующие идентификаторы;
- `when`, обращающийся к неопределённым `inputs` или к работе не выше по графу;
- обязательный `param` работы, не переданный через `with`; лишние ключи в `with`;
- запрошенный в `secrets` идентификатор, не объявленный в пайплайне;
- неизвестный бэкенд, отсутствующий файл промпта или схемы;
- `until` без `budget` и без `max_iterations`;
- выход, читаемый ниже по графу, но не объявленный в `outputs`;
- нераскрываемые `uses:`.

Предупреждает:

- у шага нет ни одного структурного предиката в `expect`;
- у работы нет бюджета — верхняя оценка неполна;
- транзитивная зависимость перечислена в `needs` явно;
- `env_inherit: full`;
- худшая оценка превышает `budget` пайплайна.
