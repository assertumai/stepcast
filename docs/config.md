# Конфигурация

| Файл | Область | В git |
|---|---|---|
| `~/.stepcast/config.yml` | машина: пути, бэкенды, политика | нет |
| `.stepcast/config.yml` | проект: умолчания и ужесточения | да |

Проектный конфиг перекрывает глобальный, пайплайн перекрывает оба, флаги CLI
перекрывают всё. Исключения — `env_deny`, `context.deny`, `plugins` и
`limits`: первые три складываются, `limits` снизу только ужесточается.
Политика, которую отменяет тот, кого она ограничивает, — не политика.

## Формат

```yaml
version: 1
kind: config

runs:
  root: ~/.stepcast/runs
  keep: 30d

defaults:
  agent: claude
  # model: sonnet             # общее явное переопределение; побеждает model_tier
  workspace: { mode: cwd }
  session: shared
  concurrency: 1
  fail_fast: true
  step_timeout: 30m
  stall_timeout: 5m
  max_wait: 6h                 # предел суммарного ожидания сброса окна лимита за прогон

limits:                        # потолки, которые пайплайн не может поднять
  tokens: 20M                  # трафик прогона, а не объём контекста
  wallclock: 4h
  concurrency: 8
  attempts: 5
  iterations: 10

plugins:                       # расширения движка, см. docs/plugins.md
  - stepcast/backends/codex    # адаптер Codex, поставляемый пакетом
  - ./plugins/local.mjs        # путь — от файла, в котором объявлен
  - stepcast-plugin-http       # имя — пакет из node_modules проекта

env_deny:                      # SSH_* здесь нет: он ловит SSH_AUTH_SOCK
  - "AWS_*"                    # и ломает git по ssh, а ключи ловит *_KEY
  - "*_KEY"
  - "KUBECONFIG"

context:
  inline_threshold: 4k         # выше порога запись передаётся путём
  max_tokens: 120k             # предел на весь собранный контекст шага
  note_max_tokens: 4k          # предел на выдержку о непройденной проверке
  deny:
    - "**/.env*"
    - "**/*.pem"
    - "**/*.key"
    - "**/id_rsa*"
    - "**/.git/**"

backends:
  claude:
    command: claude
    default_model: sonnet
    concurrency: 2
    cache_read_weight: 0.1
    sessions: true             # умеет продолжать сессию по идентификатору
    structured_output: true
    strict_permissions: true  # умеет применять enforce: strict
    mcp: true                 # умеет транслировать объявленные MCP-серверы
    permissions:
      mode: auto
      allow: ["Edit", "Read", "Bash(npm *)", "Bash(git *)"]
      deny: ["Bash(rm -rf *)"]
      enforce: inherit
    env:
      DISABLE_AUTOUPDATER: "1"
  codex:                       # запись появляется умолчаниями плагина (plugin:codex):
    default_model: gpt-5.6-terra # command, sessions, structured_output, mcp, concurrency,
    permissions:               # cache_read_weight — переписывать не нужно
      mode: workspace-write    # словарь Codex: read-only | workspace-write | danger-full-access

ui:
  port: 7717

project:
  check: npm run check         # только в .stepcast/config.yml, см. «Команда проверки проекта»
  tools: [npm, npx, node]      # имена инструментов, см. «Инструменты репозитория»
  spec:                        # объявление практики спецификации, см. «Практика спецификации»
    dir: openspec/changes
    rules: .stepcast/prompts/spec-rules.md
    tool: openspec
    check: openspec validate "$SPEC_CHANGE" --strict
  edit_paths: [src/**, test/**, docs/**, package.json]  # границы правок, см. «Границы правок»
```

## Агенты и модели

Страница **Агенты** (`/agents`) задаёт `defaults.agent`, модель по умолчанию и
модели для пяти tier каждого агента: `max`, `deep`, `balance`, `fast`, `mini`.
Она пишет `~/.stepcast/config.yml`, сохраняет комментарии и показывает источник
значений. Можно подключить поставляемый плагин Codex; для запуска нужен
установленный и авторизованный Codex CLI. Подключённые плагины других агентов
также появляются на странице.

Встроенный агент по умолчанию — `claude`. Его модель — `sonnet`; у плагина
`codex` — `gpt-5.6-terra` (GPT 5.6 Terra). Карты tier изначально пусты: пользователь
сам выбирает модели, и один tier у разных агентов может обозначать разные модели.

```yaml
plugins: [stepcast/backends/codex]
defaults:
  agent: codex
backends:
  claude:
    default_model: sonnet
    model_tiers:
      max: opus
      deep: opus
      balance: sonnet
      fast: haiku
      mini: haiku
  codex:
    default_model: gpt-5.6-terra
    model_tiers:
      balance: gpt-5.6-terra
```

Это пример пользовательских назначений, а не встроенная таблица соответствий.
Проект может переопределить отдельные значения `backends.<agent>.default_model`
и `backends.<agent>.model_tiers.<tier>`, сохранив остальные из глобального файла.
На странице пустое поле удаляет глобальное переопределение. Если tier не задан
ни одним слоем, используется модель агента по умолчанию.

Старое `defaults.model` остаётся общим явным переопределением: оно имеет приоритет
над tier и моделью агента. Страница «Агенты» показывает его, если оно задано;
снять его можно на странице «Настройки». При одновременном использовании Claude
и Codex удобнее задавать модели отдельно в `backends`.

Порядок выбора и примеры уровней pipeline/job/step описаны в
[формате пайплайна](pipeline-format.md#агент-модель-и-tier).

### Список моделей на странице

Каждое из шести полей модели (по умолчанию и пять tier) даёт выбрать значение
из списка, распознанного у CLI агента: демон опрашивает его отдельным запросом
после того, как страница уже отрисована по настройкам, — список приходит
вторым шагом и не задерживает поля. Пока он не пришёл, поле остаётся правимым
и говорит, что список распознаётся.

**Список — подсказка, а не перечень допустимого.** Он снят с самого CLI
(`claude --help` и подобное), а не с сервера моделей, и по устройству неполон
— у Claude Code, например, справка называет лишь псевдонимы (`sonnet`, `opus`,
…) и один пример полного имени. Поэтому выбор вне списка — обычный случай, а
не ошибка: сохранённое значение, которого в списке нет, остаётся выбранным и
помечено как значение вне распознанного списка, а не как неверное. Правка
соседнего поля его не трогает и не сбрасывает. Ручной ввод доступен всегда,
независимо от того, пришёл список и что в нём есть.

Когда агент не отвечает, карточка называет причину словами: агент не
установлен, не ответил за отведённое время, ответил отказом (текст CLI идёт
при подписи «агент ответил отказом»), его ответ не разобран или распознавание
сорвалось на коде самого бэкенда — либо, если у бэкенда вовсе нет пробы (так
пока устроен `codex`), что он перечислять модели не умеет. Отказ одного агента
не прячет список остальных: у каждой карточки своя причина.

Распознанное — и список, и отказ — демон держит, пока жив: пробы не поднимаются
заново на каждое открытие страницы. Поэтому под общим пояснением стоит кнопка
**перечислить заново**: установили агента, поправили `backends.<agent>.command`
или обновили аутентификацию — нажмите её, и списки будут собраны сызнова, без
перезапуска `stepcast up`.

Рядом с каждым полем — кнопка **копировать**: кладёт в буфер имя модели без
пояснения CLI и без имени tier, чтобы вставить его в `model:` пайплайна или
работы. Если браузер отказал в доступе к буферу, об этом сказано рядом с
кнопкой, а значение остаётся обычным текстом поля — его можно выделить и
скопировать вручную.

## Единицы

`k` / `M` — тысячи и миллионы токенов, допускается дробное (`1.5M`).
`s` / `m` / `h` / `d` — время. `context.inline_threshold` — в токенах.
Регистр у множителей токенов и у единиц времени различается намеренно: `m` —
минуты, `M` — миллионы.

`defaults.step_timeout` — умолчание таймаута шага (`docs/pipeline-format.md#таймауты`)
— не имеет отношения к сроку ожидания шага `decision` (`deadline`,
`docs/decisions.md`): вид шага, объявивший `waits: true`, движок против этого
таймаута не гонит вовсе, и `step_timeout` для него остаётся справочным
значением. Срок ожидания — свой, объявляется на самом шаге и считается от
начала ожидания, а не от конфигурации.

## Что где уместно

**Глобальный** — машина и политика: где лежат бэкенды, их возможности и веса,
корень прогонов, retention, базовые запреты, `limits`.

**Проектный** — умолчания команды: агент, модель, режим рабочей директории,
дополнительные запреты. Он в репозитории и попадает в ревью, поэтому линтер
отклоняет в нём `runs.root` и `backends.*.command` — машинно-зависимым путям
там не место.

**Каталог прогонов обязан лежать вне рабочего дерева.** Иначе запись журнала
сама выглядела бы изменением дерева. Проверяется до запуска первой работы.

## Команда проверки проекта

`project.check` — команда, которой репозиторий проверяет сам себя: `npm run
check`, `go vet ./... && go test ./...`, `./gradlew check`. Значение — строка,
исполняемая оболочкой; пустая строка и строка из одних пробелов отклоняются
разбором конфигурации, потому что пустая команда даёт нулевой код возврата —
зелёный гейт на любом коде хуже отсутствующего вовсе.

Ключ допустим только в `.stepcast/config.yml` и отклоняется в
`~/.stepcast/config.yml` — тем же правилом, что `runs.root` и
`backends.*.command`, только в обратную сторону: команда проверки принадлежит
репозиторию, а не машине, и одна на все репозитории машины была бы верна ровно
для одного из них.

Встроенного умолчания у `project.check` нет и не появится: команда,
подставленная за автора, исполнялась бы в чужом дереве. Ключ необязателен —
репозиторий, которому проверять нечем, секцию не заводит, и это не ошибка.

Документ пайплайна может объявить `project.check` сам, верхним ключом
`project` — тем же порядком слоёв, каким пайплайн уже перекрывает `defaults` и
`context`: пайплайн, затем проектный конфиг, ни один не обязателен. Так
репозиторий с несколькими пайплайнами объявляет команду один раз в
конфигурации, а репозиторий с одним — там, где у него и так всё описано.

Команда обязана быть самодостаточной — в том числе по зависимостям. Петля
исполняет её не только в дереве, которое кто-то подготовил руками: `stepcast
merge-lanes` накладывает дифф дорожки на дерево проекта и проверяет **там**, а
дифф умеет менять манифест зависимостей (`package.json`, `go.mod`,
`build.gradle.kts`). Установленное агентом в его рабочем дереве в дерево
наложения не переезжает: дифф несёт манифест, но не установленные пакеты.
Проверка, полагающаяся на чужую установку, падает тогда на первом импорте
новой зависимости, и зелёная во всём остальном дорожка откатывается. Движок
установки за автора не подставляет и подставить не может: `--check` для него —
произвольная строка, и об экосистеме репозитория он не знает ничего. Поэтому
установку зависимостей объявляет сама команда — `npm install && npm run check`,
`go mod download && go test ./...`, `./gradlew check` (Gradle разрешает
зависимости сам).

Значение доступно подстановкой `${project.check}` в пайплайне, файлах работ и
файлах промптов (см. [«Когда что раскрывается»](pipeline-format.md#когда-что-раскрывается)) —
доезжает до оболочки как есть, и экранирование сложной команды остаётся на
авторе. Проверку, которая не укладывается в одну строку без риска разъехаться
с кавычками вызывающего места, правильнее завести скриптом репозитория
(`./scripts/check.sh`) и объявить в `project.check` сам скрипт.

## Плагины

Состав плагинов — дерево именованных строк (`docs/plugins.md`), собранное
тремя слоями снизу вверх: встроенное описание пакета, домашний слой,
проектный слой. Каждый слой видит дерево, накопленное предыдущими, и вправе
заменить в нём любую строку по `id`, вставить свою на названное место или
отключить чужую.

Домашний и проектный слои несут по **три документа** каждый: привычный
`config.yml`, рядом с ним **`plugins.patch.yml`** — файл того же каталога,
`~/.stepcast/plugins.patch.yml` и `.stepcast/plugins.patch.yml`, — и тем же
приёмом **`routes.yml`**, файл маршрутов витрины (`~/.stepcast/routes.yml` и
`.stepcast/routes.yml`): формат, слои и слияние по `id` у него свои, описаны
отдельно (`docs/routes.md`), а отсутствие файла — то же обычное состояние, не
отказ.

Формат `plugins.patch.yml`:

```yaml
version: 1
kind: plugins-patch
plugins:
  - id: backend-claude          # известный id — замена строки целиком
    use: ./plugins/my-claude.mjs
  - id: my-http-checks          # новый id — вставка
    use: stepcast-plugin-http
    after: backend-claude       # либо before: <id>, либо ничего — тогда в конец
    enabled: true                # необязателен, умолчание true
```

Строка с **известным `id`** заменяет одноимённую строку дерева целиком и на
её месте: поля, которых патч не назвал (кроме `id`), берут умолчания
формата, а не значения заменяемой строки, — заменённая `enabled: false`
станет действующей, если новая строка `enabled` не называет. Строка с
**новым `id`** вставляется по `before`/`after`, а без обоих — в конец слоя.
Отсутствие файла патча — обычное состояние, не отказ.

`id` — обычно слаг в kebab-case, придуманный автором патча, но схема его этим
не ограничивает: патч, заменяющий строку ключа `plugins` (см. ниже), обязан
назвать тот же `id`, каким она объявлена, — сам спецификатор модуля, будь то
путь или имя пакета.

Ключ `plugins` конфигурации — **сокращённая форма** строки дерева: каждая его
строка становится операцией «вставить в конец своего слоя» с `id`, равным
спецификатору. Синтаксис и разрешение путей не изменились: строка,
начинающаяся с `./` или `../`, разрешается от каталога файла, в котором
объявлена; форма `stepcast:<имя>` называет строку, поставляемую пакетом;
остальные — имя пакета от корня проекта, а при неудаче от каталога самого
движка. Ключ допустим в обоих слоях, списки между ними **объединяются**, а
пустой список отклоняется разбором. Повтор одного модуля — хоть в двух слоях,
хоть между ключом и патчем — даёт одну строку дерева и одну загрузку.

Повтор ключом **ничего не меняет**: строка с этим `id` уже в дереве, вставлять
нечего, и она остаётся за слоем, объявившим её первым, — вместе со своим
файлом, а значит и базой разрешения относительного пути. `./adapters/x.mjs`,
названный и в `~/.stepcast/config.yml`, и в `.stepcast/config.yml`, грузится
из домашнего каталога, как и грузился. Заменить такую строку верхний слой
по-прежнему может — патчем, который для того и заведён.

Действующее значение ключа `plugins` — проекция итогового дерева: модули
действующих строк в порядке дерева. Строки встроенного слоя в него не входят
(`stepcast:<имя>` — не модуль), отключённая патчем строка — тоже, а строка,
которую принёс патч, входит, хотя ключа `plugins` не объявлял ни один слой.
Отчёт `stepcast config` показывает рядом с этим значением вклад каждого слоя
в сам ключ — то, что было **объявлено**.

Плагины загружаются до разбора аргументов команды, зависящей от конфигурации,
и отказ загрузки прекращает такую команду целиком — включая `stepcast config`.
Единственное исключение — `stepcast plugins`: она печатает итоговое дерево и
тогда, когда одна из строк не загрузилась, называя виновницу причиной.
Команды `data`, `down` и `init` конфигурацию не разрешают вовсе (раздел
«Разрешение» ниже) и плагинов не загружают, поэтому отказ загрузки их не
касается.

`stepcast plugins` печатает итоговое дерево: место в порядке, `id`, слой,
давший строку (`встроенный` либо путь файла), модуль и состояние (`действует`
/ `отключена`). Отчёт `stepcast config` печатает соседний раздел «Плагины» —
имя, версию, путь модуля и вклады каждого загруженного плагина, — но
полного ответа на «что загружено, в каком порядке и из какого слоя» не даёт;
за этим — `stepcast plugins`. Значения, пришедшие из умолчаний плагина,
показаны в отчёте `stepcast config` источником `plugin:<имя>` и
перекрываются любым пользовательским слоем.

Правка `plugins.patch.yml` на работающем демоне витрины действует без
перезапуска: вклады строки, ушедшей из дерева, снимаются, вклады появившейся
— действуют со следующего запроса.

Плагин исполняется с правами процесса движка: изоляции нет. Контракт, пример
и ограничения — [docs/plugins.md](plugins.md).

### Отключение встроенного экрана витрины

Каждый встроенный экран витрины — тоже строка встроенного слоя
(`docs/plugins.md`, «Строки поставки от вызывающего»; `docs/ui-plugins.md`,
«Экран как плагин»), и патчится тем же документом:

```yaml
version: 1
kind: plugins-patch
plugins:
  - id: screen-usage
    use: stepcast:screen-usage
    enabled: false
```

Отключённый экран пропадает из пункта меню и отвечает 404 на свои маршруты
API — при работающем демоне это видно со следующего запроса, без
`stepcast down && stepcast up`; уже открытая вкладка узнаёт об этом
перезагрузкой (`docs/ui-plugins.md`). Эти строки видны только в дереве
демона: `stepcast plugins` и дерево команд `stepcast run`/`stepcast config`
об экранах ничего не знают.

Отключённый экран забирает с собой свои маршруты, а не только себя: сосед,
который их звал, получает 404 с названием снятого маршрута и показывает это
отказом. Так, без `screen-runs` экран уборки теряет отбор и групповое
удаление прогонов — сами записи расхода он при этом убирает по-прежнему.

Единственная строка витрины, отключать которую бессмысленно, — каркас
`ui-shell`: он заводит реестры экранов и маршрутов, и состав без него не
может обслужить ни одного запроса. Такой патч демон не исполняет буквально:
он продолжает отвечать последним успешно собранным составом (а при старте —
встроенным) и называет причину полосой над экраном и полем `buildError` в
`GET /api/screens`. Пока ни одна сборка не удалась, маршруты, отвечающие
значениями конфигурации, — настройки и агенты — отказывают с той же
причиной, а не выдают встроенные умолчания за настройки пользователя.

## Раннеры шагов script

`runners` — таблица «имя → чем исполнять» для шага `script`
([docs/pipeline-format.md](pipeline-format.md#script)). Запись выглядит так:

```yaml
runners:
  uv:
    command: [uv, run, --script]
    extensions: ['.py']
```

`command` — список argv-префикса: раннер запускается без оболочки, и правил
разбиения строки на слова у движка нет — строковой формы у `command` поэтому
нет вовсе. Названный, он обязан быть непустым списком непустых строк.
`extensions` необязателен и перечисляет расширения файлов, которые запись
берёт на себя по умолчанию; каждое обязано начинаться с точки. argv шага
собирается конкатенацией: `command`, затем абсолютный путь скрипта, затем
`args` шага.

Встроенный слой уже даёт четыре записи — `node` (`.js`, `.mjs`, `.cjs`),
`node-ts` (`.ts`, `.mts`, с `--experimental-strip-types`), `python3` (`.py`) и
`sh` (`.sh`) — с происхождением «встроенное умолчание» в `stepcast config`.
`node-ts` — отдельная запись, а не флаг, который `node` добавляет при виде
`.ts`: `--experimental-strip-types` неприменим на Node 22.0-22.5 и не нужен на
новых, приписывать его всякому `node` нельзя.

Ключ допустим **в обоих слоях** — в отличие от `backends.*.command`, который
всегда путь к CLI на конкретной машине. Раннер обычно имя в `PATH` (`uv`,
`bun`, `deno`), и зависимость проекта от него — законное содержимое
проектного конфига; абсолютный путь к интерпретатору по-прежнему уместен в
домашнем. Слои сливаются по листьям, как `backends`, и в обе стороны: запись,
назвавшая только `command`, сохраняет `extensions` одноимённой записи нижнего
слоя, а запись, назвавшая только `extensions`, — её `command`. Повторять
встроенную команду копией, чтобы закрепить расширение, не нужно. Сам список
`extensions` при этом заменяется целиком, как всякий список конфигурации:
добавляя `.py3` к `python3`, перечислите и `.py`.

Действующая запись обязана иметь `command` хотя бы из одного слоя. Раннер, ни
в одном слое её не назвавший, — ошибка разбора конфигурации с его именем:
пустая команда дала бы argv из одного пути скрипта, то есть попытку запустить
файл напрямую вместо объявленного раннера. `stepcast config` печатает
действующие `command` и `extensions` значениями, рядом с назвавшим их слоем, —
по ним и видно, чем исполнится `.py` и кто перехватил расширение.

Расширение вправе объявить не одна запись сразу — проект добавляет `uv` с
`.py`, а встроенная таблица уже держит `.py` за `python3`. Побеждает запись
ближнего слоя: проектный конфиг важнее домашнего, домашний — встроенной
таблицы. Две записи **одного** слоя, назвавшие одно расширение, — ошибка
разбора конфигурации с именами обеих: между собой они несравнимы, и выбор по
порядку ключей документа был бы решением случая. Явный `runner:` на самом шаге
сильнее любого закрепления расширения в любом слое.

Движок не устанавливает отсутствующий раннер сам — ни `uv sync`, ни `npm i`:
он называет отсутствующее и останавливается с подсказкой объявить
`runners.<имя>.command` либо установить интерпретатор.

### wrapper

Запись вправе назвать `wrapper` — путь, который argv шага несёт между
командой раннера и путём скрипта: `command`, обёртка, скрипт, `args`. Три
формы значения:

- `stepcast:<имя>` — файл, поставляемый пакетом. Сегодня одна обёртка —
  `stepcast:step` ([docs/plugins.md](plugins.md#обёртка-раннера)): она зовёт
  default export модуля, если он есть. Незнакомое имя — отказ разбора
  конфигурации с перечнем поставляемых;
- путь — по тем же правилам, что значение `script`: голое имя ищется слоями
  `.stepcast/scripts/`, `./` и `../` разрешаются от файла, объявившего
  `wrapper`;
- `none` — обёртки у раннера нет.

Встроенные `node` и `node-ts` объявляют `wrapper: stepcast:step`; `python3` и
`sh` — нет, пакет поставляет обёртку только для Node. `none` — единственный
способ снять унаследованную обёртку: слияние по листьям поля не удаляет, и
проект, направивший `node` на `bun`, получил бы чужую обёртку молча, если бы
не мог явно её снять:

```yaml
runners:
  node:
    command: [bun]
    wrapper: none
```

`stepcast config` печатает действующий `wrapper` значением, рядом с `command`
и `extensions`.

## Инструменты репозитория

`project.tools` — имена инструментов, которыми репозиторий собирается,
проверяется и запускается: `[npm, npx, node]`, `[./gradlew, java]`. Объявляются
**имена**, а не готовые записи прав (`Bash(npm *)`) — форма права знает файл
работы, а не конфигурация. Репозиторий, сменивший бэкенд, увидевший другой
синтаксис политики, правит только файл работы; объявление имени переживает эту
смену без правки.

Значение — список, а не строка с разделителем: разделитель потребовал бы его
расщепления движком (тогда имя с пробелом объявить нельзя) либо бэкендом
(`Bash(npm npx node *)` не значит ничего). Список раскрывается в пайплайне
особым правилом — по элементу списка на значение (см.
[«Раскрытие списочного значения»](pipeline-format.md#раскрытие-списочного-значения-в-элемент-списка)).

Пустой список — `tools: []` — отклоняется разбором, как пустая
`project.check`: объявление, не называющее ни одного инструмента, почти
наверняка забытая правка, а не «инструментов нет» — для этого случая ключ
просто не заводят вовсе, и это не ошибка. Каждый элемент — та же непустая
строка, что `project.check` и `project.spec.tool`; пробел внутри значения
допущен намеренно (`./gradlew`, `npm run` — второе осмысленно сужает право до
`Bash(npm run *)`, разрешая скрипты и запрещая `npm install`).

Ключ допустим только в `.stepcast/config.yml` и отклоняется в
`~/.stepcast/config.yml` — тем же правилом, что `project.check`: инструменты
принадлежат репозиторию, а не машине.

Документ пайплайна может объявить `project.tools` сам, верхним ключом
`project`. В отличие от `env_deny` и `context.deny`, слой не объединяется со
слоем ниже, а заменяет его целиком: пайплайн, назвавший свои инструменты,
называет их вместо инструментов конфигурации, а не в дополнение к ним, —
объединение здесь означало бы предположение, что оба списка описывают один и
тот же репозиторий одинаково, а верно как раз обратное. Соседний ключ секции
`project`, объявленный другим слоем (скажем, `check` в конфигурации, а `tools`
в пайплайне), от этой замены не страдает: слияние внутри секции по-прежнему
полистовое.

Значение доступно подстановкой `${project.tools}` — только в элементе списка,
не в скалярном поле (см.
[«Когда что раскрывается»](pipeline-format.md#когда-что-раскрывается)).

## Границы правок

`project.edit_paths` — пути и шаблоны глоба от корня репозитория, правка
которых и есть работа над ним: `[src/**, test/**, docs/**, package.json]`,
`[cmd/**, internal/**, go.mod]`. Объявляются **пути**, а не готовый предикат
`changed_only` — форму предиката собирает файл работы, а не конфигурация;
работа добавляет к объявленному свои записи (каталог документов изменения,
файлы петли), и если бы конфигурация объявляла готовый предикат целиком,
добавить к нему было бы нечего — список между слоями заменяется целиком.

Каждый элемент проверяется той же моделью, что `project.spec.dir`: непустой
относительный путь без сегмента `..`. Причина та же, только прямее: значение и
есть граница правок, и абсолютный путь или путь с `..` либо не совпал бы ни с
одним path в предикате `changed_only` никогда (пути туда приходят сравнением
двух снимков рабочего дерева и потому всегда относительны его корню), либо
вывел бы границу за пределы проверяемого дерева. Шаблоны глоба (`src/**`)
модель пропускает беспрепятственно.

Пустой список — `edit_paths: []` — отклоняется разбором, как пустой
`project.tools`: объявление, не называющее ни одного пути, почти наверняка
забытая правка, а не «границ нет» — для этого случая ключ просто не заводят.

Ключ допустим только в `.stepcast/config.yml` и отклоняется в
`~/.stepcast/config.yml` — тем же правилом, что `project.check` и
`project.tools`: границы репозитория принадлежат репозиторию, а не машине.

Документ пайплайна может объявить `project.edit_paths` сам, верхним ключом
`project`. Как и `project.tools`, слой не объединяется со слоем ниже, а
заменяет его целиком: пайплайн, назвавший свои границы, называет их вместо
границ конфигурации, а не в дополнение к ним. Соседний ключ секции `project`,
объявленный другим слоем, от этой замены не страдает — слияние внутри секции
по-прежнему полистовое.

Значение доступно подстановкой `${project.edit_paths}` — только в элементе
списка, не в скалярном поле, тем же правилом, что `${project.tools}` (см.
[«Когда что раскрывается»](pipeline-format.md#когда-что-раскрывается)).
Заводить статическую проверку существования объявленных путей `edit_paths` не
обещает: `stepcast lint` шаблоны `changed_only` не проверяет и сегодня, а
опечатка в объявленном пути обнаруживается первой же правкой, вышедшей за
молча суженную границу.

## Режим доставки правки кабинета

```yaml
project:
  proposals: queue   # умолчание; либо direct
```

`project.proposals` (`queue` | `direct`) решает, встаёт ли предложенная
агентом правка файла кабинета (`.stepcast/widgets/`, `.stepcast/dashboards/`,
`.stepcast/plugins/`) в очередь предложений или пишется немедленно —
подробности и формат записи в [`docs/proposals.md`](proposals.md). Умолчание
— `queue`.

Ключ допустим только в `.stepcast/config.yml` и отклоняется в
`~/.stepcast/config.yml` — тем же правилом, что `project.check` и
`project.tools`: режим доставки принадлежит репозиторию, а не машине.

В отличие от `project.edit_paths`, документ пайплайна ключ не заводит вовсе:
объявление `proposals` верхним ключом `project` в пайплайне отклоняется
своим текстом, называющим, что режим доставки объявляет только конфигурация
репозитория, — пайплайн ровно тот, кого эта настройка ограничивает, и
объявить себе `direct` он не вправе.

## Вложенные репозитории

`project.nested_repos` — список каталогов дерева, каждый из которых сам
является отдельным репозиторием git: `[public-site, vendor/sdk]`. Объявление
не переносит содержимое вложенного репозитория в якорь автоматически —
`git add -A` в корне на границе вложенного репозитория останавливается,
игнорируемый попадает мимо якоря целиком, отслеживаемый сворачивается в
gitlink, который правка рабочего дерева не двигает, — а даёт движку узнать,
что вложенный репозиторий есть, и завести по нему собственное частное
состояние (составной якорь, [«Составной якорь: несколько
репозиториев»](run-layout.md#составной-якорь-несколько-репозиториев)).

Каждый элемент — тот же непустой относительный путь без сегмента `..`, что и
`project.edit_paths`, но сверх него отклоняет символы шаблона глоба (`*`,
`?`). Значение здесь называет **конкретный каталог**, а не образец: по нему
заводится отдельное частное состояние, и им же префиксуются пути в
`changed_only` и `diff.patch` — раскрывать в этой роли нечего, шаблон обязан
свернуться в один путь до объявления, а не во время его. Пустой список
отклоняется той же причиной, что `edit_paths: []`.

Ключ допустим только в `.stepcast/config.yml`, и в `~/.stepcast/config.yml` он
отклоняется тем же правилом, что `project.check` и `project.edit_paths`. В
отличие от них, **документ пайплайна ключ не заводит вовсе**, и объявить его
верхним ключом `project` нельзя: состав вложенных репозиториев — это форма
состояния дерева, а она обязана быть одна на дерево. Позволь пайплайн
переопределять состав, два пайплайна одного проекта снимали бы в одном
каталоге якоря разного состава, несравнимые между собой, — и `stepcast diff`
двух прогонов одного и того же проекта начал бы отказывать сравнивать деревья
без всякой видимой причины. По той же причине значение не публикуется
подстановкой `${project.*}`: подстановка — это то, что документ куда-то
вставляет, а состав вложенных репозиториев никуда не вставляется, его читает
движок при снятии якоря.

Границы правок такого дерева объявляются обычным `project.edit_paths` —
второго механизма для того же не заводится. Запись `public-site/**`
покрывает содержимое вложенного репозитория: пути оттуда приходят в
`changed_only` уже с префиксом каталога, и `public-site/**` совпадает с ними
по тому же правилу, что `src/**` совпадает с `src/api.ts`. Если вложенный
репозиторий вдобавок отслеживается корнем как gitlink, сдвиг коммита внутри
него виден отдельным путём — самим каталогом без хвостового разделителя
(`public-site`), и для него нужна вторая запись: `public-site` рядом с
`public-site/**`. Оба пути настоящие, оба описывают разные события (правка
внутри репозитория и сдвиг ссылки на его коммит), и правило `matches`
превращает `public-site/**` в `^public-site/.*$`, с самим `public-site` не
совпадающее.

Объявленный каталог проверяется до первой работы: он должен существовать,
быть рабочим деревом **собственного** репозитория (а не подкаталогом
корневого) и — если корень его не игнорирует — иметь хотя бы один коммит.
Последнее не придирка: `git add -A` в корне встраивает вложенный репозиторий
ссылкой на коммит, а на репозитории без коммитов отказывает целиком («does
not have a commit checked out»), и якорь не снялся бы вовсе. Часть, которую
корень игнорирует, в его обход не попадает и коммита не требует.

Объявленный состав работает и в изолированном режиме `worktree` ([«Рабочее
дерево»](run-layout.md#рабочее-дерево)): каждый каталог материализуется
собственным рабочим деревом своего репозитория внутри дерева дорожки, и якорь
там остаётся составным, а не одиночным корневым. К изложенным двум проверкам
это добавляет ещё две, действующие только при работе в `worktree`: часть
обязана иметь коммит **независимо** от того, игнорирует ли её корень —
`git worktree add … HEAD` в репозитории без коммита невозможен даже для
игнорируемой части, — а корень не должен отслеживать обычные файлы по пути
части (это бывает, когда каталог стал репозиторием позже, чем попал в индекс
корня): такой путь выкладка корня заняла бы, и `worktree add` части отказал
бы диагностикой git посреди подготовки. Режим `copy` при объявленном составе
остаётся отклонённым: копия `.git` не содержит, и часть в ней была бы
каталогом без репозитория.

Состав читает не только якорь. Предусловие чистоты дерева (`stepcast
assert-clean`, `stepcast merge-lanes` — [«Проверка чистоты
дерева»](run-layout.md#проверка-чистоты-дерева-stepcast-assert-clean)) снимает
`git status` отдельно в корне и в каждом объявленном каталоге по той же
причине, по которой `git add -A` корня в них не заглядывает: свой `git
status` корня видит игнорируемый вложенный не полнее, чем свой `git add -A`.

### Проверка и практика вложенного репозитория

Элемент `nested_repos` допускает вторую, объектную форму — вложенный
репозиторий объявляет вместе со своим каталогом собственную команду проверки
и собственную практику спецификации, теми же ключами, что и корень:

```yaml
project:
  nested_repos:
    - public-site                 # строка — тот же элемент без объявлений
    - dir: backend
      check: "./gradlew check"
      tools: ["./gradlew"]      # вдобавок к project.tools, а не вместо
      spec:
        dir: docs/changes
        rules: docs/spec-rules.md
        tool: openspec
        check: make spec-check
```

`dir` обязателен, `check`, `tools` и `spec` — те же необязательные модели, что
у одноимённых ключей секции `project`: непустая строка у `check` и у
`spec.tool`/`spec.check`, относительный путь без сегмента `..` у `spec.dir` и
`spec.rules`, непустой список непустых строк у `tools`, отказ символам
шаблона глоба у `dir` (та же причина, что и у строковой формы).

`check` и `spec` вложенный репозиторий объявляет **вместо** корневых — они
описывают его целиком, и корневое значение здесь было бы просто неверным.
`tools` — единственное исключение: перечень **складывается** с корневым,
корневые впереди, повторы схлопнуты. Причина в том, что инструменты
складываются по смыслу: `git` и `npm`, объявленные корнем, верны в любом
дереве, а `./gradlew` верен только там, где лежит обёртка. Репозиторий,
которому нечего добавить, ключ не заводит и получает ровно корневой перечень.

Строковая форма элемента остаётся тем же каталогом без
объявлений — читателям состава (составной якорь, проверка чистоты, изоляция
дорожки) обе формы дают один и тот же перечень каталогов, приведение форм к
одному виду делается один раз при разрешении конфигурации. Повтор одного
каталога в составе — отказ разбора конфигурации, в любых формах: два
объявления одного каталога, из которых объектная форма несёт
`check`/`tools`/`spec`, несравнимы по приоритету между собой.

Как и сам состав, объявления вложенных репозиториев не публикуются
подстановкой `${project.*}`: значений тут по числу репозиториев, и выбрать
из них нечем, пока не выбран пункт очереди. Читает их команда движка,
разрешающая репозиторий, названный пунктом, в объявление — `stepcast project
repos` (см. `docs/backlog.md`), — а не подстановка документа пайплайна.

### Объявление, читаемое командой, живёт в конфигурации

`stepcast project repos` и `stepcast assert-clean` конфигурацию читают сами
(`resolveConfig`), а верхний ключ `project` документа пайплайна им не виден
— команда о документе не знает и знать не должна. Значит объявление,
которое обязано быть видно и команде, живёт в `.stepcast/config.yml`, а не
только в пайплайне: репозиторий, объявивший `check` (или практику
спецификации) лишь верхним ключом `project` документа, получит от этих
команд отказ, называющий `.stepcast/config.yml` — местом, где объявление
недостаёт.

Пайплайновый слой (верхний ключ `project` документа, перекрывающий
конфигурацию) этим не отменяется — он остаётся способом подставить
`${project.*}` в пайплайн, файлы работ и промпты, и репозиторий, у которого
несколько пайплайнов с разными командами проверки, продолжает объявлять её
на месте, а не только в конфигурации. Расхождение двух слоёв не молчит:
подстановка `${project.*}` раскрывается тем значением, что видит документ
(пайплайн поверх конфигурации, как и всегда), а команда движка — тем и
только тем, что лежит в `.stepcast/config.yml`.

## Практика спецификации

`project.spec` — объявление того, где репозиторий держит документы изменения,
по каким правилам они пишутся, каким инструментом заводятся и какой командой
проверяются. Четыре независимых ключа:

- `dir` — каталог документов изменения; документы изменения `<слаг>` лежат в
  `<dir>/<слаг>/`. Это единственное, что петля саморазвития
  (`self-improvement-loop.md`) знает о структуре: имена и состав документов
  внутри каталога изменения ей неизвестны — контекст собирается глобом.
- `rules` — путь к файлу правил репозитория: чем документы заводятся, из чего
  состоят, в каком порядке пишутся и чем проверяются. Файл получает контекстом
  работа, заводящая описание изменения; остальные работы петли о нём не знают.
- `tool` — имя инструмента спецификации. Значение открывает право
  `Bash(<tool> *)` — не команда с аргументами, а только имя, которым право
  называется; аргументы — дело правил репозитория. Репозиторий, чьи документы
  пишутся без инструмента, объявляет тем, чем документы всё же проверяются
  (`markdownlint`, `make`); право на команду, которую правила ни разу не
  называют, ничего не даёт и не ломает.
- `check` — команда, которой петля саморазвития гейтит документы изменения:
  исполняемая строка целиком, а не имя. Движок её не разбирает и передаёт
  оболочке как есть — из одного `tool` эту команду не собрать, потому что
  движку неоткуда взять грамматику подкоманды конкретной практики (`validate`,
  флаги вроде `--strict`), а знать её для каждой практики движок не обязан.
  Слаг проверяемого изменения доезжает до команды переменной окружения
  `SPEC_CHANGE`; объявляет её работа петли — `env` в `verify.yml`,
  `implement.yml`, `fix-review.yml` и `implement-express.yml` (облегчённая
  ветка гейтит документы наравне с полной), — и само объявление `check` читать эту
  переменную не обязано — она просто оказывается в окружении, когда команда
  исполняется. `tool` и `check` не заменяют друг друга: `tool` — имя для
  записи права агента, `check` — команда для исполнения движком вне агентского
  шага; репозиторий может объявить оба, только `tool` (документы не гейтятся
  петлёй автоматически) или только `check` (агенту не нужно самому звать
  инструмент).

Каждый ключ необязателен сам по себе — слои конфигурации сливаются по
листьям, и объявить можно часть группы. Как и у `project.check`, встроенных
умолчаний нет: путь или имя, подставленные за автора, указывали бы в чужом
репозитории на несуществующее.

`dir` и `rules` — относительные пути от корня репозитория: пустая строка,
строка из пробелов, абсолютный путь и путь с сегментом `..` отклоняются
разбором конфигурации. Причина в потребителе: `dir` раскрывается в границу
правок `<dir>/**`, и пустое значение превратило бы её в разрешение на всё
дерево, а `..` вывело бы границу за пределы проверяемого дерева. `tool` и
`check` подчиняются тому же требованию непустоты, что `project.check`.

Ключ `project.spec`, как и `project.check`, допустим только в
`.stepcast/config.yml` — запрет действует и на вложенные ключи группы:
`project.spec.dir` в `~/.stepcast/config.yml` отклоняется так же, как
`project.check` там же.

Документ пайплайна может объявить `project.spec` сам, верхним ключом
`project`, — тем же порядком слоёв, что и `check`, и по каждому ключу группы
отдельно: пайплайн может назвать один ключ, оставив остальные конфигурации,
без риска затереть то, что в пайплайне не названо.

Значения доступны подстановками `${project.spec.dir}`, `${project.spec.rules}`,
`${project.spec.tool}` и `${project.spec.check}` — там же, где `${project.check}`
(см. [«Когда что раскрывается»](pipeline-format.md#когда-что-раскрывается)).

Репозиторий без специального инструмента спецификации не объявляет `project.spec`
вовсе, если работы, которым он нужен, не подключены, — необъявленная группа не
ошибка сама по себе, отказ наступает только на обращении к ней подстановкой.
Репозиторий, переносящий к себе петлю саморазвития stepcast, объявляет все
четыре ключа: `dir` — каталог, куда `propose` кладёт новые документы, `rules`
— файл правил (пусть даже такой же простой, как «пиши обоснование и план в
один markdown-файл»), `tool` — имя инструмента, которым эти документы
проверяются, если он вообще есть, `check` — команда, которой петля их гейтит.
Репозиторий без инструмента объявляет `check` тем, чем документы всё же
проверяются на практике (`markdownlint`, `make spec-check`) — так же, как
`tool` в его отсутствие.

## Практика памяти

`project.knowledge` — объявление того, чем репозиторий читает своё знание, где
оно лежит и по каким правилам пишется. Устроено тем же порядком, что
`project.spec`, и по той же причине: движок узнаёт, что практика есть, и не
узнаёт, как она устроена. Раскладку знает источник.

| Ключ | |
|---|---|
| `provider` | `fs` — встроенный источник, `cmd` — свой, названный `command` |
| `command` | команда своего источника; глагол приходит ей первым аргументом |
| `dir` | каталог знания встроенного источника |
| `rules` | файл правил письма единицы знания |
| `index_max_tokens` | предел на записи единиц знания в оглавлении (дисциплина памяти), по умолчанию `2k` |
| `spec_index_max_tokens` | предел на записи каталогов практики спецификации в оглавлении, по умолчанию `2k` |
| `unit_max_tokens` | предел на тело одной единицы знания, по умолчанию `1k` |
| `stale_after` | срок наблюдения, после которого известное расхождение краснеет, по умолчанию `14d` |
| `timeout` | предел на один вызов источника, по умолчанию `10s` |

Срок отсчитывается не от коммита, а от момента, когда расхождение датировал
`check --record` (`docs/knowledge.md`, «Дрейф»): недатированное остаётся
жёлтым сколько угодно. Величина короче промежутка между заходами петли имеет
смысл, но не тот, что для более длинного срока, — она означает «краснеет со
второго наблюдения», потому что заметить расхождение чаще, чем идут заходы,
нечем.

Умолчаний нет у `provider`, `command`, `dir` и `rules` — по той же причине,
что у `project.check`: источник или каталог, подставленные за автора, читали
бы в чужом репозитории несуществующее. У пяти величин умолчания есть: они
описывают поведение движка, а не устройство дерева, и независимы друг от
друга — объявление одной не меняет действующее значение другой.

Ключ допустим только в `.stepcast/config.yml` и отклоняется в
`~/.stepcast/config.yml` — тем же правилом, что `project.check` и
`project.spec`. `dir` и `rules` проверяются той же моделью, что
`project.spec.dir`: непустой относительный путь без сегмента `..`. Документ
пайплайна может объявить секцию сам, верхним ключом `project`, полистовым
слиянием.

Согласованность объявления проверяется на **слитом** значении, а не в каждом
слое: `provider: cmd` без `command` и `provider: fs` без `dir` отклоняются
разбором, но провайдер, объявленный пайплайном, и команда, объявленная
конфигурацией, законны вместе.

Значения доступны подстановками `${project.knowledge.dir}`,
`${project.knowledge.rules}` и `${project.knowledge.provider}` — там же, где
`${project.spec.*}`. Величины подстановками не публикуются: их читает движок и
источник, а вставлять их некуда.

Репозиторий, практику памяти не объявивший, работает как прежде: записи
контекста `knowledge:` и предикат `knowledge_valid` в нём отклоняет
`stepcast lint`, а не молча отдаёт пустоту. Развернуть встроенную раскладку:
`stepcast init --knowledge fs`. Подробности — [docs/knowledge.md](knowledge.md).

## Возможности бэкендов

`sessions`, `structured_output` и подобные флаги — не настройка, а описание
того, что адаптер умеет. Если бэкенд не продолжает сессии, `session: shared`
деградирует в `per_step` с предупреждением на старте, а не падает.

`strict_permissions` — та же по духу возможность: умеет ли адаптер применять
`enforce: strict` (запрещать неназванное и отсекать настройки бэкенда вне
репозитория). В отличие от `sessions`, здесь **нет** тихой деградации:
выключенная возможность превращает объявленный где угодно `enforce: strict` в
ошибку конфигурации до старта прогона, а не в послабление режима. Деградация
с предупреждением здесь недопустима — она оставила бы пайплайн с границей,
которой на самом деле нет, ровно тем способом, из-за которого стал возможен
неучтённый коммит в прогоне `a50755` (см. `openspec/changes/job-permission-mode/design.md`).

`mcp` — устроена так же, как `strict_permissions`: умеет ли адаптер
транслировать объявленные MCP-серверы (`docs/pipeline-format.md`, раздел
`mcp`) в параметры запуска. Деградации тоже нет: шаг, для которого действует
объявление, на бэкенде без этого флага останавливает прогон до первого шага, а
`stepcast lint` отклоняет такое объявление ещё раньше, до старта. У встроенного
`claude` включена по умолчанию.

Выключенный флаг убирает из запуска **все** параметры про MCP, а не только
объявленные серверы: шаг с `enforce: strict` на таком бэкенде не получает и
отсечения чужих серверов (`--strict-mcp-config` у Claude Code). Такой шаг
серверов не объявляет, и ни линт, ни ворота прогона о нём не спросят, — а флаг
выключают как раз под CLI, которому про MCP знать нечего. Исключение из запрета
— пустое объявление `mcp: {}`: оно снимает унаследованные серверы, от бэкенда
не требует ничего и потому не отклоняется и прогон не останавливает.

`cache_read_weight` — с каким весом чтение кеша идёт в бюджет токенов. Чтение
дешевле обычного ввода примерно вдесятеро, отсюда умолчание `0.1`.

Бэкенд `codex` (плагин `stepcast/backends/codex`, `docs/plugins.md`) приносит
свою запись умолчаниями вклада: `strict_permissions: false` — жёсткого режима у
CLI нет, а `permissions.allow`/`deny` он выразить не умеет и отказывает на них
до запуска процесса; `permissions.mode` принимает только словарь песочницы CLI.
Если Codex аутентифицирован ключом, а не входом через ChatGPT, переменная
`OPENAI_API_KEY` попадает под встроенный `env_deny` (`*_KEY`) и до процесса не
дойдёт — разрешите её точечно записью `backends.codex.env` (она ложится поверх
отфильтрованного окружения) либо войдите через `codex login`.

`concurrency` — сколько вызовов этого бэкенда (агентских шагов и судей) может
идти одновременно, независимо от того, сколько работ пайплайн ведёт разом.
Место занимается перед запуском процесса и освобождается по завершении —
успехом, отказом, таймаутом или отменой. Предел общий на прогон и считается по
имени бэкенда: разные бэкенды друг другу мест не занимают. Он работает поверх
параллелизма графа (`pipeline.concurrency` / `limits.concurrency`, см.
[формат пайплайна](pipeline-format.md)) — тот определяет, сколько работ идёт
разом, этот — сколько из них одновременно достучится до данного бэкенда.

`permissions` задаёт базовую политику доступа агента; работа и шаг могут её
целиком переопределить — ближайшее объявление побеждает, списки не
складываются. Без неё агентский шаг упрётся в отказ на первой же записи файла:
неинтерактивный режим не спрашивает разрешений, он их не даёт.

`permissions.enforce` здесь — тот же базовый режим применения, что и у работы
со шагом (см. [формат пайплайна](pipeline-format.md#agent)). В отличие от
списков, режим не заменяется целиком блоком нижнего уровня: базовый режим
бэкенда действует и на шаг, объявивший свой `permissions`, но не назвавший в
нём `enforce`. Ослабить его можно, но только явно — `enforce: inherit` на
работе или шаге.

`env: DISABLE_AUTOUPDATER: "1"` стоит держать: агентские CLI обновляются сами и
могут обновиться посреди прогона, изменив поведение шагов. Версия бэкенда
пишется в `run.json`.

## Запреты

`env_deny` — глобы по именам переменных, применяются последними при сборке
окружения. На Windows сравнение регистронезависимое, потому что там таковы сами
переменные.

`context.deny` — глобы по путям, файлы не попадают в контекст, даже если
объявлены явно. Контур отдельный от `env_deny`: переменная утекает в
подпроцесс, а файл — в промпт и в `prompt.txt` на диске.

Ни один из запретов не защищает от самого агента: он работает с полным доступом
к файловой системе от имени пользователя. Ограничивать его — задача
`permissions` и песочницы бэкенда.

## Размер контекста

`context.inline_threshold` разделяет два способа передачи одной записи: меньше
порога — вставляется содержимым, больше — передаётся путём.

`context.max_tokens` ограничивает весь собранный контекст шага и проверяется до
запуска бэкенда. Переопределяется на уровне пайплайна, работы и шага ключом
`context_max_tokens`.

Это предел на контекст **одного шага**, а не на прогон, и с бюджетным
`budget.tokens` (см. [pipeline-format.md](pipeline-format.md#бюджет)) он не
связан: `budget.tokens` считает трафик по всем обращениям к API за область,
`context.max_tokens` — то, что stepcast кладёт в промпт один раз, до запуска.
Упор в один потолок не говорит ничего об упоре в другой.

Это защита от одного неудачного глоба. Без неё перерасход обнаруживается
бюджетом уже после того, как за отправку заплачено. При превышении система
сначала понижает записи режима `auto` с вставки на передачу путём, начиная с
самой крупной, и только если это не помогло — отказывает шагу до запуска
бэкенда. Записи с явным `mode: inline` и записи `text` не понижаются.

Оценка размера делается локально и приблизительно — точного токенизатора у
клиента нет, поэтому предел стоит задавать с запасом. Те же числа показывает
`stepcast context`.

`context.note_max_tokens` ограничивает выдержку о непройденной проверке
предыдущей итерации, которую движок сам добавляет в контекст следующего
захода (см. [pipeline-format.md](pipeline-format.md#until)). Умолчание
заведомо меньше `context.max_tokens` — выдержка одна запись среди прочих, а не
весь бюджет контекста. Если шаг получает выдержку, а объявленный для него
`context_max_tokens` меньше `context.note_max_tokens`, шаг отказывает до
запуска бэкенда: выдержка физически не может уложиться в такой предел. Шага без
выдержки — командного, первой итерации, работы без `until.check` — это
противоречие не касается: узкий `context_max_tokens` сам по себе не повод
отказывать.

## Потолки

`limits` — верхняя граница значений пайплайна. Пайплайн с `budget.tokens: 30M`
при `limits.tokens: 20M` отклоняется линтером, а не урезается молча: тихое
урезание превращает объявленный бюджет в ложь.

Потолки только ужесточаются: между слоями берётся строжайшее значение, и ни
проектный конфиг, ни глобальный, ни флаг поднять их не могут. Верхняя граница
для всех — встроенное значение; чтобы её сдвинуть, правится оно.

`limits.tokens` считает трафик прогона — сумму префиксов по всем обращениям к
API, — а не объём контекста. Агентская сессия на полторы сотни обращений даёт
десятки миллионов чтения кэша, держа в контексте втрое меньше окна модели, так
что с окном эта величина не соотносится.

`limits.attempts` и `limits.iterations` ограничивают `attempts.max` и
`until.max_iterations`. Поскольку бюджет пайплайна необязателен, это основной
предохранитель против неограниченных повторов.

`limits.cost` — потолок на объявленный `budget.cost` тем же правилом, что и
`limits.tokens`: `stepcast lint` отклоняет пайплайн, где `cost` любого уровня
превышает его. Умолчание — `$50`: прогон, стоивший $16, укладывается втрое с
запасом, а случайный лишний ноль в потолке ловится до запуска, а не по факту.
Движок эту величину не расходует и ничем, кроме `lint`, не пользуется — как и
остальными `limits.*`.

## Разрешение

```
$ stepcast config
defaults.agent        claude          .stepcast/config.yml
defaults.model        opus            --model (флаг)
defaults.workspace    { mode: cwd }   встроенное умолчание
runs.root             ~/.stepcast/runs   ~/.stepcast/config.yml
limits.tokens         20M             встроенное умолчание
env_deny              9 шаблонов      ~/.stepcast/config.yml (6) + .stepcast/config.yml (3)
```

Настройка, про которую непонятно, откуда она взялась, обходится дороже, чем её
отсутствие.

**Не всякая команда разрешает конфигурацию.** `stepcast data`, `stepcast down`
и `stepcast init` не читают ни одного её значения, поэтому исполняются при
любом состоянии `.stepcast/config.yml` и `~/.stepcast/config.yml` — нечитаемом
файле, неразбираемом YAML, несоответствии схеме, ключе, недопустимом в своём
слое. Все прочие команды читают конфигурацию (сами или через окружение,
которое им передаёт движок) и при той же ошибке отказывают кодом
`configError`, называя файл и место. Подставить вместо непрочитанного
объявления встроенные умолчания и исполнить команду дальше — решение отвергнутое:
`runs.root` из умолчания увёл бы `gc --older-than 30d` уборкой не в тот
каталог, а `status` — в отчёт «прогонов нет» при непустом каталоге прогонов;
отказ виден и чинится правкой файла, молчаливая подстановка не видна никогда.

**Настройки правят только глобальный файл.** Витрина охватывает все проекты
сразу, поэтому пишет в `~/.stepcast/config.yml`, а проектный слой в чтении
отключён (`src/ui/settings.ts`). Проектную настройку с экрана не поправить —
для неё остаётся файл `.stepcast/config.yml` в самом проекте. Экран пайплайнов,
однако, раскрывает каждый проект его собственными `defaults` и `backends`
(`src/ui/pipelines.ts`): показ пайплайна и правка настроек читают конфигурацию
по-разному, и проект со своим `defaults.model` виден на экране пайплайнов своим
значением, даже когда демон поднят из другого каталога.

**`defaults.model` применяется только к шагам, не объявившим модель ни сами, ни
через `defaults.model` документа пайплайна.** Область действия у него уже, чем
у имени: правка этого поля не трогает шаг, назвавший модель явно. Экран
настроек называет размер этой области в известных витрине пайплайнах —
сколько агентских шагов затронет правка, сколько объявляют модель сами и
потому не затронуты, и сколько пайплайнов не разобрано и потому не сосчитано
ни в одну из групп. Отдельным числом идут шаги, чью модель дал файл ближе
правимого — проектный `.stepcast/config.yml` или умолчание плагина: слой у них
тот же, `defaults.model`, но правка глобального файла им проиграет, и считать
их затронутыми значило бы обещать перемену, которой не будет. Различает их имя
файла, победившего в проекте, — то самое, что карточка шага показывает рядом со
слоем.

## Отложено

**Секреты.** Отдельной сущности с маскированием в логах и точечной выдачей пока
нет — она требует решений про доставку в подпроцессы агента и про очистку всех
артефактов прогона, а не только логов. До тех пор учётные данные передаются
обычным окружением, с оглядкой на то, что оно наследуется всем, что запустит
агент, и на то, что содержимое промптов лежит на диске.
