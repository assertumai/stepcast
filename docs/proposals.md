# Очередь предложений (`ui-proposals`)

Виджет, дашборд и плагин пользователя — обычные файлы проекта, и агент правит
их теми же инструментами, что и любой другой файл репозитория. Очередь
предложений — задвижка между агентом и кабинетом: правка сначала встаёт в
очередь, и в кабинет попадает только той, что человек принял на экране
«Предложения».

**Очередь — дверь, а не забор.** У stepcast нет песочницы: границы шагу
ставят объявленные права бэкенда (`permissions.allow`/`deny`,
`enforce: strict`), а не движок. Агент, которому шаг дал `Edit` в
`.stepcast/`, запишет файл мимо очереди, и ничего в устройстве очереди этого
не предотвращает. Очередь даёт правильный путь для того, кто ею пользуется, —
не обещание, что другого пути нет.

## Каталог и формат записи

Очередь лежит в `<проект>/.stepcast/proposals/`, по файлу `<id>.json` на
предложение. `<id>` собирается из момента постановки и цели, свёрнутой в
сегмент имени файла (`2026-09-12T17-15-26Z-widgets-clock`): момент первым —
сортировка имён и есть порядок очереди, цель вторым — чтобы каталог читался
`ls`. Штамп момента — до секунды, поэтому два предложения одной цели в
пределах одной секунды расходятся суффиксом (`…-widgets-clock-2`): имя,
уже занятое записью, не переписывается. Отсутствие каталога — обычное
состояние проекта, не отказ.

Запись несёт:

- `target` — путь цели относительно проекта;
- `action` — `create` либо `update`;
- `content` — содержимое файла **целиком**, не патч: предложение соревнуется
  с диском по отпечатку, а не сливается с ним построчно;
- `reason` — причина, необязательна;
- `origin` — прогон, работа и шаг, если предложение сделано внутри прогона;
- `baseFingerprint` — отпечаток цели (`mtimeMs`, `size`) на момент
  постановки, либо `null`, если файла ещё не было;
- `state` — `pending` | `accepted` | `rejected`, с моментом решения у обоих
  исходов.

Предел содержимого записи — 256 КиБ: виджет и манифест плагина на порядки
меньше, а мегабайт в очереди — не предложение, а промах. Запись пишется
атомарной заменой.

Решённая запись остаётся в каталоге со своим состоянием и моментом — не
стирается. Уборка решённых записей — дело человека, движок не стирает их ни
по сроку, ни по числу. Постановка, совпавшая с уже **отклонённой** записью по
цели и хешу содержимого, отказывает с названием этой записи: иначе пайплайн
миграции, запущенный второй раз, просился бы в очередь тем же, от чего
человек уже отказался.

## Цель — только кабинет проекта

Целью предложения вправе быть ровно один из трёх видов файла:

- `.stepcast/widgets/<id>.tsx` — непосредственно в каталоге виджетов;
- `.stepcast/dashboards/<id>.yml` — непосредственно в каталоге дашбордов;
- любой файл внутри `.stepcast/plugins/<id>/` — на любой глубине.

Каждый сегмент цели проверяется тем же предикатом безопасного сегмента, что
и сегменты адресов витрины, а итоговый путь приводится к реальному и обязан
остаться внутри каталога кабинета: шаг вверх по дереву и выход по
символической ссылке — отказ. Любая иная цель — файл конфигурации, файл вне
`.stepcast`, вложенный каталог виджетов, чужое расширение — отказ постановки
с названной причиной.

## `stepcast propose` — единственный писатель очереди

```
stepcast propose <цель> --from <файл> [--reason <текст>]
```

Содержимое берётся из файла, названного `--from`, либо со стандартного
ввода — оба источника пустыми есть отказ, очередь не меняется. Причина
`--reason` необязательна. Команда — единственный писатель очереди, тем же
правилом, каким `stepcast decide` — единственный писатель решения; файл
записи, созданный мимо неё, показывается негодной записью с именем файла, а
не разбирается молча.

Пайплайн зовёт команду командным шагом через `node "$STEPCAST_BIN"`; агент —
из своего `Bash`, если шаг это право ему дал, той же формой: голый `stepcast`
полагается на `PATH`, которого движок не дополняет, и у снимка движка в
каталоге прогона исполняемый бит не гарантирован. Право шага выписывается на
ту же форму — при `enforce: strict` вызов, не подходящий ни под одно право,
отклоняется, и пайплайн завершился бы успехом, не поставив ничего. Проект, чью очередь получает
предложение, определяется по прогону, внутри которого команда вызвана
(`STEPCAST_RUN_DIR` → манифест прогона → его настоящий корень), а не по
рабочей директории шага: в режимах `worktree` и `copy` эта директория —
временное дерево, которое снимет `stepcast gc`, и очередь, записанная в
него, исчезла бы вместе с ним. Вне прогона (вызов руками) проект берётся из
каталога запуска.

## Режим доставки — `project.proposals`

```yaml
# .stepcast/config.yml
project:
  proposals: queue   # умолчание; либо direct
```

`queue` (умолчание) ставит предложение в очередь; `direct` превращает ту же
команду в немедленную запись цели теми же проверками пути и той же атомарной
заменой, не создавая записи очереди. Ключ допустим только в
`.stepcast/config.yml`, тем же правилом, что `project.check` и
`project.tools`: режим доставки принадлежит репозиторию, а не машине
(`docs/config.md`). Ключ отклоняется и в документе пайплайна — пайплайн
ровно тот, кого настройка ограничивает, и объявить себе `direct` он не
вправе.

## Экран «Предложения»

`/proposals` показывает очередь всех проектов: цель, причину, прогон-источник
и построчный диф между содержимым цели на диске и предложенным текстом —
диф считает браузер (`src/core/textDiff.ts`), запросив `GET /api/proposals`
(записи вместе с текущим содержимым цели). Записи одного прогона
сгруппированы; открытые показаны развёрнуто, решённые — свёрнуто. Действующий
режим доставки виден на экране: «прямая запись» не тихое состояние.

`POST /api/proposals` решает одну названную запись — принять либо отклонить.
Принятие записывает цель атомарной заменой, создавая недостающие каталоги
внутри кабинета, переводит запись в `accepted` и будит наблюдателя демона:
дальше идёт обычная живая перезагрузка (событие `widgets`/`dashboards`,
переимпорт без перезапуска). Отклонение переводит запись в `rejected` и не
трогает ни цель, ни один другой файл проекта.

Принятие сверяет отпечаток цели с записанным при постановке: расхождение —
отказ с названной причиной, запись остаётся `pending`, файл не тронут. Тот
же приём, что у записи дашборда: между предложением и решением проходят
часы, за которые файл могли поправить руками. Отказ решения показывается на
месте своей записи, не гася остальные.

Каталог очереди — часть отпечатка наблюдателя, и поток `GET /api/events`
несёт её состав отдельным событием `proposals`, тем же правилом «только при
отличии от отправленного», каким идут `backlog`, `widgets` и `dashboards`:
предложение, записанное идущим прогоном, появляется в открытой витрине само.
Содержимое записей в поток не идёт — оно лежит в `GET /api/proposals`, который
экран и перечитывает по событию: событие здесь сигнал, а не источник данных
для дифа.

Режим доставки берётся из конфигурации проекта, и неразбираемый
`.stepcast/config.yml` одного проекта очередей остальных не гасит: причина
показывается негодной записью с именем файла, а режим такого проекта считается
умолчанием `queue` — `direct` объявляется той самой конфигурацией, которая не
прочиталась.

## Очередь не грязнит дерево

`stepcast init` вносит `.stepcast/proposals/` в `.gitignore` проекта. Для
проекта, заведённого раньше появления этой возможности, допишите ту же
строку сами:

```
.stepcast/proposals/
```

Без неё первое же предложение делает дерево грязным и останавливает петлю
саморазвития на собственной проверке чистоты (`stepcast assert-clean`).
