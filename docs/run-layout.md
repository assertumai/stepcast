# Прогон: состояние, рабочее дерево, возобновление

> Документ описывает формат целиком. Что из него уже работает, а что
> отклоняется с ошибкой, — в [состоянии реализации](status.md).

Состояние прогона — файлы: источник правды — директория, и всё, что можно
сравнить обычным `diff`, сравнивается обычным `diff`. Витрина (`stepcast up`)
читает эти файлы напрямую и обходится без индекса; SQLite остаётся возможным
ускорением, а не необходимостью.

Журнал прогона всегда лежит вне проекта, независимо от режима рабочей
директории.

## Расположение

```
~/.stepcast/
  projects.json                       # hash → путь репозитория
  runs/
    a3f19c2b7e40/                     # sha256(realpath корня проекта)[0:12]
      2026-08-16T14-03-22Z-3f9a1c/
      latest -> 2026-08-16T14-03-22Z-3f9a1c
```

Права `0700` на дерево, `0600` на файлы: в логи попадает содержимое исходников.

Ключ проекта считается от реального пути. Переименование каталога осиротит
прошлые прогоны — `stepcast runs --project <старый-путь>` находит их по
`projects.json`.

## Дерево прогона

```
2026-08-16T14-03-22Z-3f9a1c/
  run.json              # манифест: пайплайн, входы, git ref, окружение, итог
  pipeline.lock.yml     # пайплайн после раскрытия uses/defaults/inputs/params
  status.json           # текущее состояние, достаточно для возобновления
  events.ndjson         # поток событий для UI и постмортема
  usage.json            # агрегат расхода
  workspace/            # только при workspace.mode: copy
    implement/
  artifacts/
    plan.json           # структурированный выход работы
    implement.json
  jobs/
    implement/
      job.json
      resolved.json    # определение работы с раскрытыми отложенными подстановками
      steps/            # iter-N появляется только у работ с until
        01-write-code/
          step.json     # ключ, статус, попытки, usage, tree_id
          context.json  # что вошло в контекст, откуда, сколько токенов
          prompt.txt    # то, что stepcast отправил бэкенду
          stdout.log
          stderr.log
          output.json   # структурированный вывод бэкенда
          expect.json   # результат каждого предиката
          judge-1/      # промпт и ответ судьи, если он был
          diff.patch    # что шаг изменил в рабочем дереве
```

Каталоги шагов нумеруются для порядка (`01-write-code`), адресуются по
идентификатору (`write-code`). Везде, где нужна полная адресация, — `<job>/<step>`.

`prompt.txt` — то, что отправил stepcast. Бэкенд добавляет к этому свой системный
промпт, `CLAUDE.md`, автопамять, хуки, MCP и плагины; их состав пишется в
`step.json` из события инициализации. Изменение `CLAUDE.md` шаги не
инвалидирует — это осознанный размен в пользу работы с проектным контекстом.

## Рабочее дерево

| Режим | Где работают шаги | Изоляция | Возврат результата |
|---|---|---|---|
| `cwd` | каталог запуска | нет | не нужен |
| `worktree` | git worktree на работу | между работами | `stepcast apply` |
| `copy` | `<run_dir>/workspace/<job>/` | между работами | `stepcast apply` |

`worktree` ответвляется от текущего `HEAD` и не содержит незакоммиченных
изменений. `copy` копирует дерево как есть, минуя игнорируемые пути, и работает
вне git.

Worktree и копии сохраняются после прогона — по ним разбирают, что произошло.
`stepcast gc` удаляет их вместе с прогоном.

## Витрина

```bash
stepcast up [--foreground]
stepcast down
```

`stepcast up` поднимает фоновый локальный сервер и печатает URL, не занимая
терминал. Витрина наблюдает за корнем прогонов целиком — за всеми проектами
сразу, — подхватывает прогоны, запущенные уже после её старта, и обновляет
страницу по мере того, как движок пишет журнал. По каждой работе видно, что она
получила на вход (выходы предшественников) и что опубликовала на выход, а файлы
журнала раскрываются прямо в интерфейсе.

Повторный `stepcast up` при уже поднятой витрине печатает её адрес, процесс и
время старта — отдельной команды о состоянии демона поэтому нет; `stepcast
status` был и остаётся командой о состоянии *прогона*. Порт берётся из
`ui.port`, сервер слушает только `127.0.0.1` и работает исключительно на
чтение.

### Якорь дерева

После каждого шага движок фиксирует состояние рабочего дерева как git-объект
(`write-tree` без коммита в историю) и пишет `tree_id` в `step.json`.

Это одна запись, закрывающая четыре вопроса: возобновление восстанавливает
дерево по `tree_id`, а не полагается на то, что каталог уцелел; `changed_only`
получает определённую базу сравнения; `diff.patch` становится производным от
пары деревьев; `stepcast diff` сравнивает состояния, а не только промпты.

В режиме `copy` вне git фиксируется хеш-манифест дерева — то же самое, дешевле
и без git.

## Ключ шага и инвалидация

```
step_key = sha256(
    нормализованное определение шага из pipeline.lock.yml
  + развёрнутый текст промпта и контекста
  + backend id + model + версия бэкенда
  + выходы работ выше по графу
  + отпечаток входов
)
```

Ключ отвечает на один вопрос: остаётся ли прошлый успех шага действительным.

**Отпечаток входов по умолчанию — всё рабочее дерево** (`tree_id` на начало
шага). Объявлять ничего не нужно. Инвалидация грубая, но режим отказа
правильный: перевыполняется лишнее, а результат никогда не бывает тихо
устаревшим.

**Наблюдённые входы уточняют автоматически.** Агентские бэкенды в потоковом
выводе отдают вызовы инструментов, откуда виден фактически прочитанный набор
файлов. Движок сохраняет его в `step.json` и на следующем прогоне сужает
инвалидацию до него. От пользователя не требуется ничего.

**Объявленные `inputs` работы — опция** для тех, кому нужна предсказуемость:
самый узкий вариант под ответственность автора, пропущенный файл означает
пропущенную инвалидацию.

`stepcast status` и `stepcast resume --dry-run` показывают, **почему** шаг признан
невалидным:

```
implement/write-code   invalid  — дерево изменилось (src/auth/token.ts)
review/review-diff     invalid  — пересчитан выход implement
plan/read-change       valid    — переиспользуется из 3f9a1c
```

Непрозрачный кеш — главная претензия к Bazel и Nix, повторять её незачем.

## Кеш промптов

Кешированием управляет бэкенд, не stepcast. Claude Code кеширует по совпадению
начала запроса, а начало — это его собственный системный промпт, куда входят
рабочий каталог, ветка и снимок git-статуса. Отсюда три факта, которые стоит
знать заранее:

- разные рабочие каталоги не делят кеш вообще — в том числе worktree одного
  репозитория, поэтому `workspace.mode: worktree` исключает попадания между
  работами;
- последовательные сессии делят префикс, только если снимок git-статуса на
  старте совпал, а пайплайн по своей природе меняет файлы;
- внутри одной сессии кеш работает штатно, и на подписке живёт час.

Практический вывод один: единственный надёжный способ получить кеш — **общая
сессия внутри работы**, которая включена по умолчанию. Порядок склейки контекста
на кеш не влияет и нужен для детерминизма.

## status.json

Новая сессия без прежнего контекста должна продолжить работу, имея этот файл,
`pipeline.lock.yml` и каталог прогона.

```json
{
  "run_id": "3f9a1c",
  "pipeline": "implement-change",
  "lock_hash": "8e21…",
  "workspace": { "mode": "worktree", "base": "83c2513" },
  "inputs": { "change": "add-oauth-e2e-tests" },
  "status": "failed",
  "jobs": {
    "plan": { "status": "success", "output": "artifacts/plan.json" },
    "implement": { "status": "success", "iterations": 2, "tree_id": "4c1b…" },
    "typecheck": {
      "status": "failed",
      "failed_step": "tsc",
      "attempt": 3,
      "expect_failed": [{ "predicate": "exit_code", "expected": 0, "actual": 2 }],
      "excerpt": "src/auth/token.ts(41,7): error TS2345…",
      "log": "jobs/typecheck/steps/01-tsc/stdout.log"
    },
    "archive": { "status": "skipped", "reason": "on: success, зависимость упала" }
  },
  "budget": { "tokens_used": 412000, "tokens_limit": 2000000 },
  "resume": { "command": "stepcast resume 3f9a1c --from typecheck" }
}
```

## Возобновление

```bash
stepcast resume <run-id> [--from <job|job/step>] [--set k=v]
```

Создаётся новый прогон со ссылкой `resumed_from`. Шаги с совпавшими ключами и
статусом `success` берутся из старого прогона. `--set` меняет ключ и
обесценивает всё ниже по графу.

**Восстановление точечное.** Возвращаются только пути, произведённые
переиспользованными шагами, — по `tree_id` последнего из них. Полный сброс
дерева стёр бы файлы, созданные пользователем после прогона, в том числе ту
правку, ради которой он и возобновляет. Путь, произведённый шагом и
изменившийся после завершения прогона, признаётся невалидным и
переисполняется — см. известное ограничение в `docs/status.md` о том, что это
различение временное, а не по авторству, и о слепом пятне параллельного
редактирования в режиме `cwd`.

**Основание инвалидации — изменившиеся пути**, а не сравнение отпечатков:
отпечаток снимался, когда дерево было в другом состоянии. Вопрос ставится
иначе — что пользователь тронул с момента окончания прогона и задевает ли это
входы шага.

**Гранулярность.** При `session: shared` шаг нельзя переисполнить в одиночку —
его результат зависит от диалога, — поэтому единицей повтора становится работа.
При `session: per_step` возобновление идёт с точностью до шага.

В контекст первого переисполняемого шага подкладывается `previous_failure.md`:
выдержка из `status.json` прошлого прогона и `expect.json` упавшего шага.
Протокол попыток не переносится.

## Дифф прогонов

```bash
stepcast diff <run-a> <run-b>
```

Сравнивает по ключам: какие шаги идентичны, какие изменились, какие появились.
Для изменившихся — `diff` по `prompt.txt`, `context.json`, `expect.json` и
деревьям по `tree_id`. Основной сценарий: фича не взлетела со второго захода,
надо увидеть, чем второй прогон отличался от первого.

## Расход

В `step.json`, записью на каждую попытку:

```json
"usage": {
  "backend": "claude", "model": "opus",
  "tokens_in": 18422, "tokens_out": 3110,
  "cache_read": 120340, "cache_write": 8200,
  "wallclock_ms": 41250,
  "rate_limits": {
    "five_hour": { "used_pct": 37, "resets_at": 1786000000 },
    "seven_day": { "used_pct": 61, "resets_at": 1786400000 }
  },
  "reported_cost_usd": 0.42
}
```

Бэкенды сообщают разный набор полей: у Codex нет `cache_write`, окна лимитов
есть только у Claude Code и только на подписке. Отсутствующее поле остаётся
пустым и помечается как «не сообщается» — бюджет не досчитывает молча.

`reported_cost_usd` записывается справочно и в бюджете не участвует.

`usage.json` — агрегат снизу вверх. `stepcast usage <run>` показывает
распределение по номеру попытки: какие шаги стабильно не проходят с первого
раза.

## Логи и события

`stdout.log` и `stderr.log` — построчный текст без управляющих
последовательностей: запуск через pipe, эмуляции терминала нет. Логи грепаются,
диффаются и показываются в UI без эмулятора терминала.

`events.ndjson` — по строке на событие: `job.started`, `step.attempt`,
`step.stalled`, `expect.failed`, `env.denied`, `budget.warning`,
`budget.waiting`. UI читает хвост файла.

```bash
stepcast logs <run-id> [<job>/<step>] [--follow]
```

`--follow` подключается к идущему прогону. Девяностоминутный прогон без живого
вывода — это про «непонятно, работает ли оно вообще».

## Отмена

`Ctrl-C` или `SIGTERM`: движок шлёт `SIGTERM` дереву процессов текущих шагов,
ждёт 30 секунд, затем `SIGKILL`. Шаги получают статус `canceled`, артефакты
дописываются, рабочие деревья сохраняются, `status.json` содержит команду
возобновления. Работы с `needs: all` выполняются и в этом случае.

## Уборка

```bash
stepcast gc [--older-than 30d]
```

Удаляет прогоны целиком, включая рабочие деревья и `artifacts/`, сохраняя
`run.json`, `status.json` и `usage.json`. Артефакты, которые должны пережить
уборку, забираются из прогона заранее — `stepcast apply` или обычным `cp`.

## CLI

```
stepcast init                                    создать stepcast.yml и пример работы
stepcast lint [pipeline] [--budget] [--resolve]
stepcast run <pipeline> [--input k=v] [--dry-run]
stepcast status [--run <id>]
stepcast resume <run-id> [--from <job|job/step>] [--set k=v]
stepcast apply <run-id> [--job <job>]            наложить результат на текущее дерево
stepcast diff <run-a> <run-b>
stepcast context [--job <job>] [--step <step>]
stepcast logs <run-id> [<job>/<step>] [--follow]
stepcast usage <run-id>
stepcast runs [--project <path>]
stepcast config
stepcast gc [--older-than 30d]
stepcast up [--foreground]                       поднять витрину наблюдения
stepcast down                                    остановить витрину
```

Коды возврата: `0` — успех, `1` — работа завершилась отказом, `2` — ошибка
конфигурации или линта, `3` — остановлено по бюджету, `130` — отменено.
