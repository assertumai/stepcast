# Прогон: состояние, рабочее дерево, возобновление

> Документ описывает формат целиком. Что из него уже работает, а что
> отклоняется с ошибкой, — в [состоянии реализации](status.md).

Состояние прогона — файлы: источник правды — директория, и всё, что можно
сравнить обычным `diff`, сравнивается обычным `diff`. Витрина (`stepcast up`)
читает эти файлы напрямую и обходится без индекса; SQLite остаётся возможным
ускорением, а не необходимостью.

Журнал прогона всегда лежит вне проекта, независимо от режима рабочей
директории.

## Расположение

```
~/.stepcast/
  projects.json                       # hash → путь репозитория
  runs/
    a3f19c2b7e40/                     # sha256(realpath корня проекта)[0:12]
      2026-08-16T14-03-22Z-3f9a1c/
      latest -> 2026-08-16T14-03-22Z-3f9a1c
```

Права `0700` на дерево, `0600` на файлы: в логи попадает содержимое исходников.

Ключ проекта считается от реального пути. Переименование каталога осиротит
прошлые прогоны — `stepcast runs --project <старый-путь>` находит их по
`projects.json`.

## Дерево прогона

```
2026-08-16T14-03-22Z-3f9a1c/
  run.json              # манифест: пайплайн, входы, git ref, окружение, итог
  pipeline.lock.yml     # пайплайн после раскрытия uses/defaults/inputs/params
  status.json           # текущее состояние, достаточно для возобновления
  events.ndjson         # поток событий для UI и постмортема
  usage.json            # агрегат расхода
  workspace/            # только при workspace.mode: copy
    implement/
  artifacts/
    plan.json           # структурированный выход работы
    implement.json
  jobs/
    implement/
      job.json
      resolved.json    # определение работы с раскрытыми отложенными подстановками
      scratch/          # черновики шагов — общий на работу, вне рабочего дерева
      steps/            # iter-N появляется только у работ с until
        01-write-code/
          step.json     # ключ, статус, попытки, usage, tree_id
          context.json  # что вошло в контекст, откуда, сколько токенов
          prompt.txt    # то, что stepcast отправил бэкенду
          stdout.log
          stderr.log
          output.json   # структурированный вывод бэкенда
          expect.json   # результат каждого предиката
          judge-1/      # вызов судьи: промпт, поток, вердикт, расход
          judge-2/      # нумерация сквозная в пределах шага — растёт через попытки и предикаты
          diff.patch    # что шаг изменил в рабочем дереве
```

Каталоги шагов нумеруются для порядка (`01-write-code`), адресуются по
идентификатору (`write-code`). Везде, где нужна полная адресация, — `<job>/<step>`.

`prompt.txt` — то, что отправил stepcast. Бэкенд добавляет к этому свой системный
промпт, `CLAUDE.md`, автопамять, хуки, MCP и плагины; их состав пишется в
`step.json` из события инициализации. Изменение `CLAUDE.md` шаги не
инвалидирует — это осознанный размен в пользу работы с проектным контекстом.

Каталог `scratch/` — общее место для черновиков работы, доступное шагу
переменной `STEPCAST_SCRATCH` и подстановкой `${run.scratch}`. Он живёт до
`stepcast gc` вместе с остальным прогоном, но пустым не сохраняется: движок
снимает его сам по завершении работы, если ни один шаг ничего в него не
записал. Агентскому шагу каталог объявляется доступным только под
`permissions.enforce: strict` (см. [формат
пайплайна](pipeline-format.md#инжектируемые)).

Каталог `judge-<n>` заводится вызовом предиката `judge` (см. [формат
пайплайна](pipeline-format.md#judge)). Содержит промпт, поток вывода бэкенда,
вердикт (`verdict.json`, с номером попытки и проверявшимся утверждением) и
расход этого конкретного вызова; последний сливается с расходом попытки в
`step.json`. Если в попытке уже не прошёл жёсткий предикат, вычисляемый без
обращения к агенту, судья не вызывается вовсе — каталога для этой попытки
не появляется, а в `expect.json` предикат помечен невычисленным.

## Рабочее дерево

| Режим | Где работают шаги | Изоляция | Возврат результата |
|---|---|---|---|
| `cwd` | каталог запуска | нет | не нужен |
| `worktree` | git worktree на работу | между работами | `stepcast apply` |
| `copy` | `<run_dir>/workspace/<job>/` | между работами | `stepcast apply` |

`worktree` ответвляется от текущего `HEAD` и не содержит незакоммиченных
изменений. `copy` копирует дерево как есть, минуя игнорируемые пути, и работает
вне git.

Worktree и копии сохраняются после прогона — по ним разбирают, что произошло.
`stepcast gc` удаляет их вместе с прогоном.

### `apply --lane`

`stepcast apply <run-id> --lane <имя>` накладывает изолированные работы,
объявившие эту `lane`, — **одним** диффом: от `tree_before` первого шага
дорожки до последнего непустого `tree_id` последней, в порядке графа. Одна
дорожка — один `git apply --3way`, а не по вызову на работу, как без `--lane`
или с `--job`.

`--lane` и `--job` взаимоисключимы. Дорожка без единой изолированной работы,
несущей якорь, — «накладывать нечего» и код `0`, как и в общем случае.
Конфликт ведёт себя как обычно: дерево не трогается, конфликтующие пути
перечисляются.

## Витрина

```bash
stepcast up [--foreground]
stepcast down
```

`stepcast up` поднимает фоновый локальный сервер и печатает URL, не занимая
терминал. Витрина наблюдает за корнем прогонов целиком — за всеми проектами
сразу, — подхватывает прогоны, запущенные уже после её старта, и обновляет
страницу по мере того, как движок пишет журнал. По каждой работе видно, что она
получила на вход (выходы предшественников) и что опубликовала на выход, а файлы
журнала раскрываются прямо в интерфейсе.

Повторный `stepcast up` при уже поднятой витрине печатает её адрес, процесс и
время старта — отдельной команды о состоянии демона поэтому нет; `stepcast
status` был и остаётся командой о состоянии *прогона*. Порт берётся из
`ui.port`, сервер слушает только `127.0.0.1` и работает исключительно на
чтение.

### Якорь дерева

После каждого шага движок фиксирует состояние рабочего дерева как git-объект
(`write-tree` без коммита в историю) и пишет `tree_id` в `step.json`.

Это одна запись, закрывающая четыре вопроса: возобновление восстанавливает
дерево по `tree_id`, а не полагается на то, что каталог уцелел; `changed_only`
получает определённую базу сравнения; `diff.patch` становится производным от
пары деревьев; `stepcast diff` сравнивает состояния, а не только промпты.

В режиме `copy` вне git фиксируется хеш-манифест дерева — то же самое, дешевле
и без git.

## Ключ шага и инвалидация

```
step_key = sha256(
    нормализованное определение шага и работы, взятое ДО раскрытия отложенных
    подстановок (то же состояние, что уходит в pipeline.lock.yml)
  + текст промпта и контекста в том же нераскрытом виде
  + backend id + model + версия бэкенда
  + выходы работ выше по графу — отдельной составляющей
  + отпечаток входов
)
```

Ключ отвечает на один вопрос: остаётся ли прошлый успех шага действительным.

**Определение берётся до раскрытия отложенных подстановок.** Пространства
`jobs`, `run` и `env` раскрываются только по ходу исполнения работы — `run.dir`
и `run.workspace` вообще не существуют раньше, чем подготовлена её рабочая
директория, — и потому величины пространства `run` (`run.id`, `run.dir`,
`run.workspace`) не входят в ключ ни прямо, ни через раскрытый текст: раскрытая
работа с ними была бы разной в каждом прогоне, и ни один шаг такой работы
никогда бы не переиспользовался. Раскрытое определение (`jobs/<job>/resolved.json`)
пишется в журнал рядом — вопрос «по какому пути шаг на самом деле пошёл в
файловую систему» отвечается им, а не догадкой по логам.

**Выходы работ выше по графу входят отдельной составляющей**, а не через
раскрытый текст промпта или контекста: `${jobs.<id>.output.*}` в нераскрытом
виде — это одна и та же строка независимо от того, что вернула работа
выше по графу, и без отдельной составляющей смена её выхода ключ бы не
меняла. Составляющая берёт сами значения `output` завершившихся работ, не их
текстовое представление после подстановки, и приводится к одному порядку —
по идентификатору работы: исполнитель копит выходы в порядке завершения работ,
разбор прогона — в порядке своего обхода, и ключ не должен зависеть от того,
кто из них его считает.

Значения `env` работы входят в ключ как часть её определения — как и всё
остальное, взятое до раскрытия отложенных подстановок.

**Отпечаток входов по умолчанию — всё рабочее дерево** (`tree_id` на начало
шага). Объявлять ничего не нужно. Инвалидация грубая, но режим отказа
правильный: перевыполняется лишнее, а результат никогда не бывает тихо
устаревшим.

**Наблюдённые входы уточняют автоматически.** Агентские бэкенды в потоковом
выводе отдают вызовы инструментов, откуда виден фактически прочитанный набор
файлов. Движок сохраняет его в `step.json` и на следующем прогоне сужает
инвалидацию до него. От пользователя не требуется ничего.

**Объявленные `inputs` работы — опция** для тех, кому нужна предсказуемость:
самый узкий вариант под ответственность автора, пропущенный файл означает
пропущенную инвалидацию.

`stepcast status` и `stepcast resume --dry-run` показывают, **почему** шаг признан
невалидным:

```
implement/write-code   invalid  — дерево изменилось (src/auth/token.ts)
review/review-diff     invalid  — пересчитан выход implement
plan/read-change       valid    — переиспользуется из 3f9a1c
```

Непрозрачный кеш — главная претензия к Bazel и Nix, повторять её незачем.

## Кеш промптов

Кешированием управляет бэкенд, не stepcast. Claude Code кеширует по совпадению
начала запроса, а начало — это его собственный системный промпт, куда входят
рабочий каталог, ветка и снимок git-статуса. Отсюда три факта, которые стоит
знать заранее:

- разные рабочие каталоги не делят кеш вообще — в том числе worktree одного
  репозитория, поэтому `workspace.mode: worktree` исключает попадания между
  работами;
- последовательные сессии делят префикс, только если снимок git-статуса на
  старте совпал, а пайплайн по своей природе меняет файлы;
- внутри одной сессии кеш работает штатно, и на подписке живёт час.

Практический вывод один: единственный надёжный способ получить кеш — **общая
сессия внутри работы**, которая включена по умолчанию. Порядок склейки контекста
на кеш не влияет и нужен для детерминизма.

## status.json

Новая сессия без прежнего контекста должна продолжить работу, имея этот файл,
`pipeline.lock.yml` и каталог прогона.

```json
{
  "run_id": "3f9a1c",
  "pipeline": "implement-change",
  "lock_hash": "8e21…",
  "workspace": { "mode": "worktree", "base": "83c2513" },
  "inputs": { "change": "add-oauth-e2e-tests" },
  "status": "failed",
  "jobs": {
    "plan": { "status": "success", "output": "artifacts/plan.json" },
    "implement": { "status": "success", "iterations": 2, "tree_id": "4c1b…" },
    "typecheck": {
      "status": "failed",
      "failed_step": "tsc",
      "attempt": 3,
      "expect_failed": [{ "predicate": "exit_code", "expected": 0, "actual": 2 }],
      "excerpt": "src/auth/token.ts(41,7): error TS2345…",
      "log": "jobs/typecheck/steps/01-tsc/stdout.log"
    },
    "archive": { "status": "skipped", "reason": "on: success, зависимость упала" }
  },
  "budget": {
    "tokens_used": 412000, "tokens_limit": 2000000,
    "cost_used_usd": 6.42, "cost_limit_usd": 20,
    "cost_unreported_attempts": 1
  },
  "resume": { "command": "stepcast resume 3f9a1c --from typecheck" }
}
```

`budget.cost_used_usd` и `cost_limit_usd` — денежный аналог `tokens_used` и
`tokens_limit`, в долларах (не в микродолларах — файл читают посторонние
инструменты, и единица должна совпадать с той, в которой цену объявляют).
`cost_unreported_attempts` — число попыток, чей известный на сейчас расход не
содержит цены; поле появляется, только если такие попытки есть. Все три поля
необязательны: `status.json` прежней формы, где их нет, читается без изменений.

Прогон, ушедший в ожидание сброса окна лимита (`on_exceed: wait`), дописывает
`status.json` до начала сна: статус остаётся `running`, а поле `wake_at`
называет момент пробуждения. Поле снимается после продолжения — так спящий
прогон отличим от зависшего снаружи, не заглядывая в журнал событий.

## Возобновление

```bash
stepcast resume <run-id> [--from <job|job/step>] [--set k=v]
```

Создаётся новый прогон со ссылкой `resumed_from`. Шаги с совпавшими ключами и
статусом `success` берутся из старого прогона. `--set` меняет ключ и
обесценивает всё ниже по графу.

**Восстановление точечное.** Возвращаются только пути, произведённые
переиспользованными шагами, — по `tree_id` последнего из них. Полный сброс
дерева стёр бы файлы, созданные пользователем после прогона, в том числе ту
правку, ради которой он и возобновляет. Путь, произведённый шагом и
изменившийся после завершения прогона, признаётся невалидным и
переисполняется — см. известное ограничение в `docs/status.md` о том, что это
различение временное, а не по авторству, и о слепом пятне параллельного
редактирования в режиме `cwd`.

**Основание инвалидации — изменившиеся пути**, а не сравнение отпечатков:
отпечаток снимался, когда дерево было в другом состоянии. Вопрос ставится
иначе — что пользователь тронул с момента окончания прогона и задевает ли это
входы шага.

**Изменения относятся к своему источнику.** Множество изменившихся путей
разбирается на произведённое шагами исходного прогона (по парам его якорей
`tree_before`/`tree_id`) и на всё остальное. При проверке входов шага из
множества изменений вычитаются пути, произведённые этим шагом и всеми шагами,
исполнявшимися после него, — они ещё не были его входом, когда отпечаток
снимался. Пути, произведённые шагами до него, не вычитаются: их правка
по-прежнему может обесценить шаг. Отдельно от этого сохраняется правило
«результат шага тронут после завершения прогона» — оно проверяет пересечение
изменений с путями самого шага и вычитанием не отменяется.

**Файлы определения не входят в множество изменений.** `Pipeline.file` и
`Job.source` уже учтены ключом шага: правка файла работы даёт несовпадение
ключа ровно у её шагов и не задевает шаги остальных работ. Оставлять эти
файлы в множестве изменившихся путей значило бы гасить весь пайплайн любой
правкой любой работы — то самое возобновление, ради которого команда и
существует.

**`--from` защищает верх графа.** Работы выше названной точки переиспользуются
целиком, если это физически возможно — есть запись шага, статус `success`,
якорь доступен, ключ не изменился, — независимо от того, что случилось с
деревом. Проверки изменений дерева и каскад пересчёта выше точки не
применяются: `--from` — решение запускающего, и он берёт верх графа на себя.
Чужие правки, которые тем самым проигнорированы, не замалчиваются: `--dry-run`
и `stepcast status --explain` перечисляют их отдельной строкой.

**Гранулярность.** При `session: shared` шаг нельзя переисполнить в одиночку —
его результат зависит от диалога, — поэтому единицей повтора становится работа.
При `session: per_step` возобновление идёт с точностью до шага.

**Выходы переиспользованных работ публикуются как обычно.** Работа, все шаги
которой переиспользованы, проходит обычный путь исполнения работы и публикует
свой выход в `artifacts/<job>.json` нового прогона — так же, как исполненная.
Структурированный выход отдельного переиспользованного шага переносится из
исходного прогона в новый: это единственный источник `output.from` при
частичном переиспользовании работы, когда выход работы целиком не перенесён.
Работа, объявившая выход, который восстановить нельзя — артефакт источника
удалён уборкой или не читается, — переисполняется целиком, а не
переиспользуется без выхода: иначе `${jobs.<id>.output.*}` у нижележащих работ
разрешался бы в ничто.

В контекст первого переисполняемого шага подкладывается `previous_failure.md`:
выдержка из `status.json` прошлого прогона и `expect.json` упавшего шага.
Протокол попыток не переносится.

## Дифф прогонов

```bash
stepcast diff <run-a> <run-b>
```

Сравнивает по ключам: какие шаги идентичны, какие изменились, какие появились.
Для изменившихся — `diff` по `prompt.txt`, `context.json`, `expect.json` и
деревьям по `tree_id`. Основной сценарий: фича не взлетела со второго захода,
надо увидеть, чем второй прогон отличался от первого.

## Расход

В `step.json`, записью на каждую попытку:

```json
"usage": {
  "backend": "claude", "model": "opus",
  "tokens_in": 18422, "tokens_out": 3110,
  "cache_read": 120340, "cache_write": 8200,
  "wallclock_ms": 41250,
  "rate_limits": {
    "five_hour": { "used_pct": 37, "resets_at": 1786000000 },
    "seven_day": { "used_pct": 61, "resets_at": 1786400000 }
  },
  "reported_cost_usd": 0.42
}
```

Бэкенды сообщают разный набор полей: у Codex нет `cache_write`, окна лимитов
есть только у Claude Code и только на подписке. Отсутствующее поле остаётся
пустым и помечается как «не сообщается» — бюджет не досчитывает молча.

`reported_cost_usd` попытки — источник для `budget.cost` (см.
[pipeline-format.md](pipeline-format.md#бюджет)): расход шага и вызванного им
судьи складывается, а попытка, не сообщившая цены, в денежные счётчики не
входит вовсе — вместо нуля.

`usage.json` — агрегат снизу вверх, по прогону, работе, шагу и, внутри шага, по
номеру попытки:

```json
{
  "run_id": "2026-08-25T16-00-00Z-demo",
  "total": {
    "tokens_in": 412300, "tokens_out": 88200, "cache_read": 900000, "cache_write": 40000,
    "billable_tokens": 612300, "wallclock_ms": 940000, "cost_usd": 6.42
  },
  "unreported": [],
  "jobs": {
    "implement": {
      "billable_tokens": 612300, "wallclock_ms": 940000, "cost_usd": 6.42,
      "steps": {
        "write-code": {
          "billable_tokens": 612300, "wallclock_ms": 940000, "cost_usd": 6.42,
          "peak_prefix_tokens": 58000,
          "attempts": [
            { "attempt": 1, "backend": "claude", "model": "sonnet",
              "billable_tokens": 180100, "wallclock_ms": 402000, "peak_prefix_tokens": 15000 },
            { "attempt": 2, "backend": "claude", "model": "opus",
              "billable_tokens": 432200, "wallclock_ms": 538000, "cost_usd": 6.42, "peak_prefix_tokens": 58000 }
          ]
        }
      }
    }
  }
}
```

`cost_usd` — в долларах, необязателен на каждом уровне (`total`, работа, шаг,
попытка): отсутствует там, где ни одна вошедшая попытка не сообщила цены,
вместо того чтобы печатать `0`. Несообщённая цена хотя бы одной завершившейся
попытки пополняет `unreported` значением `"reported_cost_usd"` — тем же
правилом, что и у токенных измерений.

`peak_prefix_tokens` — наибольший объём одного обращения к API (`tokens_in +
cache_read + cache_write` того сообщения потока, где сумма была наибольшей),
на уровнях попытки и шага; у работы и `total` этого поля нет вовсе — «самое
большое обращение за работу» не говорит, в каком шаге оно случилось. Пик шага
— **максимум по попыткам, а не сумма**: в примере выше пик шага (58000) равен
пику второй попытки, не сумме 15000 + 58000. То же правило действует при
слиянии расхода шага с расходом вызванного им судьи. Поле необязательно и
отсутствует, если бэкенд не сообщает расход по отдельным сообщениям потока —
как и денежное поле, оно читается как отсутствующее значение, а не ноль, и
записи, снятые до появления этого поля, его не несут вовсе (см. «Известные
ограничения» в docs/status.md).

Запись шага несёт перечень попыток, а не голый счётчик: у каждой — номер,
бэкенд, модель, billable-токены и время. Переисполнение одной и той же
попытки (например, после ожидания сброса окна лимита) схлопывается в одну
запись с суммарным расходом — две строки с одним номером читались бы как
ошибка. Число попыток шага выводится из длины перечня.

`stepcast usage <run>` показывает ту же разбивку — работа → шаг → попытка —
поверх `status.json` (переживает `gc` и работает на идущем прогоне) и
`usage.json` (даёт billable-токены и список несообщённого):

```
$ stepcast usage a50755
прогон a50755  self-improve  success
расход: 612.3k токенов, 15m40s, $6.42
                бэкенд  модель  вход  выход  чт. кэша  зап. кэша  время   списано  пик  цена
  implement                                                       15m40s  612.3k        $6.42
    write-code                                                    15m40s  612.3k   58k  $6.42
      #1        claude  sonnet  100   50     900k      40k        6m42s   180.1k   15k  —
      #2        claude  opus    200   80     900k      40k        8m58s   432.2k   58k  $6.4200
```

Столбец справа от «списано» — тот самый пик: наибольшее одно обращение попытки
или, у шага, максимум по его попыткам. Он на порядок меньше трафика (58k
против 612.3k у прогона) — это ожидаемо: трафик суммирует все обращения к
сессии, а пик — наибольшее из них (см. docs/pipeline-format.md, раздел
«Бюджет»). У работы и у итоговой строки прогона столбец пустой — как и у
сырых токенов, эта величина не агрегируется выше шага.

Пик строки попытки берётся из `usage.json` — там он, как и «списано» в той же
строке, уже с учётом вызванного шагом судьи, — и только при отсутствующей
сводке подставляется из `status.json`, где лежит пик одного агента. Иначе шаг
показывал бы пик больше, чем любая его попытка, всякий раз, когда самое
крупное обращение сделал судья.

Несообщённое бэкендом измерение печатается прочерком, а не нулём — денежный
столбец и столбец пика подчиняются тому же правилу; если хотя бы одна попытка
не сообщила цены, отдельная строка называет их число и напоминает, что
денежная сумма неполна. Сводки, записанные до появления пика, читаются как
обычно, а сам пик на них показывается прочерком — досчитать его неоткуда.
Если `usage.json` ещё не записан (прогон идёт) или не проходит схему (сводка
устаревшей формы), отчёт всё равно строится по `status.json`, а внизу
поясняется, что именно недоступно.

Если хотя бы одна работа прогона несёт `lane`, `stepcast usage` печатает
строку итога дорожки над строками её работ — по тем же измерениям, что и у
работы, с той же пометкой прочерком вместо нуля для несообщённой величины.
Работы без `lane` печатаются вне группировки, на своих местах. Прогон без
объявленных дорожек выглядит ровно как прежде.

## Логи и события

`stdout.log` и `stderr.log` — построчный текст без управляющих
последовательностей: запуск через pipe, эмуляции терминала нет. Логи грепаются,
диффаются и показываются в UI без эмулятора терминала.

`events.ndjson` — по строке на событие: `job.started`, `step.attempt`,
`step.stalled`, `expect.failed`, `env.denied`, `budget.warning`,
`budget.waiting`, `budget.resumed`, `context.note_truncated` (выдержка о
прошлой итерации усечена по своему пределу — запись несёт работу, шаг,
исходный и итоговый размер выдержки в токенах), `budget.cost_unreported`
(первая завершившаяся попытка без цены при объявленном `budget.cost` — работа,
шаг и номер попытки; не чаще одного раза за прогон), `backend.refused`
(неустранимый отказ бэкенда — работа, шаг, номер попытки, класс отказа
(`rate_limit` или `unauthenticated`), код состояния, если бэкенд его назвал,
сообщение бэкенда и разобранный момент сброса, если он разобран — виден без
чтения `stdout.log` шага). UI читает хвост файла.

```bash
stepcast logs <run-id> [<job>/<step>] [--follow]
```

`--follow` подключается к идущему прогону. Девяностоминутный прогон без живого
вывода — это про «непонятно, работает ли оно вообще».

## Ход прогона (`run`)

`stepcast run` печатает ход по мере его хода — строку на событие журнала, не
дожидаясь `run.finished`. Лента строится из того же потока, что уходит в
`events.ndjson`, — второго источника правды о происходящем нет.

Печатается закрытый перечень: начало и исход прогона, начало, исход и отказ
работы, начало и исход шага с номером попытки, начало и исход итерации цикла,
остановка по тишине, провал предиката, предупреждение и превышение бюджета,
сон и пробуждение по бюджету, неустранимый отказ бэкенда. Остальное — записи
для разбора постфактум (`context.denied`, `context.downgraded`,
`context.note_truncated`, `env.denied`, `backend.unparsed`,
`backend.degraded`, `bookkeeping.failed`, `step.reused`, `tree.restored`,
`workspace.inherited`, `run_dir.carried`, `budget.cost_unreported`,
`resume.note_undelivered`) — остаются в `events.ndjson` и в ленту не попадают.

Формат строки:

```
+0:00:00  прогон: начат — self-improve
+0:00:01  propose-a: работа начата
+0:00:01  propose-a/plan: шаг начат (попытка 1)
+0:04:31  propose-a/plan: шаг success (попытка 1) — 42.1k токенов, $0.31, 271s
+0:41:02  прогон: success (код 0)
```

Слева — время от старта прогона (`ч:мм:сс`, считается по меткам времени самих
событий, не по `elapsedMs()` снимка расхода — тот вычитает сон и после
`budget.waiting` пошёл бы назад). Затем адрес: `работа` или `работа/шаг` —
строки прогона в целом называют «прогон», а не работу. Под `concurrency`
больше единицы события двух дорожек перемешаны, и без адреса строка не
сообщает, о чём она. Ни отступов, ни вложенности, ни цвета, ни возврата
каретки, ни какой-либо иной управляющей последовательности — вывод остаётся
тем же построчным текстом и в терминале, и при перенаправлении в файл
(`stepcast run … | tee run.log`).

Деталь события — чужой текст: `expect.failed` предиката `cmd` несёт весь вывод
команды, часто раскрашенный, отказ бэкенда — сообщение произвольной длины. В
ленту он идёт свёрнутым в одну строку: управляющие последовательности сняты,
переводы строк заменены пробелами, хвост длиннее двух сотен знаков обрезан
многоточием. Целиком деталь остаётся в `events.ndjson` и в файлах шага.

Величины бюджета печатаются в единицах своего измерения — токены токенами,
деньги деньгами, время длительностью, окно лимитов процентами: у события
`budget.warning`/`budget.exceeded` для этого есть поле `dimension`, и без него
`3500000/3000000` читалось бы как токены при денежном потолке.

Строка исхода шага дополнена накопленным расходом прогона на этот момент —
токены, цена и время теми же величинами, что уходят в блок `budget`
`status.json`. Несообщённая цена — прочерк, а не ноль, тем же правилом, что и
`stepcast usage`.

Идентификатор прогона и путь к каталогу журнала печатаются первыми строками, по
событию `run.started`, — то, чем прогон адресуется в `logs`, `status`,
`usage` и `resume`, нужно знать, пока прогон ещё идёт, а не когда он
закончился.

`--quiet` подавляет ленту целиком и возвращает нынешнее молчание: печатаются
только итог прогона, предупреждение о неприменённом денежном потолке, список
изолированных рабочих деревьев и диагностика отказов — то, что не ход, а
результат. Код возврата от ключа не зависит. `stepcast resume` ленту не
печатает: наблюдение в движке общее для обеих команд, но `resume` его пока не
подключает — у него своя преамбула с планом переиспользования.

## Отмена

`Ctrl-C` или `SIGTERM`: движок шлёт `SIGTERM` дереву процессов текущих шагов,
ждёт 30 секунд, затем `SIGKILL`. Шаги получают статус `canceled`, артефакты
дописываются, рабочие деревья сохраняются, `status.json` содержит команду
возобновления. Работы с `needs: all` выполняются и в этом случае.

## Уборка

```bash
stepcast gc [--older-than 30d]
```

Удаляет прогоны целиком, включая рабочие деревья и `artifacts/`, сохраняя
`run.json`, `status.json` и `usage.json`. Артефакты, которые должны пережить
уборку, забираются из прогона заранее — `stepcast apply` или обычным `cp`.

## CLI

```
stepcast init                                    создать stepcast.yml и пример работы
stepcast lint [pipeline] [--budget] [--resolve]
stepcast run <pipeline> [--input k=v] [--dry-run] [--quiet]
stepcast status [--run <id>]
stepcast resume <run-id> [--from <job|job/step>] [--set k=v]
stepcast apply <run-id> [--job <job> | --lane <lane>]   наложить результат на текущее дерево
stepcast diff <run-a> <run-b>
stepcast context [--job <job>] [--step <step>]
stepcast logs <run-id> [<job>/<step>] [--follow]
stepcast usage <run-id>
stepcast runs [--project <path>]
stepcast config
stepcast gc [--older-than 30d]
stepcast up [--foreground]                       поднять витрину наблюдения
stepcast down                                    остановить витрину
```

Коды возврата: `0` — успех, `1` — работа завершилась отказом, `2` — ошибка
конфигурации или линта, `3` — остановлено по бюджету (включая упор в окно
лимита подписки бэкенда, когда ожидание не состоялось), `4` — отказ
аутентификации бэкенда (окружение неисполнимо, а не пайплайн упал), `130` —
отменено.
