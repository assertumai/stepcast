# Прогон: состояние, рабочее дерево, возобновление

Состояние прогона — файлы: источник правды — директория, и всё, что можно
сравнить обычным `diff`, сравнивается обычным `diff`. Витрина (`stepcast up`)
читает эти файлы напрямую и обходится без индекса; SQLite остаётся возможным
ускорением, а не необходимостью.

Журнал прогона всегда лежит вне проекта, независимо от режима рабочей
директории.

## Расположение

```
~/.stepcast/
  projects.json                       # hash → путь репозитория
  runs/
    a3f19c2b7e40/                     # sha256(realpath корня проекта)[0:12]
      2026-08-16T14-03-22Z-3f9a1c/
      latest -> 2026-08-16T14-03-22Z-3f9a1c
```

Права `0700` на дерево, `0600` на файлы: в логи попадает содержимое исходников.

Ключ проекта считается от реального пути. Переименование каталога осиротит
прошлые прогоны — `stepcast runs --project <старый-путь>` находит их по
`projects.json`.

## Дерево прогона

```
2026-08-16T14-03-22Z-3f9a1c/
  run.json              # манифест: пайплайн, входы, git ref, окружение, плагины, итог
  pipeline.lock.yml     # пайплайн после раскрытия uses/defaults/inputs/params
  status.json           # текущее состояние, достаточно для возобновления
  events.ndjson         # поток событий для UI и постмортема
  usage.json            # агрегат расхода
  workspace/            # только при workspace.mode: copy
    implement/
  artifacts/
    plan.json           # структурированный выход работы
    implement.json
  jobs/
    implement/
      job.json
      resolved.json    # определение работы с раскрытыми отложенными подстановками
      data.json         # данные, опубликованные работой (stepcast data)
      scratch/          # черновики шагов — общий на работу, вне рабочего дерева
      steps/            # iter-N появляется только у работ с until
        01-write-code/
          step.json     # ключ, статус, попытки, usage, tree_id
          context.json  # что вошло в контекст, откуда, сколько токенов
          prompt.txt    # то, что stepcast отправил бэкенду
          stdout.log
          stderr.log
          output.json   # структурированный вывод бэкенда
          expect.json   # результат каждого предиката
          judge-1/      # вызов судьи: промпт, поток, вердикт, расход
          judge-2/      # нумерация сквозная в пределах шага — растёт через попытки и предикаты
          diff.patch    # что шаг изменил в рабочем дереве
```

Каталоги шагов нумеруются для порядка (`01-write-code`), адресуются по
идентификатору (`write-code`). Везде, где нужна полная адресация, — `<job>/<step>`.

`prompt.txt` — то, что отправил stepcast. Бэкенд добавляет к этому свой системный
промпт, `CLAUDE.md`, автопамять, хуки, MCP и плагины; их состав пишется в
`step.json` из события инициализации. Изменение `CLAUDE.md` шаги не
инвалидирует — это осознанный размен в пользу работы с проектным контекстом.

`data.json` — плоская карта строк, которую работа публикует по ходу
исполнения командой `stepcast data` (см.
[pipeline-format.md](pipeline-format.md#данные-работы-jobsiddata)). Пишет её
подпроцесс шага, атомарно, поверх уже записанного; движок после каждого шага
складывает содержимое в запись работы в `status.json` — сам подпроцесс
состояние прогона не трогает. Файл живёт на всю работу: все её шаги и все
итерации цикла `until` пишут в один и тот же. При возобновлении он переносится
из исходного прогона для работ, чьи шаги переиспользуются.

Каталог `scratch/` — общее место для черновиков работы, доступное шагу
переменной `STEPCAST_SCRATCH` и подстановкой `${run.scratch}`. Он живёт до
`stepcast gc` вместе с остальным прогоном, но пустым не сохраняется: движок
снимает его сам по завершении работы, если ни один шаг ничего в него не
записал. Агентскому шагу каталог объявляется доступным только под
`permissions.enforce: strict` (см. [формат
пайплайна](pipeline-format.md#инжектируемые)).

Каталог `judge-<n>` заводится вызовом предиката `judge` (см. [формат
пайплайна](pipeline-format.md#judge)). Содержит промпт, поток вывода бэкенда,
вердикт (`verdict.json`, с номером попытки и проверявшимся утверждением) и
расход этого конкретного вызова; последний сливается с расходом попытки в
`step.json`. Если в попытке уже не прошёл жёсткий предикат, вычисляемый без
обращения к агенту, судья не вызывается вовсе — каталога для этой попытки
не появляется, а в `expect.json` предикат помечен невычисленным.

`prompt.txt` содержит ту часть запроса, которую сформировал stepcast. Claude Code
добавляет к ней свой системный промпт, `CLAUDE.md`, автопамять, хуки и
плагины; их состав пишется в `step.json` из события инициализации, но
изменение `CLAUDE.md` шаги не инвалидирует.

## Рабочее дерево

| Режим | Где работают шаги | Изоляция | Возврат результата |
|---|---|---|---|
| `cwd` | каталог запуска | нет | не нужен |
| `worktree` | git worktree на работу | между работами | `stepcast apply` |
| `copy` | `<run_dir>/workspace/<job>/` | между работами | `stepcast apply` |

`worktree` ответвляется от текущего `HEAD` и не содержит незакоммиченных
изменений. `copy` копирует дерево как есть, минуя игнорируемые пути, и работает
вне git.

При объявленных `project.nested_repos` (см. [«Вложенные
репозитории»](config.md#вложенные-репозитории)) режим `worktree` заводит
собственное рабочее дерево и на каждый объявленный каталог: после корневого
`git worktree add` часть выкладывается тем же способом из `HEAD` **своего**
репозитория — не гитлинка корня и не рабочего дерева части в проекте, — и
остаётся настоящим рабочим деревом git со своей базой объектов. Незакоммиченные
изменения частей в дерево дорожки не попадают — то же правило, что у корня.
Заведение атомарно: отказ на любой части снимает всё, что подготовка успела
завести. Режим `copy` при объявленном составе остаётся отклонённым — копия
`.git` не содержит, и часть в ней была бы каталогом без репозитория.

Worktree и копии сохраняются после прогона — по ним разбирают, что произошло.
`stepcast gc` удаляет их вместе с прогоном, снимая и учётные записи заведённых
рабочих деревьев — корневых и частей — в их собственных репозиториях. Каталог,
снесённый мимо движка (`rm -rf`), оставляет такую запись висеть в чужом
репозитории до `git worktree prune`, — движок его не зовёт нигде (см.
«Составной якорь: несколько репозиториев» ниже), и убрать осиротевшую запись
после ручного сноса каталога остаётся человеку.

**Разбор `.gitignore` вне git неполон.** Поддержаны комментарии, маски,
каталоги и привязка к корню; отрицания (`!`) и вложенные `.gitignore` — нет.
Неподдержанное правило пропускается, а не толкуется наугад. В репозитории
исключениями занимается сам git, и ограничение не проявляется.

### `apply --lane`

`stepcast apply <run-id> --lane <имя>` накладывает изолированные работы,
объявившие эту `lane`, — **одним** диффом: от `tree_before` первого шага
дорожки до последнего непустого `tree_id` последней, в порядке графа. Одна
дорожка — один `git apply --3way`, а не по вызову на работу, как без `--lane`
или с `--job`.

`--lane` и `--job` взаимоисключимы. Дорожка без единой изолированной работы,
несущей якорь, — «накладывать нечего» и код `0`, как и в общем случае.
Конфликт ведёт себя как обычно: дерево не трогается, конфликтующие пути
перечисляются.

### Сведение дорожек: `stepcast merge-lanes`

```bash
stepcast merge-lanes [<run-id>] --lanes a,b --check "<команда>" [--file backlog.md]
```

Обходит названные дорожки прогона в объявленном порядке, накладывая каждую на
дерево запуска через `apply --lane` (внутрипроцессно, тем же кодом), проверяя
объединённое дерево и коммитя зелёную дорожку, прежде чем перейти к
следующей. Прогон берётся из позиционного аргумента, при его отсутствии — из
переменной `STEPCAST_RUN_ID`; «последний прогон» по умолчанию не
подставляется — команда коммитит и стирает дерево. Ключи `--lanes` и
`--check` обязательны.

**Годность дорожки** решается по исходам всех работ, несущих её метку `lane`
в `status.json`, — не по имени одной из них. Дорожка годна, когда каждая
работа завершилась `success`; дорожка, у которой все работы `skipped`, —
незаполненный слот, пропускается без отказа и без правки очереди; любой
другой случай (в том числе смесь `success` и `skipped`) — негодность, дорожка
пропускается с причиной, называющей помешавшие работы и их статусы, а обход
продолжается. Дорожка, у которой в `status.json` нет ни одной работы, —
отказ с кодом `2`, перечисляющий дорожки, известные прогону.

**Чистое дерево — предусловие команды.** Она отказывается начинать, если
дерево запуска не репозиторий git либо содержит незакоммиченные или
неотслеживаемые изменения: откат красной проверки стирает и то, и другое.
Отказ случается до первого наложения. При объявленных `project.nested_repos`
проверка охватывает и каждый вложенный репозиторий — свой `git status` корня
внутрь них не заглядывает (см. «Проверка чистоты дерева» ниже), — а отказ
называет все репозитории, оказавшиеся нечистыми. Файл очереди может лежать в
любом из них: репозиторий, в чьём дереве он лежит, коммитится в конце (см.
«Порядок коммитов» ниже), а не обязан быть корнем.

**Затронутые репозитории и их проверки известны до первой правки дерева.**
Затронутым дорожкой считается репозиторий, чьи снятые состояния до и после
неё различаются, — не тот, что назвал пункт очереди в поле `repos`: дифф
говорит о правках точнее объявления. Команда проверки корня приезжает ключом
`--check`; команда вложенного репозитория читается из его объявления в
`project.nested_repos` — корневая вложенному не подставляется. Затронутый
репозиторий без объявленной команды — отказ с кодом `2` до первого наложения,
называющий репозиторий и дорожку. Спрашивается команда только с дорожек,
которые до наложения дойдут: негодная дорожка и дорожка, которой пункт очереди
не достался, не сведутся ни при какой конфигурации, и обход остальных из-за
них не роняется — они получают свой прежний исход.

**Наложение и проверка идут по репозиториям, коммит — после всех зелёных.**
Вклад дорожки накладывается в каждый затронутый репозиторий его собственным
`git apply --3way`, затем в каждом из них, в детерминированном порядке (корень,
затем части в каноническом порядке состава), исполняется его команда проверки
— и только когда зелены все, дорожка коммитится: по коммиту в каждом
затронутом репозитории, с одним и тем же сообщением `<слаг>: <заголовок>`, где
слаг и заголовок берутся из файла `item-<дорожка>.json` каталога прогона.

**Порядок коммитов — снизу вверх по гитлинкам.** Гитлинк асимметричен: коммит
внутри части двигает запись о ней в надпроекте, и надпроект остаётся с
незакоммиченной правкой, пока не закоммитит её сам. Поэтому вложенный
репозиторий коммитится раньше корня, который его ведёт, а корень стоит в
перечне коммитов всегда — даже когда дорожка его дифом не задела: подхватить
сдвинутые записи некому больше, а грязный корень остановил бы головное
предусловие следующего захода. Репозиторий, в чьём рабочем дереве лежит файл
очереди, коммитится последним из тех, кого корень гитлинком не ведёт: в нём
лежит отметка `done`, проставленная после зелёных проверок и до первого
коммита, и он коммитится даже тогда, когда дорожка его дифом не задела. Ведёт
корень сам репозиторий очереди — корень идёт и после него: одним коммитом на
репозиторий «отметка в последнем коммите» и «корень чист» вместе не выполнимы,
и чистота важнее порядка в истории (сообщение у обоих всё равно одно). Коммит
на пустом индексе (файл очереди этим репозиторием не отслеживается — лежит вне
дерева либо игнорируется, а дифом дорожка его не задела) пропускается без
отказа, и такой репозиторий не называется среди репозиториев сведённой
дорожки. Однорепозиторное сведение (состав не объявлен) не меняется ничем:
затронутый репозиторий там один, он же держит очередь, и коммит по-прежнему
ровно один.

**Красная проверка любого затронутого репозитория** откатывает **все**
затронутые к коммитам, записанным в них до наложения этой дорожки (`git reset
--hard` на этот коммит и `git clean -fd` без `-x` в каждом — игнорируемые пути
не трогаются) и уступает место следующей дорожке перечня: обход не
прекращается. Файл очереди отслеживается git, и откат снял бы вместе с диффом
дорожки исходы, проставленные более ранним дорожкам этого же обхода и ещё не
попавшие ни в один коммит, — команда проставляет их заново сразу после
отката. Сразу после отката команда подтверждает чистоту дерева запуска и
объявленных вложенных репозиториев тем же предусловием, каким начинала заход:
адресный откат отвечает только за затронутые репозитории, а команда проверки
— произвольная строка проекта и могла тронуть то, чего он не покрывает.
Подтверждено — обход идёт дальше на дерево, к которому вернул откат, то самое,
на которое легла бы следующая дорожка, не будь упавшей в перечне вовсе; не
подтверждено — обход прекращается, называя дорожку и неподтверждённый откат;
причина самой откачённой дорожки называет его тоже — иначе запись о грязном
дереве пропала бы, кончись перечень на ней. Артефакты красной проверки, лежащие в игнорируемых путях (например,
собранное), откат не трогает — следующая дорожка обхода застаёт их и обязана
пересобрать своё сама, если её проверка читает собранное.

**Конфликт наложения** на любом репозитории останавливает обход, не трогая ни
один из затронутых, — это уже свойство `applyRun`: отличить «дерево
восстановлено» от «восстановление тоже отказало» сведению нечем, и
продолжать по дереву неизвестного содержания оно не станет. Тем же образом
отказывает и патч, двигающий запись gitlink объявленного каталога: её меняет
коммит внутри части, которого дорожка не делает, а движок такого состояния не
порождает сам. Конфликт наложения и неподтверждённый откат красной проверки —
единственные основания прекратить обход; причина недостигнутой дорожки
называет, какое из них сработало. **Дорожка без вклада в дерево** (`applyRun`
вернул «накладывать нечего») не считается сведённой: обход продолжается, но
коммита не возникает.

**Обрыв между коммитами читается по состоянию репозиториев, до первой правки
дерева.** Если `HEAD` какого-то репозитория несёт сообщение `<слаг>: …`
пункта, чей исход в очереди не проставлен, — прошлое сведение оборвалось между
коммитами репозиториев, и команда отказывает с кодом `2`, называя репозитории
с этим коммитом и те, кому он полагался (затронутые дорожкой и держащий
очередь), но не лёг. Самолечения здесь нет: команда, делающая
необратимое, обязана остановиться и назвать состояние, а не дописывать
недостающий коммит сама.

Любая другая дорожка перечня, которой достался пункт очереди, получает
`failed` с причиной, различающей случай. Файл пункта читается до наложения:
дорожка, которой пункт не достался, пропускается, не тронув дерево (иначе её
дифф остался бы наложенным и незакоммиченным), и по той же причине там же
отказывает файл пункта без слага.

**Коды возврата**: `0` — обход дошёл до конца перечня и ни одна дорожка не
была откачена (в том числе когда все дорожки пропущены); `1` — обход
прекращён (конфликтом наложения либо неподтверждённым откатом) либо хотя бы
одна дорожка откачена красной проверкой — её работы зелены, и сведение
единственное место, где отказ вообще виден; `2` — ошибка ключей, неизвестная
дорожка, грязное дерево, обрыв между коммитами прошлого сведения, недостающая
команда проверки затронутого репозитория или ненайденный прогон.

**Сведение зависит от собранного `dist/`.** `$STEPCAST_BIN` — точка входа
собранного движка; `merge-lanes` и `backlog settle`, как и остальные команды
петли, недоступны до `npm run build`. То же ограничение, что и у остальной
бухгалтерии очереди: пункт, зависший в `in_progress` дольше порога давности,
снова свободен.

**Отказ на коммите оставляет пункт `done` без коммита.** Правка очереди идёт
до `git commit` этой же дорожки — так улучшение и его бухгалтерия остаются
одним событием, которое `git revert` снимает целиком, — но если сам `git
commit` откажет (например, чужой `pre-commit`-хук), команда не откатывает уже
проставленный `done`: наложенное и правка очереди остаются на дереве,
разбирает человек. Откат после зелёной проверки уничтожил бы результат
работы дорожки.

**Бухгалтерия очереди зависит от собранного `dist/`.** `finish` идёт через
собранный движок, а не через отдельный скрипт без сборки — сломанная сборка
могла бы помешать проставить исход именно тогда, когда он нужнее всего.
Смягчение то же, что было в очереди с самого начала: пункт, оставшийся
`in_progress` дольше порога давности, снова свободен, и следующий заход
берёт его сам — отказ бухгалтерии становится задержкой, а не потерей пункта.

### Проверка чистоты дерева: `stepcast assert-clean`

```bash
stepcast assert-clean [--allow <пути через запятую>]
```

Отвечает, чисты ли рабочее дерево и объявленные в `project.nested_repos`
вложенные репозитории, — не изменяя ни один из них: ни коммита, ни удаления,
ни отката. Проверяется корень рабочего дерева git, а не буквальный каталог
запуска: и проектный конфиг, и пути состава объявлены от корня, поэтому из
подкаталога команда отвечает ровно то же, что из корня. Существует потому, что состав вложенных репозиториев сознательно
не публикуется подстановкой `${project.*}` (форма состояния дерева, а не
значение документа, — см. [«Вложенные
репозитории»](config.md#вложенные-репозитории)), и файлу работы прочитать его
неоткуда: `.stepcast/jobs/slots.yml` зовёт эту команду через `$STEPCAST_BIN`
вместо собственного `git status`, ровно тем же приёмом, каким соседний шаг
той же работы зовёт `backlog pick`.

Обходит корень дерева и каждый объявленный вложенный репозиторий отдельным
`git status` — тем же устройством, что и предусловие `merge-lanes` выше, — и
называет в отказе **все** репозитории, оказавшиеся нечистыми, а не первый
попавшийся: корень словом «корень», вложенный своим объявленным каталогом.
Объявленный каталог, которого нет либо который не является рабочим деревом
**собственного** репозитория (а не подкаталогом корневого), — отдельный
отказ, называющий этот каталог: пропустить непроверяемую часть молча команда
не вправе, тишина здесь неотличима от чистоты.

`--allow` называет пути, чьи правки чистоту не нарушают, — тем же смыслом,
что `--file` у `merge-lanes`. Пути пишутся абсолютными либо относительно
каталога запуска, а достаётся каждый ровно одному дереву — по самому длинному
совпавшему объявленному префиксу — и сверяется с `status` именно этого
репозитория: названный файл корня прощается корню, а одноимённый файл внутри
объявленного вложенного репозитория остаётся нарушением чистоты. Умолчания у
ключа нет: в отличие от `merge-lanes`, здесь нет своей отметки прогона,
которую можно было бы прощать по умолчанию, — не названный явно путь чистоту
нарушает.

**Коды возврата**: `0` — все проверенные репозитории чисты; `2` — любой из
них нечист, любой объявленный каталог не проверить, либо ошибка ключей.
Отдельного кода у грязного дерева нет: вызывающий — шаг пайплайна с
предикатом `exit_code: 0`, различать причины отказа ему незачем, а сообщение
их называет и так.

## Витрина

```bash
stepcast up [--foreground]
stepcast down
```

`stepcast up` поднимает фоновый локальный сервер и печатает URL, не занимая
терминал. Витрина наблюдает за корнем прогонов целиком — за всеми проектами
сразу, — подхватывает прогоны, запущенные уже после её старта, и обновляет
страницу по мере того, как движок пишет журнал. По каждой работе видно, что она
получила на вход (выходы предшественников) и что опубликовала на выход, а файлы
журнала раскрываются прямо в интерфейсе.

Повторный `stepcast up` при уже поднятой витрине печатает её адрес, процесс и
время старта — отдельной команды о состоянии демона поэтому нет; `stepcast
status` был и остаётся командой о состоянии *прогона*. Порт берётся из
`ui.port`, сервер слушает только `127.0.0.1` и работает исключительно на
чтение.

**Витрина не защищена ничем, кроме петлевого интерфейса.** `stepcast up`
слушает только `127.0.0.1` и работает исключительно на чтение, но
аутентификации у неё нет: любая страница, открытая в том же браузере, может
обратиться к `localhost` на её порт. Инструмент рассчитан на локальную
однопользовательскую машину; токен доступа и проверка `Origin` не вводились
сознательно и остаются отдельным изменением, если понадобятся.

**Витрина видит прогоны всех проектов пользователя.** Это её задача, но
следствие стоит знать: в дашборде окажутся пути и имена проектов, за которыми
пользователь мог не собираться наблюдать вместе.

**Витрина не показывает уровни объявления.** Разрез по уровням в витрине строится из `context.json` по полю `origin`, поэтому склеенная запись видна там целиком на своём уровне-источнике, а `declared_in` не отображается: уровень, объявивший файл повторно, выглядит в витрине пустым. В `stepcast context` и в самом `context.json` уровни объявления названы.

**Прогон, чей манифест не читается, находит пайплайн только по имени.**
Первый экран связывает прогон с пайплайном по файлу, которым тот был запущен
(`RunOverview.pipelineFile` против `PipelineView.file`, склейка — в
`src/ui/grouping.ts`). Файл берётся из манифеста прогона; если манифест
повреждён, остаётся имя из состояния, а оно неоднозначно: два файла одного
проекта с одинаковым `name` дадут такому прогону первый попавшийся из них.
Прогоны с целым манифестом это не задевает.

**Инвентарь пайплайнов не приходит потоком.** `GET /api/pipelines` читает
файлы проектов заново на каждый запрос; демон не следит за ними
наблюдателем. Список перечитывается при входе на первый экран, но новый
или изменённый файл пайплайна, появившийся при уже открытой странице, будет
виден только после возврата на экран, а не сам собой. Прогоны под уже
показанными пайплайнами при этом остаются живыми.

### Якорь дерева

После каждого шага движок фиксирует состояние рабочего дерева как git-объект
(`write-tree` без коммита в историю) и пишет `tree_id` в `step.json`.

Это одна запись, закрывающая четыре вопроса: возобновление восстанавливает
дерево по `tree_id`, а не полагается на то, что каталог уцелел; `changed_only`
получает определённую базу сравнения; `diff.patch` становится производным от
пары деревьев; `stepcast diff` сравнивает состояния, а не только промпты.

В режиме `copy` вне git фиксируется хеш-манифест дерева — то же самое, дешевле
и без git.

### Составной якорь: несколько репозиториев

Объявленные `project.nested_repos` (см. [«Вложенные
репозитории»](config.md#вложенные-репозитории)) меняют способ фиксации на
составной: движок держит по одному git-якорю на корень и на каждый
объявленный каталог — каждый в своей базе объектов, со своим индексным
файлом — и склеивает их состояния в один идентификатор:

```
<12 знаков sha256 от отсортированного состава>+<oid корня>+<oid части>+…
```

Части идут в порядке отсортированного состава; отпечаток состава — первые
двенадцать шестнадцатеричных знаков `sha256` от списка каталогов — делает
идентификаторы разного состава различимыми на вид, не вписывая сами пути в
поле, которое печатается человеку (`stepcast status`, объяснение
инвалидации, `stepcast diff`).

Отпечаток проверяется в обе стороны: якорь сверяет состав каждого
разбираемого идентификатора со **своим** составом, а не только две стороны
сравнения между собой. Иначе два состояния чужого состава — а именно такие и
приходят от прогона, снятого с другим `nested_repos`, — совпали бы по
отпечатку друг с другом и разошлись только с сегодняшним: oid части чужого
состава ушёл бы в `diff-tree` части сегодняшней. Ни составной, ни одиночный
якорь идентификатор чужого способа или чужого состава в git не передаёт: это
объявленная несравнимость с причиной, а не диагностика git наружу. Поэтому
`stepcast diff` двух составных прогонов в дереве, где `nested_repos` уже не
объявлен, отмечает деревья несравнимыми в `notes` и продолжает сравнивать
промпт и контекст.

Пути вложенных репозиториев приходят в `changedPaths` с префиксом своего
каталога: `public-site/src/api.ts`. `diff.patch` собирается тем же способом —
патч корня плюс патч каждой части, снятый с `--src-prefix=a/<каталог>/
--dst-prefix=b/<каталог>/`, — и пути в патче совпадают с путями, которые
вернул `changedPaths`, так что файл читается как один документ.

Составное состояние восстанавливается там, где объявленные части на месте:
`restore` приводит корень, затем каждую часть — каждую средствами её
собственного репозитория, и только после того, как убедится, что каждая часть
в приводимом каталоге и правда является рабочим деревом своего репозитория
(проверка идёт до первой записи — наполовину приведённого дерева не остаётся).
`restorable()` для составного якоря истинен, и наследование дерева работает
без оговорок: продолжение цепочки получает каталог предшественника вместе с
уже заведёнными в нём частями, развилка заводит дерево целиком — корень и
части — и приводит их к якорю источника. Каталог, где хотя бы одной части нет,
по-прежнему получает отказ: объекты вложенного репозитория лежат в его
собственной базе, которой у такого каталога нет.

Каждая разрушительная операция адресована одному репозиторию и не выходит за
его границы: восстановление части не трогает соседние части и корень, а
восстановление корня не заходит внутрь объявленных частей — свойство самого
`read-tree -u`, а не соглашение движка. Изолированный режим `worktree` при
объявленном составе разрешён и материализует части (см. «Рабочее дерево»
выше); `copy` остаётся отклонённым — своей причиной, не общей для
изолированных режимов. `checkWorkspaceAvailability` и `stepcast lint`
отказывают до первой работы, называя работу и причину.

Там же, до первой работы, проверяется и пригодность самих объявленных
каталогов — существование, принадлежность собственному репозиторию и наличие
в них хотя бы одного коммита, когда корень их не игнорирует (см. [«Вложенные
репозитории»](config.md#вложенные-репозитории)). Для режима `worktree`
добавлены ещё две проверки, действующие только в нём: часть обязана иметь
коммит независимо от того, игнорирует ли её корень (`git worktree add … HEAD`
в репозитории без коммита невозможен), а путь части не должен быть занят
файлами, которые отслеживает сам корень (иначе `git worktree add` части
откажет посреди подготовки). Отказ якоря — внутренний учёт: он тихий, и после
него `changed_only` и границы правок просто не оцениваются, поэтому
непригодный состав обязан быть ошибкой конфигурации.

**`stepcast apply` и `merge-lanes` накладывают составной результат по
репозиториям.** `diff.patch` составного прогона склеен из патчей разных баз
объектов — по одному на репозиторий, — и наложение идёт тем же делением: один
`git apply --3way` на корень и по одному на каждую часть, чьи oid до и после
различаются, каждый в её собственном каталоге и без приставки пути. Отказ
наложения на любом репозитории возвращает **все** затронутые к состоянию до
наложения — наполовину наложенного составного результата не остаётся. Итог
`stepcast run` для составного прогона предлагает `stepcast apply` наравне с
однорепозиторным.

`merge-lanes` идёт тем же делением по репозиториям, но с другим порядком:
вклад дорожки накладывается во все затронутые репозитории, затем в каждом
исполняется его команда проверки (корневая — ключом `--check`, вложенная — из
объявления `project.nested_repos`), и только когда зелены все, дорожка
коммитится — по коммиту в каждом затронутом репозитории, с одним и тем же
сообщением `<слаг>: <заголовок>`. Репозиторий, в чьём рабочем дереве лежит
файл очереди, коммитится последним — в нём же лежит отметка `done`. Красная
проверка любого репозитория откатывает все затронутые к их коммитам до
наложения. Затронутый репозиторий без объявленной команды проверки — отказ до
первого наложения, называющий репозиторий и дорожку; тем же способом
отказывает и патч, двигающий запись gitlink объявленного каталога (её меняет
коммит внутри части, которого дорожка не делает). Однорепозиторное сведение
(состав не объявлен) не меняется ничем: тот же единственный коммит, что и до
этого раздела.

## Ключ шага и инвалидация

```
step_key = sha256(
    нормализованное определение шага и работы, взятое ДО раскрытия отложенных
    подстановок (то же состояние, что уходит в pipeline.lock.yml)
  + текст промпта и контекста в том же нераскрытом виде
  + backend id + model + версия бэкенда
  + выходы работ выше по графу — отдельной составляющей
  + отпечаток входов
)
```

Ключ отвечает на один вопрос: остаётся ли прошлый успех шага действительным.

**Определение берётся до раскрытия отложенных подстановок.** Пространства
`jobs`, `run` и `env` раскрываются только по ходу исполнения работы — `run.dir`
и `run.workspace` вообще не существуют раньше, чем подготовлена её рабочая
директория, — и потому величины пространства `run` (`run.id`, `run.dir`,
`run.workspace`) не входят в ключ ни прямо, ни через раскрытый текст: раскрытая
работа с ними была бы разной в каждом прогоне, и ни один шаг такой работы
никогда бы не переиспользовался. Раскрытое определение (`jobs/<job>/resolved.json`)
пишется в журнал рядом — вопрос «по какому пути шаг на самом деле пошёл в
файловую систему» отвечается им, а не догадкой по логам.

**Выходы работ выше по графу входят отдельной составляющей**, а не через
раскрытый текст промпта или контекста: `${jobs.<id>.output.*}` в нераскрытом
виде — это одна и та же строка независимо от того, что вернула работа
выше по графу, и без отдельной составляющей смена её выхода ключ бы не
меняла. Составляющая берёт сами значения `output` завершившихся работ, не их
текстовое представление после подстановки, и приводится к одному порядку —
по идентификатору работы: исполнитель копит выходы в порядке завершения работ,
разбор прогона — в порядке своего обхода, и ключ не должен зависеть от того,
кто из них его считает.

Значения `env` работы входят в ключ как часть её определения — как и всё
остальное, взятое до раскрытия отложенных подстановок.

**Отпечаток входов по умолчанию — всё рабочее дерево** (`tree_id` на начало
шага). Объявлять ничего не нужно. Инвалидация грубая, но режим отказа
правильный: перевыполняется лишнее, а результат никогда не бывает тихо
устаревшим.

**Наблюдённые входы уточняют автоматически.** Агентские бэкенды в потоковом
выводе отдают вызовы инструментов, откуда виден фактически прочитанный набор
файлов. Движок сохраняет его в `step.json` и на следующем прогоне сужает
инвалидацию до него. От пользователя не требуется ничего.

**Объявленные `inputs` работы — опция** для тех, кому нужна предсказуемость:
самый узкий вариант под ответственность автора, пропущенный файл означает
пропущенную инвалидацию.

`stepcast status` и `stepcast resume --dry-run` показывают, **почему** шаг признан
невалидным:

```
implement/write-code   invalid  — дерево изменилось (src/auth/token.ts)
review/review-diff     invalid  — пересчитан выход implement
plan/read-change       valid    — переиспользуется из 3f9a1c
```

Непрозрачный кеш — главная претензия к Bazel и Nix, повторять её незачем.

**Переиспользование при возобновлении ограничено шириной входов.** Шаг без
объявленных `inputs` работы и без наблюдённых входов зависит от всего дерева,
и любая правка его обесценивает. Сужают инвалидацию два механизма: объявленные
`inputs` работы и наблюдённые входы, которые агентские бэкенды отдают сами, —
сохранённый по прошлому успешному исполнению перечень сужает область
независимо от того, по чему был снят отпечаток того исполнения. У пайплайна из
одних командных шагов наблюдённых входов не бывает, поэтому объявленные входы
там — единственный способ получить переиспользование. Кроме того, изменившийся
путь, произведённый самим исходным прогоном на судимом шаге или на любом из
следующих за ним, в область изменений не входит вовсе — он относится к
прогону, а не к пользователю. Пути, произведённые раньше судимого шага, из
области не вычитаются: они уже были его входом. Флаг `--from` позволяет
переиспользовать всё выше названной точки поверх любых изменений дерева, если
это физически возможно; такие изменения перечисляются в отчёте и не
восстанавливаются из якоря.

**Выбранный дорожкой репозиторий входит в ключ шага не определением, а
выходом работы.** У петли саморазвития (`self-improvement-loop.md`) каталог,
команду проверки и практику спецификации выбранного репозитория несёт выход
работы `slots`, а работы дорожки читают их параметром с места подключения
(`${jobs.slots.output.lanes.<дорожка>.repo.*}`) — тем же текстом независимо от
того, какой репозиторий выбран, поэтому в нераскрытом определении работы сам
репозиторий не виден вовсе. Обесценивает шаги дорожки при смене выбора не
определение, а составляющая ключа «выходы работ выше по графу» (см. выше):
`slots` входит в неё транзитивно у каждой работы дорожки, и смена выбранного
пункта — а с ним и репозитория — меняет эту составляющую и переисполняет шаги
той же причиной, что и всякий пересчёт выхода работы выше по графу
(«изменилось определение шага, промпт или бэкенд»).

Это правило действует, пока ключ вообще проверяется. Флаг `--from` проверку
выше названной точки не делает вовсе — по своему прямому назначению,
переиспользовать всё выше неё поверх любых изменений. Если `slots` лежит
выше названной точки, её прошлый выход (а с ним и выбранный репозиторий)
переносится в возобновляемый прогон как есть, и работы дорожки ниже точки
получат его без проверки, актуален ли он всё ещё, — тем же способом, каким
`--from` переносит и любой другой выход работы выше точки.

**Прогоны, записанные до сужения ключа шага, возобновляются с нуля.** Ключ
шага перешёл с хеша всего пайплайна на хеш определения одной работы: правка
файла одной работы перестала гасить остальные. Ключи прежних прогонов
считались иначе, поэтому первое возобновление такого прогона переисполнит все
шаги с причиной «изменилось определение шага, промпт или бэкенд». Определение
при этом не менялось — изменился способ его хеширования. Досчитать прежний
ключ нельзя: хеш всего пайплайна из записи шага не восстанавливается.
Единичная потеря переиспользования на прогонах, записанных раньше, — цена
того, чтобы дальше правка одной работы не обесценивала остальные.

То же самое действует на прогоны, записанные до сужения ключа до нераскрытого
определения работы: раньше ключ шага работы с отложенными подстановками
(`${run.dir}`, `${run.id}`, `${run.workspace}` и подобные) считался от
раскрытого текста, уникального для каждого прогона, и потому такой шаг никогда
не совпадал с самим собой в другом прогоне. Первое возобновление прогона,
записанного до этого сужения, переисполнит шаги таких работ по той же
причине «изменилось определение шага, промпт или бэкенд» — и по той же
причине: досчитать прежний ключ из новой формулы нельзя.

## Кеш промптов

Кешированием управляет бэкенд, не stepcast. Claude Code кеширует по совпадению
начала запроса, а начало — это его собственный системный промпт, куда входят
рабочий каталог, ветка и снимок git-статуса. Отсюда три факта, которые стоит
знать заранее:

- разные рабочие каталоги не делят кеш вообще — в том числе worktree одного
  репозитория, поэтому `workspace.mode: worktree` исключает попадания между
  работами;
- последовательные сессии делят префикс, только если снимок git-статуса на
  старте совпал, а пайплайн по своей природе меняет файлы;
- внутри одной сессии кеш работает штатно, и на подписке живёт час.

Практический вывод один: единственный надёжный способ получить кеш — **общая
сессия внутри работы**, которая включена по умолчанию. Порядок склейки контекста
на кеш не влияет и нужен для детерминизма.

## status.json

Новая сессия без прежнего контекста должна продолжить работу, имея этот файл,
`pipeline.lock.yml` и каталог прогона.

```json
{
  "run_id": "3f9a1c",
  "pipeline": "implement-change",
  "lock_hash": "8e21…",
  "workspace": { "mode": "worktree", "base": "83c2513" },
  "inputs": { "change": "add-oauth-e2e-tests" },
  "status": "failed",
  "jobs": {
    "plan": { "status": "success", "output": "artifacts/plan.json" },
    "implement": { "status": "success", "iterations": 2, "tree_id": "4c1b…" },
    "typecheck": {
      "status": "failed",
      "failed_step": "tsc",
      "attempt": 3,
      "expect_failed": [{ "predicate": "exit_code", "expected": 0, "actual": 2 }],
      "excerpt": "src/auth/token.ts(41,7): error TS2345…",
      "log": "jobs/typecheck/steps/01-tsc/stdout.log"
    },
    "archive": { "status": "skipped", "reason": "on: success, зависимость упала" }
  },
  "budget": {
    "tokens_used": 412000, "tokens_limit": 2000000,
    "cost_used_usd": 6.42, "cost_limit_usd": 20,
    "cost_unreported_attempts": 1
  },
  "resume": { "command": "stepcast resume 3f9a1c --from typecheck" }
}
```

`budget.cost_used_usd` и `cost_limit_usd` — денежный аналог `tokens_used` и
`tokens_limit`, в долларах (не в микродолларах — файл читают посторонние
инструменты, и единица должна совпадать с той, в которой цену объявляют).
`cost_unreported_attempts` — число попыток, чей известный на сейчас расход не
содержит цены; поле появляется, только если такие попытки есть. Все три поля
необязательны: `status.json` прежней формы, где их нет, читается без изменений.

Прогон, ушедший в ожидание сброса окна лимита (`on_exceed: wait`), дописывает
`status.json` до начала сна: статус остаётся `running`, а поле `wake_at`
называет момент пробуждения. Поле снимается после продолжения — так спящий
прогон отличим от зависшего снаружи, не заглядывая в журнал событий.

## Возобновление

```bash
stepcast resume <run-id> [--from <job|job/step>] [--set k=v]
```

Создаётся новый прогон со ссылкой `resumed_from`. Шаги с совпавшими ключами и
статусом `success` берутся из старого прогона. `--set` меняет ключ и
обесценивает всё ниже по графу.

**Восстановление точечное.** Возвращаются только пути, произведённые
переиспользованными шагами, — по `tree_id` последнего из них. Полный сброс
дерева стёр бы файлы, созданные пользователем после прогона, в том числе ту
правку, ради которой он и возобновляет. Путь, произведённый шагом и
изменившийся после завершения прогона, признаётся невалидным и
переисполняется — различение временное, а не по авторству, и о слепом пятне
параллельного редактирования в режиме `cwd` см. ниже, в «Состояние каталога
прогона переносится вместе с переиспользованием».

**Основание инвалидации — изменившиеся пути**, а не сравнение отпечатков:
отпечаток снимался, когда дерево было в другом состоянии. Вопрос ставится
иначе — что пользователь тронул с момента окончания прогона и задевает ли это
входы шага.

**Изменения относятся к своему источнику.** Множество изменившихся путей
разбирается на произведённое шагами исходного прогона (по парам его якорей
`tree_before`/`tree_id`) и на всё остальное. При проверке входов шага из
множества изменений вычитаются пути, произведённые этим шагом и всеми шагами,
исполнявшимися после него, — они ещё не были его входом, когда отпечаток
снимался. Пути, произведённые шагами до него, не вычитаются: их правка
по-прежнему может обесценить шаг. Отдельно от этого сохраняется правило
«результат шага тронут после завершения прогона» — оно проверяет пересечение
изменений с путями самого шага и вычитанием не отменяется.

**Файлы определения не входят в множество изменений.** `Pipeline.file` и
`Job.source` уже учтены ключом шага: правка файла работы даёт несовпадение
ключа ровно у её шагов и не задевает шаги остальных работ. Оставлять эти
файлы в множестве изменившихся путей значило бы гасить весь пайплайн любой
правкой любой работы — то самое возобновление, ради которого команда и
существует.

**`--from` защищает верх графа.** Работы выше названной точки переиспользуются
целиком, если это физически возможно — есть запись шага, статус `success`,
якорь доступен, ключ не изменился, — независимо от того, что случилось с
деревом. Проверки изменений дерева и каскад пересчёта выше точки не
применяются: `--from` — решение запускающего, и он берёт верх графа на себя.
Чужие правки, которые тем самым проигнорированы, не замалчиваются: `--dry-run`
и `stepcast status --explain` перечисляют их отдельной строкой.

**Гранулярность.** При `session: shared` шаг нельзя переисполнить в одиночку —
его результат зависит от диалога, — поэтому единицей повтора становится работа.
При `session: per_step` возобновление идёт с точностью до шага. Объявленная
`session_group` расширяет то же правило на группу: работа, продолжающая диалог,
начатый соседом, в одиночку не переисполняется.

**Выходы переиспользованных работ публикуются как обычно.** Работа, все шаги
которой переиспользованы, проходит обычный путь исполнения работы и публикует
свой выход в `artifacts/<job>.json` нового прогона — так же, как исполненная.
Структурированный выход отдельного переиспользованного шага переносится из
исходного прогона в новый: это единственный источник `output.from` при
частичном переиспользовании работы, когда выход работы целиком не перенесён.
Работа, объявившая выход, который восстановить нельзя — артефакт источника
удалён уборкой или не читается, — переисполняется целиком, а не
переиспользуется без выхода: иначе `${jobs.<id>.output.*}` у нижележащих работ
разрешался бы в ничто.

В контекст первого переисполняемого шага подкладывается `previous_failure.md`:
выдержка из `status.json` прошлого прогона и `expect.json` упавшего шага.
Протокол попыток не переносится.

**Состояние каталога прогона переносится вместе с переиспользованием.** Шаг
может оставить промежуточный файл не в дереве, а в каталоге прогона
(`$STEPCAST_RUN_DIR/item.json`, `${run.dir}/…`), и следующий шаг — прочитать его
оттуда же. Каталог у каждого прогона свой и создаётся пустым, поэтому
переиспользованный шаг ничего в нём не оставляет: то, что он записал, лежит в
каталоге исходного прогона. Возобновление, переиспользующее хоть один шаг,
копирует из исходного каталога всё, что не принадлежит раскладке журнала, — и
переисполняемый читатель находит файл на месте. Шаг, который тот же путь пишет
заново, перезаписывает копию прежде, чем её кто-нибудь прочитает.

Различение чисто временное, по хешам содержимого между концом прогона и
моментом возобновления, — движок не проверяет, кто именно тронул файл.
Разработчик, git-хук или фоновый форматтер дают одну и ту же метку. Обратная
сторона: если файл тронут *пока шаг ещё выполняется* — в режиме `cwd`, где
рабочая директория совпадает с рабочим деревом, ничто этому не мешает, — правка
неотличима от результата самого шага и при возобновлении может быть свободно
переиспользована вместе с ним, без предупреждения. В режимах `worktree` и
`copy` это не возникает: пока прогон идёт, дерево пользователя физически в
другом месте.

## Дифф прогонов

```bash
stepcast diff <run-a> <run-b>
```

Сравнивает по ключам: какие шаги идентичны, какие изменились, какие появились.
Для изменившихся — `diff` по `prompt.txt`, `context.json`, `expect.json` и
деревьям по `tree_id`. Основной сценарий: фича не взлетела со второго захода,
надо увидеть, чем второй прогон отличался от первого.

## Расход

В `step.json`, записью на каждую попытку:

```json
"usage": {
  "backend": "claude", "model": "opus",
  "tokens_in": 18422, "tokens_out": 3110,
  "cache_read": 120340, "cache_write": 8200,
  "wallclock_ms": 41250,
  "rate_limits": {
    "five_hour": { "used_pct": 37, "resets_at": 1786000000 },
    "seven_day": { "used_pct": 61, "resets_at": 1786400000 }
  },
  "reported_cost_usd": 0.42
}
```

Бэкенды сообщают разный набор полей: у Codex нет `cache_write`, окна лимитов
есть только у Claude Code и только на подписке. Отсутствующее поле остаётся
пустым и помечается как «не сообщается» — бюджет не досчитывает молча.

`reported_cost_usd` попытки — источник для `budget.cost` (см.
[pipeline-format.md](pipeline-format.md#бюджет)): расход шага и вызванного им
судьи складывается, а попытка, не сообщившая цены, в денежные счётчики не
входит вовсе — вместо нуля.

`usage.json` — агрегат снизу вверх, по прогону, работе, шагу и, внутри шага, по
номеру попытки:

```json
{
  "run_id": "2026-08-25T16-00-00Z-demo",
  "total": {
    "tokens_in": 412300, "tokens_out": 88200, "cache_read": 900000, "cache_write": 40000,
    "billable_tokens": 612300, "wallclock_ms": 940000, "cost_usd": 6.42
  },
  "unreported": [],
  "jobs": {
    "implement": {
      "billable_tokens": 612300, "wallclock_ms": 940000, "cost_usd": 6.42,
      "steps": {
        "write-code": {
          "billable_tokens": 612300, "wallclock_ms": 940000, "cost_usd": 6.42,
          "peak_prefix_tokens": 58000,
          "attempts": [
            { "attempt": 1, "backend": "claude", "model": "sonnet",
              "billable_tokens": 180100, "wallclock_ms": 402000, "peak_prefix_tokens": 15000 },
            { "attempt": 2, "backend": "claude", "model": "opus",
              "billable_tokens": 432200, "wallclock_ms": 538000, "cost_usd": 6.42, "peak_prefix_tokens": 58000 }
          ]
        }
      }
    }
  }
}
```

`cost_usd` — в долларах, необязателен на каждом уровне (`total`, работа, шаг,
попытка): отсутствует там, где ни одна вошедшая попытка не сообщила цены,
вместо того чтобы печатать `0`. Несообщённая цена хотя бы одной завершившейся
попытки пополняет `unreported` значением `"reported_cost_usd"` — тем же
правилом, что и у токенных измерений.

`peak_prefix_tokens` — наибольший объём одного обращения к API (`tokens_in +
cache_read + cache_write` того сообщения потока, где сумма была наибольшей),
на уровнях попытки и шага; у работы и `total` этого поля нет вовсе — «самое
большое обращение за работу» не говорит, в каком шаге оно случилось. Пик шага
— **максимум по попыткам, а не сумма**: в примере выше пик шага (58000) равен
пику второй попытки, не сумме 15000 + 58000. То же правило действует при
слиянии расхода шага с расходом вызванного им судьи. Поле необязательно и
отсутствует, если бэкенд не сообщает расход по отдельным сообщениям потока —
как и денежное поле, оно читается как отсутствующее значение, а не ноль, и
записи, снятые до появления этого поля, его не несут вовсе (см.
[pipeline-format.md](pipeline-format.md#бюджет)).

Запись шага несёт перечень попыток, а не голый счётчик: у каждой — номер,
бэкенд, модель, billable-токены и время. Переисполнение одной и той же
попытки (например, после ожидания сброса окна лимита) схлопывается в одну
запись с суммарным расходом — две строки с одним номером читались бы как
ошибка. Число попыток шага выводится из длины перечня.

`stepcast usage <run>` показывает ту же разбивку — работа → шаг → попытка —
поверх `status.json` (переживает `gc` и работает на идущем прогоне) и
`usage.json` (даёт billable-токены и список несообщённого):

```
$ stepcast usage a50755
прогон a50755  self-improve  success
расход: 612.3k токенов, 15m40s, $6.42
                бэкенд  модель  вход  выход  чт. кэша  зап. кэша  время   списано  пик  цена
  implement                                                       15m40s  612.3k        $6.42
    write-code                                                    15m40s  612.3k   58k  $6.42
      #1        claude  sonnet  100   50     900k      40k        6m42s   180.1k   15k  —
      #2        claude  opus    200   80     900k      40k        8m58s   432.2k   58k  $6.4200
```

Столбец справа от «списано» — тот самый пик: наибольшее одно обращение попытки
или, у шага, максимум по его попыткам. Он на порядок меньше трафика (58k
против 612.3k у прогона) — это ожидаемо: трафик суммирует все обращения к
сессии, а пик — наибольшее из них (см. docs/pipeline-format.md, раздел
«Бюджет»). У работы и у итоговой строки прогона столбец пустой — как и у
сырых токенов, эта величина не агрегируется выше шага.

Пик строки попытки берётся из `usage.json` — там он, как и «списано» в той же
строке, уже с учётом вызванного шагом судьи, — и только при отсутствующей
сводке подставляется из `status.json`, где лежит пик одного агента. Иначе шаг
показывал бы пик больше, чем любая его попытка, всякий раз, когда самое
крупное обращение сделал судья.

Несообщённое бэкендом измерение печатается прочерком, а не нулём — денежный
столбец и столбец пика подчиняются тому же правилу; если хотя бы одна попытка
не сообщила цены, отдельная строка называет их число и напоминает, что
денежная сумма неполна. Сводки, записанные до появления пика, читаются как
обычно, а сам пик на них показывается прочерком — досчитать его неоткуда.
Если `usage.json` ещё не записан (прогон идёт) или не проходит схему (сводка
устаревшей формы), отчёт всё равно строится по `status.json`, а внизу
поясняется, что именно недоступно.

Если хотя бы одна работа прогона несёт `lane`, `stepcast usage` печатает
строку итога дорожки над строками её работ — по тем же измерениям, что и у
работы, с той же пометкой прочерком вместо нуля для несообщённой величины.
Работы без `lane` печатаются вне группировки, на своих местах. Прогон без
объявленных дорожек выглядит ровно как прежде.

**Сводка прежней формы читается неполно.** До разбивки по попыткам
`usage.json` хранил в `attempts` их число, а длительность работы и шага не
накапливал вовсе. Такие сводки принимаются — терять из-за одного поля весь
агрегат прошлых прогонов незачем, — но разбивки по попыткам в них нет, а время
работы и шага в них нулевое. Ни то, ни другое из старого файла не
восстанавливается: показывается как есть, без досчёта.

## Логи и события

`stdout.log` и `stderr.log` — построчный текст без управляющих
последовательностей: запуск через pipe, эмуляции терминала нет. Логи грепаются,
диффаются и показываются в UI без эмулятора терминала.

`events.ndjson` — по строке на событие: `job.started`, `step.attempt`,
`step.stalled`, `expect.failed`, `env.denied`, `budget.warning`,
`budget.waiting`, `budget.resumed`, `context.note_truncated` (выдержка о
прошлой итерации усечена по своему пределу — запись несёт работу, шаг,
исходный и итоговый размер выдержки в токенах), `budget.cost_unreported`
(первая завершившаяся попытка без цены при объявленном `budget.cost` — работа,
шаг и номер попытки; не чаще одного раза за прогон), `backend.refused`
(неустранимый отказ бэкенда — работа, шаг, номер попытки, класс отказа
(`rate_limit` или `unauthenticated`), код состояния, если бэкенд его назвал,
сообщение бэкенда и разобранный момент сброса, если он разобран — виден без
чтения `stdout.log` шага). UI читает хвост файла.

```bash
stepcast logs <run-id> [<job>/<step>] [--follow]
```

`--follow` подключается к идущему прогону. Девяностоминутный прогон без живого
вывода — это про «непонятно, работает ли оно вообще».

**Обратный откат журнала несимметричен.** Новые записи читаются прежней
версией по-разному: `usage.json` с `peak_prefix_tokens` она просто не примет
как сводку текущей формы, и `stepcast usage` деградирует мягко — отчёт
строится по `status.json`, а внизу поясняется, что сводка не прочитана. А вот
запись попытки в `status.json` разбирается строгой схемой, и незнакомое поле
для неё — ошибка: `stepcast status` и `stepcast usage` на таком прогоне
откажут целиком. Прогоны, снятые новой версией, прежней не читаются; лечится
это только тем, чтобы не откатывать движок под уже записанным журналом.

**Служебные записи остаются только в `events.ndjson`.** `context.denied`,
`context.downgraded`, `context.note_truncated`, `env.denied`,
`backend.unparsed`, `backend.degraded`, `bookkeeping.failed`, `step.reused`,
`tree.restored`, `workspace.inherited`, `run_dir.carried`,
`budget.cost_unreported`, `resume.note_undelivered` — разбор постфактум, а не
ход, и в ленту не идут ни при каком режиме вывода.

**Манифест называет загруженные плагины.** Поле `plugins` несёт имя, версию и
разрешённый путь модуля каждого — в порядке загрузки, пустым списком, если
плагинов не было. Без него прогон с плагинным предикатом нечем воспроизвести:
журнал называет предикат по имени и исходу, а чем оно предоставлено, знает
только конфигурация, которой у читателя может уже не быть. Отсутствие поля
означает прогон прежней версии, а не прогон без плагинов, — читатели
принимают манифест и без него. `stepcast diff` называет различие в составе
плагинов отдельной заметкой: два прогона с одинаковыми ключами шагов, но
разными плагинами — ровно тот случай, когда «те же шаги» значат разное.

**Отказ освобождения ресурса виден `bookkeeping.failed` с именем операции.**
Ресурсы прогона захватываются областями: захват регистрирует обратную
операцию, выход из области исполняет зарегистрированные в порядке, обратном
захвату. Так снимаются служебные файлы якоря работы (`снятие служебных файлов
якоря работы`), пустой каталог черновиков (`снятие каталога черновиков`),
слушатели отмены шага и — при отказе самой подготовки изолированной рабочей
директории — заведённые каталоги: части в обратном порядке, затем корень
(`снятие части <каталог> рабочего дерева работы`, `снятие рабочего дерева
работы`). Отказ любой из них — учётная операция: он пишется этим событием и
не меняет ни статус работы, ни код возврата, а исходная причина отказа
подготовки уходит наружу нетронутой. Раньше отказ уборки за неудавшейся
подготовкой проглатывался молча и не доходил ни до журнала, ни до
пользователя.

**Журнал с `lane` не читается движком прежней версии.** `JobRecordSchema`
строгая: `status.json`, где у работы записано поле `lane`, отклоняется
разбором, не знающим об этом поле, — в обратную сторону совместимость есть
(журнал прежней формы, без `lane`, читается этой версией как работы без
дорожки), а в эту — нет.

## Ход прогона (`run`)

`stepcast run` печатает ход по мере его хода — строку на событие журнала, не
дожидаясь `run.finished`. Лента строится из того же потока, что уходит в
`events.ndjson`, — второго источника правды о происходящем нет.

Печатается закрытый перечень: начало и исход прогона, начало, исход и отказ
работы, начало и исход шага с номером попытки, начало и исход итерации цикла,
остановка по тишине, провал предиката, предупреждение и превышение бюджета,
сон и пробуждение по бюджету, неустранимый отказ бэкенда. Остальное — записи
для разбора постфактум (`context.denied`, `context.downgraded`,
`context.note_truncated`, `env.denied`, `backend.unparsed`,
`backend.degraded`, `bookkeeping.failed`, `step.reused`, `tree.restored`,
`workspace.inherited`, `run_dir.carried`, `budget.cost_unreported`,
`resume.note_undelivered`) — остаются в `events.ndjson` и в ленту не попадают.

Формат строки:

```
+0:00:00  прогон: начат — self-improve
+0:00:01  propose-a: работа начата
+0:00:01  propose-a/plan: шаг начат (попытка 1)
+0:04:31  propose-a/plan: шаг success (попытка 1) — 42.1k токенов, $0.31, 271s
+0:41:02  прогон: success (код 0)
```

Слева — время от старта прогона (`ч:мм:сс`, считается по меткам времени самих
событий, не по `elapsedMs()` снимка расхода — тот вычитает сон и после
`budget.waiting` пошёл бы назад). Затем адрес: `работа` или `работа/шаг` —
строки прогона в целом называют «прогон», а не работу. Под `concurrency`
больше единицы события двух дорожек перемешаны, и без адреса строка не
сообщает, о чём она. Ни отступов, ни вложенности, ни цвета, ни возврата
каретки, ни какой-либо иной управляющей последовательности — вывод остаётся
тем же построчным текстом и в терминале, и при перенаправлении в файл
(`stepcast run … | tee run.log`).

Деталь события — чужой текст: `expect.failed` предиката `cmd` несёт весь вывод
команды, часто раскрашенный, отказ бэкенда — сообщение произвольной длины. В
ленту он идёт свёрнутым в одну строку: управляющие последовательности сняты,
переводы строк заменены пробелами, хвост длиннее двух сотен знаков обрезан
многоточием. Целиком деталь остаётся в `events.ndjson` и в файлах шага.

Величины бюджета печатаются в единицах своего измерения — токены токенами,
деньги деньгами, время длительностью, окно лимитов процентами: у события
`budget.warning`/`budget.exceeded` для этого есть поле `dimension`, и без него
`3500000/3000000` читалось бы как токены при денежном потолке.

Строка исхода шага дополнена накопленным расходом прогона на этот момент —
токены, цена и время теми же величинами, что уходят в блок `budget`
`status.json`. Несообщённая цена — прочерк, а не ноль, тем же правилом, что и
`stepcast usage`.

Идентификатор прогона и путь к каталогу журнала печатаются первыми строками, по
событию `run.started`, — то, чем прогон адресуется в `logs`, `status`,
`usage` и `resume`, нужно знать, пока прогон ещё идёт, а не когда он
закончился.

`--quiet` подавляет ленту целиком и возвращает нынешнее молчание: печатаются
только итог прогона, предупреждение о неприменённом денежном потолке, список
изолированных рабочих деревьев и диагностика отказов — то, что не ход, а
результат. Код возврата от ключа не зависит. `stepcast resume` ленту не
печатает: наблюдение в движке общее для обеих команд, но `resume` его пока не
подключает — у него своя преамбула с планом переиспользования.

**Перечень печатаемых видов закрыт и не расширяется автоматически.** Новый вид
события, добавленный в движок, в ленту не попадёт, пока для него явно не
описано правило печати в `src/cli/progress.ts` — по устройству, а не по
недосмотру: сырой JSON нового события в терминале хуже, чем его отсутствие.

**Неудача наблюдения самому наблюдателю не доставляется.** `bookkeeping.failed`,
порождённая отказом `onEvent`, идёт в файл событий, но `onEvent` на ней не
зовётся: доставка либо зациклила бы отказ, либо повторила бы его в терминале.
Единственный вид события, который наблюдатель видит не всегда.

## Отмена

`Ctrl-C` или `SIGTERM`: движок шлёт `SIGTERM` дереву процессов текущих шагов,
ждёт 30 секунд, затем `SIGKILL`. Шаги получают статус `canceled`, артефакты
дописываются, рабочие деревья сохраняются, `status.json` содержит команду
возобновления. Работы с `needs: all` выполняются и в этом случае.

## Уборка

```bash
stepcast gc [--older-than 30d]
```

Удаляет прогоны целиком, включая рабочие деревья и `artifacts/`, сохраняя
`run.json`, `status.json` и `usage.json`. Артефакты, которые должны пережить
уборку, забираются из прогона заранее — `stepcast apply` или обычным `cp`.

**Отбор к уборке знает два признака.** `abandoned` и `failed` — то, что
принимает `GET /api/runs`. Отобрать, скажем, все убранные (`swept`) или все
успешные прогоны с экрана нельзя, хотя срок и проект применимы к любым.

## CLI

```
stepcast init                                    создать stepcast.yml и пример работы
stepcast lint [pipeline] [--budget] [--resolve]
stepcast run <pipeline> [--input k=v] [--dry-run] [--quiet]
stepcast status [--run <id>]
stepcast resume <run-id> [--from <job|job/step>] [--set k=v]
stepcast apply <run-id> [--job <job> | --lane <lane>]   наложить результат на текущее дерево
stepcast merge-lanes [<run-id>] --lanes a,b --check "<команда>" [--file backlog.md]
                                                  свести дорожки: наложить, проверить, закоммитить зелёную
stepcast assert-clean [--allow путь,путь]        проверить чистоту дерева и объявленных вложенных репозиториев
stepcast diff <run-a> <run-b>
stepcast context [--job <job>] [--step <step>]
stepcast logs <run-id> [<job>/<step>] [--follow]
stepcast usage <run-id>
stepcast runs [--project <path>]
stepcast config
stepcast gc [--older-than 30d]
stepcast up [--foreground]                       поднять витрину наблюдения
stepcast down                                    остановить витрину
stepcast backlog list|pick|finish                очередь улучшений backlog.md, см. docs/backlog.md
```

Коды возврата: `0` — успех, `1` — работа завершилась отказом, `2` — ошибка
конфигурации или линта, `3` — остановлено по бюджету (включая упор в окно
лимита подписки бэкенда, когда ожидание не состоялось), `4` — отказ
аутентификации бэкенда (окружение неисполнимо, а не пайплайн упал), `130` —
отменено.
