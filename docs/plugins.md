# Плагины

Движок расширяется вкладами трёх видов: **бэкенды**, **предикаты** и
**команды**. Всё остальное — виды шагов, якоря состояния дерева, триггеры,
витрина — закрыто и остаётся делом самого движка.

Плагин объявляется в конфигурации явно. Автообнаружения по имени пакета или
топику нет: то, что движок загружает и исполняет, обязано быть названо.

```yaml
# .stepcast/config.yml
plugins:
  - stepcast/backends/codex      # плагин, поставляемый самим пакетом (раздел «Второй бэкенд»)
  - ./plugins/my-checks.mjs      # путь от файла, в котором объявлен
  - stepcast-plugin-http-checks  # пакет из node_modules проекта
```

**Плагин — код с правами процесса движка.** Песочницы нет и не обещано: он
читает те же файлы, запускает те же процессы и видит те же переменные, что
`stepcast`. Список `plugins` живёт в конфигурации репозитория и попадает в
ревью там же, где `project.check`. Это же исполнение происходит и в фоновом
демоне витрины — по запросу к `/api/pipelines`, а не только в момент, когда
пользователь набрал команду в репозитории; рамки доверия — в разделе
«Витрина» ниже.

## Объявление и разрешение

| Форма строки | Откуда разрешается |
|---|---|
| `./…`, `../…` | от каталога файла конфигурации, в котором объявлена |
| абсолютный путь | как есть |
| имя пакета | от корня проекта, при неудаче — от каталога движка |

Ключ допустим в обоих слоях, и между ними списки **объединяются**, как
`env_deny`: глобальный конфиг называет машинное (адаптер бэкенда, стоящий на
этой машине), проектный — то, от чего зависит пайплайн репозитория. Один и
тот же модуль в обоих слоях — не ошибка, загрузка одна. Пустой список
отклоняется разбором: объявление, не объявляющее ничего, — забытая правка.

Загрузка идёт **до разбора аргументов команды**: команда плагина обязана
попасть в перечень раньше, чем разбор объявит её неизвестной. Модуль, который
не найден, не импортируется, не экспортирует объект по умолчанию или не
проходит проверку контракта, прекращает ошибкой конфигурации любую команду,
**зависящую от конфигурации** — включая `stepcast config`, потому что отчёт о
конфигурации, которой не будет, врал бы о составе.

Из этого правила исключены три встроенные команды — `data`, `down`, `init`:
они не читают ни одного значения конфигурации и ни одного вклада реестра
(`docs/config.md`, раздел «Разрешение»), и поэтому исполняются, не разрешая
конфигурацию и не загружая плагины вовсе. Отказ загрузки плагина их не
касается, потому что они его не видят — плагины для них не импортируются.
Команда самого плагина в число исключений не попадает никогда: её имя
приходит из той же конфигурации, и при неразобранной конфигурации о нём
неизвестно ничего.

## Контракт

Модуль экспортирует объект по умолчанию. Типы — в подпути `stepcast/plugin`;
внутренние пути `dist/src/core/**` импортировать не нужно и не следует: что
экспортировано подпутём, то и обещано.

```js
// plugins/my-backend.mjs
export default {
  name: 'my-backend',           // слаг, уникальный среди загруженных
  version: '1.0.0',

  backends: {
    mybot: {
      create: (config) => ({ /* BackendAdapter */ }),
      defaults: { command: 'mybot', sessions: false, structured_output: true },
    },
  },

  predicates: [
    {
      name: 'http_ok',
      schema: { type: 'string', format: 'uri' },
      hard: true,
      evaluate: async (value, input) => {
        const response = await fetch(String(value));
        return {
          predicate: 'http_ok',
          passed: response.ok,
          hard: true,
          expected: value,
          actual: response.status,
        };
      },
      lint: (value, site) =>
        String(value).startsWith('http://')
          ? [{ severity: 'warning', message: `в ${site.at} объявлен незашифрованный адрес` }]
          : [],
    },
  ],

  commands: [
    {
      name: 'mybot-doctor',
      spec: { description: 'проверить установку mybot', flags: {} },
      run: (args, io, env) => {
        io.out(`бэкендов в реестре: ${env.registry.backends.size}`);
        return 0;
      },
    },
  ],
};
```

Плагин **ничего не вызывает у движка при загрузке** — он экспортирует
описание, а движок его читает. Поэтому конфликт имён и валидность формы
проверяются целиком до того, как исполнится хоть одна строка плагина сверх
импорта, и результат не зависит от порядка загрузки.

### Бэкенд

`create(config)` получает действующую запись `backends.<имя>` и возвращает
адаптер того же контракта, что и встроенный `claude`: `launch` собирает
запуск, `parseLine` разбирает строку потока, `capabilities` объявляет
поддержку сессий, структурированного вывода и жёсткого режима прав. Флаги
конкретного CLI живут здесь и только здесь.

`capabilities.sessionIdSource` называет, кто заводит идентификатор сессии:
`'engine'` — движок заводит его до запуска и передаёт бэкенду, как принимает
Claude Code (`--session-id`); `'backend'` — идентификатор заводит сам бэкенд и
сообщает его первой записью потока: `parseLine` отвечает событием `{ kind:
'session_started', sessionId }` либо, если та же запись потока — ещё и начало
разговора, событием `init` с полем `sessionId` (так устроен `thread.started` у
Codex; `parseLine` отдаёт одно событие на строку и состояния между строками
не держит, поэтому разнести такую запись на два события нечем). Движок
передаёт идентификатор обратно только на продолжении, когда он уже известен. Судья — всегда свежий разговор, и
идентификатор ему заводится по тому же правилу: адаптеру с `'engine'` —
свежий, адаптеру с `'backend'` — никакого.

Поле обязательное, без умолчания — по тому же прецеденту, что и `mcp`: адаптер,
написанный до появления этой возможности, не заявит направление молча.
Проверяет это подбор адаптера (`resolveAdapter`, до первой работы): значение
не `'engine'` и не `'backend'` — отказ, называющий бэкенд и недостающее поле.
Проверка живёт именно там, потому что типы плагину не указ: он грузится
готовым JS-модулем, и забытое поле дошло бы до движка как `undefined`,
неотличимое в ветвлении от `'engine'`.

Адаптер, объявивший `'backend'`, но не отвечающий событием `session_started`,
не роняет шаг — он просто никогда не заводит сессию: шаг записывается вовсе
без идентификатора (поля `session` в его записи нет), а `session: shared` не
продолжает диалог, потому что движку нечем его продолжить. То же самое с
шагом, оборванным отменой или таймаутом до того, как бэкенд назвал нить:
пустая строка вместо идентификатора не пишется никогда — иначе следующий
прогон пошёл бы продолжать несуществующий диалог и потратил бы на это попытку.

`defaults` — умолчания записи `backends.<имя>`: слой между встроенными
значениями и глобальным конфигом. В `stepcast config` они видны источником
`plugin:<имя плагина>` и перекрываются любым пользовательским слоем. Без них
каждый пользователь плагина переписывал бы `sessions`/`structured_output` из
его README себе в конфигурацию.

Настроить бэкенд всё равно нужно: имя без записи в `backends` — прежняя
ошибка «неизвестный бэкенд». Настроенное имя без вклада — отдельная ошибка,
и она отличается намеренно: первое чинит пользователь конфигурацией, второе —
составом плагинов. Оба отказа наступают **до первой работы**.

### Предикат

`schema` — JSON Schema значения, а не zod-модель: у плагина своя версия zod, и
модель чужой версии в объединении схем документа даёт неотлаживаемые отказы.
Значение проверяется при разборе документа, до первого токена.

Схема обязана быть самодостаточной: ссылки и их цели — `$ref`, `$id`,
`$schema`, `$anchor`, `$dynamicRef`, `$dynamicAnchor`, `$recursiveRef`,
`$recursiveAnchor` — недопустимы в ней на любом уровне: `stepcast schema`
вкладывает схему в документ проекта, и там эти ключи разрешались бы от чужого
корня. Такая схема (равно как схема, которую не принимает `ajv`, и схема,
после вложения которой не компилируется документ целиком) не отменяет
генерации: предикат попадёт в схему проекта ключом, но без проверки формы
значения, и команда назовёт причину.

`evaluate(value, input)` получает те же входные данные, что встроенные
предикаты: код возврата, текст, структурированный вывод, рабочий каталог,
окружение, изменившиеся пути. Промис допустим — проверка, обращающаяся к
внешней системе, иначе невозможна; предикаты вычисляются последовательно в
объявленном порядке. Исключение вычислителя — непройденный предикат с
названной причиной, а не крушение шага.

`hard` по умолчанию `true`: предикат, заведённый ради проверки, обычно и есть
гейт. Жёсткий отказ плагинного предиката отменяет вызов судьи наравне со
встроенным.

`lint(value, site)` — необязательная статическая проверка. Её диагностики
печатает `stepcast lint` с путём поля и файлом работы; ошибка среди них
останавливает прогон до захода.

**Имена встроенных предикатов заняты.** Плагин не может объявить `exit_code`
или `cmd`: предикат под знакомым именем, ведущий себя иначе, — то же, что
подменённый `claude`.

### Команда

`spec` описывает позиционные аргументы и флаги в том же формате, что
встроенные команды, и попадает в общую справку. `run(args, io, env)` получает
разобранные аргументы, ввод-вывод и окружение — текущий каталог, действующую
конфигурацию и реестр. Код возврата команды становится кодом возврата
процесса.

## Второй бэкенд: Codex

Пакет поставляет адаптер Codex CLI плагином — `src/backends/codex/`, подпуть
`stepcast/backends/codex`. Он **не встроен**: `builtinPlugin()` его не знает, и
без объявления бэкенда `codex` не существует. Подключение:

```yaml
# ~/.stepcast/config.yml
plugins:
  - stepcast/backends/codex
defaults:
  agent: codex
```

Умолчания вклада: `command: codex`, `sessions: true`, `structured_output:
true`, `strict_permissions: false`, `mcp: true`, `concurrency: 2`,
`cache_read_weight: 0.1` — в `stepcast config` источником `plugin:codex`.
Проверено на `codex-cli 0.149.0`; фикстуры записаны с настоящего CLI
(`test/fixtures/codex/README.md`), приёмка — `examples/codex/`.

Адаптер заведён не ради самого Codex, а как проверка контракта: второй CLI с
другой формой потока, другим понятием сессии, другой моделью доступа и другим
способом отдать структурированный вывод. Что при этом выяснилось — ниже, потому
что молчание про «хватило» неотличимо от недосмотра.

**Что пришлось добавить.**

- `capabilities.sessionIdSource` и событие `session_started` (изменение
  `first-real-backend-plugin`): идентификатор нити выдаёт CLI, продолжение —
  формой `codex exec resume <id>`.
- Поле `sessionId` у события `init` (изменение `codex-backend-adapter`):
  `thread.started` у Codex — одновременно и начало разговора, и единственное
  место, где назван идентификатор; без `init` движок принял бы упавший турн на
  продолженной нити за неоткрывшееся продолжение и снял бы засев.
- Окружение шага у процесса судьи: судья запускался с одним `launch.env`
  бэкенда, без `PATH`, и бинарник вне системного пути по умолчанию
  (`~/.local/bin`) не находился — «Процесс судьи не удалось запустить» при
  исправно отработавшем шаге. Claude Code в стандартном префиксе npm попадал в
  системный путь случайно.
- `stepcast run`, `lint` и `resume` берут конфигурацию, разрешённую точкой
  входа вместе с плагинами: раньше они читали её заново без слоя умолчаний
  плагинов, и `backends.codex` для них не существовал, хотя `stepcast config`
  его показывал. Прочие команды с собственным разрешением конфигурации
  (`status`, `usage`, `gc`, `up`, …) к бэкендам не обращаются и не правились.
- Экспорт `effectivePermissions` и типов `Permissions`/`McpServer`/`McpServers`
  подпутём `stepcast/plugin`: правила слияния политики шага с политикой
  бэкенда адаптер иначе переписал бы у себя.

**Чего хватило без правок.** Путь схемы вывода (`outputSchemaPath` — путь,
`--output-schema` принимает путь; поле `$schema` CLI не отвергает);
классификация отказов (`BackendRefusal`, класс по коду `status` из JSON внутри
сообщения `turn.failed`); умолчания вклада; `-c key=value` как способ передать
всё, у чего нет флага — им же переводятся песочница (`sandbox_mode`),
подтверждения (`approval_policy="never"`) и MCP-серверы (`mcp_servers.<имя>.*`),
одинаково для новой нити и для `resume`, у которого нет `-s`, `-C` и
`--add-dir`.

**Чего не хватило и что не правилось — с последствием для пользователя.**

- *Расход приходит одним итогом на турн* (`turn.completed`), дельт по
  обращениям нет. Итог попытки верен, но потолок расхода не обрывает идущий шаг
  Codex по ходу — он срабатывает по завершении турна; `timeout` шага работает
  как прежде. Чинится полем возможностей «расход дельтой или итогом» — правкой
  ядра вне этого изменения. Вычитать нарастающие итоги внутри адаптера нельзя:
  экземпляр адаптера один на прогон и обслуживает одновременные шаги.
- *Пооперационных списков доступа у CLI нет.* `permissions.mode` принимает
  словарь песочницы (`read-only`, `workspace-write`, `danger-full-access`);
  `allow`/`deny` отказывают из сборки запуска на первой попытке — предстартовой
  проверки «бэкенд не умеет списков» в ядре нет, и это названо как находка.
  `enforce: strict` не поддержан (`strict_permissions: false`): у CLI есть
  `--ignore-user-config`, но нет ни запрета неназванного, ни аналога
  `--strict-mcp-config`, а линт сверяет разрешающие режимы со словарём Claude.
- *Состав поднятых MCP-серверов поток не сообщает* — `init` идёт без
  `mcpServers`, и сличения с объявлением нет: сервер, который не поднялся,
  виден только по `stderr` и поведению агента.
- *Семантика токенов.* У OpenAI `input_tokens` включает кешированные, у Claude
  — нет; адаптер отдаёт `tokens_in = input_tokens − cached_input_tokens`, чтобы
  трафик не считал кеш дважды. Стоимости и окон лимитов Codex не сообщает.
- *Структурированный вывод* — текст `agent_message`; адаптер разбирает его как
  JSON у каждого сообщения (не зная, была ли схема запрошена), движок берёт
  последнее и пишет `output.json` только у шага со схемой. Схема при этом
  применяется ко **всем** сообщениям турна: пояснений между инструментами от
  Codex под схемой лучше не просить.
- *Пользовательский `~/.codex/config.toml` подгружается всегда* — вместе с
  чужими MCP-серверами и навыками; отсечь их нечем без `strict`.
- *`OPENAI_API_KEY` попадает под встроенный `env_deny` (`*_KEY`).* Вход через
  ChatGPT (`codex login`) этого не касается; для ключа — см. `docs/config.md`.

## Конфликты имён

Имя вклада, занятое встроенным вкладом или ранее загруженным плагином, —
отказ загрузки, называющий вид вклада, имя и обоих претендентов.
Переопределение не предусмотрено: тихая подмена сделала бы лжецом и
`stepcast config`, и журнал прогона, которые называют имя, а не источник.

Одно имя в разных видах конфликтом не считается: бэкенд `codex` и команда
`codex` уживаются.

## Наблюдаемость

`stepcast config` печатает раздел «Плагины»: имя, версию, путь модуля и
вклады по видам.

Манифест прогона (`run.json`) несёт поле `plugins` — имя, версию и
разрешённый путь каждого загруженного плагина. Прогон, снятый с плагинным
предикатом, читается и без плагина: журнал называет предикат по имени и
исходу, а поле манифеста отвечает, чем оно было предоставлено. `stepcast
diff` называет различие в составе плагинов заметкой.

## Витрина

Витрина раскрывает пайплайн проекта тем же реестром вкладов, какой собрала бы
команда, запущенная в этом проекте: демон читает конфигурацию проекта,
которому принадлежит файл, и загружает объявленные ею плагины. Документ с
предикатом плагина показывается устройством — работами и шагами, — а не
ошибкой «неизвестный ключ», и умолчание плагинного бэкенда участвует в модели
шага на карточке.

Отказ загрузки плагина одного проекта показывается карточкой этого проекта:
причина, файл, объявивший плагин, и подсказка — тем же составом полей, что и
у нечитаемой конфигурации. Остальные проекты обходятся дальше, демон
продолжает отвечать. Это сознательно расходится с поведением CLI, где отказ
загрузки прекращает **любую команду, зависящую от конфигурации** (три
независимые — `data`, `down`, `init` — плагинов не загружают вовсе): команда
работает в одном проекте и
исполняет его пайплайн, и молча пропущенный плагин дал бы неверный прогон.
Витрина ничего не исполняет и показывает все проекты корня прогонов сразу;
уронить экран целиком из-за одного проекта значило бы скрыть и остальные, а
скрыть сломанный — выдать его отсутствие за исправность.

Собранный реестр держится дольше одного запроса — по корню проекта, пока жив
демон, — и обновляется, когда меняется список объявленных плагинов: новый
плагин в конфигурации проекта виден следующим запросом, без `stepcast down &&
stepcast up`.

## Схема для редактора

`schema/pipeline.schema.json` и `schema/job.schema.json`, поставляемые
пакетом, печатаются из моделей встроенного набора — до того, как известно,
какие плагины объявлены. Документ с плагинным предикатом эту схему не
проходит: редактор, подключивший её, подсветит валидный ключ как неизвестный.

`stepcast schema` печатает схему проекта — `.stepcast/schema/pipeline.schema.json`
и `.stepcast/schema/job.schema.json` — от того же реестра, каким проект
разбирается: она знает предикаты объявленных плагинов и форму их значения
(схему вклада). Проект без плагинных предикатов получает файл, побайтово
совпадающий с поставляемым пакетом.

Файл стоит коммитить: изменение плагинного состава видно в ревью там же, где
правка `plugins`, и подсказка редактора остаётся верной у всех, кто открыл
репозиторий. Устаревший файл — плагин добавили, схему не перегенерировали —
называет предупреждением `stepcast lint`; это предупреждение, а не ошибка:
устаревшая подсказка редактора прогону не мешает.

## Известные ограничения

- **Семантика вклада в ключ шага не входит.** Ключ несёт имя и значение
  предиката, но не то, что вычислитель делает; смена поведения плагина при
  той же версии не инвалидирует шаг. Версия плагина видна в манифесте — по
  ней сравнивают прогоны.
- **Виды шагов, якоря и триггеры не открыты; витрина вкладов не принимает, но
  вкладами пользуется.** Вид шага прошит в раннере, журнале и ключе шага;
  открывать его значит переписывать раннер, а второго потребителя у этого
  пока нет. У витрины своих экранов и карточек для вкладов плагина нет и не
  появится этим — она лишь раскрывает документ и модель шага реестром вкладов
  проекта (раздел «Витрина» выше).
- **Изменённый код уже загруженного плагина витрина не подхватывает.** Модуль
  импортируется один раз на корень проекта за время жизни демона; правка кода
  на диске требует `stepcast down && stepcast up`. Модуль, упавший *при
  исполнении* (а не при импорте), Node запоминает упавшим — повторный импорт
  того же пути в этом процессе вернёт ту же ошибку, и такой плагин чинится
  только перезапуском демона, а не правкой файла.
- **Изоляции плагина нет.** См. предупреждение в начале документа.
- **Сессия, начатая одновременно в двух работах одной группы, у бэкенда со
  своими идентификаторами (`sessionIdSource: 'backend'`) не склеивается.**
  Идентификатор появляется только после старта первой нити, и вторая работа,
  начавшаяся раньше, чем первая его сообщила, заводит свою — у бэкенда, чей
  идентификатор выдаёт движок, этой гонки нет, потому что идентификатор
  известен ещё до запуска. Ограничение неустранимо в этой форме контракта.
- **Расход Codex не обрывает шаг по ходу.** Поток несёт расход одним итогом
  на турн, и потолок срабатывает по завершении турна, а не внутри него —
  раздел «Второй бэкенд».
- **Плагин в том же пакете — не настоящая дистанция вытянутой руки.**
  Близость к ядру ограничена механически (`src/backends/**` пропускает только
  встроенные модули Node, `../../plugin.js` и соседние модули самого
  `src/backends` — это проверяет `test/plugin-surface.test.ts`, считая наравне
  со статическим импортом побочный, динамический и `require`, и правило
  `no-restricted-imports` в `eslint.config.js`), но полностью дистанцию это не
  заменяет: модуль всё равно собирается той же сборкой и живёт в том же
  репозитории, что и ядро.
