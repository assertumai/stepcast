# Очередь улучшений (`backlog.md`) и команда `stepcast backlog`

Очередь — список пунктов, которые предстоит сделать, в одном файле
Markdown. Ведёт её человек в обычном редакторе; `stepcast backlog`
разбирает, отбирает и правит файл, не зная ничего о проекте, в котором он
лежит, — ни конфигурации, ни `.stepcast/`, ни каталога прогона. Заводится
очередь в любом репозитории созданием файла в этом формате — второй
документ не нужен.

## Формат файла

Файл состоит из преамбулы и пунктов.

Преамбула — всё до первого заголовка второго уровня. Она не разбирается:
в ней можно писать что угодно, включая таблицы и строки вида
«ключ: значение» — движок в неё не заглядывает. Огороженный блок кода
(тремя обратными кавычками либо `~~~`) в преамбуле пропускается целиком,
так что пример пункта, приведённый во вводном тексте, пунктом очереди не
становится.

Пункт начинается с заголовка второго уровня, слаг которого — kebab-case
(строчные латинские буквы, цифры и дефис, без пробелов и заглавных букв):

```markdown
## slug-of-the-item

status: todo
title: Короткое название
why: Зачем это нужно
done_when: По чему признаётся выполненным
```

Под заголовком — плоские поля вида `ключ: значение`, по одному на
физическую строку; значение не переносится на следующую строку. Пустые
строки внутри пункта пропускаются. Строка, которая не разбирается ни как
следующий заголовок, ни как поле, ни как пустая строка, — отказ разбора.

Обязательные поля: `status`, `title`, `why`, `done_when`.

| Поле | Значение |
|---|---|
| `status` | слово из строчных латинских букв, цифр и `_`; смысл движок знает у `todo`, `in_progress`, `done`, `failed` |
| `title` | одна строка о том, что делается |
| `why` | зачем это нужно |
| `done_when` | по чему признаётся выполненным |

Необязательные поля: `group`, `track`, `started_at`, `reason`, `repos`.

| Поле | Значение |
|---|---|
| `group` | слаг смежности; по умолчанию действующая группа равна слагу самого пункта |
| `track` | вес пункта — метка, по которой пайплайн выбирает цепочку работ |
| `started_at` | ISO 8601, проставляется командой `pick` при взятии в работу |
| `reason` | причина отказа; проставляется командой `finish` при `--status failed` |
| `repos` | репозитории, которых касается пункт, — перечень каталогов через запятую (`.` называет корень дерева); по умолчанию корень |

Значение `track` — слаг в kebab-case; значение другой формы — отказ разбора,
называющий пункт и значение. Проверяется **форма, а не словарь**: какие слова
что означают, решает пайплайн, читающий выдачу, а перечень допустимых в движке
запретил бы репозиторию назвать свои веса своими словами. Пункт без поля даёт
пустую метку, а не слово по умолчанию: слово было бы тем же навязанным
словарём.

Цена этого выбора названа прямо: опечатка (`expres` вместо `express`) — не
отказ разбора, а несовпадение с меткой, которую ищет ветка пайплайна. Пункт
пойдёт цепочкой по умолчанию — той, что пайплайн назначил непомеченным. В
петле этого репозитория умолчание — полная цепочка, то есть опечатка стоит
денег, а не качества.

Что именно облегчается, очередь не знает и знать не должна: она несёт метку, а
цепочку под неё выбирает пайплайн. В петле саморазвития этого репозитория
(`.stepcast/pipelines/self-improve.yml`) облегчённая ветка снимает планирование
и ревью, оставляя описание изменения, реализацию и объявленную проверку.
**Разметка — весь критерий:** снятое ревью ничем другим не заменено, и пункт,
названный простым по ошибке, доедет до коммита без второго мнения. Работы
облегчённой ветки обязаны сказать об ошибке разметки вслух, а не подгонять
работу под неё; такой заход завершается отказом дорожки, и пункт возвращается
человеку с `failed` — перевести его в полный вес правкой поля и есть
исправление.

Значение `repos` — перечень имён через запятую (`repos: backend` либо
`repos: ., backend`): каждое имя — относительный путь без сегмента `..`, без
символов шаблона глоба и без абсолютной формы; пустое значение, пустой
элемент перечня и повтор имени — отказ разбора. Разбор не проверяет, что
названный каталог объявлен составом `nested_repos` — очередь не знает
устройства проекта, это проверяет `stepcast project repos` (см. ниже).
Пункт без поля означает корень — ровно то же, что `repos: .`.

Разбор `reason` не требует даже при `status: failed`: очередь, у которой
пункт помечен отказом без причины, читается дальше — терять на этом всю
очередь было бы хуже, чем недосчитаться объяснения. Обязателен ключ
`--reason` у самой команды `finish`, а не поле у разбора.

Поле, не входящее ни в один из этих списков, разбором принимается и
переживает любую правку файла — команда переписывает и дописывает только
названные ей поля, остальные строки пункта не трогает.

Слаг пункта обязан быть уникален в пределах файла — повторный слаг делает
неоднозначным и отбор, и проставление исхода, и это отказ разбора.

## Файл `archived.md`

Пункты, доведённые до исхода (`done` либо `failed`), со временем делают
`backlog.md` нечитаемым — открытая работа тонет в решённом. `archived.md`,
рядом с `backlog.md` в корне того же проекта, хранит историю таких пунктов в
том же формате. `stepcast backlog` этого файла не знает вовсе: перенос
пункта из `backlog.md` в `archived.md` делает человек вручную, тем же
редактированием, каким ведётся сама очередь.

Экран «Очередь» витрины читает у каждого проекта оба файла и показывает их
пункты одним списком: сперва пункты `backlog.md` в его порядке, затем пункты
`archived.md` в его порядке, — с именем файла-источника у каждого пункта.
Отсутствие `archived.md` не ошибка, тем же приёмом, каким уже не ошибка
отсутствие `backlog.md`.

Статус вне этих четырёх (`postponed`, `review`) — не ошибка разбора: очередь
вправе завести своё состояние. Для движка такой пункт просто не свободен —
отбор его не берёт, пока статус не вернут в `todo`.

## Доска витрины (`/scrum`)

Экран «Доска» показывает очередь одного проекта колонками. Встроенных четыре:
три — состояния формата (`todo`, `in_progress`, `done`), четвёртая — архив, то
есть файл `archived.md`. Пункт со статусом `failed` показывается в колонке
«Сделано» с меткой отказа: отказ — исход, а не место в работе.

Пункт со статусом, под который колонки нет, доску не ломает и в чужую колонку
не подкладывается: над доской появляется полоса «статус … на доске без
колонки» с кнопкой «Добавить колонку». Диалог спрашивает название колонки и
место — между какими соседями её поставить. Раскладка целиком пишется в
`.stepcast/board.yml` проекта (маршрут `POST /api/board/columns`):

```yaml
columns:
  - id: todo
  - id: postponed
    title: Отложено
  - id: in_progress
  - id: done
  - id: archive
```

Встроенные колонки в файле обязаны быть все, имена колонок — статусы той же
формы, что в очереди. Отсутствие файла — встроенная раскладка; сломанный файл
показывается отказом рядом с очередью, а доска встаёт встроенными колонками.
Заведённая колонка принимает карточки наравне с `todo` и `done`: бросок
проставляет пункту её статус.

Щелчок по карточке открывает справа от доски панель деталей: поля `title`,
`why`, `done_when`, `group`, `track` и `repos` правятся прямо там и
сохраняются маршрутом `POST /api/backlog/item`. Пустое значение
необязательного поля убирает само поле. Статус в панели не правится — его
задаёт колонка; `started_at` и `reason` показаны, но принадлежат движку —
их пишут `backlog pick` и `backlog finish`.

Карточки перетаскиваются. Перенос между колонками правит `status` пункта,
перестановка внутри колонки — его место в файле, а перенос в архив и обратно
переносит пункт между `backlog.md` и `archived.md`, не трогая проставленный
исход. Пишет файлы сам демон, маршрутом `POST /api/backlog/move`, и отвечает
результатом: отказ виден на доске, а не теряется.

Колонка «В работе» — единственная, в которую доска не пишет. Бросок на неё
открывает выбор пайплайна, и в работу пункт берёт уже запуск:

```
stepcast run <пайплайн> --input item=<слаг>
```

Пайплайн доезжает до пункта тем же путём, каким получает любой вход: объявляет
`inputs.item`, передаёт его работе, раздающей слоты, а та зовёт `backlog pick
--only "<слаг>"`. Пайплайн, не объявивший входа `item`, в диалоге не
предлагается: запуск взял бы не этот пункт, а очередной свободный, и молчаливая
подмена хуже отсутствия кнопки.

## Отбор пункта в работу

Свободен для взятия пункт со статусом `todo`, а также пункт
`in_progress`, взятый раньше объявленного порога давности (по умолчанию
шесть часов): такой пункт считается зависшим — прогон, который его взял,
оборвался по сигналу, крашу или бюджету, и ждать больше нечего. Пункт
`in_progress` без поля `started_at` либо с значением, не разбираемым как
дата, тоже считается зависшим и свободен. Пункты `done` и `failed`
свободными не бывают никогда.

Открытое состояние одно — `todo`. Отбор берёт сперва зависшие `in_progress`
(начатое не вытесняется новым), затем `todo` сверху вниз по строкам файла:
порядок строк и есть весь приоритет.

Отбор выдаёт не больше запрошенного числа пунктов, по одному на действующую
группу. Действующая
группа пункта — значение его поля `group`, а если поля нет — слаг самого
пункта. Группа, в которой есть незавершённый и не зависший пункт
`in_progress`, целиком пропускается — независимо от того, выше или ниже
места отбора этот пункт стоит; группа, выбранная в этом же отборе,
становится занятой до его конца. Других правил приоритета, кроме состояния и
порядка строк, нет. Если свободных пунктов меньше, чем
запрошено, отбор отдаёт сколько есть — это не отказ.

## Команда `stepcast backlog`

```
stepcast backlog list                                     [--file backlog.md]
stepcast backlog pick    [--slots N | --lanes a,b] [--only слаг] [--stale-hours 6] [--run-dir путь] [--file backlog.md]
stepcast backlog finish  <slug> --status done|failed [--reason …]            [--file backlog.md]
stepcast backlog settle  --run-dir путь                                      [--file backlog.md]
```

Файл очереди — единственный вход команды: `--file`, по умолчанию
`backlog.md` в текущем рабочем каталоге. Ни пайплайн, ни `.stepcast/`, ни
конфигурация проекта, ни каталог прогона команде не нужны и не
разрешаются — `stepcast backlog list` работает в пустом каталоге, где
кроме файла очереди ничего нет. Отсутствующий или нечитаемый файл, а
также файл, не разбирающийся по формату выше, — отказ с кодом `2` и
путём к файлу в сообщении.

### `list`

Печатает разобранную очередь в стандартный вывод одним документом JSON —
массивом записей в порядке их следования в файле. Каждая запись несёт
`slug`, `title`, `why`, `done_when`, действующую `group`, объявленный `track`
(пустая строка, когда поля нет) и `repos` — перечень названных репозиториев, пустой, когда пункт поле не
заполнил.
Файл при этом не правится.

### `pick`

Отбирает свободные пункты по правилам выше, проставляет каждому
выбранному `status: in_progress` и `started_at` текущим моментом в ISO
8601 — одной и той же меткой для всех пунктов, взятых за этот вызов, — и
печатает выбранное в стандартный вывод.

Порог давности задаётся ключом `--stale-hours` (по умолчанию `6`).

Ключ `--only <слаг>` берёт именно названный пункт вместо первого свободного по
очерёдности: так очередь берёт в работу пункт, выбранный человеком на доске
витрины. Правило группы при этом остаётся в силе — занятость считается по всей
очереди, и пункт, чья группа занята идущей работой, не отбирается. Неизвестный
слаг и пункт, который не свободен (`done`, `failed`, свежий `in_progress`), —
отказ с кодом `2` и названной причиной, а не пустая выдача: опечатка в слаге не
должна выглядеть как «свободных пунктов нет».

У выдачи две формы, и они не смешиваются: `--slots` вместе с `--lanes` —
отказ с кодом `2`, а не молчаливый выбор одной из них.

- `--slots N` (по умолчанию `N = 1`) — массив записей, до `N` штук.
- `--lanes a,b` — объект дорожек: имена дорожек, через запятую, попарно
  различные слаги в kebab-case. Отбирается не больше пунктов, чем названо
  дорожек, каждая названная дорожка присутствует в ответе всегда, даже
  если ей не хватило свободного пункта — тогда `filled: false`, `item:
  null`, а `slug`/`title`/`group`/`track` — пустые строки. Заполненная
  дорожка несёт `filled: true` и запись пункта в `item`.

  Вес пункта дублируется у дорожки плоским полем `track` рядом со слагом и
  заголовком: условие `if` пайплайна читает его без захода внутрь `item`.

При `--run-dir <каталог>` каждая заполненная дорожка дополнительно
записывается отдельным файлом `item-<дорожка>.json` в этот каталог —
незаполненная дорожка файла не получает. Каталог создаётся, если его нет, и
готовится до правки очереди: недоступный путь — отказ с кодом `2` и
нетронутая очередь, а не взятые пункты без файлов дорожек. Относительный
путь, как и у `--file`, разрешается от текущего рабочего каталога.

Свободных пунктов не нашлось — не отказ: команда завершается кодом `0`,
`--slots` печатает пустой массив, `--lanes` — дорожки с `filled: false`, а
файл очереди остаётся неизменным.

Пустой перечень дорожек, повтор имени в нём или имя не в kebab-case —
отказ с кодом `2`.

**Параллельные `pick` не исключают друг друга.** Два одновременных прогона
петли на одной очереди могут прочитать файл до того, как другой его перепишет,
и раздать один и тот же пункт дважды. Блокировки файла нет; сегодня заход у
петли ровно один, и до второго это не проверить.

**У `pick` нет прежних форм `--now`, `--out` и голого объекта одного пункта.**
Часы теперь только внутренние (текущий момент проставляется командой, а не
приходит ключом — он был нужен исключительно старым тестам скрипта, которые
переписаны на прямые вызовы ядра); печать в отдельный файл через `--out`
снята — тот же результат печатается в стандартный вывод, и вызывающему
достаточно его перенаправить; `--slots` без числа теперь тоже даёт массив
(из одной записи), а не одиночный объект. Внешнего вызывающего этих форм в
репозитории не осталось: `--lanes` объявляется в `slots.yml`, а `finish`
зовут два скрипта петли — обе замены уже сделаны.

### `finish`

```
stepcast backlog finish <slug> --status done
stepcast backlog finish <slug> --status failed --reason "почему"
```

Проставляет названному пункту исход. `--status` принимает только `done`
или `failed` — другое значение отклоняется. При `failed` ключ `--reason`
обязателен и не может быть пустым; при `done` он не нужен.

Причина приходит как есть — обычно это кусок чужого вывода, — а поле
очереди однострочно, поэтому текст сводится в одну строку (переводы строк и
отступы становятся пробелами) и урезается по длине. Полностью он остаётся в
логе шага, который его собрал; в очереди нужна опознаваемая фраза, а не
протокол.

Пункт, которому исход уже проставлен (`status` уже `done` либо `failed`),
остаётся нетронутым, а команда завершается кодом `0`: повторный вызов
`finish` не должен состязаться за последнее слово — первый проставленный
исход и есть окончательный. Слаг, которого в очереди нет, — отказ с кодом
`2`, называющий этот слаг.

### `settle`

```
stepcast backlog settle --run-dir <каталог> [--file backlog.md]
```

Закрывает заход: каждому пункту, взятому в этот прогон и оставшемуся без
исхода, проставляет `failed` с единой причиной «заход до сведения дорожки не
дошёл». Взятые пункты определяются по файлам `item-<дорожка>.json` каталога
`--run-dir` — тем самым, которые пишет `pick --lanes --run-dir`; других
файлов каталога прогона команде не нужно, как и остальным подкомандам
`backlog`.

Различимые причины несведения (негодная дорожка, конфликт, красная проверка,
остановка на более ранней с названным основанием — конфликт наложения либо
неподтверждённый откат) проставляет сведение дорожек (`stepcast merge-lanes`);
`settle` остаётся ровно для случая, когда до дорожки дело не дошло вовсе —
отмена по сигналу, остановка по бюджету, гибель шага.

**`settle` коммитит свою правку очереди**, если хоть один пункт проставила —
адресно, в том репозитории, где файл очереди лежит (`project.nested_repos`
находит его тем же правилом, что и `merge-lanes`), сообщением `backlog: исходы
дорожек прогона <короткий id прогона>`. Коммит адресован файлу, а не индексу:
`settle` отвечает за очередь и не подметает в коммит посторонние правки
рабочего дерева. Правок нет, файл не отслеживается этим репозиторием
(игнорируется либо никогда не был закоммичен) или лежит вне репозитория git
вовсе — коммита нет, и вывод команды это называет. Отметка исхода дорожки
обязана пережить восстановление дерева при `resume` — незакоммиченной она
исчезает при первом же таком восстановлении, а коммит `merge-lanes` для
работ, до которых заход не дошёл, никогда не появляется вовсе.

Файл очереди не обязан лежать в корне дерева запуска — при объявленном
`project.nested_repos` (см. [«Вложенные репозитории»](config.md#вложенные-репозитории))
он может лежать и внутри объявленного вложенного репозитория. Коммитов у
сведённой дорожки столько, сколько репозиториев она затронула, — по одному в
каждом, с одним и тем же сообщением `<слаг>: <заголовок>`, — а репозиторий, в
чьём рабочем дереве лежит сам файл очереди, коммитится последним: в нём же
лежит отметка `done`, и она не имеет права появиться раньше того, что
отмечает. Дорожка, затронувшая только тот репозиторий, где лежит очередь (в
том числе однорепозиторное сведение без объявленного состава), даёт ровно
один коммит — вклад и правку очереди он несёт вместе. Этот коммит остаётся
заботой `merge-lanes` — коммит `settle` покрывает только те пункты, до
сведения которых заход не дошёл. Подробности — в
[«Сведение дорожек»](run-layout.md#сведение-дорожек-stepcast-merge-lanes).

Пункт, которому исход уже проставлен (`done` либо `failed`), остаётся
нетронутым — `settle` закрывает заход, а не переписывает его результат.
Каталога без файлов `item-*.json` — не отказ: команда завершается кодом `0`,
сообщая, что проставлять нечего, а очередь не правится. `--run-dir` без
значения либо на несуществующий каталог — отказ с кодом `2`, а файл дорожки
без слага — отказ с кодом `2`, называющий этот файл. На каждый помеченный
пункт печатается строка со слагом, дорожкой и причиной.

## Команда `stepcast project repos`

```
stepcast backlog pick --lanes a,b --run-dir путь | stepcast project repos [--file путь]
```

Дополняет документ дорожек — ответ `pick --lanes` — объявлениями того
репозитория, который назвал пункт каждой заполненной дорожки: каталог
репозитория, его команда проверки и его практика спецификации (каталог
документов изменения, файл правил, имя инструмента, команда, которой петля
их гейтит). В отличие от
`backlog`, эта команда конфигурацию проекта читает — секцию `project` и
объявленный ею состав вложенных репозиториев (`.stepcast/config.yml`, см.
`docs/config.md`) — и потому не заведена подкомандой `backlog`: очередь не
должна зависеть от устройства проекта.

Документ приходит со стандартного ввода либо из файла, названного `--file`
(тогда стандартный ввод не читается вовсе). Печатается тот же документ:
незаполненные дорожки, порядок дорожек и записи пунктов не меняются,
единственное добавление — блок `repo` у заполненной дорожки:

```json
"repo": {
  "dir": "backend",
  "check": "./gradlew check",
  "spec": {
    "dir": "backend/docs/changes",
    "rules": "backend/docs/spec-rules.md",
    "tool": "openspec",
    "check": "make spec-check"
  }
}
```

Пути практики спецификации в блоке склеены от корня рабочего дерева
(`backend/docs/changes`) — так каждый потребитель получает готовое значение,
не склеивая его самостоятельно. У корня (пункт не назвал репозиторий либо
назвал `.`) `dir` равен `.`, а пути практики — без приставки
(`openspec/changes`), то есть ровно то же, что и до этой команды. Команда
ничего не правит: ни очередь, ни конфигурацию, ни рабочее дерево.

Отказывает кодом `2`, если: названный каталог не объявлен составом и не
`.` (называет пункт, имя и перечень объявленных каталогов); пункт назвал
больше одного репозитория (дорожка ведёт один репозиторий); у названного
репозитория (включая корень) не хватает `check` либо одного из
`spec.dir`/`spec.rules`/`spec.tool`/`spec.check` (называет репозиторий,
недостающий ключ и `.stepcast/config.yml` — место, где его объявляют); стандартный ввод пуст
или не разбирается как JSON. Пустой либо неразбираемый ввод — намеренно тот
же отказ, что и у неполного документа: так отказ `pick` доезжает до этой
команды ненулевым кодом второго звена конвейера, не полагаясь на
`set -o pipefail`.

## Коды возврата

`0` — успех, включая пустую выдачу `pick`, когда свободных пунктов нет, и
`settle`, когда проставлять нечего. `2` — ошибка конфигурации: файла нет,
файл не разбирается, каталог `--run-dir` не подготовить или не найден, ключ
бессмыслен (в том числе некорректный перечень дорожек, `--lanes` вместе с
`--slots`, `--stale-hours` не положительное число, `failed` без причины),
слаг не найден в очереди у `finish`, файл `item-<дорожка>.json` без слага у
`settle`.

## Схема формата в чужом репозитории

Формат пункта и форма ответа `pick --lanes` публикуются пакетом схемами
`schema/backlog.schema.json` и `schema/backlog-slots.schema.json` —
порождёнными из тех же моделей, которыми команда проверяет разбор. Работа
пайплайна, проверяющая выход `pick --lanes` ключом `output.schema`, называет
схему ссылкой `stepcast:backlog-slots` — движок разрешает её сам, от
собственного расположения, независимо от того, откуда пакет установлен
(`node_modules`, ссылка, исходники) и есть ли рядом с работой каталог `schema/`
вовсе. Указывать путь `node_modules/stepcast/schema/` вручную не нужно. В этом
репозитории (stepcast и есть проект) работа `slots` ссылается той же формой —
`stepcast:backlog-slots` — на тот же файл в дереве исходников.

## Правка файла

Правка не переписывает файл заново — она атомарна (обрыв записи не
оставляет файл в промежуточном состоянии) и точечна: существующее поле
переписывается на своей строке, новое поле дописывается сразу за
последним полем своего пункта. Строки остальных пунктов, преамбула и
порядок пунктов в файле остаются посимвольно неизменными.

**Преамбула `backlog.md` этого репозитория продолжает дублировать формат.**
Нормативное описание — `docs/backlog.md`, но вводный текст самого файла
очереди (таблица полей, правило группы, правило шести часов) не сокращён:
файл вне границы правок агентских работ петли, а `pick` переписывает его в
том же прогоне, что сделало бы правку диффом поверх этого игрой без нужды.
Расхождение не остаётся незамеченным — тест движка разбирает `backlog.md`
этого репозитория как есть и падает при несовпадении с моделью.
