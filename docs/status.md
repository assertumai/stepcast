# Что реализовано

Срезы `add-minimal-run-engine` и `add-worktree-anchor-and-resume`. Остальные
документы описывают целевое состояние формата целиком; здесь — граница между
тем, что работает, и тем, что пока отклоняется с внятной ошибкой.

Нереализованное не игнорируется молча: линт или движок отказывают и называют
причину. Тихая деградация превратила бы объявленное поведение в ложь.

`docs/status.md` — собранный документ: он получается склейкой этой базы с
фрагментами изменений `openspec/changes/*/status.md` скриптом
`scripts/status.mjs` и правится не руками, а правкой базы (для содержимого,
накопленного до введения фрагментов) либо фрагмента своего изменения.
Пересборка — `npm run status:build`.

## Работает

| | |
|---|---|
| Команды | `run`, `lint`, `status`, `logs` (в том числе `--follow`), `usage`, `config`, `gc`, `init`, `context`, `up`/`down` |
| Формат | пайплайн и файлы работ, `uses`/`with`, подстановки (включая числовые поля — `concurrency`, `until.max_iterations`, `attempts.max`, `budget.rate_limit_pct`, `exit_code`), умолчания, `pipeline.lock.yml` |
| Граф | `needs`, `on`, `if`, `needs: all`, `fail_fast`, отмена по сигналу |
| Шаги | `run` (argv и строка) и `agent` (Claude Code), таймаут, детектор тишины, попытки с эскалацией |
| Сессии | `shared`, `per_step`, именованные псевдонимы, общая сессия нескольких работ (`session_group`); деградация при отсутствии поддержки |
| Контекст | три уровня, блок выходов предшественников, `inline`/`reference`/`auto`, предел с понижением |
| Проверки | `exit_code`, `file_exists`, `schema`, `matches`, `not_matches`, `cmd`, `judge` (оценка агентом-судьёй) |
| Выход работы | `output.from`, публикация в `artifacts/`, `${jobs.<id>.output.*}` |
| Журнал | манифест, состояние, события, логи, промпты, контекст, расход |
| Бюджет | три уровня — `tokens`, `cost`, `wallclock`, `rate_limit_pct` — непрерывный учёт трафика прогона (сумма по всем обращениям к API, не объём контекста), останов по превышению; `on_exceed: wait` усыпляет прогон до сброса окна (по превышению `rate_limit_pct` или по отказу бэкенда — на `cost` не действует); `limits.cost` в конфигурации и проверка `stepcast lint`; см. разграничение трёх пределов в разделе «Бюджет» `pipeline-format.md` |
| Отказ бэкенда | упор в окно лимита подписки и отказ аутентификации распознаются по конверту результата (код состояния, при его отсутствии — закрытый перечень формулировок); первый ведёт себя как второе основание для `on_exceed: wait` (код возврата 3 при остановке), второй прекращает прогон независимо от `fail_fast` с кодом возврата 4; событие `backend.refused` и причина шага видны без чтения `stdout.log` |
| Рабочая директория | `cwd`, `worktree`, `copy`; наследование дерева зависимой работой (`workspace.inherit`), продолжение цепочки в одном каталоге, засев развилки; `stepcast apply` для возврата результата |
| Якорь дерева | `tree_id` после каждого шага: `git write-tree` в репозитории — в том числе для рабочей копии, лежащей вне его и пользующейся его базой объектов, — хеш-манифест вне репозитория |
| Возобновление | `stepcast resume` с `--from`, `--set`, `--dry-run`; `stepcast status --explain` |
| Сравнение прогонов | `stepcast diff` по ключам шагов, промптам, контексту и деревьям |
| Цикл работы | `until` с `max_iterations`, раскладка `iter-N`, предикат `changed_only` |
| Витрина | `stepcast up` — демон, наблюдающий за прогонами всех проектов; живое обновление, вход и выход работ, просмотр файлов журнала, расход прогона, работы и шага; `stepcast down`; экраны доступны боковым меню — прогоны, пайплайны, уборка, настройки, — с признаком связи в подвале колонки, на узком окне колонка ложится полосой сверху, и адрес каждого экрана переживает перезагрузку, а пункт меню и разбор адреса берутся из одного перечня; настройки правятся с экрана — агент выбором из объявленных бэкендов и модель полем, с путём правимого файла и происхождением каждого значения, пустая модель снимает значение и возвращает модель бэкенда, отказ демона показан его же текстом; уборка отбирает прогоны по признакам, сроку и проекту и показывает число и объём **до** всякого удаления, удаляет ровно показанный список одним подтверждением и называет исход по каждому адресу, включая отклонённый живой прогон; первым экраном идут прогоны таблицей с шапкой — имя, статус, начало, длительность, стоимость и токены с раскрываемым разрезом по видам, — где длительность идущего прогона считается от его начала, а таблица прокручивается в своих берегах, не растягивая страницу; экран пайплайнов показывает их устройство — граф работ, условия перехода, шаги выбранной работы с агентом и моделью или командой, параллельность и fail_fast, — а прогоны на нём сведены к счёту и ссылке на последний вместо повторения таблицы первого экрана; прогон удаляется и поштучно из списка — в два нажатия, с причиной отказа целой фразой в его строке, и уходит с экрана живым потоком; колонки списка стоят друг под другом при любой ширине статуса, на узком окне строка переносится потоком без горизонтальной прокрутки страницы, а длительность округляется один раз и не показывает разрядов вроде «52м 60с»; собирается из исходников репозитория одной командой (`npm run build:ui`, входит в `npm run build`) в единственный самодостаточный `dist/ui-web/index.html`, а `npm run check` проверяет эти исходники типизацией, линтом и сборкой; первый экран показывает пайплайны проектов с их прогонами — имя, путь файла, число работ, неразбираемый пайплайн с текстом ошибки и со своими прогонами (прогон находит пайплайн по файлу, которым запущен, а не по имени), пайплайн без прогонов помечен явно, прогон без найденного пайплайна виден отдельной группой проекта; прогон открывается собственной страницей по адресу `/runs/<проект>/<прогон>`, переживающему перезагрузку и годному для ссылки и открытия в новой вкладке, «назад» работает браузерными средствами; живое обновление одним потоком событий действует на обоих экранах — новый прогон и смена статуса работы приходят без перезагрузки, а страница прогона получает свой снимок тем же потоком, а не отдельным запросом на каждое изменение обзора; удаление прогона из истории целиком — поштучно (`DELETE /api/run`) и группой по списку адресов (`DELETE /api/runs`), с исходом на каждый адрес и суммой освобождённого места; живость прогона определяется тем же правилом, что и в движке — процессом из манифеста, а не статусом `running`, поэтому прогон, застрявший в `running` после гибели процесса, теперь удаляется наравне с завершённым, а идущий и спящий по-прежнему отклоняются кодом `409`; отбор прогонов к групповому удалению (`GET /api/runs`) по признакам — оборванные, отказавшие, старше срока — объединённым по «или», по всем проектам или одному, с размером и числом до подтверждения и без изменений на диске; прогон с испорченным журналом из отбора не выпадает — статус берётся из манифеста, возраст считается по времени каталога, и такой прогон помечен нечитаемым; обзор несёт признак оборванности прогона отдельно от `running` |
| Показ расхода | `stepcast usage <run-id>` и `stepcast status` — работы, шаги, попытки с бэкендом, моделью, токенами, кешем, временем и денежной ценой на всех уровнях, и наибольшим префиксом одного обращения («пик») на уровнях попытки и шага рядом со списанным трафиком; строится из `status.json` и `usage.json`, работает на убранном и на идущем прогоне; несообщённое (в том числе цена и пик) помечается, а не обнуляется |
| Петля саморазвития | `.stepcast/pipelines/self-improve.yml` — движок улучшает сам себя по очереди `backlog.md`, коммит на улучшение; `stepcast backlog pick --slots N` выдаёт до N пунктов за проход, по одному на действующую группу (`group` пункта или его слаг) |
| Параллелизм | независимые работы идут одновременно в пределах `Math.min(pipeline.concurrency, limits.concurrency)`; `backends.<имя>.concurrency` — отдельный предел на одновременные вызовы бэкенда, общий на прогон; `fail_fast` и отмена дожидаются уже идущих работ, не обрывая их; `stepcast lint` предупреждает о ссылке `if` на работу вне зависимостей при `concurrency` больше единицы |
| Каталог черновиков работы | `<run_dir>/jobs/<id>/scratch` заводится вместе с каталогом работы, до первого шага, — переменной `STEPCAST_SCRATCH` и подстановкой `${run.scratch}` он доступен и агентскому, и командному шагу, включая шаги в итерациях `until`. Каталог лежит вне рабочего дерева при любом режиме `workspace` (`cwd`, `worktree`, `copy`), поэтому черновик, положенный туда, не идёт против предиката `changed_only` (заход `616c1b`: черновики живой проверки, положенные в системный временный каталог относительным путём, ложились внутрь дерева и заваливали границу правок вместе со всей работой). В жёстком режиме прав (`enforce: strict`) адаптер Claude объявляет каталог доступным флагом `--add-dir` рядом с `--setting-sources project` — без этого первая же запись в черновик упёрлась бы в отказ прав. Вне жёсткого режима движок доступ агента не расширяет — границы там ставит сам бэкенд, и это оговорено в документации. По завершении работы пустой каталог снимается движком сам — при любом исходе, включая отказ на подготовке рабочей директории или на раскрытии подстановок, до первого шага; непустой остаётся нетронутым до `stepcast gc`. Отказ снятия — учётная операция (`bookkeeping.failed`), статус работы не меняет; каталог, убранный самим шагом, отказом не считается. Правило петли о временных файлах для живой проверки (`implement.md`, `fix-review.md`) переведено на `${run.scratch}` — с той же оговоркой, что удалять оттуда за собой ничего не нужно. |
| Пункт очереди называет затрагиваемый репозиторий | необязательное поле `repos` пункта — перечень каталогов через запятую, `.` называет корень дерева; пункт без поля означает корень, ровно прежнее поведение. Публикуемая запись пункта (`list`, `pick`, файл дорожки) несёт перечень строк, пустой при отсутствии поля. Разбор не проверяет, что названный каталог объявлен составом, — это делает `stepcast project repos`. |
| Вложенный репозиторий объявляет свою проверку и практику спецификации | элемент `project.nested_repos` допускает объектную форму `{ dir, check, spec }` наравне со строкой — `check`, `spec.dir`, `spec.rules`, `spec.tool` теми же моделями, что у одноимённых ключей секции `project`. Объявление, читаемое командой движка, живёт в `.stepcast/config.yml`; пайплайновый слой (верхний ключ `project` документа) остаётся для подстановки `${project.*}` и с конфигурацией не расходится молча. |
| Команда `stepcast project repos` разрешает названный репозиторий в объявление | дополняет документ дорожек (`backlog pick --lanes`) блоком `repo` — каталог, команда проверки, практика спецификации с путями, склеенными от корня рабочего дерева, — у каждой заполненной дорожки. Отказывает кодом ошибки конфигурации на неизвестном имени, на нескольких именах у одного пункта и на неполном объявлении названного репозитория, называя пункт и место, где объявление недостаёт. |
| Гейты дорожки исполняются в каталоге выбранного репозитория | головная работа `slots` конвейером `backlog pick --lanes … \| project repos` проставляет каждой заполненной дорожке объявления её репозитория, а `verify`, `implement` и `fix-review` берут команду проверки и инструмент практики спецификации из этих объявлений — параметрами с места подключения — и гоняют их в каталоге выбранного репозитория (`cd "${params.repo_dir}" && …`), а не в корне независимо от пункта. Пункт, не назвавший репозиторий (в том числе прежние пункты очереди), ведёт заход ровно как до изменения. |
| Документы изменения пишутся по практике выбранного репозитория | `propose`, `plan`, `implement` и `review` читают каталог документов изменения, файл правил и имя инструмента практики параметром дорожки, а не подстановкой `${project.spec.*}` документа пайплайна, — переносимость файлов работ и промптов петли в чужой репозиторий это не задевает: ни имени инструмента, ни имён документов эти файлы по-прежнему не называют литералом. |
| Встроенное сведение дорожек | `stepcast merge-lanes [<run-id>] --lanes a,b --check "<команда>" [--file backlog.md]` накладывает названные дорожки прогона на дерево запуска по очереди — годность решается по исходам всех работ дорожки (метка `lane`, а не имя одной из них), проверка объявленной командой идёт исполнителем процессов движка, красная проверка откатывает дерево к коммиту до наложения и останавливает обход, конфликт наложения останавливает обход без правки дерева, дорожка без вклада в дерево получает `failed`, дорожка без взятого пункта пропускается до наложения; сведённая дорожка получает в очереди `done`, а следом — один коммит `<слаг>: <заголовок>`, забирающий и вклад дорожки, и правку очереди; коды возврата — `0` обход дошёл до конца, `1` остановлен конфликтом либо красной проверкой, `2` ошибка ключей, неизвестная дорожка или грязное дерево запуска; `stepcast backlog settle --run-dir <каталог>` проставляет `failed` каждому пункту, взятому в прогон и оставшемуся без исхода, единой причиной «заход до сведения дорожки не дошёл», не трогая уже проставленный исход; `.stepcast/jobs/merge.yml` и `.stepcast/jobs/finalize.yml` зовут обе команды через `$STEPCAST_BIN` |
| Границы правок репозитория настройкой, а не литералом | ключ `project.edit_paths` — непустой список путей и шаблонов глоба от корня репозитория, правка которых и есть работа над ним (`[src/**, test/**, docs/**, package.json]`, `[cmd/**, internal/**, go.mod]`). Каждый элемент — та же модель, что у `project.spec.dir` (`RelativeRepoPathSchema` переиспользуется, а не копируется): относительный путь без сегмента `..`, шаблоны глоба ожидаемы. Пустой список (`edit_paths: []`) отклоняется разбором, как пустой `project.tools`. Ключ проектный: в `~/.stepcast/config.yml` отклоняется той же проверкой и тем же сообщением, что `project.check` там же. Документ пайплайна может объявить `project.edit_paths` сам, верхним ключом `project`, заменяя список конфигурации целиком — тем же правилом, что `project.tools`. Пространство подстановки `${project.*}` пополнено именем `edit_paths` и раскрывается тем же правилом «список строк — в элемент списка», что уже действует для `${project.tools}`. Работы `implement` и `fix-review` несут границы одной записью `${project.edit_paths}` вместо двенадцати литералов раскладки репозитория в `changed_only`; каталог документов изменения и файл правил остаются отдельными записями `${project.spec.dir}/**` и `${project.spec.rules}` — их называет другой ключ, `project.spec`, а не раскладка. `.stepcast/pipelines/self-improve.yml` объявляет сегодняшние двенадцать путей этого репозитория; промпты `implement.md` и `fix-review.md` больше не пересказывают раскладку словами, а говорят об объявленных границах. |
| Команда проверки проекта настройкой, а не литералом | секция `project` в `.stepcast/config.yml` с единственным ключом `check` — непустой строкой, пустая и состоящая из пробелов отклоняется разбором конфигурации. Ключ проектный: в `~/.stepcast/config.yml` он отклоняется с ошибкой, называющей файл и предлагающей `.stepcast/config.yml`. Встроенного умолчания нет — не объявлено, значит `project.check` отсутствует, и это не ошибка, пока на него никто не сослался. Документ пайплайна может объявить `project.check` сам, верхним ключом `project` того же состава — он перекрывает конфигурацию тем же порядком слоёв, каким пайплайн уже перекрывает `defaults` и `context`. Пространство подстановки `${project.check}` раскрывается при разборе документа наравне с `inputs` и `params` — в пайплайне, файлах работ и файлах промптов, — и раскрытое значение попадает в `pipeline.lock.yml` строкой, а не подстановкой. Ссылка на необъявленный `project.check` — отказ разбора, называющий оба места объявления; обращение к имени вне состава пространства (`${project.name}`) называет доступные имена. Петля этого репозитория (`.stepcast/pipelines/self-improve.yml`) объявляет `project.check: npm run check` и ссылается на него подстановкой во всех местах, где раньше нёс литерал: циклы `until` работ `implement` и `fix-review`, шаг работы `verify` (теперь один: движок не разбирает объявленную команду на части), аргумент `--check` работы `merge`, тексты промптов и абзац `context` пайплайна. Файлы петли переносятся в другой репозиторий копированием — без правки внутри, только своим объявлением `project.check`. Экран пайплайнов витрины раскрывает каждый пайплайн секцией `project` того проекта, которому файл принадлежит: конфигурация демона одна на все проекты корня прогонов, а команда проверки объявлена в репозитории. |
| Склейка повторно объявленных путей контекста | файл, разрешённый при сборке контекста более одного раза — на разных уровнях, дважды на одном уровне или явным путём вперемешку с глобом, — входит в собранный контекст единственной записью. Тождество считается по абсолютному пути после раскрытия, а не по тому, как путь написан. Склеенная запись стоит на месте первого объявления (порядок «выходы предшественников → пайплайн → работа → шаг»), а файл читается один раз. Оценка размера и понижения `applyBudget` считают склеенную запись один раз, поэтому повтор больше не может вывести контекст за предел, которого он на самом деле не превышает. `stepcast context` печатает склеенные записи перечнем следом за разрезом по уровням: разрез относит такую запись к уровню её места, и без перечня ноль у уровня не отличить от «на этом уровне ничего не объявлено». Составное состояние восстанавливается там, где все объявленные части на месте (`restore` приводит корень, затем каждую часть; `restorable()` истинен), и наследование дерева переносит части наравне с корнем — продолжение цепочки получает их вместе с каталогом, развилка приводит их к якорю источника. |
| Учёт и уборка рабочих деревьев | заведённые части записываются в состояние работы (`workspace.nested`) до первого шага — переживают отказ, отмену и остановку по бюджету. `stepcast gc`, удаление прогона из истории (`stepcast gc`, `DELETE /api/run(s)` витрины) и снос каталога при отказе подготовки снимают учётные записи всех изолированных деревьев прогона — корневых и частей, каждую в её собственном репозитории — адресно (`git worktree remove --force`, а при его отказе снос каталога и удаление той единственной записи репозитория, чей `gitdir` называет снимаемый путь), прежде чем удалить каталоги. Слепой `git worktree prune` движок не зовёт нигде, включая корневой репозиторий, — он снял бы всякую осиротевшую запись чужого репозитория, не только свою. Неснятая запись называется в исходе (`stepcast gc`, ответ витрины), а не пропадает молча, — и называется только настоящая: уборка, которой снимать уже нечего (повторный заход по тому же прогону), молчит. |
| Радиус разрушения ограничен репозиторием и каталогом прогона | каждая разрушительная операция исполняется в каталоге того дерева, которое правит, и не выходит за его границы — восстановление части не трогает соседние части и корень, восстановление корня не заходит внутрь объявленных частей (свойство `read-tree -u`, закреплено сценарием). Снятие рабочего дерева отказывает `StepcastError`, если адресуемый путь лежит вне директории прогона, — ошибка в вычислении пути становится отказом, а не снесённым чужим деревом. |
| Практика спецификации репозитория настройкой, а не литералом | секция `project.spec` в `.stepcast/config.yml` (или одноимённая группа верхнего ключа `project` документа пайплайна, перекрывающая конфигурацию по каждому ключу отдельно) с тремя необязательными ключами — `dir` (каталог документов изменения; документы изменения `<слаг>` лежат в `<dir>/<слаг>/`), `rules` (путь к файлу правил их написания) и `tool` (имя инструмента спецификации, открывающее право `Bash(<tool> *)`). `dir` и `rules` — относительные пути от корня репозитория; пустая строка, строка из пробелов, абсолютный путь и путь с сегментом `..` отклоняются разбором конфигурации той же парой проверок, что и `project.check` (`.trim()` в модели, образец `\S` в публикуемой JSON Schema). `project.**` в `~/.stepcast/config.yml` отклоняется на любой глубине — не только `project.check`, как раньше, но и вложенные `project.spec.*`. Пространство подстановки `${project.*}` пополнено составными именами `spec.dir`, `spec.rules`, `spec.tool` — раскрываются при разборе документа наравне с `check`, доступны в пайплайне, файлах работ и файлах промптов; ссылка на необъявленное имя называет оба места объявления, обращение к имени вне состава называет доступные имена. Петля саморазвития (`.stepcast/pipelines/self-improve.yml`) объявляет `project.spec: { dir: openspec/changes, rules: .stepcast/prompts/spec-rules.md, tool: openspec }` рядом с `project.check` и ссылается на объявление подстановкой во всех местах, где раньше нёс литерал OpenSpec: пути контекста работ `plan`, `implement` и `review` (один глоб `${project.spec.dir}/${params.change}/**/*.md` на каталог изменения — работы не знают имён и состава документов внутри), границы `changed_only` работ `propose`, `implement` и `fix-review`, файл контекста и право `Bash(… *)` работы `propose`. Файлы работ и промпты петли (кроме нового файла `.stepcast/prompts/spec-rules.md`, куда переехали правила именно OpenSpec — включая имя документа, обновляемого по итогам реализации, и команду его пересборки) не содержат литерала «openspec», имён документов OpenSpec и имени `status.md` — репозиторий без OpenSpec переносит `.stepcast/jobs/**` и `.stepcast/prompts/**` копированием, объявляет свои `project.check` и `project.spec`, пишет свой файл правил — и петля доводит пункт очереди от `propose` до `fix-review`, не требуя правок внутри скопированного. Файл правил получают контекстом работы `propose` и `implement`. |
| Обязательная запись контекста | у записи контекста в форме объекта есть ключ `required`; при `required: true` запись, не давшая ни одного файла, роняет шаг до запуска бэкенда, называя объявленный путь. Умолчание прежнее — пустой глоб не ошибка. Требование проверяется до отсева по `context.deny` и `context_exclude` и удовлетворяется одним совпадением: неполнота набора им не проверяется. Работы `plan`, `implement` и `review` петли объявляют так глоб по каталогу изменения: перечень путей, который он заменил, ронял работу при отсутствующем документе, а глоб без совпадений отправлял бы работу планировать по пустому контексту. |
| Линт проверяет пути из объявления проекта | путь, все подстановки которого принадлежат пространству `${project.*}`, проверяется на существование наравне с литералом — опечатка в `project.spec.rules` видна `stepcast lint`, а не только отказом работы посреди прогона. Глоб пропускается независимо от происхождения. |

## Известные ограничения

**Денежный потолок под параллелизмом может немного отставать от факта.**
Проверка бюджета видит расход по завершённым попыткам; несколько работ,
упёршихся в потолок одновременно, каждая успевает потратить ещё до одной
попытки (и одного вызова судьи), прежде чем остановка их догонит, — тот же
допустимый перерасход, что и при последовательном исполнении, но кратный
числу работ, идущих в этот момент разом.

**Сводка прежней формы читается неполно.** До разбивки по попыткам
`usage.json` хранил в `attempts` их число, а длительность работы и шага не
накапливал вовсе. Такие сводки принимаются — терять из-за одного поля весь
агрегат прошлых прогонов незачем, — но разбивки по попыткам в них нет, а время
работы и шага в них нулевое. Ни то, ни другое из старого файла не
восстанавливается: показывается как есть, без досчёта.

**Денежный потолок проверяется на границе попытки, не внутри неё.** Цена
приходит от бэкенда один раз, в финальной записи попытки — денежный потолок
не может связать раньше. Допустимый перерасход — не больше цены одной попытки
(и одного вызова судьи). Подробности и оговорка о том, чем сообщённая цена
является и чем не является — в разделе «Бюджет» `pipeline-format.md`.

**Денежный потолок зависит от того, сообщает ли бэкенд цену.** Если ни одна
попытка за весь прогон цены не сообщила, объявленный `budget.cost` фактически
не применялся ни на одном уровне — прогон доводится до конца с прежним кодом
возврата, а не останавливается вслепую, но и не даёт защиты, которую как
будто обещал потолок. Частично сообщённая цена даёт частичную сумму: она
применяется по учтённой части, а число неучтённых попыток называется рядом.

**Денег в сводках прогонов, записанных до этого изменения, нет.** `usage.json`
и `status.json` старой формы не несут ни `cost_usd`, ни `cost_used_usd` — поля
читаются как отсутствующие, а не как ноль, и `stepcast usage`/`status`
показывают на их месте прочерк. Досчитать цену задним числом неоткуда: старые
записи попыток её не хранили.

**Пика в сводках и записях, записанных до этого изменения, тоже нет.** Поле
`peak_prefix_tokens` появилось вместе с показом наибольшего префикса —
записи `usage.json`/`status.json`, снятые раньше, его не несут и читаются как
отсутствующее значение, а не ноль; `stepcast usage` печатает прочерк на их
месте. Досчитать пик задним числом неоткуда: пооткликовых данных в старом
журнале нет.

**Обратный откат журнала несимметричен.** Новые записи читаются прежней
версией по-разному: `usage.json` с `peak_prefix_tokens` она просто не примет
как сводку текущей формы, и `stepcast usage` деградирует мягко — отчёт
строится по `status.json`, а внизу поясняется, что сводка не прочитана. А вот
запись попытки в `status.json` разбирается строгой схемой, и незнакомое поле
для неё — ошибка: `stepcast status` и `stepcast usage` на таком прогоне
откажут целиком. Прогоны, снятые новой версией, прежней не читаются; лечится
это только тем, чтобы не откатывать движок под уже записанным журналом.

**Развилка не переносит неотслеживаемое содержимое источника.** Каталог
работы, получающей собственное дерево при наличии нескольких потомков у
предшественника, засевается его якорем — а якорь хранит только отслеживаемое
и не игнорируемое содержимое. Установленные зависимости, кеши сборки и прочий
неотслеживаемый след предшественника в такой каталог не попадают; для линейной
цепочки (единственный потомок) это не ограничение — она делит каталог
предшественника целиком, без засева.

**Развилка требует репозитория git.** Засев каталога чужим состоянием
возможен только там, где состояние зафиксировано средствами git: внутри
репозитория это верно и для `worktree`, и для `copy` (рабочая копия `.git` не
содержит, но её состояние фиксируется базой объектов проекта). Вне репозитория
состояние фиксируется хеш-манифестом, содержимого файлов он не хранит, и
пайплайн с развилкой отклоняется до первой работы. Линейная цепочка вне git
работает: она делит каталог предшественника и в приведении не нуждается.

**Пропущенное звено цепочки вне git обрывает наследование.** Если источник
пропущен условием, наследование ищет дерево дальше по цепочке — но вне
репозитория засеять им каталог нечем, и работа начинает с исходного
состояния, а не с результата предшественника предшественника. Внутри
репозитория такого нет.

**`stepcast apply --job` на работе из цепочки может не лечь на чужое дерево.**
Ограничение работой даёт вклад именно этой работы — дифф между её `tree_before`
и последним `tree_id`. Если работа продолжала каталог предшественника, этот
дифф предполагает уже применённые вклады предшествующих работ цепочки; наложить
его в одиночку, на дерево без них, обычно означает конфликт. Это ожидаемо и не
лечится: наложение всей цепочки (без `--job`) складывает вклады по порядку и
такого не имеет.

**Переиспользование при возобновлении ограничено шириной входов.** Шаг без
объявленных `inputs` работы и без наблюдённых входов зависит от всего дерева,
и любая правка его обесценивает. Сужают инвалидацию два механизма: объявленные
`inputs` работы и наблюдённые входы, которые агентские бэкенды отдают сами, —
сохранённый по прошлому успешному исполнению перечень сужает область
независимо от того, по чему был снят отпечаток того исполнения. У пайплайна из
одних командных шагов наблюдённых входов не бывает, поэтому объявленные входы
там — единственный способ получить переиспользование. Кроме того, изменившийся
путь, произведённый самим исходным прогоном на судимом шаге или на любом из
следующих за ним, в область изменений не входит вовсе — он относится к
прогону, а не к пользователю. Пути, произведённые раньше судимого шага, из
области не вычитаются: они уже были его входом. Флаг `--from` позволяет
переиспользовать всё выше названной точки поверх любых изменений дерева, если
это физически возможно; такие изменения перечисляются в отчёте и не
восстанавливаются из якоря.

**Прогоны, записанные до сужения ключа шага, возобновляются с нуля.** Ключ
шага перешёл с хеша всего пайплайна на хеш определения одной работы: правка
файла одной работы перестала гасить остальные. Ключи прежних прогонов
считались иначе, поэтому первое возобновление такого прогона переисполнит все
шаги с причиной «изменилось определение шага, промпт или бэкенд». Определение
при этом не менялось — изменился способ его хеширования. Досчитать прежний
ключ нельзя: хеш всего пайплайна из записи шага не восстанавливается.
Единичная потеря переиспользования на прогонах, записанных раньше, — цена
того, чтобы дальше правка одной работы не обесценивала остальные.

То же самое действует на прогоны, записанные до сужения ключа до нераскрытого
определения работы: раньше ключ шага работы с отложенными подстановками
(`${run.dir}`, `${run.id}`, `${run.workspace}` и подобные) считался от
раскрытого текста, уникального для каждого прогона, и потому такой шаг никогда
не совпадал с самим собой в другом прогоне. Первое возобновление прогона,
записанного до этого изменения, переисполнит шаги таких работ по той же
причине «изменилось определение шага, промпт или бэкенд» — и по той же
причине: досчитать прежний ключ из новой формулы нельзя.

**Восстановление дерева не трогает правки пользователя.** Возобновление
восстанавливает только пути, произведённые переиспользованными шагами. Путь,
произведённый шагом и изменившийся после завершения прогона, признаётся
невалидным и переисполняется: стирать эту правку, ради которой чаще всего и
возобновляют, недопустимо.

**Состояние каталога прогона переносится вместе с переиспользованием.** Шаг
может оставить промежуточный файл не в дереве, а в каталоге прогона
(`$STEPCAST_RUN_DIR/item.json`, `${run.dir}/…`), и следующий шаг — прочитать его
оттуда же. Каталог у каждого прогона свой и создаётся пустым, поэтому
переиспользованный шаг ничего в нём не оставляет: то, что он записал, лежит в
каталоге исходного прогона. Возобновление, переиспользующее хоть один шаг,
копирует из исходного каталога всё, что не принадлежит раскладке журнала, — и
переисполняемый читатель находит файл на месте. Шаг, который тот же путь пишет
заново, перезаписывает копию прежде, чем её кто-нибудь прочитает.

Различение чисто временное, по хешам содержимого между концом прогона и
моментом возобновления, — движок не проверяет, кто именно тронул файл.
Разработчик, git-хук или фоновый форматтер дают одну и ту же метку. Обратная
сторона: если файл тронут *пока шаг ещё выполняется* — в режиме `cwd`, где
рабочая директория совпадает с рабочим деревом, ничто этому не мешает, — правка
неотличима от результата самого шага и при возобновлении может быть свободно
переиспользована вместе с ним, без предупреждения. В режимах `worktree` и
`copy` это не возникает: пока прогон идёт, дерево пользователя физически в
другом месте.

**Витрина не защищена ничем, кроме петлевого интерфейса.** `stepcast up`
слушает только `127.0.0.1` и работает исключительно на чтение, но
аутентификации у неё нет: любая страница, открытая в том же браузере, может
обратиться к `localhost` на её порт. Инструмент рассчитан на локальную
однопользовательскую машину; токен доступа и проверка `Origin` не вводились
сознательно и остаются отдельным изменением, если понадобятся.

**Витрина видит прогоны всех проектов пользователя.** Это её задача, но
следствие стоит знать: в дашборде окажутся пути и имена проектов, за которыми
пользователь мог не собираться наблюдать вместе.

**Каталог прогонов обязан лежать вне рабочего дерева.** Иначе запись журнала
сама выглядела бы изменением дерева. Проверяется до запуска первой работы.

**Судья видит только вывод шага, а не его контекст, и не имеет его прав.**
Предикат `judge` получает утверждение, задание шага, его текстовый и
структурированный вывод и результаты остальных предикатов — но не контекст,
собранный шагу, и не его политику доступа. Вызов идёт в свежей сессии со
своими (или умолчальными) бэкендом и моделью. Из этого следует, что судья не
может свериться с файлами проекта или спекой напрямую — только с тем, что шаг
сам показал в своём ответе; утверждение стоит формулировать так, чтобы его
можно было проверить по выводу шага, не заглядывая дальше.

**Выдержка о непройденной проверке усечена по `context.note_max_tokens`.** В
контекст следующей итерации попадает хвост вывода непрошедших предикатов, а не
он целиком; отброшенное начало помечается явно. Полный вывод из усечения не
теряется — он остаётся в логах шага проверки того прогона.

**Разбор `.gitignore` вне git неполон.** Поддержаны комментарии, маски,
каталоги и привязка к корню; отрицания (`!`) и вложенные `.gitignore` — нет.
Неподдержанное правило пропускается, а не толкуется наугад. В репозитории
исключениями занимается сам git, и ограничение не проявляется.

**`on_exceed: wait` ждёт только окно лимита подписки.** У ожидания два
основания: измеренное превышение `rate_limit_pct` в области с `wait`, и упор
самого бэкенда в то же окно (отказ, распознанный по конверту результата —
см. ниже). В обоих случаях прогон усыпляется до сообщённого момента сброса и
переисполняет прерванный шаг заново — без расхода попытки, но с сохранением
расхода оборванной попытки в потолках. Потолки `tokens` и `wallclock` этим
режимом не спасаются: они не сбрасываются, и упор в них останавливает прогон
при любом `on_exceed`. Суммарная длительность ожиданий за прогон ограничена
`defaults.max_wait` (умолчание — 6 часов); отсутствие сообщённого момента
сброса и момент дальше предела вырождают `wait` в `stop`, а причина называет
основание. Время ожидания не входит ни в один потолок `wallclock`.

**Классов неустранимого отказа бэкенда ровно два.** Упор в окно лимита
подписки и отказ аутентификации — больше движок не различает. Кандидат на
классификацию — только запись результата, объявившая себя ошибкой и несущая
признак ошибки бэкенда (код состояния ответа либо `terminal_reason:
"api_error"`); класс решает сначала код состояния (429 → лимит, 401/403 →
аутентификация), а тело ответа смотрится лишь тогда, когда кода нет вовсе, и
только по закрытому перечню узнаваемых формулировок. Отказ, не совпавший ни с
одним классом, остаётся обычным отказом шага: попытка повторяется по
`attempts.max`, как при любой непройденной проверке, а не по правилам
неустранимого отказа. Момент сброса окна лимита разбирается только из двух
форм — настенного времени с часовым поясом (`resets 11pm (Asia/Nicosia)`,
ближайшее будущее наступление через `Intl.DateTimeFormat`) и метки ISO 8601 со
смещением или `Z`; нераспознанная форма, неизвестный часовой пояс и
отсутствие упоминания сброса дают отказ без момента сброса, а не угаданное
время.

**Сведение зависит от собранного `dist/`.** `$STEPCAST_BIN` — точка входа
собранного движка; `merge-lanes` и `backlog settle`, как и остальные команды
петли, недоступны до `npm run build`. То же ограничение, что и у остальной
бухгалтерии очереди: пункт, зависший в `in_progress` дольше порога давности,
снова свободен.

*Заведено изменением `builtin-merge-lanes`.*

**Отказ на коммите оставляет пункт `done` без коммита.** Правка очереди идёт
до `git commit` этой же дорожки — так улучшение и его бухгалтерия остаются
одним событием, которое `git revert` снимает целиком, — но если сам `git
commit` откажет (например, чужой `pre-commit`-хук), команда не откатывает уже
проставленный `done`: наложенное и правка очереди остаются на дереве,
разбирает человек. Откат после зелёной проверки уничтожил бы результат
работы дорожки.

*Заведено изменением `builtin-merge-lanes`.*

**Обход останавливается на первой же красной проверке.** `verify` дорожки
прошла на её собственном изолированном дереве, но `merge-lanes` гоняет
объявленную проверку уже на дереве, объединённом с прежде сведёнными
дорожками, — красный исход там означает конфликт между дорожками, а не то,
что дорожка сама по себе плоха. Сведение останавливается, дерево
откатывается к коммиту, записанному до наложения этой дорожки, а
недостигнутые дорожки перечня получают `failed` с причиной остановки; ключа,
разрешающего продолжать обход после красной проверки, нет.

*Заведено изменением `builtin-merge-lanes`.*

**Повтор между сообщениями общей сессии не склеивается.** При `session: shared` унаследованный контекст уходит в первое сообщение, а собственный контекст следующих шагов сессии собирается отдельным вызовом `assembleContext`, которому уже отправленные записи не видны. Файл, объявленный шагом сессии повторно, будет отправлен второй раз.

*Заведено изменением `context-dedup`.*

**Витрина не показывает уровни объявления.** Разрез по уровням в витрине строится из `context.json` по полю `origin`, поэтому склеенная запись видна там целиком на своём уровне-источнике, а `declared_in` не отображается: уровень, объявивший файл повторно, выглядит в витрине пустым. В `stepcast context` и в самом `context.json` уровни объявления названы.

*Заведено изменением `context-dedup`.*

**`context.json` с `declared_in` не читается движком прежней версии.** Схема отчёта строгая: поле добавлено обратной совместимостью снизу вверх (запись без него по-прежнему читается как объявленная однажды), но откат движка под уже записанным таким журналом схема отклонит — та же оговорка, что и у `lane` в `status.json`.

*Заведено изменением `context-dedup`.*

**Эффект жёсткого режима на живом бэкенде не проверен сквозным прогоном.**
Тесты фиксируют состав флагов запуска (`--setting-sources project`,
`--permission-mode manual`), а семантика самих флагов снята разведкой CLI до
реализации (см. `design.md`). Прогон двух шагов с одинаковым списком прав и
разным `enforce` при разрешающих настройках машины не выполнялся: он требует
временной правки `~/.claude/settings.json` — общего ресурса машины. То есть
утверждение «правило пользовательского уровня на шаг с `enforce: strict`
больше не действует» опирается на поведение флагов бэкенда, а не на измерение
внутри stepcast.

*Заведено изменением `job-permission-mode`.*

**Жёсткий режим отсекает не только права.** В `enforce: strict` бэкенд не
читает настройки уровня пользователя целиком, а не только правила доступа —
вместе с ними перестают действовать пользовательский `CLAUDE.md`, стили
вывода и прочие настройки машины. Для агентского шага, чей промпт собирает
движок, это способствует воспроизводимости, но поведение шага может
неожиданно разойтись с тем, что разработчик привык видеть локально.

*Заведено изменением `job-permission-mode`.*

**Синтаксис `allow`/`deny` остаётся бэкендовым.** Движок не разбирает и не
проверяет записи политики — опечатка в шаблоне (`Bash(npm*)` вместо
`Bash(npm *)`) в жёстком режиме превращается в неожиданный отказ, а не в
разрешение; причина видна в журнале как отказ в разрешении.

*Заведено изменением `job-permission-mode`.*

**Смена состава обесценивает возобновление целиком.** Добавление или удаление
каталога в `project.nested_repos` делает якоря прошлого прогона несравнимыми с
сегодняшними: `resume` исполняет пайплайн с начала, а причина в отчёте
называет оба состава — сегодняшний и записанный в манифесте исходного
прогона.

*Заведено изменением `nested-repo-anchor`.*

**Режим `copy` при объявленном составе остаётся отклонённым.** Копия `.git`
не содержит, и объявленная часть в ней была бы каталогом без репозитория —
снимать с неё составное состояние нечем. Отклонение — своим сообщением,
отдельным от прочих причин отказа режима.

*Заведено изменением `nested-repo-isolation`.*

**`stepcast apply` и `merge-lanes` недоступны составному прогону.**
Изолированный режим делает их достижимыми для составного прогона впервые, но
наложения через границу репозиториев в движке нет: `diff.patch` составного
прогона склеен из патчей разных баз объектов, а `git apply` в корне применил
бы его к чужому индексу. Отказ называет составной способ фиксации и отдельное
изменение `merge-lanes-per-repo`; итог `stepcast run` для составного прогона
печатает пути рабочих деревьев, но не предлагает команду наложения. Сведение
отказывает до обхода дорожек и не помечает их пункты очереди провалившимися:
пункт остаётся невзятым до захода, где наложение по репозиториям появится.

*Заведено изменением `nested-repo-isolation`.*

**Каталог прогона, снесённый мимо движка, оставляет записи в чужих репозиториях.** `rm -rf` каталога прогона в обход `stepcast gc` не снимает
учётные записи заведённых рабочих деревьев — ни корневых, ни частей: движок
узнаёт о заведённом только через собственную уборку. Записи остаются в
`.git/worktrees` соответствующих репозиториев до `git worktree prune`,
который человек делает у себя сам, — то же поведение, что и у корневого
worktree до этого изменения.

*Заведено изменением `nested-repo-isolation`.*

**Правки самой петли действуют только со следующего прогона.** Границы правок, пути контекста и объявление `project.spec`, раскрытые в `.stepcast/jobs/**` и `.stepcast/pipelines/self-improve.yml`, фиксируются вместе с пайплайном в начале захода — заход, вносящий правку в эти файлы, работает по прежней, ещё не раскрытой версии. Единственный способ увидеть ошибку подстановки до следующего прогона — `stepcast lint .stepcast/pipelines/self-improve.yml` вручную; сам прогон её не покажет.

*Заведено изменением `openspec-follows-repo`.*

**Смежность дорожек объявляет человек.** Движок не выводит `lane` из `needs`
или `workspace.inherit` — работа несёт дорожку, только если она объявлена
явно на месте подключения. Пропущенная в разводке пайплайна работа тихо
остаётся вне группировки расхода и вне `apply --lane`.

*Заведено изменением `pipeline-lanes`.*

**Журнал с `lane` не читается движком прежней версии.** `JobRecordSchema`
строгая: `status.json`, где у работы записано поле `lane`, отклоняется
разбором, не знающим об этом поле, — в обратную сторону совместимость есть
(журнал прежней формы, без `lane`, читается этой версией как работы без
дорожки), а в эту — нет.

*Заведено изменением `pipeline-lanes`.*

**Бухгалтерия очереди зависит от собранного `dist/`.** `finish` идёт через
собранный движок, а не через отдельный скрипт без сборки — сломанная сборка
могла бы помешать проставить исход именно тогда, когда он нужнее всего.
Смягчение то же, что было в очереди с самого начала: пункт, оставшийся
`in_progress` дольше порога давности, снова свободен, и следующий заход
берёт его сам — отказ бухгалтерии становится задержкой, а не потерей пункта.

*Заведено изменением `portable-backlog-format`.*

**Параллельные `pick` не исключают друг друга.** Два одновременных прогона
петли на одной очереди могут прочитать файл до того, как другой его перепишет,
и раздать один и тот же пункт дважды. Блокировки файла нет; сегодня заход у
петли ровно один, и до второго это не проверить.

*Заведено изменением `portable-backlog-format`.*

**Преамбула `backlog.md` этого репозитория продолжает дублировать формат.**
Нормативное описание — `docs/backlog.md`, но вводный текст самого файла
очереди (таблица полей, правило группы, правило шести часов) не сокращён:
файл вне границы правок агентских работ петли, а `pick` переписывает его в
том же прогоне, что сделало бы правку диффом поверх этого игрой без нужды.
Расхождение не остаётся незамеченным — тест движка разбирает `backlog.md`
этого репозитория как есть и падает при несовпадении с моделью.

*Заведено изменением `portable-backlog-format`.*

**У `pick` нет прежних форм `--now`, `--out` и голого объекта одного пункта.**
Часы теперь только внутренние (текущий момент проставляется командой, а не
приходит ключом — он был нужен исключительно старым тестам скрипта, которые
переписаны на прямые вызовы ядра); печать в отдельный файл через `--out`
снята — тот же результат печатается в стандартный вывод, и вызывающему
достаточно его перенаправить; `--slots` без числа теперь тоже даёт массив
(из одной записи), а не одиночный объект. Внешнего вызывающего этих форм в
репозитории не было — `--lanes` в `slots.yml`, `finish` в двух скриптах петли,
и обе замены сделаны в этом же изменении.

*Заведено изменением `portable-backlog-format`.*

**`stepcast resume` ленту не печатает.** Наблюдение `onEvent` в `RunOptions`
общее для `run` и `resume`, но `resume` его не подключает — у команды своя
преамбула с планом переиспользования, и место ленты в ней осталось за
пределами этого изменения.

*Заведено изменением `run-progress-output`.*

**Перечень печатаемых видов закрыт и не расширяется автоматически.** Новый вид
события, добавленный в движок, в ленту не попадёт, пока для него явно не
описано правило печати в `src/cli/progress.ts` — по устройству, а не по
недосмотру: сырой JSON нового события в терминале хуже, чем его отсутствие.

*Заведено изменением `run-progress-output`.*

**Неудача наблюдения самому наблюдателю не доставляется.** `bookkeeping.failed`,
порождённая отказом `onEvent`, идёт в файл событий, но `onEvent` на ней не
зовётся: доставка либо зациклила бы отказ, либо повторила бы его в терминале.
Единственный вид события, который наблюдатель видит не всегда.

*Заведено изменением `run-progress-output`.*

**Служебные записи остаются только в `events.ndjson`.** `context.denied`,
`context.downgraded`, `context.note_truncated`, `env.denied`,
`backend.unparsed`, `backend.degraded`, `bookkeeping.failed`, `step.reused`,
`tree.restored`, `workspace.inherited`, `run_dir.carried`,
`budget.cost_unreported`, `resume.note_undelivered` — разбор постфактум, а не
ход, и в ленту не идут ни при каком режиме вывода.

*Заведено изменением `run-progress-output`.*

**На бэкенде без поддержки сессий унаследованный контекст не переотправляется — это дефект, а не устройство.** Отметка «контекст сессии уже отправлен» рассуждает так, будто бэкенд помнит предыдущие сообщения сессии, — а бэкенд без `sessions` в возможностях адаптера этого не делает: каждый его запуск получает лишь собственный промпт нового процесса, без истории. Движок не подстраивается под это различие: `session: shared` для такого бэкенда исполняется как `per_step` молча для промпта и с одним предупреждением `backend.degraded` на бэкенд в журнале, а второй шаг сессии на деле остаётся без свода правил пайплайна и работы, которые агент уже должен был прочитать в первом сообщении. Направление починки известно и невелико: отметка обязана спрашивать возможности адаптера и на деградировавшем бэкенде вести себя как при `per_step`. Здесь она не сделана намеренно — изменение проверяет существующее правило и движок не трогает; пункт очереди на починку ставится отдельно.

*Заведено изменением `session-context-test`.*

**`context.json` шага с несколькими попытками показывает состав только последней.** Запись — одна на шаг и перезаписывается каждой попыткой, тогда как промпт каждой попытки сохраняется отдельным файлом (`prompt.txt`, `prompt.2.txt`, …). Разбор состава по попытке, кроме последней, поэтому недоступен: узнать, что́ именно ушло агенту на первой попытке шага общей сессии, можно только по тексту `prompt.txt`, а не по `context.json`.

*Заведено изменением `session-context-test`.*

**Содержимое, накопленное до введения фрагментов, атрибуции не несёт.** Блоки
известных ограничений и строки таблиц, перенесённые из прежнего
`docs/status.md` в `docs/status.base.md` при введении сборки, не подписаны
изменением — они принадлежат базе, а не какому-то одному фрагменту, и
атрибуция `*Заведено изменением ...*` у них не появляется. Это относится
только к содержимому на момент переноса; всё, что вносят фрагменты новых
изменений, подписывается как обычно.

*Заведено изменением `status-doc-fragments`.*

**Сведённый объединением `docs/status.md` до пересборки может быть неверен.**
Слияние двух веток, каждая со своим фрагментом, не конфликтует —
`.gitattributes` объявляет файл сводимым объединением, — но результат
объединения может содержать не ту комбинацию строк и блоков, что даёт
`scripts/status.mjs`. Расхождение ловит `npm run status:check` в составе
`npm run check`; правильный документ восстанавливает `npm run status:build`.

*Заведено изменением `status-doc-fragments`.*

**Отрисовка экранов действий не покрыта тестами.** Браузерного окружения в
проекте по-прежнему нет. Чистые правила вынесены из компонентов в общие с
демоном модули и покрыты обычными тестами — разбор адресов и перечень экранов
(`src/ui/routes.ts`, `test/ui-routes.test.ts`), форматирование величин
(`src/ui/format.ts`, `test/ui-format.test.ts`), — а сама отрисовка настроек и
уборки проверена человеком по чек-листу (`tasks.md`, задача 8.2).

*Заведено изменением `ui-actions`.*

**Настройки правят только глобальный файл.** Витрина охватывает все проекты
сразу, поэтому пишет в `~/.stepcast/config.yml`, а проектный слой в чтении
отключён (`src/ui/settings.ts`). Проектную настройку с экрана не поправить —
для неё остаётся файл `.stepcast/config.yml` в самом проекте.

*Заведено изменением `ui-actions`.*

**Отбор к уборке знает два признака.** `abandoned` и `failed` — то, что
принимает `GET /api/runs`. Отобрать, скажем, все убранные (`swept`) или все
успешные прогоны с экрана нельзя, хотя срок и проект применимы к любым.

*Заведено изменением `ui-actions`.*

**Прогон, чей манифест не читается, находит пайплайн только по имени.**
Первый экран связывает прогон с пайплайном по файлу, которым тот был запущен
(`RunOverview.pipelineFile` против `PipelineView.file`, склейка — в
`src/ui/grouping.ts`). Файл берётся из манифеста прогона; если манифест
повреждён, остаётся имя из состояния, а оно неоднозначно: два файла одного
проекта с одинаковым `name` дадут такому прогону первый попавшийся из них.
Прогоны с целым манифестом это не задевает.

*Заведено изменением `ui-navigation`.*

**Инвентарь пайплайнов не приходит потоком.** `GET /api/pipelines` читает
файлы проектов заново на каждый запрос; демон не следит за ними
наблюдателем. Список перечитывается при входе на первый экран, но новый
или изменённый файл пайплайна, появившийся при уже открытой странице, будет
виден только после возврата на экран, а не сам собой. Прогоны под уже
показанными пайплайнами при этом остаются живыми.

*Заведено изменением `ui-navigation`.*

**Отрисовка витрины не покрыта тестами.** В проекте нет браузерного
окружения для автоматических тестов; исходники `ui/` проверяются типизацией
(`typecheck:ui`) и линтом, входящими в `npm run check`, и тем, что они
собираются. Смысловые правила экранов вынесены из компонентов в общие с
демоном модули именно по этой причине и покрыты обычными тестами: разбор
адресов — `src/ui/routes.ts` (`test/ui-routes.test.ts`), склейка прогонов с
пайплайнами — `src/ui/grouping.ts` (`test/ui-grouping.test.ts`). Без теста
остаётся сама отрисовка; сценарии спеки про экраны проверены человеком по
чек-листу (`tasks.md`, задача 7), а не автоматическим тестом на каждый
прогон `npm run check`.

*Заведено изменением `ui-navigation`.*

## Примечания

`prompt.txt` содержит ту часть запроса, которую сформировал stepcast. Claude Code
добавляет к ней свой системный промпт, `CLAUDE.md`, автопамять, хуки и
плагины; их состав пишется в `step.json` из события инициализации, но
изменение `CLAUDE.md` шаги не инвалидирует.

Windows не проверяется. Убийство дерева процессов реализовано через группу
процессов POSIX.

Пример `examples/target-state/` по-прежнему не проходит `lint`, но уже по
другой причине: подстановка в числовые поля работает, а пример ссылается на
файл контекста `AGENTS.md`, которого в этом репозитории нет. Правка примера
осталась за пределами этого изменения.
