# Что реализовано

Срезы `add-minimal-run-engine` и `add-worktree-anchor-and-resume`. Остальные
документы описывают целевое состояние формата целиком; здесь — граница между
тем, что работает, и тем, что пока отклоняется с внятной ошибкой.

Нереализованное не игнорируется молча: линт или движок отказывают и называют
причину. Тихая деградация превратила бы объявленное поведение в ложь.

`docs/status.md` — собранный документ: он получается склейкой этой базы с
фрагментами изменений `openspec/changes/*/status.md` скриптом
`scripts/status.mjs` и правится не руками, а правкой базы (для содержимого,
накопленного до введения фрагментов) либо фрагмента своего изменения.
Пересборка — `npm run status:build`.

## Работает

| | |
|---|---|
| Команды | `run`, `lint`, `status`, `logs` (в том числе `--follow`), `usage`, `config`, `gc`, `init`, `context`, `up`/`down` |
| Формат | пайплайн и файлы работ, `uses`/`with`, подстановки (включая числовые поля — `concurrency`, `until.max_iterations`, `attempts.max`, `budget.rate_limit_pct`, `exit_code`), умолчания, `pipeline.lock.yml` |
| Граф | `needs`, `on`, `if`, `needs: all`, `fail_fast`, отмена по сигналу |
| Шаги | `run` (argv и строка) и `agent` (Claude Code), таймаут, детектор тишины, попытки с эскалацией |
| Сессии | `shared`, `per_step`, именованные псевдонимы; деградация при отсутствии поддержки |
| Контекст | три уровня, блок выходов предшественников, `inline`/`reference`/`auto`, предел с понижением |
| Проверки | `exit_code`, `file_exists`, `schema`, `matches`, `not_matches`, `cmd`, `judge` (оценка агентом-судьёй) |
| Выход работы | `output.from`, публикация в `artifacts/`, `${jobs.<id>.output.*}` |
| Журнал | манифест, состояние, события, логи, промпты, контекст, расход |
| Бюджет | три уровня — `tokens`, `cost`, `wallclock`, `rate_limit_pct` — непрерывный учёт трафика прогона (сумма по всем обращениям к API, не объём контекста), останов по превышению; `on_exceed: wait` усыпляет прогон до сброса окна (по превышению `rate_limit_pct` или по отказу бэкенда — на `cost` не действует); `limits.cost` в конфигурации и проверка `stepcast lint`; см. разграничение трёх пределов в разделе «Бюджет» `pipeline-format.md` |
| Отказ бэкенда | упор в окно лимита подписки и отказ аутентификации распознаются по конверту результата (код состояния, при его отсутствии — закрытый перечень формулировок); первый ведёт себя как второе основание для `on_exceed: wait` (код возврата 3 при остановке), второй прекращает прогон независимо от `fail_fast` с кодом возврата 4; событие `backend.refused` и причина шага видны без чтения `stdout.log` |
| Рабочая директория | `cwd`, `worktree`, `copy`; наследование дерева зависимой работой (`workspace.inherit`), продолжение цепочки в одном каталоге, засев развилки; `stepcast apply` для возврата результата |
| Якорь дерева | `tree_id` после каждого шага: `git write-tree` в репозитории — в том числе для рабочей копии, лежащей вне его и пользующейся его базой объектов, — хеш-манифест вне репозитория |
| Возобновление | `stepcast resume` с `--from`, `--set`, `--dry-run`; `stepcast status --explain` |
| Сравнение прогонов | `stepcast diff` по ключам шагов, промптам, контексту и деревьям |
| Цикл работы | `until` с `max_iterations`, раскладка `iter-N`, предикат `changed_only` |
| Витрина | `stepcast up` — демон, наблюдающий за прогонами всех проектов; живое обновление, вход и выход работ, просмотр файлов журнала, расход прогона, работы и шага; `stepcast down` |
| Показ расхода | `stepcast usage <run-id>` и `stepcast status` — работы, шаги, попытки с бэкендом, моделью, токенами, кешем, временем и денежной ценой на всех уровнях, и наибольшим префиксом одного обращения («пик») на уровнях попытки и шага рядом со списанным трафиком; строится из `status.json` и `usage.json`, работает на убранном и на идущем прогоне; несообщённое (в том числе цена и пик) помечается, а не обнуляется |
| Петля саморазвития | `.stepcast/pipelines/self-improve.yml` — движок улучшает сам себя по очереди `backlog.md`, коммит на улучшение; `backlog.mjs pick --slots N` выдаёт до N пунктов за проход, по одному на действующую группу (`group` пункта или его слаг) |
| Параллелизм | независимые работы идут одновременно в пределах `Math.min(pipeline.concurrency, limits.concurrency)`; `backends.<имя>.concurrency` — отдельный предел на одновременные вызовы бэкенда, общий на прогон; `fail_fast` и отмена дожидаются уже идущих работ, не обрывая их; `stepcast lint` предупреждает о ссылке `if` на работу вне зависимостей при `concurrency` больше единицы |
| Жёсткий режим применения прав агента | `permissions.enforce: strict` — в конфигурации бэкенда, в работе и в шаге — делает объявленный список `allow` границей, а не пожеланием. Списки берутся у ближайшего уровня целиком, а сам режим — у ближайшего уровня, который его назвал: блок `permissions` без `enforce` базовый режим бэкенда не снимает, ослабление объявляется явно (`enforce: inherit`). Адаптер Claude в этом режиме отсекает настройки бэкенда вне репозитория (`--setting-sources project`) и передаёт режим, отклоняющий неназванное (`--permission-mode manual`), если шаг не назвал свой запрещающий режим явно. Умолчание `inherit` сохраняет прежнее поведение без изменений. Умение бэкенда применять жёсткий режим — объявленная возможность адаптера (`strict_permissions` в конфигурации, у Claude — включена по умолчанию); бэкенд без неё и `enforce: strict` рядом с разрешающим режимом бэкенда (`bypassPermissions` и подобные) отклоняются `stepcast lint` до старта прогона, а прогон в обход линта останавливается сам, до первого шага, — деградации молча нет. Отказ бэкенда в разрешении на вызов инструмента виден в ленте и в журнале (`permission.denied`) и посчитан в записи попытки — сам по себе он не проваливает шаг. Работы петли (`propose`, `plan`, `implement`, `review`, `fix-review`) переведены на `enforce: strict`. |
| Ссылка на несуществующую или недостижимую работу | `stepcast lint` отклоняет ошибкой обращение к работе, идентификатора которой в графе пайплайна нет, — подстановку `${jobs.<id>...}` (в теле пайплайна, `with`, файле работы или файле промпта, подключённом через `prompt: file:`) и `jobs.<id>` в `if` — независимо от `concurrency` и от `needs: all`; подсказка перечисляет похожие идентификаторы работ (по префиксу до дефиса), если они есть. Подстановку `${jobs.<id>.output.*}`, называющую работу, которая в графе есть, но не входит в число предшественниц ссылающейся — прямых или транзитивных, — тоже отклоняет ошибкой независимо от `concurrency`, кроме `needs: all` и ссылки работы на собственный выход. Диагностика подстановки из файла промпта называет путь к этому файлу и позицию выражения в нём (строку и столбец); подстановки, найденные при раскрытии файла промпта, записываются в карту подстановок раскрытого пайплайна под тем же путём поля, что и подстановки промпта, объявленного в документе |
| Дорожки (`lane`) | метка обвязки на месте подключения работы, слаг в kebab-case, запрещена внутри файла работы; переносится в `pipeline.lock.yml` и в запись работы `status.json`; на порядок исполнения графа не влияет |
| Группировка расхода по дорожкам | `stepcast usage` печатает строку итога дорожки над строками её работ, с той же пометкой прочерком вместо нуля для несообщённой величины; прогон без объявленных дорожек не меняется |
| `stepcast apply --lane` | накладывает изолированные работы дорожки одним диффом, в порядке графа; взаимоисключимо с `--job`; дорожка без якорей — «накладывать нечего» и код `0` |
| Структурированный выход командного шага | `run`-шаг с объявленным `output_schema` разбирает `stdout` как один JSON-документ и публикует его тем же путём, что и агентский шаг — `output.from`, предикат `schema`; неразбираемый вывод — отказ попытки, подчинённый `attempts.max` |
| `STEPCAST_BIN` | путь к точке входа исполняющего процесса в инжектируемых переменных шага — не переопределяется объявленным `env` |
| Петля с параллельными дорожками | `.stepcast/pipelines/self-improve.yml` ведёт до двух пунктов очереди одновременно, по дорожке на каждый (`workspace.mode: worktree`, `concurrency: 2`); `backlog.mjs pick --lanes a,b` раздаёт слоты одной записью файла; `scripts/merge-lanes.mjs` сводит зелёные дорожки по очереди, проверяя каждую свежим `npm run check` перед коммитом; `scripts/finalize.mjs` проставляет `failed` пунктам, чей исход не проставлен, и коммитов не создаёт |
| Наблюдение за потоком событий (`run-journal`) | `RunJournal.create` принимает необязательный `onEvent`, вызываемый после того, как событие уже дописано в `events.ndjson`, тем же составом и в том же порядке; исключение наблюдателя гасится и превращается в `bookkeeping.failed`, статусов не меняя; наблюдателю рядом с событием передаётся снимок накопленного расхода прогона (токены, цена, прошедшее время, число попыток с несообщённой ценой) — цена отсутствует, а не равна нулю, если её не сообщила ни одна попытка |
| Отказ наблюдателя ограничен | три неудачи подряд отключают наблюдение до конца прогона (последняя `bookkeeping.failed` называет отключение), удачная доставка счёт обнуляет — закрытый поток вывода (`stepcast run | head`) иначе удваивал бы `events.ndjson` жалобами на печать |
| Свободный текст в ленте обезврежен | деталь события (вывод команды предиката, сообщение отказа бэкенда, причина исхода) сводится к одной строке — управляющие последовательности сняты, переводы строк заменены пробелами, хвост длиннее 200 знаков обрезан; полный текст остаётся в журнале и файлах шага |
| Величины бюджета в единицах измерения | события `budget.warning`/`budget.exceeded` несут `dimension`, и лента печатает деньги деньгами, время длительностью, окно лимитов процентами, а не голой дробью, читаемой как токены |
| `RunOptions.onEvent` | `runPipeline` собирает снимок из `UsageAccumulator` теми же вызовами, что и блок `budget` состояния прогона, и передаёт его наблюдателю; событие `run.started`, случившееся раньше, чем накопитель расхода создан, доставляется с нулевым снимком, а не падением |
| Лента хода команды `run` | строка на печатаемое событие, по мере его хода, а не после `run.finished`; закрытый перечень видов (начало/исход прогона, начало/исход/отказ работы, начало/исход шага с попыткой, начало/исход итерации, тишина, провал предиката, бюджетные предупреждение/превышение/сон/пробуждение, отказ бэкенда); строка — время от старта прогона (`ч:мм:сс`, посчитанное по меткам времени событий), адрес (`работа` или `работа/шаг`, у событий прогона — «прогон»), существо события; ни отступов, ни цвета, ни управляющих последовательностей ни при каком выводе |
| Расход в строке исхода шага | накопленные токены, цена и время прогона через `formatTokens`/`formatMoney`/`formatDuration`, прочерк вместо нуля на месте несообщённой цены, пометка числа неучтённых попыток при частично сообщённой |
| Ранний идентификатор | `run` печатает идентификатор прогона и путь к каталогу журнала первыми строками ленты, по `run.started`, — годны для `logs`/`status`/`usage`/`resume`, пока прогон ещё идёт |
| `--quiet` | подавляет ленту целиком (наблюдатель не подключается вовсе), оставляя печататься итог, предупреждение о неприменённом денежном потолке, список рабочих деревьев и диагностику отказов; код возврата от ключа не зависит |
| Показ реализации | `docs/status.md` — собранный документ; `scripts/status.mjs --write`/`--check` складывает его из `docs/status.base.md` и фрагментов `openspec/changes/*/status.md`, а `npm run check` ловит расхождение |

## Известные ограничения

**Денежный потолок под параллелизмом может немного отставать от факта.**
Проверка бюджета видит расход по завершённым попыткам; несколько работ,
упёршихся в потолок одновременно, каждая успевает потратить ещё до одной
попытки (и одного вызова судьи), прежде чем остановка их догонит, — тот же
допустимый перерасход, что и при последовательном исполнении, но кратный
числу работ, идущих в этот момент разом.

**Сводка прежней формы читается неполно.** До разбивки по попыткам
`usage.json` хранил в `attempts` их число, а длительность работы и шага не
накапливал вовсе. Такие сводки принимаются — терять из-за одного поля весь
агрегат прошлых прогонов незачем, — но разбивки по попыткам в них нет, а время
работы и шага в них нулевое. Ни то, ни другое из старого файла не
восстанавливается: показывается как есть, без досчёта.

**Денежный потолок проверяется на границе попытки, не внутри неё.** Цена
приходит от бэкенда один раз, в финальной записи попытки — денежный потолок
не может связать раньше. Допустимый перерасход — не больше цены одной попытки
(и одного вызова судьи). Подробности и оговорка о том, чем сообщённая цена
является и чем не является — в разделе «Бюджет» `pipeline-format.md`.

**Денежный потолок зависит от того, сообщает ли бэкенд цену.** Если ни одна
попытка за весь прогон цены не сообщила, объявленный `budget.cost` фактически
не применялся ни на одном уровне — прогон доводится до конца с прежним кодом
возврата, а не останавливается вслепую, но и не даёт защиты, которую как
будто обещал потолок. Частично сообщённая цена даёт частичную сумму: она
применяется по учтённой части, а число неучтённых попыток называется рядом.

**Денег в сводках прогонов, записанных до этого изменения, нет.** `usage.json`
и `status.json` старой формы не несут ни `cost_usd`, ни `cost_used_usd` — поля
читаются как отсутствующие, а не как ноль, и `stepcast usage`/`status`
показывают на их месте прочерк. Досчитать цену задним числом неоткуда: старые
записи попыток её не хранили.

**Пика в сводках и записях, записанных до этого изменения, тоже нет.** Поле
`peak_prefix_tokens` появилось вместе с показом наибольшего префикса —
записи `usage.json`/`status.json`, снятые раньше, его не несут и читаются как
отсутствующее значение, а не ноль; `stepcast usage` печатает прочерк на их
месте. Досчитать пик задним числом неоткуда: пооткликовых данных в старом
журнале нет.

**Обратный откат журнала несимметричен.** Новые записи читаются прежней
версией по-разному: `usage.json` с `peak_prefix_tokens` она просто не примет
как сводку текущей формы, и `stepcast usage` деградирует мягко — отчёт
строится по `status.json`, а внизу поясняется, что сводка не прочитана. А вот
запись попытки в `status.json` разбирается строгой схемой, и незнакомое поле
для неё — ошибка: `stepcast status` и `stepcast usage` на таком прогоне
откажут целиком. Прогоны, снятые новой версией, прежней не читаются; лечится
это только тем, чтобы не откатывать движок под уже записанным журналом.

**Якорь снимается с одного репозитория.** Содержимое вложенных репозиториев
git в отпечаток входов не входит: внешний репозиторий их, как правило,
игнорирует, а `git write-tree` не заглядывает внутрь. Практические следствия
для дерева с вложенными репозиториями: `resume` может переиспользовать шаг,
чей код на самом деле изменился, `changed_only` проходит всегда, `diff.patch`
пуст. Проверка сознательно не вводится — пайплайн запускается из корня одного
репозитория, и запуск иначе остаётся ответственностью запускающего. Снимется
составным якорем в отдельном изменении.

**Развилка не переносит неотслеживаемое содержимое источника.** Каталог
работы, получающей собственное дерево при наличии нескольких потомков у
предшественника, засевается его якорем — а якорь хранит только отслеживаемое
и не игнорируемое содержимое. Установленные зависимости, кеши сборки и прочий
неотслеживаемый след предшественника в такой каталог не попадают; для линейной
цепочки (единственный потомок) это не ограничение — она делит каталог
предшественника целиком, без засева.

**Развилка требует репозитория git.** Засев каталога чужим состоянием
возможен только там, где состояние зафиксировано средствами git: внутри
репозитория это верно и для `worktree`, и для `copy` (рабочая копия `.git` не
содержит, но её состояние фиксируется базой объектов проекта). Вне репозитория
состояние фиксируется хеш-манифестом, содержимого файлов он не хранит, и
пайплайн с развилкой отклоняется до первой работы. Линейная цепочка вне git
работает: она делит каталог предшественника и в приведении не нуждается.

**Пропущенное звено цепочки вне git обрывает наследование.** Если источник
пропущен условием, наследование ищет дерево дальше по цепочке — но вне
репозитория засеять им каталог нечем, и работа начинает с исходного
состояния, а не с результата предшественника предшественника. Внутри
репозитория такого нет.

**`stepcast apply --job` на работе из цепочки может не лечь на чужое дерево.**
Ограничение работой даёт вклад именно этой работы — дифф между её `tree_before`
и последним `tree_id`. Если работа продолжала каталог предшественника, этот
дифф предполагает уже применённые вклады предшествующих работ цепочки; наложить
его в одиночку, на дерево без них, обычно означает конфликт. Это ожидаемо и не
лечится: наложение всей цепочки (без `--job`) складывает вклады по порядку и
такого не имеет.

**Переиспользование при возобновлении ограничено шириной входов.** Шаг без
объявленных `inputs` работы и без наблюдённых входов зависит от всего дерева,
и любая правка его обесценивает. Сужают инвалидацию два механизма: объявленные
`inputs` работы и наблюдённые входы, которые агентские бэкенды отдают сами, —
сохранённый по прошлому успешному исполнению перечень сужает область
независимо от того, по чему был снят отпечаток того исполнения. У пайплайна из
одних командных шагов наблюдённых входов не бывает, поэтому объявленные входы
там — единственный способ получить переиспользование. Кроме того, изменившийся
путь, произведённый самим исходным прогоном на судимом шаге или на любом из
следующих за ним, в область изменений не входит вовсе — он относится к
прогону, а не к пользователю. Пути, произведённые раньше судимого шага, из
области не вычитаются: они уже были его входом. Флаг `--from` позволяет
переиспользовать всё выше названной точки поверх любых изменений дерева, если
это физически возможно; такие изменения перечисляются в отчёте и не
восстанавливаются из якоря.

**Прогоны, записанные до сужения ключа шага, возобновляются с нуля.** Ключ
шага перешёл с хеша всего пайплайна на хеш определения одной работы: правка
файла одной работы перестала гасить остальные. Ключи прежних прогонов
считались иначе, поэтому первое возобновление такого прогона переисполнит все
шаги с причиной «изменилось определение шага, промпт или бэкенд». Определение
при этом не менялось — изменился способ его хеширования. Досчитать прежний
ключ нельзя: хеш всего пайплайна из записи шага не восстанавливается.
Единичная потеря переиспользования на прогонах, записанных раньше, — цена
того, чтобы дальше правка одной работы не обесценивала остальные.

То же самое действует на прогоны, записанные до сужения ключа до нераскрытого
определения работы: раньше ключ шага работы с отложенными подстановками
(`${run.dir}`, `${run.id}`, `${run.workspace}` и подобные) считался от
раскрытого текста, уникального для каждого прогона, и потому такой шаг никогда
не совпадал с самим собой в другом прогоне. Первое возобновление прогона,
записанного до этого изменения, переисполнит шаги таких работ по той же
причине «изменилось определение шага, промпт или бэкенд» — и по той же
причине: досчитать прежний ключ из новой формулы нельзя.

**Восстановление дерева не трогает правки пользователя.** Возобновление
восстанавливает только пути, произведённые переиспользованными шагами. Путь,
произведённый шагом и изменившийся после завершения прогона, признаётся
невалидным и переисполняется: стирать эту правку, ради которой чаще всего и
возобновляют, недопустимо.

**Состояние каталога прогона переносится вместе с переиспользованием.** Шаг
может оставить промежуточный файл не в дереве, а в каталоге прогона
(`$STEPCAST_RUN_DIR/item.json`, `${run.dir}/…`), и следующий шаг — прочитать его
оттуда же. Каталог у каждого прогона свой и создаётся пустым, поэтому
переиспользованный шаг ничего в нём не оставляет: то, что он записал, лежит в
каталоге исходного прогона. Возобновление, переиспользующее хоть один шаг,
копирует из исходного каталога всё, что не принадлежит раскладке журнала, — и
переисполняемый читатель находит файл на месте. Шаг, который тот же путь пишет
заново, перезаписывает копию прежде, чем её кто-нибудь прочитает.

Различение чисто временное, по хешам содержимого между концом прогона и
моментом возобновления, — движок не проверяет, кто именно тронул файл.
Разработчик, git-хук или фоновый форматтер дают одну и ту же метку. Обратная
сторона: если файл тронут *пока шаг ещё выполняется* — в режиме `cwd`, где
рабочая директория совпадает с рабочим деревом, ничто этому не мешает, — правка
неотличима от результата самого шага и при возобновлении может быть свободно
переиспользована вместе с ним, без предупреждения. В режимах `worktree` и
`copy` это не возникает: пока прогон идёт, дерево пользователя физически в
другом месте.

**Витрина не защищена ничем, кроме петлевого интерфейса.** `stepcast up`
слушает только `127.0.0.1` и работает исключительно на чтение, но
аутентификации у неё нет: любая страница, открытая в том же браузере, может
обратиться к `localhost` на её порт. Инструмент рассчитан на локальную
однопользовательскую машину; токен доступа и проверка `Origin` не вводились
сознательно и остаются отдельным изменением, если понадобятся.

**Страница витрины из репозитория не собирается.** `stepcast up` отдаёт
`dist/ui-web/index.html` — артефакт сборки фронта, которого в git нет, как нет
ни исходников фронта, ни команды сборки в `package.json`. В свежем клоне
витрина отвечает `503` и называет команду сборки; API при этом работает
полностью. Сборка фронта — отдельное изменение; `npm run check` от этого
артефакта не зависит: тест страницы готовит его сам.

**Витрина видит прогоны всех проектов пользователя.** Это её задача, но
следствие стоит знать: в дашборде окажутся пути и имена проектов, за которыми
пользователь мог не собираться наблюдать вместе.

**Каталог прогонов обязан лежать вне рабочего дерева.** Иначе запись журнала
сама выглядела бы изменением дерева. Проверяется до запуска первой работы.

**Судья видит только вывод шага, а не его контекст, и не имеет его прав.**
Предикат `judge` получает утверждение, задание шага, его текстовый и
структурированный вывод и результаты остальных предикатов — но не контекст,
собранный шагу, и не его политику доступа. Вызов идёт в свежей сессии со
своими (или умолчальными) бэкендом и моделью. Из этого следует, что судья не
может свериться с файлами проекта или спекой напрямую — только с тем, что шаг
сам показал в своём ответе; утверждение стоит формулировать так, чтобы его
можно было проверить по выводу шага, не заглядывая дальше.

**Выдержка о непройденной проверке усечена по `context.note_max_tokens`.** В
контекст следующей итерации попадает хвост вывода непрошедших предикатов, а не
он целиком; отброшенное начало помечается явно. Полный вывод из усечения не
теряется — он остаётся в логах шага проверки того прогона.

**Разбор `.gitignore` вне git неполон.** Поддержаны комментарии, маски,
каталоги и привязка к корню; отрицания (`!`) и вложенные `.gitignore` — нет.
Неподдержанное правило пропускается, а не толкуется наугад. В репозитории
исключениями занимается сам git, и ограничение не проявляется.

**`on_exceed: wait` ждёт только окно лимита подписки.** У ожидания два
основания: измеренное превышение `rate_limit_pct` в области с `wait`, и упор
самого бэкенда в то же окно (отказ, распознанный по конверту результата —
см. ниже). В обоих случаях прогон усыпляется до сообщённого момента сброса и
переисполняет прерванный шаг заново — без расхода попытки, но с сохранением
расхода оборванной попытки в потолках. Потолки `tokens` и `wallclock` этим
режимом не спасаются: они не сбрасываются, и упор в них останавливает прогон
при любом `on_exceed`. Суммарная длительность ожиданий за прогон ограничена
`defaults.max_wait` (умолчание — 6 часов); отсутствие сообщённого момента
сброса и момент дальше предела вырождают `wait` в `stop`, а причина называет
основание. Время ожидания не входит ни в один потолок `wallclock`.

**Классов неустранимого отказа бэкенда ровно два.** Упор в окно лимита
подписки и отказ аутентификации — больше движок не различает. Кандидат на
классификацию — только запись результата, объявившая себя ошибкой и несущая
признак ошибки бэкенда (код состояния ответа либо `terminal_reason:
"api_error"`); класс решает сначала код состояния (429 → лимит, 401/403 →
аутентификация), а тело ответа смотрится лишь тогда, когда кода нет вовсе, и
только по закрытому перечню узнаваемых формулировок. Отказ, не совпавший ни с
одним классом, остаётся обычным отказом шага: попытка повторяется по
`attempts.max`, как при любой непройденной проверке, а не по правилам
неустранимого отказа. Момент сброса окна лимита разбирается только из двух
форм — настенного времени с часовым поясом (`resets 11pm (Asia/Nicosia)`,
ближайшее будущее наступление через `Intl.DateTimeFormat`) и метки ISO 8601 со
смещением или `Z`; нераспознанная форма, неизвестный часовой пояс и
отсутствие упоминания сброса дают отказ без момента сброса, а не угаданное
время.

**Эффект жёсткого режима на живом бэкенде не проверен сквозным прогоном.**
Тесты фиксируют состав флагов запуска (`--setting-sources project`,
`--permission-mode manual`), а семантика самих флагов снята разведкой CLI до
реализации (см. `design.md`). Прогон двух шагов с одинаковым списком прав и
разным `enforce` при разрешающих настройках машины не выполнялся: он требует
временной правки `~/.claude/settings.json` — общего ресурса машины. То есть
утверждение «правило пользовательского уровня на шаг с `enforce: strict`
больше не действует» опирается на поведение флагов бэкенда, а не на измерение
внутри stepcast.

*Заведено изменением `job-permission-mode`.*

**Жёсткий режим отсекает не только права.** В `enforce: strict` бэкенд не
читает настройки уровня пользователя целиком, а не только правила доступа —
вместе с ними перестают действовать пользовательский `CLAUDE.md`, стили
вывода и прочие настройки машины. Для агентского шага, чей промпт собирает
движок, это способствует воспроизводимости, но поведение шага может
неожиданно разойтись с тем, что разработчик привык видеть локально.

*Заведено изменением `job-permission-mode`.*

**Синтаксис `allow`/`deny` остаётся бэкендовым.** Движок не разбирает и не
проверяет записи политики — опечатка в шаблоне (`Bash(npm*)` вместо
`Bash(npm *)`) в жёстком режиме превращается в неожиданный отказ, а не в
разрешение; причина видна в журнале как отказ в разрешении.

*Заведено изменением `job-permission-mode`.*

**Смежность дорожек объявляет человек.** Движок не выводит `lane` из `needs`
или `workspace.inherit` — работа несёт дорожку, только если она объявлена
явно на месте подключения. Пропущенная в разводке пайплайна работа тихо
остаётся вне группировки расхода и вне `apply --lane`.

*Заведено изменением `pipeline-lanes`.*

**Красная проверка после сведения обесценивает зелёную у себя дорожку.**
`verify` дорожки прошла на её собственном дереве, но `merge-lanes.mjs` гоняет
`npm run check` уже на дереве, объединённом с прежде сведёнными дорожками, —
и красный исход там означает конфликт между дорожками, а не то, что дорожка
сама по себе плоха. Сведение останавливается, дерево откатывается к
последнему коммиту, а дорожка ждёт следующего захода.

*Заведено изменением `pipeline-lanes`.*

**Журнал с `lane` не читается движком прежней версии.** `JobRecordSchema`
строгая: `status.json`, где у работы записано поле `lane`, отклоняется
разбором, не знающим об этом поле, — в обратную сторону совместимость есть
(журнал прежней формы, без `lane`, читается этой версией как работы без
дорожки), а в эту — нет.

*Заведено изменением `pipeline-lanes`.*

**`stepcast resume` ленту не печатает.** Наблюдение `onEvent` в `RunOptions`
общее для `run` и `resume`, но `resume` его не подключает — у команды своя
преамбула с планом переиспользования, и место ленты в ней осталось за
пределами этого изменения.

*Заведено изменением `run-progress-output`.*

**Перечень печатаемых видов закрыт и не расширяется автоматически.** Новый вид
события, добавленный в движок, в ленту не попадёт, пока для него явно не
описано правило печати в `src/cli/progress.ts` — по устройству, а не по
недосмотру: сырой JSON нового события в терминале хуже, чем его отсутствие.

*Заведено изменением `run-progress-output`.*

**Неудача наблюдения самому наблюдателю не доставляется.** `bookkeeping.failed`,
порождённая отказом `onEvent`, идёт в файл событий, но `onEvent` на ней не
зовётся: доставка либо зациклила бы отказ, либо повторила бы его в терминале.
Единственный вид события, который наблюдатель видит не всегда.

*Заведено изменением `run-progress-output`.*

**Служебные записи остаются только в `events.ndjson`.** `context.denied`,
`context.downgraded`, `context.note_truncated`, `env.denied`,
`backend.unparsed`, `backend.degraded`, `bookkeeping.failed`, `step.reused`,
`tree.restored`, `workspace.inherited`, `run_dir.carried`,
`budget.cost_unreported`, `resume.note_undelivered` — разбор постфактум, а не
ход, и в ленту не идут ни при каком режиме вывода.

*Заведено изменением `run-progress-output`.*

**Содержимое, накопленное до введения фрагментов, атрибуции не несёт.** Блоки
известных ограничений и строки таблиц, перенесённые из прежнего
`docs/status.md` в `docs/status.base.md` при введении сборки, не подписаны
изменением — они принадлежат базе, а не какому-то одному фрагменту, и
атрибуция `*Заведено изменением ...*` у них не появляется. Это относится
только к содержимому на момент переноса; всё, что вносят фрагменты новых
изменений, подписывается как обычно.

*Заведено изменением `status-doc-fragments`.*

**Сведённый объединением `docs/status.md` до пересборки может быть неверен.**
Слияние двух веток, каждая со своим фрагментом, не конфликтует —
`.gitattributes` объявляет файл сводимым объединением, — но результат
объединения может содержать не ту комбинацию строк и блоков, что даёт
`scripts/status.mjs`. Расхождение ловит `npm run status:check` в составе
`npm run check`; правильный документ восстанавливает `npm run status:build`.

*Заведено изменением `status-doc-fragments`.*

## Примечания

`prompt.txt` содержит ту часть запроса, которую сформировал stepcast. Claude Code
добавляет к ней свой системный промпт, `CLAUDE.md`, автопамять, хуки и
плагины; их состав пишется в `step.json` из события инициализации, но
изменение `CLAUDE.md` шаги не инвалидирует.

Windows не проверяется. Убийство дерева процессов реализовано через группу
процессов POSIX.

Пример `examples/target-state/` по-прежнему не проходит `lint`, но уже по
другой причине: подстановка в числовые поля работает, а пример ссылается на
файл контекста `AGENTS.md`, которого в этом репозитории нет. Правка примера
осталась за пределами этого изменения.
